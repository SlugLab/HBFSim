3.Introduction
The memory wall problem is a well-known issue in the computer architecture domain for
decades from the CPU era and continues in the current era of high-volume data-centric
processing. The disparity between the speed of GPUs and the response time of memory
creates bottlenecks in workload performance. In addition, the LLM (Large Language Model)
sizes and context lengths are increasing in every new generation that drives the need for higher
memory capacity.
High Bandwidth Flash (HBF), a non-coherent memory-centric flash device, will redefine AI
infrastructure by providing extremely high TB/s bandwidth with very high capacity. The HBF sits
very close to the GPU/TPU/xPU data processing units. HBF addresses the memory wall
problem, where wide-IO NAND-based memory architecture offers 8x to 16x of the capacity of
HBM, while delivering the same read bandwidth. In the datacenter, HBF can augment HBM with
the ability to attach terabytes of memory to xPUs. This document defines the HBF interface with
xPU for datacenter-class deployments, including electrical, packaging, test & debug, reliability,
and additional details required to integrate xPU with one or multiple UCIe modules. The
solution will focus on reducing protocol overhead, enabling more efficient data transfer, and
improving scalability across large deployments.
This document describes the High Bandwidth Flash (HBF) High Level Specification. It covers
the following sections:
● Product Description
● UCIe Host Interface Architecture
● AXI Protocol Layer
● Electrical Requirements, Reset and Initialization
● Test & Debug Interface

4.Product Description
The High Bandwidth Flash (HBF) is tightly coupled to the xPU Host Compute die with a
distributed interface. The interface is divided into independent channels. Each channel is
independent of one another. The host channels are not necessarily synchronous with each
other. HBF uses a wide-interface architecture to achieve high-speed and low-power operation.
Each host channel interface maintains a full duplex data bus operating based on UCIe 3.0
standard guidelines. Each host channel is connected to independent set of NAND dies for that
specific host channel through the UCIe module.
HBF is optimized for high-bandwidth read operations to a stack of multiple NAND devices
across several independent interfaces called channels. Each NAND stack will support up to 16
host channels, and each host channel may have one or more AXI channels. Each HBF stack
can support a very high capacity, such as 512 GiB density or higher. Each channel provides
access to an independent set of NAND dies. Requests from one UCIe channel will not access
data attached to a different UCIe channel. The UCIe channels are independently clocked and
synchronous. The Core die refers to the NAND die stack. The Base die refers to the bottom die,
where the Core die stack sits on top of the Base die.

4.1.

Features

Host Interface Features:
○ Burst Length of 4KiB on write access and on a 4KiB aligned address
○ Burst Length of 64B to 4KiB in multiple of 64B for read access on 64B aligned address and
does not cross 4KiB NAND page boundary
○ 64-bit main-band interface data width, each lane running at up to 32Gbps per channel
targeting up to 3.072 TiB/s of user bandwidth
○ Additional 1-bit sideband interface running at 800 MHz for management and user defined
application
○ Support UCIe Host streaming protocol
○ Support 16 host channels – each host channel operating independently of others

System Organization

Figure 1 shows the high-level Base die organization. The HBF is tightly coupled to the Host
Compute die with a distributed interface. The interface is divided into independent channels.
Each channel is completely independent of one another. The host channels are not
necessarily synchronous with each other. HBF uses a wide-interface architecture to achieve
high-speed and low-power operation. Each host channel interface maintains a 64-bit full
duplex data bus operating based on UCIe standard guidelines.

several independent interfaces (channels). Each NAND stack will support up to 16 host
channels. Figure 2 shows an example of four HBF chipsets connected to a host. Each HBF
chipset contains 16 host channels, each HBF with 512 GiB density.
Each channel provides access to an independent set of NAND dies. Requests from one channel

5.1.1.

UCIe Overview

Universal Chipset Interconnect express (UCIe) architecture is an open, multi-protocol
capable, on-package interconnect standard for connecting multiple dies on the same
package. The chosen advanced packaging technology is used for the performance-optimized
application of HBF. Consequently, the channel reach is short (less than 2mm, when
measured from a bump on one Die to the connecting bump of the remote Die) and the
interconnect is expected to be optimized for high bandwidth and low latency with best
performance and power efficiency characteristics.
The advanced package characteristics are summarized as the following for HBF:
● Supported speed per UCIe x64 host module: 256 GB/s for 32 GT/s
● Bump pitch: 45mm
● Channel reach to xPU: 2 mm (maximum-supported for advanced package per UCIe
specifications)
● Raw bit error rate: 1e-15 at greater than or equal to 16 GT/s, 1e-27 at 12 GT/s (maximumsupported for advanced package per UCIe specifications)
UCIe is a layered protocol, with each layer performing a distinct set of functions. The three
main layers are: Protocol layer, Die-to-Die layer, and Physical layer. The HBF specification
uses Format 6 flit format. Please refer to the UCIe v3.0 specification for more details. The
following Figure 6 shows all three UCIe layers.

5.2.

AXI Host Interface Architecture
5.2.1.

AXI over UCIe Overview

The AMBA AXI interface is a widely used open specification communication interface that is
used to connect one or more initiators to one or more targets. The xPU to HBF
communication interface uses AXI as protocol layer running on UCIe, which is an onpackage interconnect for connecting multiple dies on the same package. The link layer is a
wrapper on top of UCIe interface for flow control and packing/unpacking AXI channel
information in UCIe FLIT format.
UCIe supports multiple protocols including Streaming, or raw format that are run on UCIe if
both ends support it. The xPU to HBF link layer protocol is chosen as AXI because the
overhead of the protocol is very low. For AXI, only a subset of features is used in the xPU to
HBF interface and only several of its features are used, which helps the overhead low and
keeps the UCIe efficiency high.
The red-dotted box in Figure 24 is the standard UCIe module. The two blue-dotted boxes
that include the Link Layer are customized by the xPU and HBF vendors. This specification
has provided a version of AXI Link Layer protocol specification that runs on UCIe.

control information for a write transaction.
2. Read request channel (AR): Read request channel carries all the required address and
control information for a read transaction.
3. Write data channel (W): The write data channel carries the write data from the Manager
to the Subordinate.
4. Write response channel (B): A Subordinate uses the write response channel to respond
to write transactions. All write transactions require completion signals on the write
response channel.
5. Read data channel (R): The read data channel carries both the read data and the read
response information from the Subordinate to the Manager.

5.3.

Host Read
5.3.1.

Host Read Requirements

The host will communicate all read requests in AXI format as defined in the AXI Protocol for
HBF section 5.2.4.
1. All Read requests are 64-byte granularity; however, the host shall send 64 read
commands to retrieve the complete 4KiB data with different AXI IDs. Or if product
support burst read then send burst read with burst length (0-63).
2. AXI ID width is fixed, however if xPU would like to use lesser number of AXI-ID width ,
MSB will remain reserved, where the host can define it based on the maximum number
of outstanding 64B transactions the host would like to manage.
3. The host can choose to allocate either the least significant or the most significant 6 bits
to manage the same 4KiB transaction in AXI IDs.
4. The read request address is at 64-byte granularity.

Date: 03 AUG 2026

Page 56

Open Compute Project • HIGH BANDWIDTH FLASH (HBFTM) SPECIFICATION

5. Read command completion may be out of order for different AXI IDs, while read order is
maintained with the same AXI IDs.
a. Cache hit reads are served immediately if there are no ordering violations.
b. For cache miss reads, Core die sense is triggered when prior read for that
specific bank is done.
6. HBF follows strict ordering for sense requests to Core die within the same bank
requests.
7. HBF supports two cache buffers for each bank to hold up to at least two pages of data. It
is recommended to read the full first 4KiB page before issuing a third 4KiB address that
will evict the first 4KiB data.
8. The Base die shall immediately serve the cache hit read from the cache buffer if ordering
is not violated.
9. In the case of read failure like UECC or high correctable errors, the host configures the
Base die to retry, or the host can retry the read.

5.3.2.

Regular Read and Batch Reads

In the case of read failure like UECC or high correctable errors, the host can configure the
Base die to retry, or host can retry the read.

5.3.2.1.

Regular Reads

The reads that are issued from the host without the batch read hint are called regular reads.
The regular reads are accumulated together and scheduled to the Core die optimally for
best performance.

5.3.2.2.

Batch Reads

Batch reads issued by the host will indicate that the read is batch read by setting AXI user
bit 0 to 1 in the command fields. The Base die will not wait for the timer to expire and will
schedule all the reads that were received until a regular read command is issued. The Base
die will assume the end of batch reads whenever a regular read after batch reads.
R R R R R R R – No batch read hint set in any of the read commands
R R R R R(Batch Read bit set) R R R R – The first five read commands are scheduled
together and will not wait for the read commands behind it.

5.3.3.

Scratchpad Reads

Scratchpad reads are reads sent by the host to the scratchpad memory region in the HBF.
The host can use the scratchpad IO command to read temporarily stored data from
scratchpad memory if the HBF product supports scratchpad. Scratchpad reads are highpriority operations, and a response from HBF is expected within a few cycles, similar to that
of the host cache memory. HBF is unaware of the contents and validity of scratchpad
Date: 03 AUG 2026

Page 57

Open Compute Project • HIGH BANDWIDTH FLASH (HBFTM) SPECIFICATION

memory, and the host software is responsible for managing the scratchpad region. All reads
to the scratchpad region are regular reads and the batch read hint is ignored. Scratchpad
support by HBF is optional and is product specific.

5.4.

Host Write
5.4.1.

Host Write Requirement

1. All writes are non-posted writes. A write command received with any length receives
only one response sent to the host irrespective of length size, which follows AXI
protocol.
2. The write command is completed to the host only after the data is written to the Core die.
3. The write granularity to the Core die is 4KiB. The Base die controller first accumulates
the complete 4KiB write commands and data is sent to the Core die.
4. No skipping or jumping of 4KiB local address is allowed within a host channel's allocated
global address range.
5. HBF will internally auto-erase the NAND block from the host point of view, when
receiving a page-0 (WL-0, STR-0, NAND block-X) write request of a NAND block.
6. When HBF gets the first 64Byte write request for a local address for that channel, HBF
shall receive all the 4KiB writes within a time limit. The time limit is set by the host in the
HBF config register during initialization. If the HBF does not receive all the 4KiB within
the time limit, the HBF will error out and send the error response to the host.
7. Maximum of product specific outstanding device logical unit write requests per host
channel. For example, it is 64 or 128 or any other number of write requests supported by
the product.
8. Write ID width is defined by the number of outstanding writes as defined in the product
specification.
9. The host shall write the 4KiB local address consecutively within the NAND block. The
NAND block size is defined in the product specification.

5.4.2.

Scratchpad Write

The host can use the scratchpad write IO command to temporarily store host content in the
scratchpad region, if HBF supports the scratchpad feature. During the scratchpad write, IO
command writes the data to the scratchpad address. Scratchpad write IO is a high-priority
command, and HBF response completion occurs within a few cycles. The content of the
scratchpad remains valid until the HBF power cycle, and the host can read it back at any
time at high priority. The scratchpad write does not have to be 4KiB page size for the SRAM
write to take place. All scratchpad writes have 64B granularity and are written to the SRAM
with much less latency. HBF is unaware of the contents and validity of scratchpad memory,
and the host software is responsible for managing them. The scratchpad functionality is
optional and is product specific.

5.4.3.

Mixed Read/Write Workload

During mixed workloads, the Base die maintains the order between writes and reads at 64B
granularity with the same address even with different AXI IDs. If a read follows a write and
only some parts of 4KiB-write have been accumulated in the Base die and is still waiting for
the remaining of the 4KiB, the read that hits the accumulated part returns the data from the
accumulated part. If the read hits the pending part of the write, a read error is returned to the
host with read command status error code 0xA.

5.8.

Sideband Message Support

The purpose of the sideband link is to provide an out-of-band channel for link training and an
interface for accessing the sideband registers of the link partner. It is also used for Link
Management packets and parameter exchanges with a remote link partner.
The same protocol is also used for local die sideband accesses over FDI and RDI. When
relevant, FDI-specific rules are pointed out using “FDI sideband:”. When relevant, RDI-specific
rules are pointed out using “RDI sideband:”. When relevant, UCIe link-specific rules are
communicated using the UCIe link sideband. If no prefix is mentioned, it is a common rule
across FDI, RDI, and UCIe link.
The physical layer is responsible for framing and transporting sideband packets over the UCIe
link. Direct sideband access to remote die can originate from the adapter or the physical layer.
The adapter forwards remote die sideband access over RDI to the physical layer for framing
and transport. These include register access requests, completions, or messages.

Date: 03 AUG 2026

Page 63

Open Compute Project • HIGH BANDWIDTH FLASH (HBFTM) SPECIFICATION

The protocol layer has indirect access to remote die registers using the sideband mailbox
mechanism. The mailbox registers reside in the adapter, and it is the adapter's responsibility to
initiate remote die register access requests when it receives the corresponding access trigger
for the mailbox register over FDI
Sideband Packet Types: Three different categories of packets are permitted:
● Register Accesses: Configuration (CFG) or Memory-Mapped access for both reads
and writes are supported. These are 32-bit or 64-bit in length.
● Messages without data: These are Link Management (LM), or Vendor-defined
packets. These don’t carry additional data payloads.
● Messages with data: These are Parameter Exchange (PE), link training-related, or
vendor-defined messages. All three carry 64b of data.
Every packet carries a 5-bit opcode, 3-bit source identifier (srcid), and a 3-bit destination
identifier (dstid). The 5-bit opcode indicates the packet type, as well as whether the packet
carries 32 bits of data or 64 bits of data. For details of each opcode request and completion
format, please refer to the UCIe specification documents.

6.AXI Protocol Layer – Link Layer
The UCIe flit format is Format 6: Latency-Optimized 256B With Optional Bytes Flit Format. The
AXI protocol layer received flit (in selected flit format) from Die-to-Die adapter, flit is constructed
with many packets, each packet is AXI protocol message follow common structure of various
size, link layer job is to accept the flit from D2D Adapter or issue flit to D2D Adapter.
Link-layer will unpack the flit to AXI message and drive it to AXI interface or receive message
from AXI interface and pack it to flit. Link-layer should be compliant to D2D Adapter FDI
interface.
The D2D interface shall support these high-level features to achieve interoperability between
HBF and hosts:
1. A defined mechanism to pack AXI transactions into the FDI flit
2. Independent flow control for each AXI channel to avoid inter-channel blocking
3. Provision for multiple independent AXI ports per UCIe instance to enable interleaving
and bandwidth optimization
4. Flexibility to interface with hosts with differing AXI data widths
To transport AXI across UCIe flits, HBF adopts the AXI over UCIe Protocol Specification (AoU),
revision 0.8, available at openchipletatlas.org. To address HBF specific use cases not covered
with the AoU Basic Profile, the HBF Profile defined in Appendix D is adopted.
The HBF Profile shall support the following:
1. Sync message
2. 8b SYNC field added to most transactions
3. 9 USER bits
4. 14 bits ID
5. Error message

by the wrapper logic. System designers shall ensure that the host controller or external
probes do not misinterpret these signals as active test data or valid memory responses
during idle or non-test periods. Proper signal masking, WIR channel selection, and
explicit BYPASS instruction usage are required to isolate WSO outputs and prevent data
misinterpretation or bus arbitration conflicts.

• Clock Synchronization: WRCK shall remain stable and toggle continuously
during CaptureWR, ShiftWR, and UpdateWR phases. Asynchronous deassertion
of WRCK during active wrapper operations may corrupt WDR shift states.
• Unselected Channel Isolation: Channels not selected via WIR[12:8] are gated off
and will not respond to Capture, Shift, or Update events. This prevents crosschannel data corruption but requires explicit WIR decoding for multi-die/channel
testing.
• Reset Behavior: HBF_RESET instruction (or equivalent) does not reset the
Wrapper Serial Port (WSP) control logic or WDRs. The WSP remains active, and
the BYPASS instruction state is preserved unless explicitly overwritten.

HBF IEEE 1500 Logical Architecture

The internal logic of the HBF IEEE 1500 port is organized hierarchically to support both
standard register access and controller-mediated operations. The HBF IEEE 1500
Logical Architecture comprises the following key components.
•

•

•

•

Wrapper Instruction Register (WIR): A 14-bit shift register that decodes incoming
instructions. When SELECTWIR is asserted, the WIR captures the opcode and channel
selection bits.
Wrapper Data Registers (WDR): Includes the Wrapper Boundary Register (WBR),
Wrapper Bypass Register (WBY), and extended Data Registers connected to the
internal Base die controller. These registers support Shift (S), Capture (C), and Update
(U) stages as required by the instruction.

the serial test interface and the parallel NVM array.
Channel Multiplexer: Routes control signals (CAPTURE, SHIFT, UPDATE) and data to
specific channels (CH_SELECT[0:15]) based on the WIR decoding, enabling parallel
operation across 16 channels.

• Use Case: Balances test time and power consumption. Useful for block-level

8.5.8.

HBF IEEE 1500 Wrapper Data Register Types

•

Read only(R) Wrapper Data Registers:
Read-only WDR bit fields latch data into the shift stage register upon a CaptureWR event.
These registers maintain their current state during an UpdateWR event and do not
incorporate an update stage. During a ShiftWR event, the stored data is shifted out via
WSO. Any data shifted into WSI during this phase is disregarded.
• Write only(W) Wrapper Data Registers:
Write-only WDR bit fields transfer all data bits to the update stage register upon an
UpdateWR event. If a write-only WDR is routed between WSI and WSO, CaptureWR
events do not influence its operation. The register contents are shifted out during a ShiftWR
event.
• Read and Write (R/W) Wrapper Data Registers:
R/W WDRs combine the operational characteristics of both read-only and write-only
registers. Data bits are captured into the shift stage register during a CaptureWR event.
Subsequently, at the UpdateWR event, these bits are simultaneously transferred from the
shift stage to the update stage.
• WDR Reset State:
Asserting WRST_n to LOW asynchronously asserts these states on the HBF’s IEEE 1500
test port logic:
• All WDRs place their update and/or shift stages (where applicable) into a state that
ensures that the HBF returns to mission mode operation and all test modes are
disabled
• Any ongoing BIST operation will be terminated.

8.8.

Firmware Download Sequence
8.8.1.

Overview

This specification defines the firmware download procedure using the IEEE 1500 standard
interface. The primary purpose of this protocol is to enable firmware updates during the
manufacturing process or in-field operations. The Vendor shall provide a firmware image
aligned to the **MPS **(Maximum Payload Size), which corresponds to the IEEE 1500 WDR
(Wrapper Data Register) size. The image shall include option parameters for the download
process, along with a digital signature and CRC code to ensure data security and data
integrity. The Host segments the image into MPS-sized chunks and transmits them via the
FW_DOWNLOAD_DATA command. Upon completion, the Host issues a FW_COMMIT
command, triggering the device to internally verify the header, signature, and CRC before
writing to Non-Volatile Memory (NVM). The device reports the result to the Host. Finally, a
RESET command is issued to activate the new firmware.

8.8.3.

Firmware Download Sequence

Step 1: Initialization
The Host issues the HBF_RESET command (Hard Reset) to clear any previous states and
prepare the device for firmware download.
Step 2: Start FW Download
The Host issues the FW_DOWNLOAD_START command to initiate the download sequence
with the target address.
Step 3: Data Transmission (Segmented Write)
The Vendor shall provide a firmware image aligned to the Maximum Payload Size (MPS),
which corresponds to the IEEE 1500 Wrapper Data Register (WDR) bit-width. The firmware
binary shall be padded to the nearest MPS boundary if the actual image size is not a multiple
of the WDR size. The aligned image shall be segmented into MPS-sized chunks for sequential
transmission via the IEEE 1500 WDR.
Step 4: FW Download Commit
After all data segments are transmitted, the Host issues the FW_DOWNLOAD_COMMIT
instruction. Upon the UpdateWR event, the Device might perform the following internal
operations:
• Header Validation: Verifies the image format, target options, and version parameters.
• Security Check: Authenticates the digital signature (e.g., ECDSA/RSA) to prevent
unauthorized firmware.
• Integrity Check: Calculates and compares the CRC-16/32 code to detect data
corruption.
If all checks pass, the validated data is atomically written to the NVM. If any check fails, the
write operation is aborted, the transmitted buffer is discarded, and the previous valid firmware
is retained. No corrupted or unverified image will overwrite existing NVM contents.
Following the completion of internal verification, the Device enters a non-deterministic latency
period (tFWCOM). The Host shall monitor the download completion by issuing the
GET_STATUS instruction and reading the status field via the WDR. During the NVM write
phase, the Host shall maintain a stable power supply and shall not issue any reset or powerdown commands.

8.9.

SW Based BIST Test
8.9.1.

Overview

This section defines the software-based Built-In Self-Test (BIST) framework accessible via the
IEEE 1500 test port. Unlike fixed hardware test logic, the SW-based BIST architecture delivers
exceptional flexibility by allowing test vectors, patterns, and diagnostic routines to be updated
dynamically without hardware redesign. It supports vendor-specific instruction encoding and
WDR configuration, enabling tailored testing for novel failure modes or process variations.
Furthermore, it provides robust in-field failure response capabilities; unexpected defects
detected during operation or manufacturing is addressed through secure firmware updates and
soft-repair routines, ensuring continuous device reliability and extended lifecycle management.

8.9.2.

SW Based BIST Sequence

The SW Based BIST sequence operates through the standard IEEE 1500 TAP controller and
Wrapper registers. The procedure follows a deterministic, multi-stage sequence:
Step1. SW BIST FW Download: The target SW BIST firmware is securely deployed to NVM via
the FW_DOWNLOAD_START, FW_DOWNLOAD_DATA, and FW_DOWNLOAD_COMMIT
commands. Data segments are aligned to the MPS/WDR size, and integrity is verified via digital
signature and CRC before executing SW Based BIST testing. It's same as the firmware
download sequence.
Step2. BIST Execution: The host loads the SWBIST_EXECUTE instruction into the WIR.
Configuration parameters (e.g., target channels via WIR[13:8], test patterns, timeout settings)
are written to the WDR using ShiftWR and committed via UpdateWR.
Step3. BIST Polling: The internal Controller initiates BIST on the selected channels. The host
monitors progress by polling the GET_STATUS instruction.
Step4. BIST Result Retrieval: Upon completion, the GET_RESULT instruction captures pass/fail
flags and error codes into the WDR shift stage. The data set is vendor specific.

Using all UCIe channels of the HBF in parallel can achieve maximum performance. However,

11.3.

Scratchpad SRAM Usage Model

The host can read and write temporary data to the SRAM in the HBF, which does not hold
data after power cycle. The scratchpad size of the SRAM region is obtained by the
configuration register reads, SRAM start address, and size as defined in the MMIO register
space. The scratchpad region is fully maintained by the host software and the HBF just
supports reads and writes at full bandwidth of the UCIe channel. All read and write requests
to scratchpad memory are high-priority requests and serviced immediately as soon as
possible in the HBF. Each UCIe channel has individual SRAM space, and the total space is
used by the host software as it sees fit to improve the LLM or any other workload that it is
running.
There are many uses while executing the LLM or other workloads in the xPU. One such use
case is intermediate activations and layer to layer buffers are held in the SRAM.
Note: The scratchpad SRAM support is optional and is product specific. The HBF product
datasheet provides additional information.

11.4.

HBF Wear Leveling and GC

HBF vendors provide host/xPU software that allows selection of HBF Base-die-driven wear
leveling (product vendor-specific) or host-controlled wear leveling with zone remapping. It is
recommended to enable either host-controlled wear-leveling or Base die controlled wearleveling.
HBF does not support any GC (garbage collection) or the transfer of active data from one
physical location to another. HBF only supports remapping the UCIe channel local address
from one physical location to another, as a part of wear leveling, and further writes to that
UCIe local channel address with wearing out new assign physical location.

11.4.1.

Zone Remapping

HBF supports host/xPU controlled zone remapping, where the host can divide each UCIe
channel capacity into N zones, and each zone size/capacity should be the same. HBF Base
die supports the host to track/read each zone’s PEC (program-erase cycles) from CSR
registers. Host software can also maintain a record of each zone’s PEC if required. Based on
the assignment of each zone and current usages or future usages, the host software can
decide to swap the Hot Zone (High PEC) with the Cold Zone (Low PEC). Before swapping,
the host software needs to ensure that the data is invalid and no further IO read requests are
issued to these zones before rewriting.

11.5.

HBF to Host Error Status and Actions Needed by Host

To enable seamless, low-latency data access for the Host/xPU as defined in the product
specification, periodic data refresh is required at intervals specified in the reliability
specification (typically every 24–48 hours). It is recommended that the host software schedule
these refresh operations during maintenance periods or interleave them alongside ongoing
operations in a distributed manner.
If the host chooses to interleave refresh with active workloads, it shall ensure that refresh
commands and read commands are not issued to the same die at the same time. Otherwise,
some read operations may experience increased latency.
Data refresh conditions
•
Time-duration (Data retention time): This is HBF product specific and it shall publish the
guaranteed data retention of NAND block during power-on and power-off scenarios. Host
software needs to ensure that data is refreshed at this interval.
•
Excess reads from any physical NAND block: Due to NAND characteristics, with each
access, the NAND block data health deteriorates. It is the host's responsibility to refresh the
NAND block’s data after reading NAND block data X (product-specific) times. The host can
periodically check each NAND block’s read count using the CSR command; however, when
Base die observes that a specific physical NAND block is at risk of data loss, it will indicate
this in the command status.
Due to NAND characteristics in specific rare scenarios, it may be possible that the health of
some NAND blocks deteriorates earlier than the Read Disturb/Data Retention specification, or
the Base die encounters an error due to NAND characteristics, an invalid field in the
command, or the current Base die status. In these cases, the Base die will report an error in
the command status, and a specific follow-up action is required from the host as described in
the following subsections.

12.Security
The HBF security features are optional and product specific. The HBF is connected to the xPU
in the same package. The HBF NAND security during power on is protected by the same level
of security to access the xPU, like HBM. While the power is turned off, there may be some
additional level of protection needed to secure the contents in the HBF, though it is extremely
hard to remove the NAND flash from the xPU package and remove the Base die controller and
access the NAND contents by connecting the TSVs to external controller.
The data-at-rest security refers to protecting the data stored in NAND flash memory when the
device is powered off. There are many known SSD techniques available to protect the data-atrest in NAND. These SSD techniques may not be directly applicable or used in HBF as it
operates at very high bandwidth, and any inline encryption/decryption are a very high-power
consuming operation and affecting the performance. The security mechanisms enabled to
support HBF data-at-rest are optional and any feedback on how the HBF data is accessed at
rest would be helpful to add the security features. There are couple of low-cost features that are
implemented to protect the HBF data-at-rest without affecting the high bandwidth operation and
consumes less power.
All the security features in this chapter are optional and may not be implemented. Refer to the
product specification to check the list of security features like Sanitize (NAND block erase or
overwrite) and others may be implemented.

12.1.

Power-on Erase

Power-on erase works by obfuscating the data in the HBF every time the HBF is powered on
makes sure the data cannot be read by the xPU. And any data read by the xPU before
writing/erasing the HBF will return ECC errors to the xPU for the full capacity of all pages in
the HBF. The data needs to be written before use by the xPU after power-on.

12.2.

HBF Sanitize

The HBF sanitize is a command used to securely erase HBF data, ensuring that all data,
including cached and buffered information, is completely removed. The secure erase
command is described in section 5.2.4.3.

12.3.

Physical Tamper Proof

A physical theft of the cards that contain the xPU and HBF package from datacenters is
possible. A metal clamp strapped to heat sink can prevent the physical theft of the cards when
it passes through a metal detector. An optional embedded RFID could also provide a low-cost
solution.
