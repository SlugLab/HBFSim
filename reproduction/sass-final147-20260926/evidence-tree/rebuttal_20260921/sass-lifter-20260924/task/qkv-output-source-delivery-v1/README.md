# Frozen v7 QKV lifter source and CPU reproduction

The final six-fix QKV lifter is the **complete source crate** in `../qkv-output-repair-v1/`, especially `src/sass/lifter.rs` SHA-256 `0ec6653a78a2e8eb1ac5a8f5aa1a34c2fbe310fd5c7bb073bbb36a289ee12ca9`. Its `Cargo.toml` and `Cargo.lock` are byte-identical to the initial standalone crate (`Cargo.lock` SHA-256 `da907f869a9684f4b39b7a312e18d396800235d73f9e44eaf6856e0e439ac02c`). `instruction.rs`, `disassembler.rs`, and `cubin_parser.rs` remain byte-identical to the copied Concordia `c60cfd8ab54fd1ec4512f749ad61cccc4a390a05` originals. The modified lifter and thin CLI are held in the final crate; do not rebuild the initial standalone crate and call it v7.

The final crate omitted physical license files. This independent delivery directory supplies `LICENSE-MIT` and `LICENSE-APACHE`, copied byte-for-byte from the original standalone delivery and pinned in `profile-giga-v7.json`. The crate declares `MIT OR Apache-2.0`; preserve both files with the source. The preceding focused fixes and original CPU failures remain in their own task directories; this README does not rewrite their provenance or claim a monolithic upstream commit.

`reproduce_v7_cpu.py` takes an explicit host profile and a **new** output directory. The profile pins every Rust source file, Cargo manifest/lock, both licenses, the official QKV `cuobjdump` SASS input, exact kernel name, `sm_120`, Cargo, `rustc` and `ptxas` identities, one CPU and finite resource limits. The script passes the verified compiler as `RUSTC` to Cargo. Paths and toolchain live in the profile rather than public source code. A different host needs a newly validated profile and the locked crates in its Cargo cache; the reference giga profile is not a universal lock. The script copies the source/license/input bytes into a fresh path, runs Cargo `--locked --offline --jobs 1`, runs the focused `output_repro` CPU binary, invokes the **unchanged strict diagnostic CLI**, and assembles its quarantined QKV PTX with `ptxas -arch=sm_120`. It never launches a GPU kernel or edits a frozen source file.

On giga, `/usr/bin/cargo` and `/usr/bin/rustc` are distinct symlink names for the same rustup dispatcher. Their resolved binary hashes match, but the invoked basename selects the Cargo or rustc role. The entry verifies the resolved bytes and version while preserving each declared executable name in argv and `RUSTC`. This correction was made before the first run of this new entry; it is not a fabricated failed attempt.

```bash
python3 /path/to/qkv-output-source-delivery-v1/reproduce_v7_cpu.py \
  --profile /path/to/validated-profile.json \
  --output /path/to/new-qkv-v7-cpu-reproduction
```

The strict CLI's QKV recovery is expected to exit **1** and write only `qkv.quarantine.ptx` plus structured diagnostics: its historical synchronization markers still yield `REQUIRES_SEMANTIC_PROOF`. The script checks that `qkv.candidate.ptx` does not appear. A successful `ptxas` step means this PTX assembles for the target; it is not an `ADMITTED` status or a new GPU result. The independent existing v7 same-process replay and its 12,288-byte byte-equal result have separate raw receipts. Preserve the distinction between CPU assembly, that one controlled GPU comparison, and broader model/HBF coverage.

The historical `../qkv-output-repair-v1/cpu-build-v1/` contains `build.rc=0`, focused fixture rc0, strict recovery rc1, `ptxas.rc=0`, the source hash before/after, PTX SHA-256 `6db074711d19c3e31cbcc98c6e170f0b4330259f220c2d518ce8aee42b9c9eab`, CUBIN SHA-256 `0e154ab5dc11fc66f930e55d4cd0d235a8021dfa18c30fd06275600189b0648d`, and the 19-slot ABI inspection. Those older files **do not preserve a complete historical Cargo/PTXAS argv**, so the command above is an explicit new reproducible entry, not a verbatim claim about the prior shell invocation.

This new entry was executed once on giga under `run-cpu-v1/`: locked/offline Cargo rc0, focused fixture rc0, strict recovery rc1 with quarantine, and offline `ptxas` rc0. Its recovered PTX is byte-identical to the historical v7 PTX. Its assembled CUBIN has a **different** SHA-256 (`de624246e9c7877f88a1c5a7d81fab4b2f3b9dcb67e30c80278b0616664e17c8`), although both files are 46,736 bytes. The earlier assembler argv was not fully captured, so no cause of the byte difference is asserted.
