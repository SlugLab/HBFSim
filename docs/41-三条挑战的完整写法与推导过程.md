## 〇、先给直接答案

**读规范之前必须先记住一件事:这份规范里的 `Host` 指的是 xPU(也就是 GPU 或 TPU),不是服务器的 CPU。** 这不是推断,是规范自己写的:第 90 页 §8.5.1 `providing a direct test interface between the host(xPU) and the HBF`;第 15 页 `The High Bandwidth Flash (HBF) is tightly coupled to the xPU Host Compute die`;第 38 页 `The xPU to HBF communication interface uses AXI as protocol layer running on UCIe`。全文 130 页里 `CPU` 只出现一次,在引言的一句历史叙述里(第 13 页 `for decades from the CPU era`)。规范里所有 `host software`、`host read`、`host channel` 都是 xPU 这一侧。

**因此本文档不再使用「主机侧」这个词,本轮已逐处改掉。** 同一个词在两处指的是相反的两个东西:OCP 规范里的 `Host` 指 xPU,而本文档过去写「主机侧」时指的是服务器 CPU 那一侧。现在按含义分开写——指服务器 CPU 那一侧时写「服务器 CPU 那一侧」;强调这个位置在被测程序外面时写「被测程序之外」;指 HBF 规范意义上的访问发起方时写 xPU。**引用大纲或旧版原话的地方按原话保留,并在同处注明「主机侧」正是要换掉的那个词。**

**另一处措辞一并改掉:「效应只能写进被测程序自己的指令流」改成「写进被测程序自己的代码,包括它的运行时」。** 理由是 HBF 的写路径很可能不是一条存储指令,而是由一段运行时软件维护的:规范要求一次写以 64 字节为单位送进来、由 Base die 累积成完整的 4 KiB、在主机初始化时设定的时限内送完、在 NAND 块内按地址顺序写不许跳、写到块内第 0 页时整块被自动擦除,并且每条写命令带回一个状态码(第 58 页 §5.4.1;第 121 至 122 页 §11.5.2.2 与 §11.5.2.6;写错误码 Table 13 在第 61 至 62 页,`0x2` 地址重叠、`0x5` 4KiB 累积超时、`0x6` 写顺序违例、`0x7` program 失败需从 page-0 重放整块)。**没有任何 GPU 指令集的存储指令具备这样的语义,这一步是推断,不是规范原文。** 「指令流」这个说法把注入点限定成一条条指令,太窄:运行时那一层的代码同样是可以改写的地方。**这一条的完整依据、读那一侧为什么不受影响、以及要请合作者确认的三个问题,见 `/root/hbfsim/HBFSim/docs/重要实现问题以及需补做实验/00-write-path-may-not-be-a-store-instruction.md`。**

## 一、新的第一条挑战(可直接搬进大纲)

### 一句话概括

**Challenge1: HBF 与 GPU 封装在一起,这一层介质的每一次访问由 GPU 自己的取数单元发出、地址由 GPU 自己的页表翻译,访问在封装内部被服务完毕,而这条链路上没有可以接入第三方硬件的物理接口——三件事同时成立,以前那些模拟器所用的拦截点在这里全部落空。**

与旧写法的区别在于:旧写法断言「别的新内存都有现成的拦截位置,GPU 这一侧没有」,是一句绝对的否定,已经被两个真实系统证伪(铠侠那台机器在真实 GPU 上做成了逐次注入延迟;AMD MI300A 上服务器 CPU 那一侧确实有一个可以停留的服务点)。新写法把结论建在三个可以逐条检查的条件上,并且在表里逐个交代那些真实系统的拦截点各自被哪一条挡住。

### 三个条件各自的规范依据,以及各自的边界

**条件一:这一次访问由加速器自己的取数单元发出,地址由加速器自己的页表翻译。**

规范支持前一半,对后一半完全没写。前一半:发起方毫无疑问是 xPU(第 38 页 §5.2.3 `The AXI Master Link Layer Adapter (AMLL Adapter) is an interface between the host traffic software interface and the AXI Link Layer Master. ... translates descriptor information generated by host software into AXI signals.`,第 40 页)。后一半:规范根本没有定义任何地址翻译机制——它定义的是一个由 xPU 侧软件用算术算出来的平坦全局地址(第 22 页 Figure 3 `Host Software HBF Global Address (G_Addr) (64B Granularity => 1unit = 64B)`,正文 `Host software configures the global address and splits the global addresses across the local UCIe channel address.`)。全文检索 `TLB`、`MMU`、`page table`、`virtual address` 四个词,**命中数都是 0**。所以「地址由 GPU 自己的页表翻译」这半句的依据来自 GPU 侧的机制,不是规范;正文里要照这个分界写,不能说成规范支持。

**条件二:这一次访问在加速器封装内部被服务完毕,不离开封装。**

规范支持。HBF 与 xPU 同封装(第 124 页 `The HBF is connected to the xPU in the same package`);链路是裸片对裸片、长度不足 2 毫米(第 25 页 `channel reach is short (less than 2mm, when measured from a bump on one Die to the connecting bump of the remote Die)`);服务由 Base die 与 Core die 完成;完成状态沿 AXI 响应通道回到 xPU。全文没有任何一条路径把访问的任何一部分引到封装之外。

反面证据同样干净。全文检索的命中数:`page fault` 0 次;`interrupt` 1 次而且无关(第 99 页一句警告,说测试模式与正常模式并行会带来 `memory access interruptions and host task cancellations`);`doorbell` 0 次;`submission queue` 与 `completion queue` 各 0 次;`DMA` 0 次;`MSI` 0 次;`driver` 3 次,没有一次在数据通路上(第 65 页是设备识别码的套话 `used as one mechanism for software to determine which driver should be loaded`,第 88 页两次指的是电气线路驱动器)。

**这一条的诚实边界要自己先写出来:这是一份设备侧规范,它能确立的是「HBF 自己既不定义、也不要求任何封装外的参与」,它本身证不了某个 xPU 厂商不会在 HBF 的地址范围前面自己放一套缺页机制,因为 xPU 内部不在这份规范的范围里。** 正文按这个强度写,比写成无条件的断言站得住。

**条件三:这一层介质所在的链路上没有可以接入第三方硬件的物理接口。**

规范支持数据通路这一半,但要加一个限定词。主带走的是 45 微米间距的微凸块、封装内不足 2 毫米(第 110 页 `The HBF uses a 45um pitch in the UCIe region`,用的是 `Figure 5-23 in the Rev3p0 UCIe spec, 10-column x64 Advanced Package Bump Map for <= 32 GT/s`),没有可以接进任何东西的地方。但 HBF 确实对外露出三个测试端口,其中 IEEE 1149.1(JTAG)在模组层面明确可以接外部调试器(第 86 页 Table 25 一列写 `Target connection in Module Level: External Debugger`,第 89 页 `This specification does not restrict the physical connection topology between the xPU, external test probes, and target devices.`)。**救住这一条的限定就在规范自己身上:三个测试端口没有一个能观察或服务一次主带访问,而直接访问端口(Direct Access,第 87 页 `provides low-level, parallel access directly to the NAND Core Dies and PHY, explicitly bypassing the Base Die Controller and FW algorithm`)一旦启用,第 88 页写明 `All on-the-fly commands queued in the Base Die Controller, or UCIe layer are abandoned and cleared`、`All UCIe PHY interfaces are taken out of service`、`Data stored in HBF may be lost`——它与正常运行互斥,看不到也服务不了任何一次在飞的访问。** 所以条件三在正文里写成「数据通路上没有可接入的物理接口」,并引第 88 页。

### 「拦截点」指什么

指一个位于被测程序之外、每一次内存访问都必须经过、并且允许在那里加上等待时间的地方。关键在「之外」:被测程序的二进制一个字节都不改,慢下来这件事由机器上别的层次提供。

主机这一侧历来有四处这样的位置,此前被这样模拟过的新内存(持久内存、CXL 内存)都挂在这条路上:操作系统页表、虚拟机的扩展页表、处理器的性能计数器、内存控制器与处理器互连本身。它们的共同点是被测程序原封不动,因为机器本来就在程序和内存之间放了一层可以替换或者插桩的软件。

### 表后说明:每一行的详细理由与核实状态

**第 1 行的四处位置,失败理由是同一条,而且是结构性的。** 操作系统页表缺页的做法是把一段内存标成不在场,程序第一次碰它就陷进内核,内核里可以停留任意久再放行;代表系统是 MaxMem(arXiv:2312.00647),原文 `libMaxMem then intercepts the mmap memory allocation system call. Large (greater than 1 GB) allocations are registered with userfaultfd, allowing the central manager to manage the memory backing these allocations. Any page fault from the process on these regions is forwarded by userfaultfd to the central manager, which is responsible for allocating memory to handle the fault.`(全文第 357 至 374 行)。**MaxMem 只能用来证明这条机制今天仍在用,不能拿它论证缺页开销大**:同一篇写着 `Userfaultfd has negligible overhead for Big Data applications [33].`(第 373 至 374 行),而且它识别热页靠的是 Intel PEBS 抽样,不是靠缺页。同一篇还有一句可以直接用的反面写照:`Like HeMem [33], MaxMem write-protects pages as it migrates them. When a protection fault occurs on a page under migration, the central manager waits until the migration completes before un-protecting the page.`(第 394 至 398 行)——保护设上之后只有第一次触碰会陷入,要每次都拦到就得每次重设保护。虚拟机扩展页表的代表是 Cylon(FAST 2026),原文 `Every guest access undergoes address translation through Intel's Extended Page Tables (EPT)`;它拦的是客户机里跑的处理器指令,而访问 HBF 的指令跑在 GPU 的流多处理器上。性能监控单元这一路除了不在路径上,还有第二条毛病:它本身不是逐次的,CXLMemSim 自陈 `Since it's always a sampled model which may lose a lot of data, PEBS does not record the prefetcher and writeback information`,而 HBF 这一条要回答的正是「这一次访问落在哪一页、此前的访问在缓冲里留下了什么」,抽样丢掉的就是这个。内存控制器与处理器互连这一路(把数据放到另一个插槽下面的内存上,靠天然的远端延迟近似新介质)有三条毛病:远端节点的延迟是机器固定的、只有一个值;它给出的是「多远」,表达不了 NAND 的按页读取与排队;最要紧的是它给主机处理器用,GPU 上的负载访问的是自己的显存,绑 NUMA 节点绑不到它。**一处更正:Quartz 不是缺页机制。** 官方仓库说明写的是——带宽用内存控制器里的热管理寄存器限流;双路机上把另一个插槽的内存当作虚拟非易失内存;延迟用周期计数器加分时段插停顿;通篇没有缺页或内存保护。所以 Quartz 归在性能监控单元与内存控制器这两路,不归缺页。

**第 2 行是 GPU 侧唯一一个真实存在的、位于被测程序之外的位置,不能说它不存在,要写成不可行。** 主机把某一页在 GPU 页表里撤掉,GPU 下一次访问产生一次可重放的缺页,由服务器 CPU 那一侧的开源驱动服务,服务时可以停留任意久。arXiv:2508.12743 的三句原文:`With XNACK, when a page fault occurs, the TLB waits for the PTE to be updated by the fault handler before retrying the memory access.`;`The two copies are kept in sync using the Linux kernel's heterogeneous memory management (HMM) subsystem.`;`Unlike Nvidia's Grace Hopper, where the GPU can access both page tables, the GPU on MI300A can only access its own page table.`

不可行的理由分两半,**两半现在都有同封装机器上的实测数支撑,不再依赖 PCIe 3 那个数外推**。同一篇 arXiv:2508.12743 的 §5.2 量的就是 MI300A(处理器与 GPU 共享同一份物理内存):`The CPU single-page latency is 9 µs on average with 11 µs tail latency (95th percentile). The GPU latency is 1.8-2.0 times higher with 16 µs for a minor fault and 18 µs for a major fault. The GPU tail latency is also higher with 20 µs for minor and 22 µs for major faults, indicating higher variability.` **次要缺页(页面已经在物理内存里、只需把页表项同步过去并重放访问、不搬任何数据)仍然要 16 µs,这就是净开销。** 吞吐一侧同一节 Figure 7:`GPU Major reaches a steady state at 10 K pages with around 1.1 M pages/s, while GPU Minor throughput increases up to 9.0 M pages/s at 10 M pages`,单核 CPU 872 K pages/s、12 核 3.7 M pages/s;页是 4 KiB(论文自己写 `10 M pages (40 GiB)`),9.0 M pages/s × 4 KiB ≈ 37 GB/s。

- **第一半,方向单一、无法标定。** 一次缺页要走中断、进服务器 CPU 那一侧的驱动、改页表项、再让全部流多处理器上的地址翻译缓存把旧映射作废。**16 µs 这个下界不是「远大于」目标值,它落在目标区间里面**——TileLens 给 HBF 页读延迟扫的取值是 1、2、5、10、20 µs(arXiv:2607.04031,原文 `page read latency across 1, 2, 5, 10, and 20 µs to cover the range`)。一个手段的开销下界落在要注入的量的区间中段,这个区间里就做不出可控的延迟。
- **第二半,吞吐量对不上。** 要维持「每一次访问都缺页」,每服务完一次就得重新撤掉映射、再跨全部流多处理器让地址翻译缓存作废一次;作废是一次全局操作,同一时刻在跑的线程束都要等它完成,本来并发的访问被逐次串行化。缺页路径的吞吐上界约 37 GB/s,比 HBF 规范三档带宽 0.384 / 1.536 / 3.072 TB/s 低 **10 到 83 倍**。而 HBF 这篇论文要回答的问题——缓存开多大、权重与键值缓存怎么在两层之间分配——全部是吞吐量问题。

**旧版里那个 23 µs 的处理方式本轮改掉了。** GPUVM(arXiv:2411.05309)原文 `The latency λ is 23μs empirically estimated on the testbed we use in our experiments.`,以及 `We also analyzed the overheads of host involvement in page fault handling to be up to 7× that of page transfer time`(条件是 64 KB 传输尺寸,论文 Figure 2 图注 `Note that host involvement overheads during the page fault are around 7× higher than the transfer time at 64KB page size.`),同篇 `The target throughput is 12GBps as we are using a PCIe-3-based machine`。**这个 23 µs 出现在 GPUVM 自己的系统设计一节里,是他们套 Little's law 算队列深度时用的访问延迟,论文没有把它标成「NVIDIA 统一内存里由服务器 CPU 那一侧处理缺页的开销」;「这条路径里含着跨 PCIe 把整页搬过去的时间」是从同段目标吞吐 12 GB/s 推出来的,是推断,不是原话。** 旧版第 59 行写「要把净开销这个数补实,唯一的办法是自己在一台同封装的机器上量一次,而本项目手上是 NVIDIA 卡」——**这句话现在是错的,同封装机器上的净开销已经由 arXiv:2508.12743 §5.2 公开给出,本轮删除该句。** 旧版第 17 行「吞吐约 6 GB/s 没有出处」的更正继续有效:**「6 GB/s」从全文删除。**

**第 3 行是零件,不是竞争者,本项目已经在用。** MQSim 一类算的是「一次页读要多久」,本项目缺的是「把这个时间加到 GPU 的某一次访问上」,两件事互补不冲突。这一行在表里的作用是交代 HBF 的处境,不是否掉 MQSim。**措辞本轮更正过一次:旧版写「HBF 没有这样一条离散的请求或命令通道」,这与规范原文相反**,详见第六节错误三。

**第 4 行救不活的理由最干脆,但要写成有条件的。** 铠侠那台机器是真实 NVIDIA RTX A5000 加五块 Intel Agilex 7 FPGA 开发板,在封装外的 CXL 链路上插自己设计的延迟部件,逐次给读请求加指定的额外延迟,被测程序一个字节不改。原文 `The CXL interface has two instances of CXL.mem each connecting to latency bridges that we designed to introduce additional latency to the onboard DRAM`;`the graph processing code of EMOGI works on the CXL memory without any modification`。另有两处量级对不上:他们单台硬件自报封顶 `the throughput is capped at around 5,700 MB/sec due to the single-channel DRAM`,而 HBF 规范三档是 0.384 / 1.536 / 3.072 TB/s;他们实测门阵列最多处理 128 个未完成请求,原文 `the maximum number of outstanding requests that the current Intel Agilex®7 FPGA can handle is 128... our CXL memory prototype can handle 64 (= 128/2)`。**若将来出现带可编程延迟部件的 HBF 开发板,这一行立刻就活了,而且会比本项目的做法更直接。**

**第 5 行的三条限制是机制推论,缺一次实测。** 手上「H100 SXM 的 HBM3 为 1593 MHz、A100 SXM 的 HBM2e 为 1215 MHz、只有流多处理器频率可锁」全是二手技术资料,要在本项目自己的卡上跑一次 `nvidia-smi -q -d SUPPORTED_CLOCKS` 才算核实。本轮执行核实的机器上没有这条命令、也没有 GPU,**这是唯一一条纯粹卡在环境上的缺口**。

**第 6 行就「给 HBF 建一个时序模型」这个窄目的而言已经被做出来了,但代表系统本轮更正。** 旧版写「HAVEN 就是在 GPGPU-Sim 上加 HBF 模型做出来的」,**这是错的**(详见第六节错误一)。四篇已发表的 HBF 评估工作里,建在整机逐周期 GPU 模拟器上的只有 TileLens,原文 `We use Macsim [16], a cycle-level GPU simulator, extended with DRAM, RoMe, and HBF memory models. Kernel traces are collected from an NVIDIA H200 GPU using a SASS-level tracer built on NVBit.`(SASS 是 NVIDIA GPU 已编译的机器码)。FlashAccel 是在 LLMCompass 之上搭的事件驱动模拟器再接一个按 plane 粒度建模页访问延迟的 NAND 模拟器,原文 `We build an event-driven simulator on top of LLMCompass [69] to model the latency of LLM inference`,全文 `thermal` 与 `temperature` 各出现 0 次。HAVEN 用的是 3D-FPIM 加 NeuroSim 的电路层仿真。H3 是一个性能模型。这一行能站住的话只有一句:**它们做不了这篇论文要做的那三件事**——跑不完真实的大模型推理负载(要跑的是 Qwen3-30B-A3B 在 vLLM 上跑到结束)、输出里没有芯片温度、「一次读慢了改变后续请求」这个反馈不存在。前两件由构造决定、补不上,第三件是原理性的。**代价也要说清:如果一位审稿人只关心「HBF 的页读延迟对矩阵乘的影响」,逐周期模拟是够用的,本项目的优势只在真实执行与温度这两列。** 逐周期模拟慢多少倍现在有一个可引的数:arXiv:2502.14691(Huerta 与 González,Universitat Politècnica de Catalunya)摘要 `simulating some GPGPU workloads in a single-threaded state-of-the-art simulator such as Accel-sim can take more than five days`,正文 `This speed-up reduces the simulation slowdown compared to real hardware from 10,748,031x of the single-threaded simulator to 766,423x of the parallel one`;**引用时要带上「在 Cutlass 这个基准上」,这两个数不是全套平均。**

**第 7 行不构成第一条挑战的反例,必须照实写。** 第一条挑战说的是:三个条件同时成立之后,效应只能写进被测程序自己的代码、包括它的运行时,而 NVBit 做的恰恰就是改写被测程序的代码。差别在于 NVBit 本身不含任何存储介质模型,也没有温度这个状态,它提供的是插桩能力不是评估平台;NVBit 在 SASS 那一层,本项目在 PTX 那一层(PTX 是显卡代码的中间文本,编译后得到 cubin 这个二进制产物,里面装的就是 SASS)。覆盖问题长在这条路上,本项目与 NVBit 都逃不掉。

### 「封装在一起」起作用的方式是间接的,UCIe 只是载体

正文要正面写一句:决定拦不拦得到的是那三个条件——这一次访问由谁翻译地址、在哪里被服务完毕、那条链路上能不能接进第三方硬件。**换成硅中介层、片上网络、NVLink,这三件事一件都不变。** UCIe 是芯片与小芯片之间的互连标准,HBF 恰好用它与计算单元相连;AXI 是芯片内部常用的一组读写事务接口约定。UCIe 是这个事实的载体,不是原因。不写这一句,读者会把结论读成「UCIe 导致的」。

### 「学界的标准答案」要收窄:整机逐周期模拟,加上外推来的时序参数

大纲现在写的是「学界对这一类介质的标准答案一直是整机逐周期模拟」。这句话说少了一半:在规范已出、硅片未到的那段时期,连「把内存那一层建准」都做不到,填进模拟器的时序参数是从相邻标准外推来的。

- gem5 在 2015-09 加进去的 HBM 支持,是**喂给普通 DDR 控制器的一组时序数字**,背后没有一个按 HBM 自己的通道组织方式调度命令的控制器。真正的 HBM 控制器是 **2022 年 5 月**才有的(提交 `60317f99fe`,2022-05-14,`mem: Add an HBM memory controller`,新建 `src/mem/HBMCtrl.py`、`src/mem/hbm_ctrl.cc/hh`)。**HBM2 真正需要的控制器,比 HBM2 随 P100 出货晚了六年。**
- 提交说明白纸黑字写着参数是外推的。gem5 的 HBM 时序提交(2015 年 9 月 22 日,`src/mem/DRAMCtrl.py`,+126 行)原文是分行的,**引用时要么分行照抄、要么标明是摘引**:

  > `The configuration values are based on:`
  > `- The HBM gen1 public JEDEC spec`
  > `- Publically released data from MemCon presentations`
  > `- Timing extrapolated from existing LPDDR configurations`
  >
  > `Will adjust once specs become available.`

  代码里的注释可以一起用:`# extrapolate the following from LPDDR configs, using ns values / # to minimize burst length, prefetch differences`(作用于 tWR、tRTP、tWTR),以及类头注释 `default timings based on data publically released ("HBM: Memory Solution for High Performance Processors", MemCon, 2014), IDD measurement values, and by extrapolating data from other classes`。gem5 的 HMC 时序提交(`25fe4c2529`,2015-06-07,`mem: Add HMC Timing Parameters`,改的是 `src/mem/DRAMCtrl.py`)末句原文 `The parameters for which no input is available are inherited from the DDR3 configuration.`

**准确的说法是:对这一类介质,学界的做法是整机逐周期模拟,加上从相邻标准外推来的时序参数;参数要等真硅片出来之后好几年才补准。** 这一改对论文有利:它说明在规范已出、硅片未到的这段时期,现有办法给出的答案本身就是外推的,而 HBFSim 做的是拿真实硬件上量到的东西去标定。这一句同时把「HBFSim 与整机逐周期模拟的差别」从「速度」一条扩成两条——速度,以及参数从哪里来。

### HBM 是同类的又一例,不是反例

早先的写法把 HBM 当成反例。这是错的:HBM 也在 GPU 封装内、也以访存方式被 GPU 访问、地址也由 GPU 自己翻译,主机同样管不着。**HBM 与 HBF 在三个条件上是同一类。**

真机上唯一能改 HBM 速率的旋钮是显存降频,而降频是整块显卡一个速率,既无法只对某几段地址生效,也无法让同一次运行里两种介质并存。**HBM 与 HBF 的差别只落在「需不需要」,不落在「能不能」。** HBM 已经买得到,没有人需要在真机上模拟一个买得到的东西;HBF 现在就要回答的问题一个都等不了。把 HBM 写成同类的又一例,比写成反例更有利:它说明这套判断不是为 HBF 量身定做的,而是能预先判断「哪一层介质拦不到」。

**这一节有两句要改。** 一句是「研究不同配置的 HBM,学界的办法一直是整机逐周期模拟」——没有任何调研支撑「一直是」,改成「公开发表的 HBM 配置研究主要走整机逐周期模拟」,或者举一两个具体例子。另一句是「HBF 的首批推理设备 2027 年初才送样」——这是一句带时间的产业断言,文档里一个出处都没有,要么找到厂商公告,要么改成不带具体时间的说法。

### 不解决会看到的错误结果

一次真实 vLLM 运行一共判了 23,210 次覆盖:12,626 次这一次 kernel 启动(kernel 指显卡上执行的一段程序,主机让显卡把它跑一遍就是一次启动)根本没碰到已登记的内存,10,584 次碰到了、但那个模块到本项目手上时只有已编译的 cubin 因而改不了,成功计时 0 次(出处 `/root/hbfsim/HBFSim/docs/proofs/2026-08-11-vllm-timing-adapter.md` 第 54、58、59 行)。**如果那 10,584 次按显存原速悄悄过去、报告里又不留痕迹,端到端量到的减速会接近 1.0 倍,读的人会读成这层硬件几乎不要钱。**

**这句话是假设句,不是对本项目代码现状的描述,正文里要避免被读成后者。** 现在的代码每次 kernel 启动都写一条 JSON 记录,判定写不进日志就拒绝执行(证据见第五节)。真正缺的不是痕迹,是分母:账本的最小单位是一次 kernel 启动,不是一次访问。

容量也归在这一条:容量模式给出的地址底下没有实体显存,改不到的 kernel 真跑过去会出错,所以那一档必须拒绝执行,而容量正是 HBF 存在的全部理由;现有证据是 110 GiB 逻辑范围配 2 GiB HBM 缓存下负载照常跑完(**这一条要补一个证据文件名,出处应在 `/root/hbfsim/HBFSim/docs/proofs/` 下,正文没写是哪一份**)。

### 适用范围

以上是从今天公开可用的机制推出来的,不是说 GPU 封装内的内存原理上永远不可拦截。有三种变化会让结论改写:NVIDIA 或 AMD 开放一个允许在每次访问上停留的驱动接口;某一代产品把这一层介质挪到封装外或经可插拔链路相连;出现带可编程延迟部件的 HBF 开发板。**能确定的是:以今天公开可用的机制而言,对同时满足那三个条件的一层内存,没有一个既能逐次拦到、又能施加可控延迟、还不必改动被测程序的位置。** 正文照这个限定写,不要写成永久成立的断言。

## 二、新的第二条挑战(可直接搬进大纲)

### 一句话概括

**Challenge2: 被测程序在 GPU 上执行一条读写指令、访问一段被登记为 HBF 的地址(不是显卡自带的 HBM,也不是主机对自己内存的访问),这一次访问要花多久,无法从这一次访问自己的参数——读写多少字节、是读还是写、落在哪个地址——推算出来:它取决于此前的访问在 HBF 的缓存缓冲里留下了哪两页,以及同一个 bank 上还有哪些请求没做完。只能测,不能算。**

旧写法是「一次访问要花多久,算不出来,只能测出来」。旧写法看不懂的地方在于「一次访问」没有定义:读者不知道是 GPU 访问 HBF,还是主机访问内存,也不知道「算不出来」是从什么算不出来。新写法把两件事写进概括句——**「一次访问」是哪一次访问**,以及**算不出来是指从这一次访问自己的参数算不出来**——机制留给展开部分。

### 「一次访问」指什么:两层单位,以及一处必须自己先写出来的错位

**被测程序这一层(HBFSim 真正下手的地方):GPU 上一条访存指令,对一段被登记为 HBF 的地址,执行一次读或一次写。** 登记为 HBF 的地址范围是运行时显式注册的,同一次运行里没被登记的地址照常走 HBM 原速。这条边界在仓库里是硬的:`/root/hbfsim/HBFSim/docs/proofs/2026-08-11-cd8p-vmem-tuning.md` 记的那次实测里,输出用的那条标量写指令也被插了桩,但它仍然是普通 HBM,因为它落在登记范围之外。

**HBF 这一层(OCP 规范定义的单位):读是 64 字节,写是 4 KiB。** 两个单位不一样,这件事本身就是第二条挑战的一部分。规范原文(下面同时给 txt 行号与 PDF 页码):

- 页大小 4 KiB,txt 第 1008 行,第 15 页:`4KiB NAND page size`
- 读的粒度 64 字节,txt 第 993 至 994 行,第 15 页:`Burst Length of 64B to 4KiB in multiple of 64B for read access on 64B aligned address and does not cross 4KiB NAND page boundary`
- 一页要拆成 64 条读命令,txt 第 4095 至 4097 行,第 56 页:`All Read requests are 64-byte granularity; however, the host shall send 64 read commands to retrieve the complete 4KiB data with different AXI IDs. Or if product support burst read then send burst read with burst length (0-63).`
- 读地址按 64 字节对齐,txt 第 4103 行:`The read request address is at 64-byte granularity.`
- 写的粒度是 4 KiB,txt 第 4182 行,第 58 页:`The write granularity to the Core die is 4KiB. The Base die controller first accumulates the complete 4KiB write commands and data is sent to the Core die.`

**由此得到这一条挑战最干净的说法:一页 4 KiB 等于 64 次 64 字节的读访问,这 64 次里最多只有 1 次要付把整页从阵列感应出来的时间,另外 63 次直接从缓存缓冲取。** 同样是一条 64 字节的读,同样的对齐、同样的大小,代价差在哪一次是第一次。

**一处错位必须自己先写出来。** GPU 上一个线程束(32 条线路)的一条访存指令,会被硬件合并成 32、64 或 128 字节的若干笔传输,再落到 HBF 的 64 字节请求上。**所以「一条指令」和「一次 64 字节请求」不是一一对应的**,中间隔着合并这一步;而这层映射同样不由这条指令自己的参数决定,它取决于同一线程束里 32 条线路当时算出来的地址分布。这一条不写,懂 GPU 的审稿人第一个问。

### 这一条管什么、不管什么

管的只有一件事:一次访问的代价不能由这次访问自己的参数算出来。**温度不在这一条里,温度是第三条挑战。** 三条挑战各管一件事——第一条管能不能把效果加到某一次访问上,第二条管这一次访问要花多久,第三条管整场运行的速率随时间下降;把温度写进第二条会让第二条和第三条互相覆盖。

### 展开之一:「这一次访问自己的参数」是哪三个,代进公式为什么算不出来

现在用的公式在 `/root/hbfsim/HBFSim/configs/profiles/nominal.json` 里:`"read_latency_ns": 10000`,`"aggregate_bandwidth_bytes_per_s": 512000000000`。公式就是**固定 10,000 纳秒,加上字节数除以 512 GB/s**;4 KiB 一页等于 4096 ÷ 512e9 = 8 纳秒。代进去核对得上:1 页 10,008、4 页 10,032、16 页 10,128、64 页 10,512、256 页 12,048、512 页 14,096,全部等于 10,000 加 8 乘以页数。

公式的三个输入,正好就是「这一次访问自己的参数」:

| 参数 | 在公式里怎么用 | 为什么不够 |
|---|---|---|
| **这次访问读写多少字节** | 除以带宽,得到传输时间 | 一页 4 KiB 只贡献 8 纳秒,而实测里一页要 11,133 纳秒。字节数这一项在 512 页时只占算出来那个数的 29%,占实测的 0.02% |
| **是读还是写** | `read_latency_ns` 与 `program_latency_ns` 两个常数二选一 | 规范里读和写连单位都不一样(读 64 字节、写 4 KiB);而且一次写可能顺带触发一次整块擦除(见下),二选一表达不了 |
| **落在哪个地址** | 完全不用 | 代价对地址高度敏感:同一个 bank、同一页第二次读几乎免费;落进便签存储区那一段地址,规范说延迟是三级缓存量级;落在某个 NAND 块的第 0 页去写,会触发整块擦除 |

算出来与实测差多少(实测六个断点出处 `/root/hbfsim/HBFSim/docs/proofs/2026-08-11-cd8p-vmem-tuning.md` 第 59 至 64 行):

| 页数 | 实测 P50(纳秒) | 公式算出(纳秒) | 公式偏快 | 实测是公式的几倍 |
|---:|---:|---:|---:|---:|
| 1 | 11,133 | 10,008 | −10.11% | 1.11 |
| 4 | 41,495 | 10,032 | −75.82% | 4.14 |
| 16 | 168,606 | 10,128 | −93.99% | 16.6 |
| 64 | 2,824,351 | 10,512 | −99.63% | 268.7 |
| 256 | 10,767,793 | 12,048 | −99.89% | 893.7 |
| 512 | 20,254,374 | 14,096 | −99.93% | **1,436.9** |

每页边际成本依次是 11,133 → 10,121 → 10,593 → **55,328** → 41,372 → 37,057 纳秒,形状是先平、再跳 5.2 倍、再回落。

**同一份实测里还有第二个模型可以拿来当对照,建议一起报:按「每页固定 11,133 纳秒」线性外推,在 4 页和 16 页上误差只有 +7.32% 和 +5.65%,到 64 页变成 −74.77%,512 页 −71.86%。两个方向相反的简单模型都在同一个位置崩掉**,这比只报一个模型有说服力。

### 展开之二:真正决定代价的是什么——此前的访问在缓存缓冲里留下了什么

这一条现在有 OCP 规范原文直接支撑,不再只是 NAND 常识:

- txt 第 4118 至 4120 行,第 57 页:`HBF supports two cache buffers for each bank to hold up to at least two pages of data. It is recommended to read the full first 4KiB page before issuing a third 4KiB address that will evict the first 4KiB data.`
- txt 第 4121 至 4122 行:`The Base die shall immediately serve the cache hit read from the cache buffer if ordering is not violated.`
- txt 第 4113 至 4115 行,第 56 至 57 页:`a. Cache hit reads are served immediately if there are no ordering violations.` / `b. For cache miss reads, Core die sense is triggered when prior read for that specific bank is done.`
- 寄存器字段,txt 第 5806 至 5810 行,第 70 页:`Number of Cache Buffers per Bank (NCBB): Indicates the number of cache buffers per NAND Bank in the Base die. Each Cache Buffer Size is same as NAND Page Size(4KiB).` / `0x01: 2 Cache Buffers per Bank (default)`

**读法:每个 bank 两个 4 KiB 缓冲(bank 指 NAND 芯片内部可以各自独立进行一次读取的一块存储区域),命中立刻返回、不命中才触发 Core die 感应。所以这一次读的代价,由这个 bank 上最近两次访问碰过哪两页决定。** NCBB 这个字段有 4 位宽,但只有取值 2 是合法的、其余全部标 Reserved,所以「每 bank 两个 4 KiB 缓存缓冲」不是厂商可以省掉的选项。规范甚至替主机把调度纪律写出来了(读完第一页再动第三个地址,否则第一页被逐出)——这等于承认这个不对称大到主机必须自己管。

**旧版第 294 行的表述要改。** 旧版写「每个 Bank 配 2 个至少两页(8 KiB)的缓存缓冲」,容易被读成每个缓冲装两页。规范原文是每 bank **2 个**缓冲、**每个 4 KiB(等于一页)**,合起来至少装得下两页。

### 展开之三:规范里另外五个「代价与本次参数无关」的来源

这五条建议全部写进展开部分。它们把「算不出来」从一个机制扩成一族机制,单挑其中任何一条都驳不倒整条论点。

1. **同 bank 排队。** txt 第 4116 至 4117 行:`HBF follows strict ordering for sense requests to Core die within the same bank requests.` 这次读什么时候开始感应,取决于同一个 bank 上前一次读做完没有。
2. **普通读要等一个定时器,批量读不等。** txt 第 4136 至 4147 行,第 57 页:`The regular reads are accumulated together and scheduled to the Core die optimally for best performance.`;对比 `Batch reads issued by the host will indicate that the read is batch read by setting AXI user bit 0 to 1 ... The Base die will not wait for the timer to expire`。同一条读,只因为一个提示位不同、以及它后面跟着什么命令,代价就不同。
3. **刷新撞车。** txt 第 9645 至 9647 行,第 117 页:`it shall ensure that refresh commands and read commands are not issued to the same die at the same time. Otherwise, some read operations may experience increased latency.`
4. **错误重试路径。** txt 第 9722 至 9723 行,第 119 页:`Still, those read latencies will be high.`;以及主机驱动的读重试(§11.5.1.6,第 119 页)`Host software needs to reissue the same read command`。
5. **写会顺带触发擦除。** txt 第 4186 至 4187 行,第 58 页:`HBF will internally auto-erase the NAND block from the host point of view, when receiving a page-0 (WL-0, STR-0, NAND block-X) write request of a NAND block.` 一次 4 KiB 写的代价,取决于它落在块内第几页——这是地址的低位,不是字节数、不是读写标志。

收尾可以用一个极端例子说明地址决定一切:便签存储区在同一个地址空间里,txt 第 1018 至 1019 行,第 15 页:`Support optional scratchpad memory on all UCIe channels for high priority read/write at ultra-low latency, where latency is in the order of L3 cache read/write`。同样一条 64 字节读指令,地址落在这一段是三级缓存量级,落在别处是 NAND 感应量级。

### 展开之四:一条决定性的、可以直接写进正文的事实

**这份 130 页的规范,从头到尾没有给出一个读延迟的数值。** 全文检索的结果:`latency` 出现 15 次,没有一次带数值;唯一沾时间单位的数字是上电电压斜率(100us、20us/V 到 20ms/V)和一个以 500 毫秒为单位的超时寄存器;全文只有两处交流时序表,一处是复位(Table 23、24),一处是 IEEE 1500 测试端口(Table 30);与读延迟沾边的只有一句不带值的 `4KiB * N * 16 pages are accessed in parallel in one HBF read latency time`。规范给了带宽(0.384 / 1.536 / 3.072 TB/s,Table 4,第 16 页)、给了粒度、给了页大小、给了缓冲数量、给了排序规则、给了错误路径——**就是不给一次读要多久**。同一份规范里凡是时间量一律推给产品:`NAND block size is defined in the product specification`(第 58 页)、`The reasons for restriction and duration of restriction are HBF product-specific`(第 119 页)、Table 33 的 `Endurance: Product Specific`、`Read Disturb: Product Specific`(第 106 页)。

**这是「只能测出来」最硬的一句话:定义 HBF 接口的那份文件自己就没有这个数。** 连带一条必须改的:**「HBF 规范给出的一次页读延迟」这个说法没有出处,全文删除**(旧版第 53、71 行两处)。要给区间时,可用的是 TileLens 扫的 1、2、5、10、20 µs 与 NAND 芯片手册的 tR 25 到 90 µs。

### 这套规范材料与手上那条实测曲线是两件事,必须分开写

上面这套规范与芯片手册材料讲的是介质与芯片接口层面的机制。手上那条六个断点的实测曲线量的是**一条主机软件换页路径、后面接一块 Dell CD8P NVMe 固态盘的完整路径,不是 NAND 介质本身**,证据文件里写明 `It does not claim ... that the Dell CD8P is a CXL device`。

两者在正文里各有各的用处,不能合成一句话:**规范与手册那套回答「为什么一次访问的代价算不出来」——代价取决于缓存缓冲里现在装的是哪两页,这是此前访问留下的状态,不是这一次访问的参数;实测那六个断点回答「照『固定延迟加上字节数除以带宽』这种形式算会错到什么程度」——到 512 页时那种形式比实测快 99.93%。** **并且:那个先跳后落的形状,本项目手上没有已确立的机制解释,把它说成缓存缓冲命中造成的是过度宣称,正文里不许出现。**

### 比值要分两个说,而且口径必须先统一

| | 数值 | 说明 |
|---|---|---|
| 固定开销之比(tR 对列切换开销) | **口径未定,见下** | tR 与列切换各自的取值区间要先定死 |
| 端到端之比(第一次访问对第二次访问) | **8 到 46 倍** | 数据输出两次都要付,所以省不到固定开销那个倍数 |

端到端那一组的明细(按 2400 MT/s x8 计算,本轮逐条重算全部正确):tR=50 µs、整页 16 KiB 是 56.8 µs 对 7.13 µs,8.0 倍;tR=50 µs、读 4 KiB 子页是 51.7 µs 对 2.01 µs,26 倍;tR=90 µs、读 4 KiB 子页是 91.7 µs 对 2.01 µs,46 倍。

**固定开销那一组现在不自洽,这是本文档自己的问题,进正文前必须解决。** 同一个量在旧版里出现了三种互不相等的写法:旧版第 190 行写「**167 到 667 倍**,tR 取 25 到 90 µs、列切换取 0.06 到 0.5 µs」,可是按这两个区间硬算,最小是 25 ÷ 0.5 = **50**,最大是 90 ÷ 0.06 = **1500**;旧版第 184 行给的列切换总开销又是「约 0.25 到 0.35 µs」,按这个算是 25 ÷ 0.35 = 71 到 90 ÷ 0.25 = **360**;旧版第 195 行与第 213 行还把同一个量写成「**100 到 700 倍**」。**缺的是一个决定:tR 与列切换各取哪一个区间。定下来之后把算式写进正文,四个互不相等的数字不能同时留着。**

**能经得起审稿人的那句话的形状是:把数据从阵列感应出来这一步,比在已经调入的那一页里挪一次列指针贵若干倍(口径按上面定下的算式);而第二次访问端到端省下来的是 8 到 46 倍,取决于这次读多大一块以及 tR 是多少。** 只报固定开销那个倍数会被驳——数据输出的时间两次都要付,倍数落到端到端就小一个数量级;只报端到端那个倍数又说不清机制在哪。两个一起报,并且写明各自的口径。

### 后半保留:程序真的在等,能观测到的只有一个相加的结果

这一半与大纲现有写法一致,不改:真实等待时间里同时装着被建模的介质延迟和注入本身的开销。要把两者分开,需要知道「如果不注入,这次访问实际什么时候完成」——正是第一条挑战那张四个必需量的表里第 3 项、任何层都观测不到的量。**这一半在代码里只做了一半,见第五节。**

### 不解决会看到的错误结果

在大传输上系统性地把这层硬件算得比实际快(512 页那一档快 99.93%),于是缓存该开多大、要不要预取、权重与键值缓存怎么在两层之间分配,这些结论会一致地偏向「不需要这一层」。另一半是:同一份访问序列,重排一下顺序就会改变有多少次访问落在已经调入的那一页上,而按「固定延迟加上字节数除以带宽」这种形式算,重排前后一模一样——**一个连「换个访问顺序会不会更快」都答不出来的模型,回答不了 MoE 的冷专家该不该放上这一层。** **注意:这个例子现在只能用来说明那种公式形式的缺陷,不能顺带暗示本项目的模型答得出来——本项目的模型同样答不出来,见第五节。**

### 适用范围

这一条成立的前提是访问落在同一页内、并且中间没有别的阵列读把缓冲覆盖掉。流式顺序读上不成立(ONFI 第 6.15 节的 Read Cache 会把下一页的 tR 藏在当前页的数据输出后面,流水线一旦建立就是带宽受限);后端是 DRAM 的 CXL 内存扩展器上不成立;后端是 NAND 的设备上成立。**这一条主张最强的场景是随机的、子页的、能复用已调入那一页的访问;最弱的是流式顺序读。** 倍数本身随 tR 与单次读的大小变化,正文里报的是区间,不是一个数。另有一条与 CXL 有关的限定:CXL 的「常数延迟」只在空载成立,实测空载 214 到 394 ns(arXiv:2409.14317 表 1,四款真实设备),接近带宽饱和时升到 400 到 550 ns(arXiv:2405.14209 第 3 节),准确说法是「空载区间用常数够用,再加一个排队项」,而且空载值跨设备差近一倍,是每个设备一个常数、不是一个普适常数。

## 三、这一条与 HBF 的 NAND 机制的关系

### 两级缓冲,不是一级,写的时候不要混

- **Core die 那一级(NAND 芯片自己的页寄存器)。** 一次读先把整页从存储阵列感应进页寄存器(这段时间叫 tR;页寄存器指闪存芯片里存放刚感应出来那一整页数据的缓冲区),再把要的那部分输出到总线上。要读的数据所在的那一页已经在里面,就不必再付 tR,只要改一下列地址。这不是推测,是一条标准命令,ONFI 6.0 规范第 6.20 节 `Change Read Column Definition` 第 231 页原文:

  > `The Change Read Column function changes the column address from which data is being read in the page register for the selected LUN. Change Read Column shall only be issued when the LUN is in a read idle condition.`

  编码是 `05h → C1 → C2 → E0h`(编码里的 C1、C2 是这条命令自带的两个列地址周期,与本文档里挑战 C1、C2 的编号无关)。Micron 手册把它叫 `RANDOM DATA READ (05h-E0h)`,Linux 源码里是 `NAND_CMD_RNDOUT`。列切换的开销由 tCCS 决定(tCCS 指发出新列地址之后到数据可以开始输出之间必须等的时间):Macronix 手册里 60 ns、Micron 手册里 100 ns、Linux 的 ONFI mode-0 默认值 500 ns;加上 tRHW 与几个总线周期,总共约 0.25 到 0.35 µs。**这一段的三个 tCCS 值与 ONFI 第 231 页原文本轮均未核到原始文件**(ONFI 规范要会员身份、芯片手册要逐份下载),缺料与替代路径见第七节。
- **Base die 那一级(OCP 规范定义的缓存缓冲)。** 每 bank 2 个,每个 4 KiB,等于一页;命中立刻返回,不命中才触发 Core die 感应。**OCP 规范全文没有提到 Core die 的页寄存器**,它只说不命中会触发 `Core die sense`;规范里 `page register` 出现 0 次,`page buffer` 出现 1 次(第 112 页)而且指的是主机系统的页缓冲,不是 HBF 自己的。

**建议的接法:HBF 把闪存那个「第一次贵、后面便宜」的不对称原样搬到了 Base die,而且写进了规范、对主机可见。** 页寄存器那套材料(ONFI、Micron、Macronix)讲的是这个不对称从哪来;OCP 规范讲的是 HBF 确实有这个不对称、粒度是 4 KiB、深度是每 bank 两页。两者不要写成同一个东西,也不要在正文里把 Base die 的缓存缓冲直接叫成页寄存器。

### 一个悬了很久的问题,规范把它在 HBF 这一侧解掉了

旧版第 229 行留着一条未决:Change Read Column 要求 LUN 处于读空闲状态、是 die 级命令、页寄存器会被下一次阵列读覆盖,**主机软件能否通过 NVMe 用上这条命令,正反都没有证据**;如果模型建在服务器 CPU 那一侧,可能是在建模一个只有固态盘控制器固件才用得上的不对称。

**在 HBF 上这条不再是未决项。** 规范明说命中由 Base die 立刻服务、不命中才触发 Core die 感应,还给主机写了避免逐出的调度建议——**这个不对称在 HBF 上是主机可见的、规范强制的行为,不是藏在固件里的内部细节**,主机发的每一笔 64 字节读都直接吃到它。旧版那段要改写成:在固态盘上正反无证据,在 HBF 上规范直接给了答案。**在固态盘语境下这条仍然未决**,两者要分开写,缺料与条件见第七节。

### 两个比值放进 HBF 语境时要标口径

第二节末尾那两个比值(固定开销之比、端到端之比 8 到 46 倍)算的都是 **Core die 页寄存器那一级**。放进 HBF 语境时要说清:HBF 的 xPU 那一侧看到的命中与不命中之比,**规范没给数,只给了行为**;那两个比值是从 NAND 芯片参数推出来的量级,用来说明这个不对称有多大,**不是 HBF 的实测,也不是规范值**。两个比值一起报、并注明各自口径,同时注明这是芯片级推算。

## 四、以前的模拟器为什么没有这个问题、也没有解决它

### 1. 持久内存与 CXL 内存扩展器:这个不对称只有两三倍,而且服务器 CPU 那一侧看不见

**DRAM 也有类似的机制——行缓冲命中就不必重新激活一行——但差距小得多。** 出处是 Mutlu 与 Moscibroda,ISCA-35 2008(PAR-BS),ETH 托管的 PDF `people.inf.ethz.ch/omutlu/pub/parbs_isca08.pdf`,共 12 页。**Table 2 在第 8 页,不是旧版第 213 行写的第 7 页。** 可以直接照引的原句(Table 2 内):

> `Round-trip L2 miss latency For a 64-byte cache line, uncontended: row-buffer hit: 40ns (160 cycles), closed: 60ns (240 cycles), conflict: 80ns (320 cycles)`

80 ÷ 40 = **2.0 倍**,这是程序实际观察到的往返之比,原文可引。**在 bank 这一层的 3.00 倍是推算出来的,不是原文里的数,正文必须标明是推算**:推法用同一篇的两处——正文对三种情况给的 bank 访问延迟(命中等于 tCL;行关闭等于 tRCD 加 tCL;行冲突等于 `the highest bank access latency of tRP +tRCD +tCL`),加上 Table 2 的 `tCL =15ns, tRCD =15ns, tRP =15ns`,45 ÷ 15 = 3.00。两三倍的差距用一个常数近似,误差进不了结论;NAND 那个量级不行。

**更进一步,在 CXL 内存扩展器上,这点局部性从服务器 CPU 那一侧根本看不见。** **旧版第 215 行引的那句话不存在,本轮全文逐字检索确认后删除**:arXiv:2411.02814 只有 v1 有 HTML(v2 至 v5 均 404),在 v1 全文里检索 `does not exhibit latency improvements`、`comparable to random`、`prefetcher disabled` 三个片段全部零命中。替换材料出自同一篇 v1,逐字核过:

- 标题:`The Hitchhiker's Guide to Programming and Optimizing Cache Coherent Heterogeneous Systems: CXL, NVLink-C2C, and AMD Infinity Fabric`
- 测量框架默认关掉预取器:`turning off CPU hardware prefetchers, disabling simultaneous multithreading (SMT), disabling interrupt handlers while running microbenchmarks, and boosting CPUs to performance mode through the CPU scaling governor.`
- §3.1 的数(CXL 相对同机 DRAM 的延迟倍数,指针追逐加 clflush):Intel-SPR 配 ASIC-CXL,顺序本地 **1.94×**、顺序远端 **1.76×**;AMD-Zen4 顺序本地 **2.12×**、顺序远端 **1.68×**。紧接着的原句:`The same trend applies to random access, where Intel-SPR's CXL has 1.92× and 1.75× higher latency on local and remote accesses, while AMD-Zen4's CXL expander has 2.06× and 1.66×.`

**换过之后能站住的说法是:在关掉预取器的条件下,CXL 内存扩展器相对本机 DRAM 的延迟倍数,顺序访问与随机访问最多只差约 3%(1.94 对 1.92、1.76 对 1.75、2.12 对 2.06、1.68 对 1.66)——控制器后面那层 DRAM 的行缓冲局部性,服务器 CPU 那一侧基本观测不到,所以做 CXL 内存模拟的人从一开始就不必建这个模型。** 两条限定要跟着写:一,这四组是 CXL 对 DRAM 的**倍数之比**,不是顺序与随机的绝对延迟之比;二,arXiv 上只有 v1 有 HTML,而 v1 是带作者待办批注的草稿版(正文里能看到 `\zixuan TODO for V2` 一类残留),引用时要注明版本。

### 2. 整机逐周期模拟:构造上就没有这个问题

在 GPGPU-Sim、Accel-Sim、MGPUSim 这三个系统里,被建模的时间与真实流逝的时间是两回事,注入本身的开销不会混进测量值;代价是跑的不是真实执行。这一条不改。

**这批工具的主体归第一条挑战,而且措辞要改一个词。** 早先说「它们全都挂在块设备接口上」并不准确——NANDFlashSim 挂得更低,挂在闪存芯片自己的命令与引脚接口上。准确的说法是:**它们全都挂在一条离散的请求或命令通道上,应用与介质之间总有一层可以被替换或插桩的软件(驱动、队列、闪存转换层、虚拟设备、固件)。** HBF 那一侧的访问单位是 GPU 线程发出的一条读写指令,地址由 GPU 自己的内存管理单元翻译,主机软件这一侧既没有队列、也没有可替换的驱动层。所以这批工具接不上去,这是拦截点的问题,归第一条挑战(表里第 3 行)。三处外部证据支持这个归类:

- **Cylon(FAST 2026)把同一件事写成接口问题。** 本地文件 `/root/hbfsim/HBFSim/docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.txt`(行号为该文本文件的行号):第 94 至 96 行 `Unlike block-based emulators such as FEMU [14] and NVMeVirt [15], Cylon exposes CXL.mem interfaces, making it fundamentally different from NVMe SSD emulation.`;第 365 至 368 行 `While FEMU and NVMeVirt model NAND behavior through a block I/O interface, Cylon's CXL-SSD exposes its capacity directly in the CPU physical address space and is accessed through load/store instructions over CXL.mem.`。Cylon 的解法是新的拦截路径(动态扩展页表重映射,第 443 至 455 行),而**介质时序模型原样沿用 FEMU**(第 197 至 202 行 `Cylon extends FEMU as its CXL-SSD backend: on a cache miss, the request is forwarded to FEMU`)。介质模型可以跨接口搬运,拦截点不能。
- **ATC'23 那篇 CXL-flash 是同一个形状:** 介质模型用 MQSim 加 MQSim-E(第 945 行),拦截靠 Valgrind/Cachegrind 加内核页表事件离线拼出物理地址记录(第 444 至 460 行),并明说 `no publicly available tool traces the physical memory transactions between the last level cache (LLC) and the memory controller without hardware modifications`(第 465 行)。
- **本项目的仓库也是这个形状:** MQSim 被保留成介质模型,而「把一条读写指令变成一次介质页请求」那一层是本项目自己造的(`/root/hbfsim/31-HBFSim合作者意图解读-2026-08-10.md` §4.3;容量模式下 MQSim 看到的是缓存未命中与脏写回,不是每条被改写的读写指令,见 `/root/hbfsim/32-HBFSim合作者最新进展-2026-08-11.md` 第 344 行)。

**属于第二条挑战的那一半,界线画得很干净:这批工具接上之后算出来的那个数,是这一次访问自己参数的函数,不带此前访问在页寄存器里留下的状态。** 分工写法是:第一条挑战管「这批工具挂在哪一层、那一层在 GPU 与 HBF 之间不存在」;第二条挑战管「挂上之后它算出来的那个数怎么算的、为什么算不出来」。不建议整段放进第二条挑战——「块接口上的工具接不到 GPU 的读写指令」与「一次访问要花多久」无关。

**今天在用的四家逐条代码证据:**

### 4. 范围必须写死到「CXL 内存扩展器」,不能笼统写「CXL」

三星 CMM-H 是 48 GB DRAM 缓存(缓存行 4 KB)加 1 TB NVMe 固态盘后端,**这个形状正是本项目要说「只有 NAND 才有」的那个形状,而它是一款 CXL 设备**。不限定范围,懂 CXL 固态盘的审稿人一句话就能驳倒。原文出处 `/root/hbfsim/HBFSim/docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.txt` 第 179 至 186 行:`CMM-H is a hybrid CXL memory prototype that integrates a 48GB DRAM cache (4KB cacheline) with a 1TB NVMe SSD backend, coordinated by an Intel Agilex FPGA controller over PCIe Gen5`。

**但那两个延迟数的归属旧版写错了,必须改(详见第六节错误二):150 ns 与 40 µs 是 Cylon 自己的仿真配置值,不是 CMM-H 的实测值。** 40,000 ÷ 150 = **266.7 倍**这个算式成立,但它是从两个仿真参数算出来的。准确的写法是:在**后端是 DRAM 的 CXL 内存扩展器**上,这个不对称只有两三倍而且服务器 CPU 那一侧看不见;后端是 NAND 的设备(CMM-H、HBF)属于另一类,不是反例——**而且 HBF 这一类的不对称是写进规范、对主机可见的**。

## 五、本项目现在的代码能不能解决这两条挑战

这一节按代码核实的结果照实写,做不到的地方明写。**结论先给:第一条挑战里「把延迟加到某一次访问上」这一半代码是齐的,「记账」那一半只做到 kernel 启动这个粒度;第二条挑战里实测曲线在用,但「同一页第二次被读时更便宜」两条路都没有建模,而且快速路径的方向是反的——这是论文的一处硬伤,必须自己先写出来。**

### 第一条挑战:注入这一半做到了,记账这一半只做到 kernel 启动这个粒度

**注入这一层,代码是齐的。** 每一条被支持的全局读写指令在 PTX 里被换成「先调 `__hbfsim_resolve`、再用它返回的地址执行原指令」(`/root/hbfsim/HBFSim/src/ptxpass_hbf/transform.cpp` 第 223 行计数 `rewritten_instructions`,第 229 至 230 行计数 `unsupported_instructions` 并记下操作码)。`__hbfsim_resolve` 在 `/root/hbfsim/HBFSim/src/cuda_runtime/device/hbf_device.cu` 第 435 至 533 行,它自己查 GPU 可见的范围表(第 486 至 496 行)、自己算这次访问落在哪一页(第 503 行)、自己在设备上等够时间。整条路径没有任何一步落在服务器 CPU 那一侧,与第一条挑战的三个条件一致。

**记账这一层,做到的部分。** 每一次 kernel 启动都要过一次判定,判定在 `/root/hbfsim/HBFSim/src/cuda_runtime/coverage.cpp` 第 272 至 459 行,调用点在 `/root/hbfsim/HBFSim/src/cuda_runtime/launch_gate.cpp` 第 707 行。判定按登记方式分三档处置:只计时的范围遇到改不了的模块时放行,但结论标成 `opaque_unmodeled_timing`、`modeled=false`、`opaque_unmodeled=true`(coverage.cpp 第 76 至 90 行);`LegacyStrict` 与容量模式(地址底下没有实体显存)一律拒绝执行。判定写不进日志就拒绝执行这一条也是真的:`/root/hbfsim/HBFSim/src/reporting/coverage_writer.cpp` 第 54 至 60 行,`coverage_decision_permits_launch` 先写日志再看结论,写失败就返回不批准;launch_gate.cpp 第 166 至 174 行在写失败时还往标准错误打一行。**所以第九条设计目标(有 HBF 地址可能到达未插桩或不支持的访存操作时一律不放行)在代码里成立,但正文必须写成分档——只计时的放行并标注这次没计时,容量模式的拒绝执行——不能写成一律拒绝。**

**记账这一层,缺的部分,这一条要照实写进论文。** 账本的最小单位是一次 kernel 启动,不是一次访问。一次启动被标成 `opaque_unmodeled_timing`,只说明「这次启动里有 HBF 指针进了一段改不了的代码」,不说明这段代码里有多少次访问、多少字节按显存原速跑过去了。**而且没有分母:被漏掉的那些访问不产生任何事件,也没有任何计数器数它们**——共享控制区里的 `fast_requests`、`reference_requests`、`fast_modeled_ns`(`/root/hbfsim/HBFSim/src/host_service/control_layout.hpp` 第 113 至 115 行)数的全是已经计过时的那些。所以现在能报「有多少次启动漏了」,报不出「漏掉的访问占全部 HBF 访问的百分之几」。PTX 改写那一侧的 `unsupported_instructions` 是编译期的静态条数,不是运行时的执行次数,补不上这个分母。

### 第二条挑战:实测曲线在用,但「同一页第二次被读时更便宜」两条路都没有建模

**实测曲线怎么用的。** 六个断点从参数档 `/root/hbfsim/HBFSim/configs/profiles/cd8p-vmem-p50.json` 第 26 至 57 行读进来,经 `/root/hbfsim/HBFSim/src/profile/profile.cpp` 第 54 至 80 行解析、第 188 至 230 行校验(强制页大小 4096、分位数必须是 p50、SHA-256 必须是 64 位小写十六进制),再写进共享控制区的 `empirical_breakpoint_pages[6]` 与 `empirical_cumulative_ns[6]`。设备侧的取值在 `/root/hbfsim/HBFSim/src/cuda_runtime/device/hbf_device.cuh` 第 323 至 376 行:`empirical_cumulative_ns` 在两个相邻断点之间做线性内插,`empirical_service_ns` 取「读到第 n 页的累计时间减去读到第 n−1 页的累计时间」,也就是把这一次访问收成这条曲线上的边际成本。取值的自变量只有一个,叫 `run_pages`,含义是「这一页在本次连续传输里排第几」。

**快速路径的方向是反的。** `update_empirical_burst` 在 hbf_device.cuh 第 407 至 428 行,续上一次的条件写死在第 419 行:`previous_page + 1 == page`,必须是上一页的**下一页**。重复读同一页时 `previous_page == page`,这个条件不成立,`run_pages` 被重置成 1,按曲线第一个断点整页收费。**代进那六个断点算出来的具体数是:同一页连读两次,第二次收 11,133 ns;顺序往下读一页,第二次收 10,121 ns。重复读同一页比读下一页还贵约 10%。** ONFI 的 Change Read Column 说第二次应该便宜到 0.25 至 0.35 µs,代码给出的是比第一次还贵一点——**方向相反,不是幅度不够**。

还有一处同类问题:`empirical_burst_state` 是共享控制区里的**一个** 64 位字(control_layout.hpp 第 119 行),全设备所有线程束用比较并交换抢它。它记的是「上一次全局请求读的是哪一页」,既不是每个 die 一份、也不是每个 plane 一份。多个线程束交错访问时,连续段会被互相打断、`run_pages` 频繁归 1。

**详细参考路径同样没建。** `/root/hbfsim/HBFSim/src/mqsim_adapter/mqsim_online.cpp` 第 61 至 63 行把三个页读延迟(LSB/CSB/MSB)全设成同一个 `profile.read_latency_ns`;第 44 至 45 行 `Caching_Mechanism::SIMPLE`;第 121 至 122 行 `Device_Level_Data_Caching_Mode = TURNED_OFF`。MQSim 的 `Flash_Chip` 本身也不看页寄存器里现在装的是哪一页(上游代码证据见第四节)。所以详细路径同一页读两次收同一个价。

**代码里确实存在的两处「第二次更便宜」,都不是这件事,不能拿来充数。** 一是线程束内的合并:hbf_device.cu 第 504 至 520 行用 `__match_any_sync` 把同一条指令里访问同一页的活跃通道归成一组,只选一个通道去发请求;这是同一条指令内部的合并,对应真实 GPU 的访存合并,不是跨时间的页寄存器命中。二是容量模式的 HBM 页缓存(`/root/hbfsim/HBFSim/src/cuda_runtime/hbm_cache.hpp`):命中的页直接返回驻留帧、根本不发介质请求(设计文档第 143 行原文 `Hits return the resident frame without a media request`);这是把页整个搬到显存里之后的复用,第二次代价接近零,不是「省掉 tR、只付列切换」。而且容量模式(`mode == 2`)在 hbf_device.cu 第 515 至 519 行永远走详细路径,不进快速路径。

**所以第二条挑战指出的那个现象——一次访问的代价取决于此前的访问在页寄存器里留下的状态——本项目自己的实现也没有建模。这一点在论文里必须自己先写出来。** 第二条挑战现在只能声称「用实测曲线代替了固定延迟加带宽这种算法」,**不能声称「建了页寄存器命中」**。

**另有一处已声明但没接上的东西。** `AccessClass` 里有一个 `locality_bucket` 字段(`/root/hbfsim/HBFSim/include/hbfsim/hybrid_model.hpp` 第 17 行),设计文档第 401 行说快速模型要用局部性分类。全仓库检索下来,这个字段除了测试里显式填 0,没有任何生产代码给它赋过非零值。连带的是:`Calibrator` 与 `HybridSampler`(`/root/hbfsim/HBFSim/src/hybrid/calibrator.cpp`)在生产代码里没有任何调用方,只有 `tests/cpu/calibrator_test.cpp` 用到。也就是说设计目标第 5 条里的**校准**这一半没有接线;设备上真正在跑的抽样是 hbf_device.cuh 第 182 至 188 行那个独立的 `hybrid_reference_sample`,它只决定这次请求送不送去详细路径,不回头改快速模型的参数。

**第二条挑战「后半」那四个数只实现了两个。** `modeled_ns` 与 `service_ns` 有,`wall_ns` 与 `overhead_ns` 全仓库零命中,那条时序有效性判定与 `emulator-overhead-limited` 标记一行代码都没有。所以正文里这个子问题只能写成「现在把两笔合在一起报,拆开是待做工作」。

## 六、本轮查出的必须更正之处

### 错误一:HAVEN 不是建在 GPGPU-Sim 上

arXiv:2603.01175(HAVEN)全文检索 `GPGPU-Sim`、`Accel-Sim`、`gpgpu`,**零命中**。§4.1 方法学原文:

> `HAVEN and HBF Simulation. We simulate the re-architected 3D NAND subarray using 3D-FPIM [11] combining with NeuroSim [12]. The energy model is calibrated by industry-grade performance [10].`
> `Benchmarks. All experiments are conducted on a server equipped with an AMD EPYC 7302 16-core CPU, 512 GB DDR4-3200 memory, and a NVIDIA A100 40GB GPU.`

HAVEN 的 HBF 模型是电路与阵列层的仿真(3D-FPIM 加 NeuroSim),基准测试跑在一台真实 A100 服务器上。**连带影响很大:旧版第 97 行整段的论证前提是「HAVEN 就是在 GPGPU-Sim 上加 HBF 模型做出来的,所以正文不能写『逐周期模拟做不了 HBF』」,这个前提不成立。** 四篇 HBF 评估工作里建在整机逐周期 GPU 模拟器上的只有 TileLens(用 Macsim)。**要不要保留「不能写逐周期模拟做不了 HBF」这个自我设限,取决于 TileLens 一篇够不够,需要重新判断——这是一处要拍板的决定。** 顺带:HAVEN 全文 `thermal` 出现两次,一次是设计约束句 `To preserve thermal and package constraints comparable to HBM`,一次是参考文献标题,**没有温度建模**,这一点可以照写。

### 错误二:三星 CMM-H 的 150 ns / 40 µs 是 Cylon 的仿真配置值

旧版第 221 行把这两个数写成 CMM-H 的行为。核 Cylon 原文:容量与缓存行确是 CMM-H 的(第 180 行 `a 48GB DRAM cache (4KB cacheline) with a 1TB NVMe`);但 **150 ns 是 Cylon 自己那条快路径的值**(第 419 行图注 `Figure 1: Cylon architecture. Cylon with fast path (green, 150ns)`,第 884、886 行说明它来自宿主机的跨插槽内存访问时间 `remote-NUMA latency (∼150ns)`);**40 µs 是 Cylon 喂给 FEMU 的配置参数**(第 1061 行 `fixed to realistic values (40 µs read, 200 µs write, and 2,000 µs erase)`,第 1607 行同)。而且 Cylon 自己说 CMM-H 的内部是不公开的(第 71 行 `Samsung's CMM-H, for example, demonstrates cost-effective expansion but is largely opaque`)。**改法:三个数的归属分开写;「约 270 倍」是从两个仿真参数算出来的,不能说成 CMM-H 实测的不对称。** 论点(后端是 NAND 的 CXL 设备与 HBF 同类、不是反例)不受影响,证据强度要下调。

### 错误三:「HBF 没有离散的请求或命令通道」与规范原文相反

规范 §5.3.1(txt 第 4085 至 4092 行)明写主机要为一页发 64 条读命令并各带不同的 AXI ID;批量读提示走 AXI user 第 0 位(§5.3.2.2);Base die 上有命令队列,寄存器 `Maximum Outstanding Commands Supported (MOCS)` 最高 16,384 条(txt 第 5812 至 5824 行,第 70 页);每次访问带命令类型字段(Table 8,第 41 页 `ARUSER [1:0]: Cmd_packet_type; 2b'00: Flash IO CMD; 2b'01: Scratchpad IO CMD; 2b'10: CSR/ADMIN; 2b'11: Reserve`)并在响应里带每条命令的状态码(`RUSER [5:2]: CMD Status`,第 42 页;状态表 Table 12 在第 59 至 60 页)。

**所以「HBF 没有请求或命令这个概念」站不住,「HBF 是用普通读写指令访问的」这个说法也不能写。** 能站住的准确说法是:**HBF 是一个平坦按字节编址、非一致性的内存设备(第 13 页 `a non-coherent memory-centric flash device`),它的每一次访问是 xPU 经封装内的裸片对裸片链路发出的 AXI 读写事务,带每条命令的完成状态;这条请求通道在封装内部,主机软件这一侧没有提交队列、没有门铃寄存器、没有可替换的驱动层。** 论点(存储那一行几十年攒下的拦截点挂不上去)不变,措辞必须换,否则拿着规范的审稿人一句话就能驳。

### 错误四:固定开销那个倍数在文档里有三种互不相等的写法

详见第二节「比值要分两个说」。**缺的是一个决定:tR 与列切换各取哪一个区间。** 端到端那一组(8 / 26 / 46 倍)本轮逐条重算全部正确,不受影响。

### 一处必须删的说法:「HBF 规范给出的一次页读延迟」

规范全文没有任何读延迟数值(第二节已给检索结果)。旧版第 53、71 行两处依赖这个说法,**全部删除**;要给区间时改用 TileLens 扫的 1、2、5、10、20 µs 与 NAND 芯片手册的 tR 25 到 90 µs。
