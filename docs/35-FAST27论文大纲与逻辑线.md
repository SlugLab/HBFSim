# HBF背景介绍:
大模型推理能跑多大、多快，受限于加速器封装里能放下多少数据：模型权重在长大，推理过程中缓存的键值对随上下文长度和并发请求数增长，两者都要放进 HBM，而 HBM 单堆容量的增长跟不上。
HBF（High-Bandwidth Flash，高带宽闪存）是工业界给出的扩容答案：把 NAND 闪存做成与 HBM 相同的堆叠形态、放进加速器封装，**在同等造价下提供 HBM 的 8 到 16 倍容量**
适合放在HBF的数据归成三类：
一是模型权重，理由是"只写一次,读很多次,写入寿命的限制对它们不成立"；
二是多个请求共享的 KV cache，理由相同；
这两类都以访问可预测为前提. 推理逐层顺序执行,上一层算完就知道下一层要读什么,数据可以提前搬进缓冲区,HBF的劣势10 微秒的延迟因此被覆盖掉
三是MoE（混合专家模型，每一层有多个专家子网络、每个 token 只激活其中少数几个）：专家权重只读、体量也大，满足第一个条件，但激活哪个专家由路由在运行时决定，提前不知道要读什么，预取窗口得预测

hbf的很多问题需要一个能跑真实负载的模拟器可以回答的。**比如HBF的温度问题是一个值得关注的担忧**. 首批 HBF 2027 年初才送样，而"要不要在封装里放一层闪存、放多大、怎么用"这些问题现在就要回答。

## 论文主张

**我们要做的是一个模拟器 HBFSim**：让真实的推理负载照常在真实 GPU 上执行，同时在执行过程中模拟 HBF 的时序、容量与热效应。

要把这样一个模拟器做出来，有以下3个challenge: 

**第一，HBF 有多慢、能装多少这些效果必须在真实执行中施加，而真实执行覆盖不全。** 真实负载要照常执行、这些效果在执行过程中施加，而不是先把访问序列记录下来事后回放——真实程序一次读慢了，它接下来发什么请求会跟着变，这件事在回放里不存在。而能施加效应的地方本身是有限的：GPU 上大量算子到手时只有编译好的机器码（cubin），没有可改写的中间码，覆盖不到的地方必须直接拒绝执行而不是悄悄放过——在一次真实 vLLM 运行里，23,210 条覆盖决策中有 10,584 条属于这种只有机器码的算子。

**第二，时序既要准确又要跑得动。** 把参数表填进公式得到的解析模型，偏差随访问规模急剧放大，我们实测到 512 页时解析模型比实测快 99.93%，所以时序必须来自真实硬件的实测标定。而详细模型慢到无法跑真实负载，我们的详细参考路径一次生成要 44.469 s，快速路径只要 2.014352 s，相差 20.8 倍，因此要有快慢两条路径并让它们互相校准。

**第三，温度与容量是 HBF 自带的trade off。**：把 NAND 放进加速器封装，才有同等造价下 HBM 的 8 到 16 倍容量，也让 NAND 一起承受 GPU 满载时的高温。先说温度这一半。NAND 介质本身就对温度敏感，这是闪存介质层面的一手事实，不是从规范条文推出来的：HeatWatch（HPCA 2018，见附录 B.10）用 Arrhenius 关系把温度换算成失效进行的速度。**HBF 堆的正是 3D NAND**，这个常数对我们要模拟的 HBF 没有公开值。HBF 又把这样的介质放进 GPU 封装，让它和 GPU 一起承受满载时的高温：我们实测同一块 GPU 热机后吞吐下降 8.10%、峰值 85°C，而 85°C 正是规范只保证数据保持 24 小时的那个温度点；规范也把降频阈值与数据保持期限写成主机能读、能设阈值、必须响应的接口。再说容量这一半：hbf存在的理由就是容量，所以能不能评估它的前提是模拟器本身能让超过显存的工作集在真实执行下跑起来，我们现在的证据是 110 GiB 逻辑范围配 2 GiB HBM 缓存下负载照常跑完。

## 两条挑战够不够格（待定，写在这里提醒自己）

这一节记的是我对前两条挑战的疑虑：C1 和 C2 究竟是值得写进论文的研究挑战，还是只是把这个模拟器做出来必须克服的工程难处。如果只是工程难处，把它们写进动机一节会被审稿人看穿——他会问这跟我们自己选的实现路线有关、跟这一类硬件有什么关系。第三条挑战（温度与容量）不在这个疑虑之列，那一条的分量我没有疑问，理由写在本节末尾的对照里。下面每一条先写我担心什么，再写手上有什么依据，最后写一个可能的改法和它剩下的风险；改法都是建议，还没有定案。

### C1：HBF 有多慢、能装多少这些效果必须在真实执行中施加，而真实执行覆盖不全

**我担心的是前一半。** "不做事后回放、要在真实执行中施加"，严格讲是我们自己选的立场，不是外部强加给我们的困难。事后回放指先把访问序列记录下来、再按记录的顺序重放一遍；我们不用它的理由（真实程序一次读慢了，它接下来发什么请求会跟着变，这个反馈在回放里不存在）本身成立，但它论证的是我们为什么选这条路。我担心审稿人会把这半条读成一个设计取向，而不是一条挑战。

**后一半我认为站得住：覆盖注定不全。** 硬证据是一次真实 vLLM 运行的 23,210 条覆盖决策里，10,584 条落在只有已编译机器码、没有可改写中间码的算子上。已编译机器码指 cubin，即 GPU 驱动最终执行的二进制；可改写的中间码指 PTX，即编译器先生成、驱动再把它编译成 cubin 的那一层文本表示，我们这条路线的改写只能落在 PTX 上。生产环境的推理栈直接发下来的常常就是 cubin，PTX 那一层文本不在手上，我们就插不进去。

**这里有一句必须写准：cubin 到我们手上时没有可改写的中间文本，改不了它的是我们这条路线，不是 cubin 本身不可改写。** 能改已编译二进制的办法是 SASS 层的二进制插桩，NVBit（`NVBit: A Dynamic Binary Instrumentation Framework for NVIDIA GPUs`，MICRO-52，2019，DOI `10.1145/3352460.3358307`）就工作在 SASS 这一层，改的正是只有已编译二进制的程序：它的仓库说明原话是 `Because NVBit does not require application source code, any pre-compiled GPU application should work regardless of which compiler (or version) has been used`；论文第 6.1 节还量出机器学习负载里预编译库占执行指令 74% 到 96%、平均 88%，紧接着写 `NVBit instead does not require source code and it works on any application binary that makes use of these libraries, applying instrumentation at run-time only on the kernels that are actually invoked.`。我们不走这条路是自愿划的边界：合作者的设计文档 `/root/hbfsim/HBFSim/docs/superpowers/specs/2026-08-09-hbfsim-hybrid-design.md` 第 32 行在 Non-Goals 里写着 `Rewriting SASS in cubin-only kernels.`。所以覆盖不全这件事，正文里要写成我们选定的改写层次带来的边界，不能写成 cubin 到手就不可改写。

**一个重要的对照：这个困难在两篇参考论文那里根本不存在。** Cylon（FAST '26，`docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.pdf`）工作在虚拟机这一层，被测系统发出的每一次访问都要经过它；CXLMemSim（`docs/ref_article/yang2023-cxlmemsim.pdf`）工作在 CPU 性能计数器这一层，同样收得全。两者的覆盖天然完整，所以它们的挑战清单里没有一条是"有些代码插不进桩"。只有在 GPU 上按 PTX 改写这条路上才会遇到覆盖不全。

**另一个对照来自 eGPU**（HCDS '25，DOI `10.1145/3723851.3726984`，`docs/ref_article/yang2025-egpu-ebpf-ptx-injection.pdf`，作者与本仓库的提交者是同一人）。它自称是第一个通过动态 PTX 注入把 eBPF 字节码卸载到 GPU 上的框架，原文是「we introduce eGPU, the first framework and eBPF runtime that dynamically offloads eBPF bytecode onto GPUs via dynamic PTX injection」；而它在 7.2 节自己写明的局限是「While our micro-benchmark clearly demonstrates eGPU's low instrumentation overhead, we acknowledge that our current evaluation scope is limited. Specifically, we have not yet conducted extensive end-to-end performance evaluations on complex, real-world workloads such as large-scale machine learning models or HPC simulations.」——也就是说，这条路线新到连它自己都还没在大规模机器学习模型这类真实负载上做过端到端评估，而那正是我们现在在做的一步。

**可能的改法（建议，不是定案）：** 把 C1 的重心从"不做事后回放"挪到"覆盖注定不全时，报出来的数字还能不能信"。我们的答案是覆盖不到就拒绝执行——运行直接失败退出，不放行、不把没有建模的访问悄悄混进结果。这个问题别人不需要面对，所以也没有人给过答案。

**仍然存在的风险：** 即便这样改，审稿人也可能认为"覆盖不到就拒绝执行"只是一个工程上偏保守的做法，算不上方法论上的贡献。要防住这一点，评估里得有一组数字说明它值多少——例如放行那些覆盖不到的访问会让报出来的时间偏差多少。这组数字我们现在没有。

### C2：时序既要准确又要跑得动

**我的疑虑在这一条上更重。** "又要准又要快"是每一篇模拟器论文都有的取舍：Cylon 把它写成保真、速度、可扩展三项要求，CXLMemSim 报自己比 Gem5 快约 15 倍、相对原生慢 3 到 6 倍。照现在的写法，审稿人不会把它当成新东西。

**但同一条挑战里还压着一个不是取舍、而是实测出来的结论：把参数表填进公式得到的解析模型，在这一类硬件上偏差随访问规模放大。** 六个页数上实测 P50 与 nominal 标量模型的对照是 1 页 11,133 对 10,008 ns（−10.11%）、4 页 41,495 对 10,032 ns（−75.82%）、16 页 168,606 对 10,128 ns（−93.99%）、64 页 2,824,351 对 10,512 ns（−99.63%）、256 页 10,767,793 对 12,048 ns（−99.89%）、512 页 20,254,374 对 14,096 ns（−99.93%）；退一步换成常数页模型，512 页仍差 −71.86%。负号表示模型比实测快。要紧的是偏差随规模单调放大：误差不是一个可以用常数校正掉的固定偏置，而是模型形式本身不对。

**可能的改法（建议，不是定案）：** 把 C2 改写成这个发现本身——这一类硬件的时序无法从参数表加公式推出来，只能测出来。这是一个别人可以复现、也可以证伪的结论，比"我们在准确和快之间做了权衡"有分量。快慢两条路径则降格为设计一章里为了让实测标定用得起而做的工程手段，不占挑战的位置。

**仍然存在的风险：** 这个结论目前只在一台机器、一条软件路径上成立，标定源是 `/home/victoryang00/nvme-mem2nvm` 的 vmem 冷路径。要把它写成关于"这一类硬件"的结论，需要第二组来自不同硬件的数据支撑；这正是待补实验里那条用堆叠 CXL 固态盘搭物理参照平台的用意。

动机一节和设计一节都要跟着改。`systems-paper` skill 的 `references/motivation-design-traceability.md` 要求一条挑战对应且只对应一条设计回应，所以 C1、C2 一改，设计一章 D1、D2 两段的开头句（失效模式、机制名、被改变的对象、被改变的不变量）必须重写成与改写后的挑战对得上。具体的改动清单在 `/root/hbfsim/37-MoE实验可行性与前两条挑战的分量.md` 第 4 节。

## 要和导师、合作者一起讨论的两件事

这一节不是论文正文的一部分，是给三个人一起看的讨论区。两件事都需要在写完正文之前定下来。

### 讨论一：注入器留在 PTX 层，还是换到 SASS 层

**这件事为什么要讨论。** 我们现在把延迟写进 PTX（编译器先生成的中间文本，还能改）。另一条路是写进 SASS（驱动最终执行的机器指令），现成工具是 NVBit（MICRO-52，2019，DOI `10.1145/3352460.3358307`）。合作者的设计文档 `docs/superpowers/specs/2026-08-09-hbfsim-hybrid-design.md` 第 32 行把 `Rewriting SASS in cubin-only kernels.` 列为不做的事，没有写理由；eGPU 那篇给的理由是开销与工具链衔接，而它全文 `cubin` 与 `fatbin` 各出现 0 次，也就是当初的取舍里没有把覆盖代价算进去。

**两层各自的事实，逐条核实过。** SASS 层在信息可得性上严格占优：四个必需量里，第 2 项（发射与消费之间的距离）只有 SASS 层能看到；成批张量搬运的地址 SASS 层也拿得到——NVBit v1.8 发行包 `core/nvbit.h` 第 82 与 83 行有 `isTMAMem()` 与 `isTMATensor()`，第 402 行有 `nvbit_parse_tma_transfer_info`，第 477 与 497 行有 `nvbit_parse_tma_src_addrs` 及其带标志位的版本，`tools/` 下带一个可编译的 `mem_trace_tma` 示例。覆盖上 SASS 层也占优：NVBit 论文第 6.1 节量出机器学习负载里预编译库占执行指令 74% 到 96%、平均 88%，而我们一次真实 vLLM 运行的 23,210 次判定里有 10,584 次落在只有已编译二进制的模块上、成功计时 0 次。

**但换过去要付的代价，也逐条核实过。** 当前实现里比「注入点在哪一层」更大的两处误差与层无关：跨线程束、跨时间没有驻留过滤（同一页再读一次仍按一次介质访问收费），以及全部流量串在一个标量 `fast_channel_tail_ns` 上而参数档声明 16 至 64 个通道各 8 个 die。发射处阻塞这一项在 PTX 层本身就能修（把等待移到目的寄存器第一个使用者之前），只有「发射到消费这个窗口内部的位置偏差」这一项非 SASS 不可。NVBit 自己也有代价：论文第 7 节写 `before jumping to an instrumentation function, specific registers are saved in memory for every thread. Although fully parallelized, it takes many cycles and can destroy cache locality.`；删除原指令时 `NVBit does not guarantee that the application will continue to work correctly`；v1.8 发行包 `README.md` 第 44 行写 `CUDA driver version: <= 575.xx`，而验证平台驱动是 595.84，这一条没有实测过。

**主 agent 的建议（是建议，不是定案）：注入器留在 PTX 不换，SASS 只当量具。** 三条理由：一，换层只买到四项误差里最小的一项，还要付新的误差和一道没测过的驱动闸门；二，自研插桩在 FAST 不是贡献体裁（NVBit 发在 MICRO、SASSI 发在 ISCA '15），把版面花在改写契约上，等于请审稿人用插桩论文的尺子量一次，而那把尺子下 NVBit 是在位者；三，覆盖缺口这个数用 NVBit 的只读接口就能量出来，不需要把注入器换过去。相关工作一节现在的写法（NVBit 提供的是二进制插桩能力，在插桩这件事上比我们完备，差别落在它本身不含任何存储介质的时序模型）要顶住任何改成能力强弱对比的压力——论文一旦开始论证 NVBit 能力更弱，就把自己最输不起的那场比较请了进来。完整分析见 `/root/hbfsim/49-PTX还是SASS与NVBit对照实验.md`。

**要三个人一起定的是：** 采不采纳「留在 PTX、SASS 只当量具」；如果采纳，要不要花半天做一次 NVBit 冒烟测试，把驱动 595.84 能不能跑写成一句有实测支撑的脚注。

参考其他sim论文是 *Cylon: Fast and Accurate Full-System Emulation of CXL-SSDs*。

- **候选一**：*HBFSim: Fast and Measured-Calibrated Full-System Simulation of High-Bandwidth Flash for LLM Inference*。中文对照：HBFSim——面向大模型推理的高带宽闪存快速、实测标定全系统模拟。取舍：既讲了速度，也讲清了准确性从哪来；代价是 measured-calibrated 是自造的复合词，读者第一眼要停一下，摘要第一句必须立刻解释。
- **候选二**：*HBFSim: Fast and Accurate Full-System Simulation of High-Bandwidth Flash for LLM Inference*。中文对照：面向大模型推理的高带宽闪存快速、准确全系统模拟。取舍：与 Cylon 的形式最接近，也最好读；但 accurate 是审稿人最会追问的词，用它就必须在评估章拿出未参与拟合的验证点与误差百分比（见"投稿前必须补做的实验"第一条），这组数据现在得拿cxl ssd模拟hbf行为, 可能会被审稿人攻击。
- **候选三**：*HBFSim: Fast and Faithful Full-System Simulation of In-Package Flash for LLM Inference*。中文对照：面向大模型推理的封装内闪存快速、忠实全系统模拟。取舍：in-package flash（与加速器装在同一个封装里的闪存）一眼说清 HBF 在哪里；faithful的举证门槛比 accurate 低，正好对应我们已有的逐字节一致证据。代价是标题里不出现 HBF 这个正在成形的名字，检索时可能被漏掉，若用这条，摘要第一句必须马上写出 High-Bandwidth Flash (HBF)。

**一个共同的措辞风险（这是我的判断）**：Cylon 的 full-system 指在虚拟机里跑完整的操作系统与应用，我们是真实系统照常运行、只对 HBF 这一层施加模型。沿用 full-system 这个词就要在正文里给出它在我们这里的确切含义，否则审稿人会按 Cylon 的用法理解。

### 引言（`paper/intro.tex`，1.2 页，7 段）

这一节讲七件事，一段一件：大模型推理受限于 HBM 容量、HBF 是什么以及为什么现在重要、这一层适合放哪三类数据、设计决策现在就要做而已有评估手段都不够、要建这样一个平台技术上难在哪里、HBFSim 把哪三件事合成一个闭环、贡献列表加结果预览。

推进顺序照 Cylon（FAST '26 的 CXL-SSD 全系统模拟器，见附录 B.2）：先讲应用侧的容量困境，再讲这项新硬件是什么、擅长什么，然后说明设计决策现在就要做而工具不存在，接着用一整段正面回答"要建这样一个平台，技术上难在哪里"，最后才讲我们的做法与贡献。

- P1：大模型推理受限于 HBM 容量。权重规模与 KV cache 随上下文长度和并发数增长，都要放进 HBM，而 HBM 单堆容量跟不上；这一段需要一个具体规模的数字（**待补**：选定一个公开模型与上下文长度，算出 KV cache 大小，进正文前须核出处）。
- P2：HBF 是什么、为什么现在重要。它是第一份把可堆叠 NAND 定义为 xPU 同封装内存层的开放标准，2026-08-03 由 SanDisk 与 SK hynix 通过 Open Compute Project 发布 v0.7.0，Google 与 Tenstorrent 已加入；同封装用 UCIe 直连（UCIe 是芯片与小芯片之间的互连标准，规范讲解文的原话是通道"从一个芯片上的凸点到远端芯片的连接凸点测量，小于 2 毫米"，凸点指芯片表面用来和封装基板相连的焊球），协议是 AXI over UCIe，整个 PCIe、NVMe 与主机驱动栈都不存在；**同等造价下容量是 HBM 的 8 到 16 倍**，带宽与 HBM 同数量级（规范顶档 3.0 TB/s）。引 OCP 规范（待核原文）与 SanDisk 2026-08-03 新闻稿（原句 "As one of the first technical standards of its kind in the memory and storage industry"，出处 `https://www.sandisk.com/company/newsroom/press-releases/2026/2026-08-03-Sandisk-and-sk-hynix-advance-global-standardization-of-hbf`）。措辞边界见"已知弱点与诚实边界"一节。
- P3：HBF 擅长什么。三类数据适合放这一层：只写一次、读很多次的模型权重；同样只写一次读很多次的、多请求共享的 KV cache；前提是访问可预测——推理逐层顺序执行，算上一层时就知道下一层要读什么，可以提前搬进缓冲区，约 10 µs 的读延迟因此被覆盖。MoE 是这一层上的开放问题：专家权重只读、体量也大，满足前一个条件，但激活哪个专家由路由在运行时决定，预取窗口不存在。不擅长的是反复改写的数据（生成态 KV cache、激活值、训练梯度与优化器状态），一句带过即可，理由是 NAND 擦写次数有物理上限。**落点是一句话：HBF 不是 HBM 的替代品，是 HBM 之下新增的一层。** 全段依据是行业分析文章（见附录 B.7），正文里必须标明是行业观点、不是规范依据；"MoE 正好是模拟器能回答的一类问题"这句是我们的判断，要与引用分开写。
- P4：设计空间宽而未定，而已有的评估手段都不够。首批推理设备预计 2027 年初送样，系统设计者现在就要回答：HBM 缓存该开多大、哪种访问模式最吃 HBF 的延迟、权重与 KV cache 怎么在两层之间分配、持续负载下的发热与寿命代价是多少。已有手段按类别否掉，不拿某一篇当靶子：真实硬件拿不到；事后回放访问序列的存储模拟器不执行真实负载，"延迟改变访问流"这件事在回放里不存在；GPU 内存模拟器不执行真实 kernel，跑的是模型化的指令流；逐周期精确的全系统模拟器慢到无法跑真实的大模型推理；已经在 HBF 上做系统设计的工作只能用解析的事件驱动模型评估，并且把 HBF 当恒温处理（一句带过，举 FlashAccel arXiv:2607.10186 为例）。引 MQSim、SimpleSSD、FEMU、GPGPU-Sim、Accel-Sim、MGPUSim（每篇进正文前都要核原文）。
- P5：**要建这样一个平台，技术上有哪些困难**，整段回答，三条困难按动机一节的编号排，顺序是 C1、C2、C3，温度不再单独排在最前。第一条是 HBF 挂在加速器封装里面，主机侧没有一个位于被测程序之外、每次访问都必须经过的位置可以施加效应，效应只能写进被测程序自己的指令流，而指令流里没有「这次访问该付多少」这个量：此前被这样模拟过的新内存（持久内存、CXL 内存）都挂在 CPU 的访存路径上，那条路径出厂就带着页表、虚拟机的扩展页表、性能计数器、绑到远端 NUMA 节点这几处可以接管的地方，而加速器对 HBF 的读写不经过任何主机能看到的层次。真实负载还要照常执行，先把访问序列记录下来事后回放收不到"这次读慢了"对后续请求的影响。我们的改写落在 PTX 这一层（PTX 是 NVIDIA 的中间指令表示，编译器先生成 PTX，再由驱动编译成具体架构的机器码 cubin），而生产环境的推理栈直接发下来的常常只有 cubin、没有 PTX 这层文本，我们这条路线就改不到它；能直接改已编译二进制的是 SASS 层的插桩（NVBit 就工作在这一层），改 cubin 里的 SASS 是本项目在设计文档 `docs/superpowers/specs/2026-08-09-hbfsim-hybrid-design.md` 第 32 行的 Non-Goals 里自愿排除的一项（原文 `Rewriting SASS in cubin-only kernels.`），所以覆盖不全要写成我们选定的改写层次带来的边界，不是 GPU 不让改。证据是一次真实 vLLM 运行的 23,210 次覆盖判定里有 10,584 次落在只有已编译二进制的算子上。容量也并进这一条：容量模式给出的地址底下根本没有实体显存，改不到的 kernel 真跑过去会出错，所以那一档必须拒绝执行，而容量正是 HBF 存在的全部理由。第二条是一次访问要等多久是设备状态的函数，不是这次访问自己的属性：把代价当成页数乘单页延迟算，512 页时解析模型比实测快 99.93%，偏差随规模单调放大，说明模型形式本身不对；而在真实执行中注入延迟时，能观测到的只有一个相加的结果，被建模的介质延迟与注入本身的开销混在一起，四类时间必须分开记账，否则报出来的减速倍数说明不了任何事。第三条是规范给 HBF 定了芯片内部温度上限，越过上限之后 HBF 靠降速、限流直至阻断新命令阻止温度继续升高，长期运行下真正能跑到的速率因此低于厂商标称的峰值；温度会在运行中改变 HBF 的服务速率，而 NAND 对温度敏感是介质层面的一手事实（HeatWatch，见附录 B.10），因此温度不能当成事后分析的一个变量。段末点明这三条分别由设计一章的 D1、D2、D3 回应。
- P6：我们提出 HBFSim。三件事合成一个闭环：真实负载在真实 GPU 上照常执行，PTX 改写把注册范围内的访存导进模拟器；时序来自真实硬件的实测标定曲线与在线提交请求的 MQSim 介质模型；温度接进可靠性——负载产生功耗，一阶热响应模型把功耗换算成芯片内部温度（junction temperature，芯片内部实际发热点的温度，通常比封装外壳温度高）的轨迹，芯片内部温度同时决定当前处在哪一档热管理状态（从而改变服务速率）和数据保持期限（从而决定哪些块到期必须重写、产生强制刷新的写流量），这两件事又反过来改变负载看到的时序。这里说"闭环"是字面意思：温度既是这一段执行的结果，又是下一段执行的输入，不能先算完一边再算另一边。
- P7：贡献列表加结果预览。四到五条贡献，一条一个加粗小标题各占一小段，温度与可靠性这条放第一：(a) 把规范定义的热管理状态、数据保持与刷新做进模拟器，并让它在真实执行中生效；(b) 从真实硬件实测标定出来的时序曲线，以及它相对解析模型的偏差证据；(c) 在真实运行的推理框架上做到输出逐字节一致的注入机制；(d) 详细路径与快速路径两档时序模型及其一致性；(e) 超出显存容量的工作集也能跑通的容量模式。末尾一句结果预览：六个标定断点全部对齐、每例 1 次建模启动、0 次不安全启动；快速路径相对详细参考路径快 20.8x；110 GiB 逻辑范围加 2 GiB HBM 缓存、checksum `14245581564465502923` 与基线相同。

### 背景（`paper/bg.tex`，1 页，7 段）

这一节交代七件事：HBF 的接口与组织、HBF 与 HBM 与 NVMe 固态盘的三方对照、GPU 与静态调度加速器掩盖访问延迟的机制不同、规范把可靠性与温度写进了接口、NAND 介质对温度敏感的一手依据、GPU 侧插桩的基础、我们复用了哪些现成部件。

这一节把读后面几章需要的 HBF 知识与工具知识一次交代完，只讲事实、不做论证；论证留给动机一节。

- P1：HBF 的接口与组织。单堆 8 层或 16 层 NAND 堆叠、单堆最高 512 GB；16 个独立的 UCIe 通道，每通道有独立的 NAND 芯片组与独立时钟，UCIe x64 在 32 GT/s 时每通道 256 GB/s；协议层是 AXI over UCIe，256 字节的延迟优化 Flit（格式 6）；读按 64 字节粒度寻址，读一个 4 KiB 页要发 64 个不同 AXI ID 的读命令，同一个 ID 的完成保序、不同 ID 之间可以乱序；每个 Bank 配 2 个至少两页（8 KiB）的缓存缓冲；写按 4 KiB 粒度，基片先攒满 4 KiB 再下核心芯片，块内本地地址必须连续写，限时收不齐就报错，每通道未完成写请求上限 64 或 128（视产品）；另有可选的每通道 Scratchpad SRAM。引规范（待核 OCP 原文）。
- P2：HBF、HBM 与 NVMe 固态盘的三方对照表。列出介质、单堆容量、带宽、延迟、访问语义、持久性六项。这张表要能让读者读出三层关系：相对 NVMe 固态盘这条传统存储路径，带宽约两个数量级、延迟约一个数量级的优势（规范三档约 0.4 到 3.0 TB/s 对我们实测的 Dell CD8P 顺序读 7.577 到 7.587 GB/s，比值约 50 到 400 倍；HBF 物理读约 10 µs 对固态盘 4 KiB 随机读端到端几十到上百 µs）；相对 HBM，容量 8 到 16 倍、带宽同数量级（HBF 顶档 3.0 TB/s 对 HBM4 约 2.0 TB/s 的 JEDEC 基线到 3.3 TB/s 的二手对照表数字、HBM3E 1.2 到 1.33 TB/s），但延迟劣约两个数量级（约 10 µs 对约 100 ns）；三层差别的共同来源是同封装的 UCIe 连接。**表里凡是推算出来的比值都要在表注里标明是推算**，出处缺口见"已知弱点与诚实边界"一节。参数对照引知乎那份捕获时须在正文标明是行业分析观点、不是规范依据；还要注意该文自己的口径与我们别处用的数字有出入：它算的容量差是八倍（一堆 HBF 512GB 对一颗 HBM4 最多 64GB），另一处引用行业说法才是 8 到 16 倍；它给 HBM4 单堆栈带宽 2.0 到 3.0 TB/s、HBF Gen1 目标值 1.6 TB/s、规范三档从 0.4 起步；延迟它写成 HBM4 几十纳秒对 HBF 约 10 微秒、相差一百倍。正文里挑哪一套口径要挑定并标明出处，不能两套混用。该文推算的那笔预取账不放这一段，移到下一段与延迟隐藏机制一起讲。
- P3（本轮新增）：两类加速器掩盖访问延迟的机制不同，这件事对 HBF 有影响。GPU 的办法是大规模多线程：硬件上同时驻留几千个 warp（warp 指 GPU 上一组同步执行的线程，NVIDIA 的 GPU 上通常是 32 个线程一组），某个 warp 因为等数据停下来时，硬件调度器立刻切到另一个数据已经就绪的 warp，等待的时间就被别的 warp 的计算填满。行业分析文（知乎捕获，二手观点，见附录 B.7）推测这套机制对 HBF 不好用，理由是它的规模是按 HBM 那几百纳秒的延迟预算设计的——寄存器堆的容量、一个 warp slot 的数量都按这个预算定；要用同样的办法掩盖 10 µs 量级的延迟，同时在飞的工作量（已经发出、还在等数据的请求数量）得提高两个数量级，芯片面积上放不下。该文说 TPU 这类静态调度架构走的是另一条路：静态调度指数据什么时候搬、搬到哪里在编译期就排好，不靠运行时的硬件调度器临时决定；TPU 上没有传统意义的缓存，整张计算图在编译期已知，由 XLA（Google 为 TPU 一类加速器做的编译器）显式安排，实际搬运交给 DMA（直接内存访问，指由专门的搬运引擎在后台把数据从一处搬到另一处，不占用计算单元）完成，于是延迟主要变成排程问题，而不是让计算单元停下来等的问题。该文给的一笔粗账（是该文的推算，数字我们没有核过）：405B 模型 8-bit 权重约 405GB、126 层、每层约 3.2GB，8 个 HBF 堆栈按 12.8 TB/s 算，流完一层权重要 250 µs 左右，而 NAND 一次读的延迟是 10 µs 量级、占其中 4%，只要在算第 N 层的时候预取第 N+1 层，这个延迟就被覆盖掉；该文强调 Transformer 推理的权重读取序列是完全确定的，预取窗口很大。同一篇还给了一条旁证（同样是该文的观察与判断）：8 月 6 日 "Breaking the Memory Wall with HBF" 圆桌上，Google 派出的是 DeepMind 的资深工程师 Xiaoyu Ma，来自模型部门而不是硬件部门，该文认为这个信号说明是模型侧在定义内存该长什么样。**措辞纪律**：该文自己用的词是"脑洞""我猜""感觉"，正文里一律写成"该文推测"，不能写成"研究表明"或"已有工作证明"。**我们自己的边界也要在这一段写清**：我们手上的实测平台是 NVIDIA GPU，没有 TPU，所以这条只作为背景与动机里的一个观察，不声称我们验证过 TPU 上的行为。篇幅上这一段要短，背景一节的预算仍是 1 页；写不下时先压缩术语解释，把 warp、XLA、DMA 三个定义并进一句（这是我的判断）。
- P4：规范把可靠性与温度写进了接口，主机能读、能设阈值、必须响应。工作时的芯片内部温度窗口 0 到 105°C；85°C 通电条件下数据只保证保持 24 小时；四个热管理状态——正常、由 LTT 阈值触发的轻度降频（动态降低时钟）、由 STT 阈值触发的重度降频（拉高 CATTRIP 引脚、取消 AXI Ready、停止发放 Credit，队列里已有的命令按正常流程做完，新命令返回 Status 0x9）、关机；RTT 是温度回落后解除降频的阈值，与升温阈值不同，这种升温降温走不同阈值的设计叫迟滞（hysteresis），作用是避免 HBF 在阈值附近反复切换，阈值寄存器在 MMIO 0x150。此外 Base Die 按块暴露读计数器，读干扰累积到一定程度报 CECC Status 0x5 提示主机刷新，不可纠正时是 UECC Status 0x4；磨损一侧有 MAXPEC/AVGPEC 寄存器、Zone Remapping（命令 0x08，可把热区与冷区的物理指向交换）与 REDCAP 降容（命令 0x0A，MMIO 0x14C 的 1024 位故障位图），并写明 HBF 不支持片上垃圾回收、磨损管理责任在主机。"主机侧以 24 到 48 小时为周期做数据巡检与刷新"这一条目前只见于来源不明的观点文（附录 B.6），只能当问题清单用，不能当规范条文引。
- P5（本节的温度落点）：NAND 介质对温度敏感，这一条给一手依据，不用规范条文来推。引 HeatWatch（HPCA 2018，第 504 至 517 页，DOI `10.1109/HPCA.2018.00050`，见附录 B.10），四件事写进正文：一是温度到失效速度的换算就是该文的 Equation 1，`AF(T1, T2) = t1 / t2 = exp[ (Ea / kB) * (1/T1 - 1/T2) ]`，其中 AF 是两个温度之间的加速因子（同一件事在两个温度下进行快慢的比值），kB 是玻尔兹曼常数 8.62 × 10^-5 eV/K，Ea 是激活能、该文明说它是随制造工艺而定的常数；二是激活能的公开值只有平面 NAND 的 Ea = 1.1 eV，该文紧接着写 "To our knowledge, there is no public literature that reports the value of Ea for 3D NAND flash memory."，而 HBF 堆的是 3D NAND；三是高温加速的量级，该文脚注写同一组实验在室温 20°C 下要花 11 年以上才做得完；四是方向不单一，"higher temperature increases retention errors but reduces program variation errors"。同段顺带交代该文提出的两个量，后面设计一章要用：等效保持时间（把高温下的一段保持时间折算成室温下产生同样保持损失的更长时间）与等效空闲时间（dwell time 指两次编程或擦除之间的空闲时间，这段时间里部分损伤会自行修复，这个现象该文称为 self-recovery，自恢复；等效空闲时间就是把高温下的一小段空闲折算成室温下产生同样恢复效果的更长空闲）。
- P6：GPU 侧的插桩基础。PTX 与 cubin 的区别（见引言 P5 的定义），在 PTX 上改写意味着不改内核源码也不改应用源码；但生产环境的推理栈会直接提供已编译好的 cubin，那些算子没有可改写的中间码，所以在我们选定的这一层上覆盖注定不全。这句话要写成有条件的：能改已编译二进制的工具是存在的（SASS 层的二进制插桩，NVBit 就是），不走那条路是我们自愿划的边界，依据是设计文档 `docs/superpowers/specs/2026-08-09-hbfsim-hybrid-design.md` 第 32 行把 `Rewriting SASS in cubin-only kernels.` 列为不做的事。正文里不许写成「覆盖不可能做到全量」这种绝对说法。
- P7：我们复用的部件。MQSim 是已有的固态盘介质模型，通常被当作 trace 回放工具使用，本工作只取它的闪存介质模型部分、在线提交请求并按需推进事件，绕开 NVMe/PCIe/SATA 与主机驱动那些事件——这个区别必须在正文写明，否则读者会把本工作归进事后回放那一类。bpftime 提供 CUDA 调用的拦截路径。

### 动机（`paper/motv.tex`，1 页，3 段）

这一节提出三条挑战：一是 HBF 挂在加速器封装里面，主机侧没有一个位于被测程序之外、每次访问都必须经过的位置可以施加效应，于是效应只能写进被测程序自己的指令流，而指令流里没有「这次访问该付多少」这个量；二是一次访问要等多久是设备状态的函数，不是这次访问自己的属性，而在真实执行中注入延迟时，能观测到的只有一个相加的结果；三是规范给 HBF 定了芯片内部温度上限，越过上限之后 HBF 靠降速、限流直至阻断新命令阻止温度继续升高，长期运行下真正能跑到的速率因此低于厂商标称的峰值。

三条挑战的证据形态不一样，正文要照实写，不要套同一个模板：第一条的前半是从 HBF 挂在哪里推出来的结构性论证，没有对应的测量数字，后半才有实测（一次真实 vLLM 运行的 23,210 次覆盖判定里，10,584 次落在只有已编译二进制的算子上）；第二条前半有六个页数上的实测与解析模型对照，后半是关于哪个量根本观测不到的论证；第三条讲的是整场运行的速率随时间下降，靠规范条文加我们自己的热响应实测（时间常数 GPU 13.1 秒、CD8P 12.4 秒），不拆成两个子问题。一段一条挑战，每段末尾说明这条挑战为什么绕不开，并写清适用范围。三条里都会点名别的系统、讲清它们为什么不遇到这件事，但不以任何一篇已有工作为叙述中心。设计一章的 D1 到 D3 与它们一一对应。

- **C1 HBF 挂在加速器封装里面，主机侧没有一个位于被测程序之外的位置可以施加效应；效应只能写进被测程序自己的指令流，而指令流里没有「这次访问该付多少」这个量。** 一句话概括要突出的是与其他存储硬件的本质区别：**此前被这样模拟过的新内存——持久内存、CXL 内存——都挂在 CPU 的访存路径上，而那条路径出厂就带着好几层可以被接管的东西；HBF 挂在加速器封装里面，加速器对 HBF 的读写不经过任何主机能看到的层次。** 这不是我们的工具不如别人，是这层硬件挂的位置决定的。

**「拦截位置」指什么。** 指一个位于被测程序之外、每一次内存访问都必须经过、并且允许我们在那里加上等待时间的地方。关键在"之外"：被测程序的二进制一个字节都不改，效果由机器上别的层次提供。HBF 没有这样一个位置，所以要让一次访问变慢，唯一的落点是被测程序自己的指令流——改 PTX（编译器先生成的中间文本）或改 SASS（驱动最终执行的机器指令）。

**CPU 那一侧有四处可以接管，全都在程序之外。** CPU 访问内存要经过地址翻译，这条路上有好几处可以接管：

- **页表。** 操作系统把一段页标成不存在，程序一访问就触发缺页，控制权落进操作系统的处理函数，想加多少延迟、记多少账都行。持久内存早期的模拟大量用这一招。
- **虚拟机的扩展页表。** Cylon 走这条路。它论文原文是 `Every guest access undergoes address translation through Intel's Extended Page Tables (EPT)`（`docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.txt` 第 498 至 500 行，本轮亲手核过）——覆盖由硬件保证，不靠软件努力。
- **性能计数器。** CXLMemSim 走这条。但要注意它并不逐次拦截，它自陈 `it's always a sampled model which may lose a lot of data`（`docs/ref_article/yang2023-cxlmemsim.txt` 第 341 至 343 行，本轮亲手核过），估的是聚合停顿时间。
- **内存控制器本身。** 把数据绑到远端 NUMA 节点，那一侧天然就慢，用远端插槽延迟近似 CXL 延迟。连插桩都不用。

四种办法的共同点：**被测程序原封不动**，因为机器本来就在程序和内存之间放了一层。

**GPU 那一侧没有对应的位置。** 显卡上一次全局读的路径是：流多处理器发出访存 → 访存单元 → 片上交叉开关 → 二级缓存 → 显存。这条路不经过主机操作系统，不产生主机能看到的缺页，也没有逐次访问的主机侧事件。显卡自己有页表，但由驱动管着，没有开放成"每次访问让我插一手"的接口。统一虚拟内存确实会产生缺页并触发页迁移，但它能做的是**把页搬过来**，表达不了"这一次访问该慢 10 微秒"——它是搬运机制，不是计时机制。

**挂在 CPU 上的新内存没遇到这个问题。** 持久内存、CXL 内存都挂在 CPU 的访存路径上，那条路径出厂就带着可接管的层次。这不是它们的研究者更聪明，是硬件位置决定的。

**挂在 GPU 上的东西遇到了，而且有一个标准答案，只是我们用不了。** GPGPU-Sim、Accel-Sim、MGPUSim 的做法是根本不在真实硬件上跑：整块 GPU 都模拟出来，每条指令按构造都在它们手里，覆盖问题不存在。代价是跑的不是真实负载在真实硬件上的执行，速度也支撑不了完整的大模型推理（这个代价为什么我们付不起，写在本节末尾「为什么用真实 GPU」那一段）。

拿到完整覆盖一共只有三种办法，正文里用这张表把三条路一次摆清：

| 拿到完整覆盖的办法 | 谁在用 | 我们的处境 |
|---|---|---|
| 机器在被测程序之外提供的拦截层 | 页表缺页（早期持久内存模拟）、虚拟机的扩展页表（Cylon）、性能计数器（CXLMemSim）、绑到远端 NUMA 节点 | 用不了：加速器对 HBF 的读写不经过主机操作系统，GPU 上没有这样一层 |
| 把整块 GPU 模拟出来 | GPGPU-Sim、Accel-Sim、MGPUSim | 用不了：跑的不是真实负载在真实硬件上的执行，速度也支撑不了完整的大模型推理 |
| 把效果写进被测程序自己的指令流 | NVBit（SASS 层）、eGPU 与本工作（PTX 层） | 剩下的唯一位置，我们走的就是这条；代价就是这条挑战的后半 |

**这一条挑战的后半：能改写的点与「这次访问该付多少」不在同一个地方。** 一旦效应只能写进被测程序自己的指令流，没有任何一层同时拿到全部四个必需量：

| 必需量 | PTX 层 | SASS 层 |
|---|---|---|
| 1. 这次访问的字节地址 | 普通访存有；成批张量搬运（TMA）没有 | 普通访存有；成批张量搬运也有 |
| 2. 发射与消费之间的距离（硬件真正停在哪） | 没有（ptxas 之后才定，等待屏障掩码由汇编器写进控制位） | 有（控制位可见） |
| 3. 这次访问真正到达介质的时刻 | 没有 | 没有 |
| 4. 一条访存指令展开成多少个真正到达介质的请求 | 没有 | 没有 |

第 1 项那格要按核实过的事实写，不能写成两层都拿不到：NVBit 1.8 的发行包里有整套成批张量搬运的地址解析接口——`core/nvbit.h` 第 82 与 83 行的 `isTMAMem()` 与 `isTMATensor()`，第 402 行的 `nvbit_parse_tma_transfer_info`，第 430 与 449 行的 `nvbit_parse_tma_dst_addrs` 及其带标志位的版本，第 477 与 497 行的 `nvbit_parse_tma_src_addrs` 及其带标志位的版本，第 614 行的 `nvbit_add_call_arg_tma_param_handle_and_size`；`core/instr_types.h` 第 58 行的内存空间枚举里有 `GLOBAL_TO_SHARED`；`tools/` 目录下直接带一个可编译的 `mem_trace_tma` 示例。这些是主 agent 亲手下载 v1.8 发行包解开后逐行读到的。

**换到 SASS 补上第 1 项里成批张量搬运那半格和第 2 项，第 3、4 项照旧缺失。** 所以这不是「我们选错了层」，而是「指令流不是这些量被定义的地方」——**这一条对 NVBit 与对我们同等成立**，因为 NVBit 也是把效应写进被测程序自己的指令流，它换掉的是写进哪一层，不是「要不要写进去」。把我们与 Cylon、CXLMemSim 分开的是这条路上没有机器提供的拦截层，不是层选得对不对。

**不解决会看到的错误结果。** 一次真实 vLLM 运行 23,210 次覆盖判定里，12,626 次没碰已登记内存、10,584 次碰到了但模块只有已编译二进制因而被放行且标注没计时、成功计时 0 次（出处 `docs/proofs/2026-08-11-vllm-timing-adapter.md`）。如果这 10,584 次按显存原速悄悄放过而报告里不留痕迹，端到端量到的减速会接近 1.0 倍，读者会读成「这层硬件几乎不要钱」。补一句为什么覆盖补不满：把全部 61,064,245,248 字节登记进去并不能补上覆盖，那会让 vLLM 的 profiling 阶段产生数量上不可行的同步请求。

**这一条的适用范围，正文必须照这个限定写。** 以上是从访存路径的结构推出来的，**不是说 GPU 原理上永远不可拦截**。NVIDIA 若开放某种驱动接口，或统一虚拟内存将来允许在缺页处理里注入延迟，这条路就变了。能确定的是：以今天公开可用的机制而言，没有一个既能逐次拦到、又能施加可控延迟、还不必改动被测程序的位置。论文里应照这个限定写，不要写成永久成立的断言。
- **C2 一次访问要等多久是设备状态的函数，不是这次访问自己的属性；而在真实执行中注入延迟时，能观测到的只有一个相加的结果。**

**前半的证据。** 把每次访问的代价当成页数乘单页延迟算出来，1 页实测 11,133 对模型 10,008 纳秒（模型快 10.11%）、4 页 41,495 对 10,032（快 75.82%）、16 页 168,606 对 10,128（快 93.99%）、64 页 2,824,351 对 10,512（快 99.63%）、256 页 10,767,793 对 12,048（快 99.89%）、512 页 20,254,374 对 14,096（快 99.93%）；换成常数页模型，512 页仍差 71.86%（出处 `docs/proofs/2026-08-11-cd8p-vmem-tuning.md`）。**偏差随规模单调放大**，说明误差不是可以用常数校正掉的固定偏置，而是「把代价当成单次访问的函数」这个模型形式本身不对。代码里正是照这个结论写的：曲线上存的是累计时间（六个断点），单次访问的时间由相邻两点相减得到，不是页数乘单页时间。

**后半。** 真实等待时间里同时装着被建模的介质延迟和注入本身的开销。要把两者分开，需要知道「如果不注入，这次访问实际什么时候完成」——正是第一条挑战那张表里第 3 项、任何层都观测不到的量。

**别的工作为什么不遇到这一条，分三种情况写。**

- **持久内存与 CXL 那一侧不遇到前半。** 对那类介质，一次访问的代价近似是个常数，注入一个固定延迟就够用；而 NAND 不是——同一次连续传输里，越靠后的页越贵，代价还随队列状态与温度变。这是介质性质的差别，不是谁做得更细。
- **模拟整块 GPU 的那些工作（GPGPU-Sim、Accel-Sim、MGPUSim）不遇到后半。** 在它们那里，被建模的时间与真实流逝的时间从构造上就是两回事，不存在混在一起的问题；代价是跑的不是真实执行。
- **Cylon 与 CXLMemSim 各自绕开后半的办法不同，两处原文本轮亲手核过。** Cylon 的做法是把拦截本身的开销工程掉，论文原文是 `First, Dynamic EPT Remapping eliminates VM-exits on cache hits.`（`docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.txt` 第 484 至 485 行），也就是缓存命中这条路上不再有虚拟机退出这笔开销；CXLMemSim 根本不逐次注入，原文是 `CXLMemSim periodically interrupts the program with an epoch timer. Since it's always a sampled model which may lose a lot of data, PEBS does not record the prefetcher and writeback information.`（`docs/ref_article/yang2023-cxlmemsim.txt` 第 340 至 343 行），它估的是聚合停顿时间。

**不解决会看到的错误结果。** 在大传输上系统性地把这层硬件算得比实际快，于是缓存该开多大、要不要预取、权重与键值缓存怎么在两层之间分配，这些结论会一致地偏向「不需要这一层」；另一半是报出来的减速倍数说明不了任何事。

**旧 C2 里「详细模型跑不完负载」那一半**（同一个确定性用例上详细参考路径一次生成 44.469 s、快速路径 2.014352 s、相差 20.8 倍，出处 `docs/proofs/2026-08-11-hybrid-complete.md`）**降到设计一章**，作为为了让实测标定用得起而做的工程手段，不再占挑战的位置。
- **C3 规范给 HBF 定了芯片内部温度上限，越过上限之后 HBF 靠降速、限流直至阻断新命令阻止温度继续升高；长期运行下真正能跑到的速率因此低于厂商标称的峰值。**（本条按 2026-08-12 的更正整段重写，与 `/root/hbfsim/43-三条挑战的重新划分.md` 第 152 行起那一节同步。芯片内部温度改变数据保持时间、进而改变这块闪存还能被擦写多少次，那一半按同日早些时候的裁定移进 discussion 与 future work，正文里只作为一个已知的开放问题陈述，不作为本文贡献。）

**不解决会看到的错误结果：把厂商标称的峰值带宽当成长期可持续的速率。** 规范给 HBF 的三档标称带宽是 0.4 至 3.0 TB/s，这是短时值。负载自己把芯片内部温度（junction temperature，芯片内部实际发热点的温度，通常比封装外壳温度高）抬上去，越过规范定的阈值之后 HBF 先降低时钟（仍然接命令）、再撤销链路层的就绪信号并停止发放信用额度（不再接新命令，只接维护类命令）、温度继续升高则关断，长期跑下来平均能拿到的速率低于标称峰值。把芯片内部温度当常量的评估工具报出来的是冷态那一档的速率，读者会把它当成能一直跑到的速率，于是缓存该开多大、权重与键值缓存怎么在两层之间分配、要不要提前把下一层权重搬进来，这些结论全部建立在一个持续不了多久的速率上。

**这一条的贡献是什么。** 拿规范给的这套温度档位，在程序真实执行的过程中算出长期运行下真正能跑到的速率，并把这个速率作用在每一次访问上。据本轮的检索，现有的评估工具没有一个把这件事算进去：FlashAccel（arXiv:2607.10186，16 页）全文 `thermal` 与 `temperature` 各出现 0 次；Cylon 与 CXLMemSim 的 PDF 里 `retention` 与 `temperature` 合计出现 0 次；`docs/ref_article/` 十份材料里只有 HeatWatch（`temperature` 76 次）与 Ardestani 2012 热感知抽样（39 次）讲温度这件事，而这两篇都不执行真实负载、也不报服务速率。

**规范定的四档与三个阈值**（背景一节 P4 已给出完整条文，动机一节只用其中四点）：四档的英文原名依次是 `Normal`、`Light Throttling`、`Severe Throttling`、`Shutdown`；工作范围是芯片内部温度 0 摄氏度至 105 摄氏度，主机用 IEEE 1500 指令读；`Severe Throttling` 那一档把 CATTRIP 信号拉高、撤销链路层的 AXI 就绪信号、之后不再发放信用额度，在飞的命令必须做完并返回正常响应或错误码 `0x9`；三个阈值 `RTT`（回到全速的那一点）、`LTT`（升温阶段进入轻度降速的那一点）、`STT`（升温阶段进入重度降速的那一点）与启用位都定义在 MMIO 地址 `0x150`，升温与降温走不同阈值（迟滞，见背景一节 P4）。

**为什么这套档位决定的是长期速率，而不是某一个瞬时速率。** 一次运行里 HBF 在四档之间来回走：温度升到 `LTT` 进降速档，升到 `STT` 进限流档，降回 `RTT` 才恢复全速。长期平均速率等于各档速率按各档驻留时间加权，而驻留时间由三个阈值、两段迟滞的位置以及负载自己的升温速度共同决定。所以这个数算不出来的原因不是缺一个公式，是缺「程序真的在跑」这个前提——温度是此前全部执行累积出来的，先记录访问序列、事后再按记录回放一遍，得不到这条从负载到温度再到速率的换算。这也是整篇论文为什么必须让程序真的在跑的理由：这一次访问的代价取决于此前全部执行累积出来的芯片内部温度与缓存内容，状态必须与执行同步推进，不能先算完一边再算另一边。这不是我们的立场，是温度这件事本身要求的。

**与前两条挑战的分工。** 前两条挑战里，一次访问的代价只取决于这次访问本身：地址落在哪一档、这次传输读到第几页。第三条挑战的对象不是一次访问，是整场运行的速率随时间下降这件事。

**手上已有的实测证据，以及必须同时写清的边界。** 一阶热响应的时间常数实测拟合为 GPU 13.1 秒、Dell CD8P 固态盘 12.4 秒，也就是说温度在一次推理运行的时间尺度上就会显著变化（出处 `configs/thermal/gpu-cd8p-logp-live.json` 与 `docs/proofs/2026-08-11-hybrid-complete.md`）。同一块 GPU 上冷机独占 379.117 TFLOP/s、热机独占 348.427 TFLOP/s（−8.10%），采样 SM 时钟从约 2,062 MHz 降到 1,642 MHz，驱动的软件热降速累计计数器从 0 变成 8,279,678 us，三次运行的标量 checksum 都是 66.5 因而负载本身没变（出处 `docs/proofs/2026-08-10-live-gpu-cd8p-thermal.md`）。边界必须在同一段写明，否则审稿人会当场指出用错了对象：这些百分数量的是加速器计算芯片自己随温度降频，今天就存在、跟装不装 HBF 无关，不能当成「HBF 的服务速率随芯片内部温度变化」的证据；参照固态盘那次只读、零写入、只升了约 3.2 摄氏度，离它自己 77.0 摄氏度的告警点差得很远。这两组数现在只能用来说明「同一次推理运行的时间尺度上温度就会显著变化」，HBF 一侧的服务速率变化需要另外补受控实验。

**旧第三条挑战里容量那一半去了哪里。** 按 `/root/hbfsim/43-三条挑战的重新划分.md` 的划分（第 104 行与第 113 行），容量并进第一条挑战：容量模式给出的地址底下根本没有实体显存，改不到的 kernel 真跑过去会出错，所以那一档必须拒绝执行，而容量正是 HBF 存在的全部理由；证据仍是 110 GiB 逻辑范围配 2 GiB 显存页缓存、128 次访问全部完成、checksum `14245581564465502923` 与基线相同（出处 `docs/proofs/2026-08-11-hybrid-complete.md`）。

**为什么用真实 GPU，而不用那些把整块 GPU 模拟出来的工作。** 两条理由，一起写，不能只靠其中一条。

第一条是温度。GPU 的温度是整台机器的属性：取决于机箱风道、邻卡、环境温度、风扇曲线、功耗墙，以及驱动与固件的降频策略。GPGPU-Sim、Accel-Sim、MGPUSim 建模的是微体系结构时序，它们的输出里根本没有温度这个量，而第三条挑战要求温度在运行中反过来改变服务速率，所以在那类工具上做不了。已有实测支撑：`configs/thermal/gpu-cd8p-logp-live.json` 记录环境温度 28.0 摄氏度、稳态 73.5780194293642、时间常数 13.1 秒、摄氏均方根误差 2.1870756397312805；算力随温度每升高一摄氏度下降 0.3280167842295832 TFLOPS，冷态 387.7606615946093 TFLOPS、热态 373.31763045574144、下降 3.7247283103636675%，取样 1292 次，`"checksum_exact": true`。

这条理由有两处必须收紧，否则会被驳（这两处是主 agent 的判断）。**收紧一：不能写成「模拟器做不了温度」。** 体系结构模拟里有热建模这一支——`docs/ref_article/` 里就收了 Ardestani 等人 2012 年那篇《Thermal-aware sampling in architectural simulation》（ISLPED，DOI `10.1145/2333660.2333670`，`docs/ref_article/ardestani2012-thermal-aware-sampling.pdf`），讲的正是怎么在体系结构模拟里高效地把温度算出来。准确的说法是：**热行为是具体部署的属性，热模型的参数本身要从真实机器上标定**，所以无论如何绕不开真机。**收紧二：我们量的是 GPU 和一块固态盘的温度，不是 HBF 的温度**（HBF 还不存在）。诚实的写法是：量真实 GPU 在真实负载下的热响应，把它作为 HBF 堆栈的边界条件，HBF 那一侧仍然是模型。不能含糊成「我们测了 HBF 的温度」。

第二条理由与温度无关：真实的大模型推理负载在逐周期模拟器上跑不完；而且一次读慢了会改变程序接下来发什么请求——请求怎么攒成一批、按什么顺序调度、缓存里还剩什么，都随时序变化，这个反馈在模型化的指令流里不存在。两条理由一起说更结实。

- **D3（回应 C3，本节核心，约 1.5 页，热约 1.1 页、容量约 0.4 页）**：失效模式是芯片内部温度在一次运行的时间尺度上同时改变服务速率与数据保持期限，把温度当常量这两件事都会算错，而容量一旦超过显存，这一层最主要的收益就没法在真实执行下评估；机制是温度到可靠性的闭环与容量模式；被改变的对象是每个 Zone 的服务速率与保持期限，以及被注册范围的后备存储；被改变的生命周期有两条——一个块从写入到必须重写这段时间随芯片内部温度伸缩，一页在缓存与后备之间调入、驱逐与脏页写回。
  - 热这条线从功耗开始：一阶热响应模型把负载功耗换算成芯片内部温度的轨迹，时间常数用实测拟合值（GPU 13.1 s、CD8P 12.4 s）。往下是一条链，段落里要明说这几件事是一条链而不是几件并列的事。芯片内部温度先决定当前处在四档热管理状态的哪一档（升温与降温走不同阈值的 RTT/LTT/STT 迟滞，阈值寄存器在 MMIO 0x150，重度降频时拉高 CATTRIP、取消 AXI Ready、停发 Credit、新命令返回 Status 0x9，在模拟器里表现为请求环停止接收新请求、队列里的命令做完为止），服务速率因此下降。芯片内部温度同时按 HeatWatch 的 Equation 1 `AF(T1, T2) = t1 / t2 = exp[ (Ea / kB) * (1/T1 - 1/T2) ]` 决定每个 Zone 的数据保持期限，其中 kB 是玻尔兹曼常数 8.62 × 10^-5 eV/K，锚点取规范给的 85°C 通电条件下保持 24 小时；到期的块必须重写。这些强制刷新是真实的写流量，占带宽、消耗擦写寿命（MAXPEC/AVGPEC 记账，必要时 Zone Remapping 命令 0x08 交换热区与冷区的物理指向、REDCAP 命令 0x0A 按 MMIO 0x14C 的 1024 位故障位图降容），而写入本身又继续发热、回到链的开头。闭环是字面意思：温度既是这一段执行的结果，又是下一段执行的输入，不能先算完一边再算另一边。激活能 Ea 对 3D NAND 没有公开值（HeatWatch 只给出平面 NAND 的 1.1 eV，并写明公开文献里没有 3D NAND 的值），所以它在模型里是敏感性扫描的参数、不是写死的常数，正文必须写明这一点；同样要写明温度的影响方向不单一，高温增加保持错误但减少编程变异错误。
  - 容量这条线：被注册范围的后备存储换成一段没有物理后备的 CUDA 虚拟地址范围加一块 HBM 页缓存，页在两者之间调入、驱逐与脏页写回。驱逐用确定性的时钟策略是有意的选择——结果可复现，两次运行的 checksum 才能直接对比；现有配置是 110 GiB 逻辑范围配 2 GiB HBM 缓存。限定写在同一段：背后文件是稀疏的、用完自删，我们只证明逻辑跨度超过显存且页路由正确，不声称 110 GiB 被物理读过。
  - 两条线在同一节里写，是因为它们在模型里接在一起：容量模式产生的调入与脏页写回也是真实的写流量，与刷新流量一起进入寿命与发热的账。这一句是我们的判断，对应的量化留给评估 Q6 与 Q8，正文里不能写成已有结果。

### 相关工作（`paper/related.tex`，0.75 页，3 段加一张表）

这一节讲四件事：一张按能力分类的对照表、与存储和闪存模拟器的差别、与 GPU 和内存模拟器的差别、与为尚不存在的硬件做模拟的那三篇工作的差别。

位置仍在评估之后：Cylon 把相关工作放在第 3 节、设计之前，这个做法我们不采用。它按保真、速度、可及性给已有平台分类的那张表值得借用。三处最容易被问到的差别按附录 C 的表述写。

- P1（表）：一张分类表。行是已有平台的类别——真实硬件原型、FPGA 框架、事后回放访问序列的存储模拟器、逐周期精确模拟器、功能模拟器、GPU 模拟器、已有的 HBF 系统工作，最后一行是本工作；列是五项能力——真实负载执行、实测标定、温度建模、GPU 侧、可配置策略。每一列记"有"的判定标准要写在表注里，否则这张表就成了自说自话：**真实负载执行**记有的条件是被评估的程序本身的指令真的在硬件上执行过，而不是按模型推进一串时间点；**实测标定**记有的条件是时序参数来自在真实硬件上量出来的曲线，而不是从数据手册填进公式；**温度建模**记有的条件是温度是模型里的一个状态量，并且会改变时序或数据保持期限，只报温度曲线不算；**GPU 侧**记有的条件是观测点在加速器上，而不是在 CPU 或块设备接口上；**可配置策略**记有的条件是缓存与放置策略由使用者给定，而不是固件写死。表注还要写明每一格的依据来自对方论文的哪一部分，凡是我们从论文文本推断出来的要标明是推断。表的用途是把差别落到具体能力上，不用形容词做比较。
- P2：存储与闪存模拟器，MQSim、SimpleSSD、FEMU（每篇进正文前都要核原文）。末尾那句差别按同一个写法组织——先承认对方在自己的范围内成立，再落到表里的某一列上：它们建模的是块设备与主机驱动栈那一侧，在那个范围内是完备的，通常回放事先记录好的访问序列；本工作只取 MQSim 的闪存介质模型、在线提交请求，负载是真的在跑，差别落在"真实负载执行"这一列。
- P3：GPU 与内存模拟器，GPGPU-Sim、Accel-Sim、MGPUSim、NVBit（同样要核原文）。同一个写法：前三者不执行真实内核，跑的是模型化的指令流，差别落在"真实负载执行"与"实测标定"两列；NVBit 提供的是二进制插桩能力，在插桩这件事上比我们完备，差别落在"它本身不含存储介质模型"这一点上，不是能力强弱的比较。
- P4：为尚不存在的硬件做模拟的工作，CXLMemSim（arXiv:2303.06153 v2；HPDC '26 短文 567–569 页，DOI `10.1145/3806645.3820069`）、Cylon（FAST '26）、FlashAccel（arXiv:2607.10186）。三处差别按附录 C 写：与 CXLMemSim 差在被模拟的对象、观测点与时序模型的来源；与 Cylon 差在被模拟的对象与让真实负载执行的办法（它在 CPU 侧用动态 EPT 重映射，我们在 GPU 侧改写 PTX）；与 FlashAccel 差在目的（它做的是更快的推理系统设计，我们做的是评估工具）与方法（它的评估是解析的事件驱动模拟，真实负载不被执行）。末尾落到最能站住的那一条：在这些工作里温度不是接口的一部分，而 HBF 规范把温度做成主机能读、能设阈值、必须响应的寄存器与引脚，因此模拟 HBF必然包含模拟它的热行为。

### 讨论（`paper/discuss.tex`，0.5 页，5 段）

这一节讲五条边界：标定对象与被模拟对象不是同一个东西、两条没有实测支撑的假设、覆盖缺口、参数与常数的不确定性、参照用的固态盘与二手规范来源的限制。一段一条，每条两到三句，并且都要写明它影响的是哪一问的结论、影响到什么程度。

- P1：标定对象与被模拟对象不是同一个东西。我们量的是含页错误、驱动、缓存插入与用户态扫描开销的完整 vmem 路径，不是介质本身；硬件挂载的 HBF 未必有这部分软件成本，因此这个档在文档里命名为端到端模型，正文要把这层映射关系写清楚，不留给读者推。影响范围：Q2 的全部绝对时间数值与 Q3 的拆分口径都随之受限——曲线上的绝对延迟只能当作那条软件路径的参照，而同一条曲线下不同配置之间的相对比较不受影响。
- P2：两条没有实测支撑的假设。六个断点之外的曲线按最后一段斜率外推；随机、反向、重复与跨操作的访问一律按突发长度为 1 计（单页 11,133 ns），而实测在 64 到 512 页之间有明显非线性。影响范围：前者影响所有超过 512 页的传输，程度取决于负载里这种大传输占多少，正文要给出占比；后者影响 Q5 与 Q9 里稀疏与随机访问的时序结论，偏差是偏高还是偏低目前定不了，要等待补实验第五条的访问模式扫描才能说，正文不要猜方向。
- P3：覆盖缺口。注入那次只建模了一个张量的前 16,384 字节，与全部 61,064,245,248 字节的差距要写在正文；在覆盖扩大之前，结论只对被建模的那部分访问成立。影响范围：Q1、Q3、Q7 三问都建在这次运行上，尤其是端到端的 164.70x 不能外推到全量注册的情形——注册量变大之后，每次访问的路径开销与被建模的介质延迟两边都会变。
- P4：参数与常数的不确定性。三个时序档还没有按规范三档（约 0.4 到 3.0 TB/s）重新锚定，现在 aggressive 档上限是 1 TB/s；激活能对 3D NAND 没有公开值，所以热与保持相关的结论只能给出随激活能变化的区间。影响范围：前者影响所有跨时序档的比较（Q6、Q8 与访问模式扫描），待补实验第六条重跑之后可以关闭；后者影响 Q6 与 Q8 的全部保持期限与刷新流量数值，且无法靠我们自己的实验关闭，只能报区间。这一段还要写明我们能给的是相对比较（同一负载在不同热条件下的相对差别），不是绝对的寿命或失效率预测。
- P5：参照用的固态盘与二手规范来源的限制。CD8P 是普通 PCIe NVMe 端点，不是 CXL 端点，更不是 HBF，它提供的是真实的闪存行为与热行为；规范的机制与数值目前来自二手转载，OCP 原文尚未拿到。影响范围：前者影响标定曲线能不能迁移到 HBF 这一层，程度上我们只能声称方法可迁移、数值需重新标定；后者影响 D3 整条链的起点，85°C 保持 24 小时这一个数字若有出入，Q6 与 Q8 的绝对刷新周期都要重算，而相对趋势不变。

### 结论（`paper/concl.tex`，0.25 页，1 段）

这一节讲三件事：重申造了什么、给三个代表性数字、说明这套工具让别人能做什么。

- P1：一段收尾，不出新主张，也不出现评估一章里没有的数字。重申造了什么（真实负载照常执行、时序来自实测标定、温度进入可靠性闭环的 HBF 模拟器）。进结论的三个数字定为：六个标定断点全部对齐且 0 次不安全启动；快速路径相对详细参考路径快 20.8x；110 GiB 逻辑范围加 2 GiB HBM 缓存下 checksum `14245581564465502923` 与基线相同。这三个数字分别对应保真、速度与容量三件事，各来自评估的 Q2、Q4 与 Q5。待补实验第一条做出来之后，第一个数字要换成未参与拟合的验证点的误差百分比——"六个断点全部对齐"是构造出来的确定性标定检查，一个真正的预测误差比它有说服力得多。最后一句说明这套工具让别人能做什么——在 HBF 送样之前，把自己的容量与放置决策放在真实负载下量一遍。同一句里按双盲要求提一次开源范围（内容见"与参考论文相比我们还缺什么"一节第四条，仓库链接匿名化）。

- **Q8 用温度相关的保持模型重新检验已有工作的续航假设**。已有的 HBF 推理系统工作（FlashAccel，arXiv:2607.10186）这样论证寿命：引用先前工作"把数据保持时间从 3 年降到 3 天，可以把 P/E 周期延长最多 50 倍"，自己保守取 10 倍（P/E 从 100K 提到 1M），据此估计 SLC 闪存在 5 年寿命内每天约 55 个 P/E 周期、1 TB 的 HBF 每天可承受约 55 TB 写入。这条论证里数据保持时间是一个固定的设定值，而按 Arrhenius，保持时间是芯片内部温度的强函数。这一问要做的实验是：给定我们模拟出的热轨迹，算出保持期限随温度的变化，看"3 天"这个设定在真实热历史下还剩多少，以及为守住数据必须补写的刷新流量会吃掉那 55 TB 里的多大一块。**限定必须写清**：我们给的是相对比较（同一负载在不同热条件下的相对差别），不是对那套硬件的绝对寿命预测；对方全文没有出现 thermal 或 temperature，所以这是补一个它没有覆盖的维度，不是指出它算错了。
- **Q9 预取窗口对 HBF 这一层时序代价的影响**（本轮新增）。在我们的模拟器里，把取数策略从"按需读、靠并发掩盖延迟"换成"提前一层预取"，其余条件不变（同一负载、同一时序档、同一容量配置），量化 HBF 这一层的时序代价从多少降到多少。这一问的来源是那篇行业分析文的推测：该文推测靠编译期排好的预取来掩盖延迟的静态调度架构（它举的例子是 Google 的 TPU）比靠大量并发线程掩盖延迟的 GPU 更适合 HBF，依据是它自己算的那笔粗账（405B 模型每层权重约 3.2GB，8 个 HBF 堆栈按 12.8 TB/s 算，流完一层约 250 µs，NAND 单次读 10 µs 只占 4%）——详见背景 P3 与附录 B.7。我们的做法是用实验去检验这个推测，不把它当结论引用。**限定必须写清**：实验在 NVIDIA GPU 上做，改的是模拟器里的取数策略，不是在 TPU 上测的；因此结论只能说"预取窗口对 HBF 这一层的时序代价值多少"，不能说"TPU 更适合 HBF"。对应的待做实验条目见代码仓 `todo/experiments-to-run.md` 第 8 条。
- **评估设置**单独一小节，两台机器与用到的硬件写全：GPU 如 Q2；固态盘 `/dev/nvme1n2`，Dell DC NVMe CD8P E3.S 1.92TB，序列号 `7EU0A01P0XK1`，PCIe 5.0 32 GT/s x4，并声明它是普通 PCIe NVMe 端点、不是 CXL 端点、更不是 HBF，它在实验里的角色是提供真实的闪存行为与热行为。参照做法：CXLMemSim 连主机内存的实测延迟（101.4 ns、116.1 ns）都写进正文，我们同等对待。

## 投稿前必须补做的实验

按优先级排序，每条写清它回答审稿人的哪个问题。

**第一，未参与拟合的标定验证。** 在 1、4、16、64、256、512 页之外另取几个传输尺寸和几种访问模式重测，用经验曲线预测、和实测比，报误差百分比。回答的问题是"你那六个断点误差为零，是不是因为那六个点本来就是用来拟合的"——按 proof 文档自己的说法，那确实是构造出来的确定性标定检查。没有这一组，"实测标定是核心贡献"在评估一章里就没有支撑。优先级高于任何新功能。

**第二，把 164.70x 拆成两部分。** 至少在微基准上，把建模的介质延迟与模拟器每 warp 的请求路径开销分开测；做法可以是扫时间缩放系数，或者做一组注入量为零的对照。回答的问题是"这个减速里有多少是你要模拟的 HBF，有多少是你的工具自己慢"。CXLMemSim 报的是"比原生慢 3 到 6 倍"，我们现在报不出对应的数。拆不开就把限定原样写进正文。

**第三，热管理状态与刷新流量实验。** 给定热曲线，扫 LTT/STT 阈值和刷新周期，报吞吐损失、p99 延迟上升、刷新占用的带宽比例；同一组实验里把激活能也作为扫描参数，报出保持期限与刷新流量随它变化的区间（3D NAND 的激活能没有公开值，理由见附录 A.2）。回答的问题是"温度进模型到底改变了什么结论"——这是全文的核心问题，没有这组实验，温度就只是一个被声称重要的输入。

**第四，扩大 vLLM 的建模覆盖。** 从 16,384 字节扩到至少一整层权重，路线是分批注册、避开 profiling 阶段的同步请求风暴；如果确实做不到，就在正文里论证选择性范围的代表性。回答的问题是"你只建模了 61 GB 里的 16 KB，凭什么说这是真实负载"。

**第五，访问模式与 HBF 参数的扫描。** 五种模式（sequential、random、strided、pointer_chase、mixed_rw）乘时序档，报各自对延迟的敏感度。回答的问题是"这个工具能帮人做什么决策"，同时补上随机访问按单页成本计这个假设的证据缺口。

**第六，时序档锚定后重跑敏感性。** 把三档按规范约 0.4 到 3.0 TB/s 重新锚定，再跑一遍上面的实验。回答的问题是"你的结论是不是只在你自己编的参数下成立"。

**第八，预取窗口实验（对应 Q9）。** 把取数策略从"按需读、靠并发掩盖延迟"换成"提前一层预取"，其余条件不变，量化 HBF 这一层的时序代价变化。回答的问题是"预取窗口对这一层值多少"，同时也是我们检验那篇行业分析文推测的方式——该文推测靠编译期排好的预取来掩盖延迟的静态调度架构比靠大量并发线程掩盖延迟的 GPU 更适合 HBF。限定：实验在 NVIDIA GPU 上做、改的是模拟器里的取数策略，结论不能写成"TPU 更适合 HBF"。详细条目见代码仓 `todo/experiments-to-run.md` 第 8 条；优先级排在第一、二、三条之后。

**第九，在 CXL 固态盘堆叠参照平台上做交叉验证（对应"与参考论文相比我们还缺什么"第三条的第二个应对）。** 做什么：用 [todo] 块 CXL 固态盘并联搭一个可以同时发多路请求的物理参照平台（固态盘型号 [todo]，连接方式 [todo]），在上面按与经验曲线相同的方式采一条延迟随传输尺寸变化的曲线（传输尺寸从 [todo] 到 [todo]，顺序与随机两类访问模式、每种模式的参数 [todo]，每点重复 [todo] 次，取中位数与 95 百分位），再把模拟器在同样配置下给出的时序与它逐点比较。回答的问题是"你的时序模型换到另一类真实闪存硬件上还剩多少偏差"——这是我们现在完全没有的那种与真实硬件的对照。需要的条件是固态盘数量与型号 [todo]，以及把它们并联起来的机器与连接方式 [todo]。完成判据是能报出与实测曲线的逐点相对误差，以及整体的误差区间。限定必须一并写清：这个平台不是 HBF，报出来的是对参照平台的偏差，不是对 HBF的准确率。它排在这份按优先级排序的清单最后，是因为它依赖还没有到手的固态盘（这是我的判断）。

## 与参考论文相比我们还缺什么

这一节按 Cylon（FAST '26，`paper/ref_article/yoon2026-cylon-cxl-ssd-emulation.pdf`）与 CXLMemSim（`paper/ref_article/yang2023-cxlmemsim.pdf`）两篇的结构逐项对照，列出上面的章节大纲现在缺的五样东西：独立的用例一章、写成公式的时序模型、准确率数字、交付物可得性的说明、实验平台的精细描述。每条写三件事：缺的是什么、为什么重要、我们的应对是什么。

**一、没有独立的「用例」一章。** CXLMemSim 用第 4 节整章讲三类内存管理策略（分页、迁移、缓存）能在它上面做什么实验，位置在设计章之后、评估章之前。这是模拟器论文证明自己有用、而不只是准的标准做法：准确率回答"你的数字可不可信"，用例回答"有了它别人能做出什么以前做不出来的决定"，两个问题分开回答，读者才不会把工具当成一次性的实验脚本。我们的章节表里没有这一章，现成的题材其实都有：HBM 缓存该开多大、五种访问模式里哪种最吃 HBF 的延迟、模型权重放 HBF 还是留在 HBM、预取窗口值多少。**我们的应对：已定用做法二**——在评估章里单列一个小节，章节结构与页数都不变，这个小节要写什么见"章节大纲"里评估那一小节的段落计划 P7；代价是这个问题仍然与九个评估问题排在同一章里，读者要自己找到它。另一种做法（用例单独成章）已经放弃，下面这段是它的代价记录，以后篇幅有富余时可以回看：做法一是从评估里划出 Q6 到 Q9 单独成章，评估章现在用 3 页装九问，划出去之后剩五问约 1.6 到 1.8 页、用例章约 1.2 到 1.4 页，再加一个章节标题与一段引子约 0.1 页（这三个数是按现有九问的平均篇幅推算的估计值，不是排版结果），代价是正文总页数要多挤出约 0.1 页，收益是"有没有用"这个问题有了自己的位置。选定的做法二不额外占页，上面那组页数只是做法一的代价，除此之外两条路没有别的差别。

**二、时序模型没有写成公式。** CXLMemSim 把延迟、拥塞、带宽三类延迟各写成一个公式，例如把一个 epoch 切成小区间、需求超过带宽上限就把超出部分换算成额外的停顿时间。我们现在全文只有一个公式，就是 HeatWatch 的 Arrhenius 式 `AF(T1, T2) = t1 / t2 = exp[ (Ea / kB) * (1/T1 - 1/T2) ]`；经验曲线那一部分只描述了插值方式，没有式子。这件事重要，是因为审稿人判断一个时序模型对不对，靠的是看式子而不是看描述，何况我们的核心主张之一就是这条曲线来自实测标定。**我们的应对：在设计 D2 里补两个式子，与 HeatWatch 那个 Arrhenius 式并列，让全文的公式不只有热这一条线。** 一是经验曲线的插值式，给定一次传输的页数，落在哪两个断点之间、按什么方式插值得到延迟；二是突发状态的定义式，突发长度怎么从连续访问里判定、控制 ABI v4 的状态字里存的是什么。补出这两个式子之后，讨论一章那条"随机、反向、重复与跨操作一律按突发长度为 1 计"的假设才有对应的符号可以指。两个式子的具体形式以代码为准，写进正文前要核对。

**三、没有准确率数字，这是与两篇参考论文差距最大的一处。** Cylon 对着商用 CXL-SSD 原型 CMM-H（48GB DRAM 缓存、4KB 缓存行、1TB NVMe SSD 后端、Intel Agilex FPGA 控制器、PCIe Gen5）验证，重现亚微秒的缓存命中与几十微秒的未命中，并匹配带宽与延迟分布；CXLMemSim 报四种拓扑下准确率 86.81% 到 92.15%、误差 7.85% 到 13.19%、始终低于 15%，SPEC CPU2017 平均预测误差 12.8%（wrf 28%、mcf 14% 也照实写进正文），内存数据库与 vectorDB 一类 7.3% 和 8.1%。我们目前一个准确率数字都没有：六个断点误差为零是构造出来的确定性标定检查，proof 文档自己写明了这一点。大纲里要写明它的分量——标题候选二里的 accurate 这个词能不能用，取决于这组数据做不做得出来。**我们的应对有两条。** 第一条是用没有参与拟合的实测点做验证：在 1、4、16、64、256、512 页之外另取传输尺寸与访问模式重测，用经验曲线预测再与实测比，报误差百分比；这一条已经排在待补实验第一条。第二条是用户给的方向（原话是"除了第 3 点我们会拿 cxl ssd 堆叠模拟"）：用堆叠的 CXL 固态盘搭一个物理参照平台，拿它的实测结果去检验模拟器给出的时序，补上我们现在完全没有的那种与真实硬件的交叉验证。**这一条的大体计划如下，方案骨架已经定，凡是具体数量与参数一律写成 [todo]，等定下来再填，不猜。**

- **平台怎么搭。** 用 [todo] 块 CXL 固态盘并联，构成一个可以同时发多路请求的物理参照平台，用来近似 HBF 那种多条独立通道各接一组闪存芯片的组织方式（规范里是 16 个独立 UCIe 通道，每通道有独立的 NAND 芯片组与独立时钟，通道之间互不访问，见背景 P1）。固态盘型号 [todo]，连接方式 [todo]，每块的容量与接口代数 [todo]。这一步的产出是一台可以重复实验的真实硬件，它提供的证据是多路并行的闪存访问在真实硬件上是什么时序。正文里必须写明这个平台不是 HBF。

## 附录 A：温度模型的技术解读（MTBF 与 Arrhenius）

合作者给的原话只有一行：`essense . mtbf thermal model`。下面是我的解读，写清每一层的含义，供你和他确认；凡属外部事实的地方都标了出处，凡是"待核原文"的地方在进论文前必须自己抓原始文献核过。

### A.1 MTBF 是什么

MTBF 是 Mean Time Between Failures，平均无故障时间，可靠性工程里用来衡量一台设备平均多久出一次故障的指标。它等于失效率 λ 的倒数：如果一批设备的失效率是每小时百万分之一，那么 MTBF 就是一百万小时。对闪存来说，"失效"不是一个抽象事件，而是具体的物理机理——存储单元里的电荷慢慢漏掉，读出来的电压落到判决门限的另一侧，于是位翻转。温度越高，电荷漏得越快。

### A.2 Arrhenius 方程怎么把温度变成失效率

用一手来源的原式与原符号：HeatWatch（HPCA 2018，第 504 至 517 页，DOI `10.1109/HPCA.2018.00050`，见附录 B.10）的 Equation 1 是

`AF(T1, T2) = t1 / t2 = exp[ (Ea / kB) * (1/T1 - 1/T2) ]`

该文对每个符号的解释逐字是："AF is the acceleration factor between t1 and t2, where t1 is the retention or dwell time under temperature T1, and t2 is the retention or dwell time under temperature T2. kB is the Boltzmann constant, which is 8.62 × 10^-5 eV/K. Ea is the activation energy, which is a manufacturing-process-dependent constant." 用平实的话说：AF 是加速因子，也就是同一件事在两个温度下进行快慢的比值；retention time 是数据写进去之后还能读对的保持时间，dwell time 是两次编程或擦除之间的空闲时间；Ea 是激活能，指让这个失效机理进行下去所要跨过的能量门槛，单位是电子伏（eV），它随制造工艺而定；kB 是玻尔兹曼常数；T1 与 T2 是绝对温度（开尔文）。

加速因子的实际用途是这样的：厂商不可能等十年看芯片坏不坏，于是把芯片放进高温烘箱里烤几百小时，再用加速因子折算成常温下能用多少年。这个折算的倍数很大——HeatWatch 的脚注写道："Based on Arrhenius' Law, the same experiment would take more than 11 years to finish had we performed it at room temperature (20 °C)."，即他们那组实验若在室温 20°C 下做要花 11 年以上。

**激活能对我们要模拟的 HBF 是未知参数。** HeatWatch 只给出平面 NAND 的值："For a planar NAND flash memory device, Ea = 1.1 eV."，紧接着写 "To our knowledge, there is no public literature that reports the value of Ea for 3D NAND flash memory."。HBF 堆的是 3D NAND，因此**做法建议是把 Ea 当作敏感性扫描的参数，不当成已知常数**：在合理区间里扫一遍，报出保持期限、刷新流量与寿命结论随 Ea 变化的范围，并在正文里写明这个常数没有公开值。本文档早先写的"激活能约 1.05 到 1.2 eV、加速因子约 939 到 1750"来自网页检索摘要，不再作为依据使用。相关的资质标准是 JEDEC 的 JESD47（总纲）与 JESD22-A117/A108；JEDEC 对 client 级固态盘的要求是 30°C 下至少保持一年、UBER（不可纠正位错误率）不高于 1e-15。这几条仍是待核原文。

还有一条要在模型里保留：温度的影响方向不是单一的。HeatWatch 的结论是 "We conclude that higher temperature increases retention errors but reduces program variation errors."——高温增加保持错误，但减少编程变异错误（指写入时不同单元最终落到的电压水平有差异而引起的错误）。把温度效应写成单向变坏是不准确的。

### A.3 规范给的锚点：85°C 保持 24 小时

上面那套换算需要一个已知点才能起步。规范恰好给了：85°C 芯片内部温度、通电条件下，数据保证保持 24 小时。有了这一个点，加上 Arrhenius 方程，就能把任意温度下的保持期限算出来——温度低于 85°C 时保持期限按加速因子成倍伸长，高于 85°C 时成倍缩短。

需要注意两点。第一，这是**通电**条件下的保持时间，与断电存放的保持时间不是一回事，论文里不能混写。第二，这个数字目前来自二手中文转载，OCP 原文还没拿到（网站挡机器人访问），它是整条热与可靠性论证的起点，因此是**最需要优先核到原文**的一个数字。

### A.4 这个闭环怎么转起来

合作者说的 "essence"，我理解成这个意思：热模型真正的产出不是一条温度曲线，而是两个可以进论文表格的量——HBF 在这条热历史下的失效率与 MTBF，以及为了守住数据必须付出的刷新流量。刷新（refresh）在这里指主机把还没到期但保持期限快到的数据重新写一遍，让电荷回到满格；规范的做法是主机以 24 到 48 小时为周期巡检，Base Die 按块暴露读计数器，读干扰累积到阈值会报 CECC Status 0x5 提示主机刷新，程序故障或块数据刷新都由主机重放写来完成，主机可以忽略同一个块的重复刷新请求。

模拟器把这条链变成可测的量，顺序是：给定负载与热曲线 → 按 Arrhenius 算出每个通道、每个 Zone 当前的保持期限与刷新截止时间 → 把到期块的重写变成写请求注入时序模型 → 量出这部分流量占掉多少带宽、把 p99 延迟抬高多少、把有效寿命消耗掉多少。温度到此就不再是背景条件，而是一个产生真实流量、并且能被读者在表格里看到数值的输入。

### A.5 磨损这一维要一起算

只算温度会漏掉一半。闪存还有 P/E 周期限制：P/E 周期指一次编程加擦除，每个块能承受的次数有限，用完就退役。规范为此暴露了三样东西：MAXPEC 与 AVGPEC 磨损寄存器（主机可以从 CSR 读出每个 Zone 的擦写次数）；Zone Remapping（命令 0x08，主机把每个通道划成等大的 Zone，用纳秒级的映射交换把热点 Zone 换到别处，达到磨损平摊）；REDCAP（命令 0x0A，从 MMIO 0x14C 读 1024 位故障位图，把坏掉的部分退出使用、降低容量继续跑）。规范同时写明 HBF **不支持片上垃圾回收**，磨损管理的责任在主机。

三者是耦合的：温度加速老化，写入消耗擦写寿命，而刷新本身也是写入——为了对抗高温带来的保持期限缩短而做的刷新，会额外消耗擦写寿命。这个耦合就是 MTBF 模型的完整输入，也是论文里最容易讲出新意的一块：一个只报带宽和延迟的模拟器算不出"为了让数据活下来，这套负载要多付多少写入"。这里还牵出写放大（write amplification，指为了写入一份用户数据，实际落到闪存上的字节数与用户数据字节数之比；比值 2 就是写 1 GB 用户数据实际写了 2 GB），刷新流量是写放大的一个来源。

设计一章的 D3 里给热与可靠性模型约 1.1 页（D3 共约 1.5 页，容量那条线另占约 0.4 页），写三件事：一阶热响应模型与我们实测拟合出的时间常数（GPU 13.1 s、CD8P 12.4 s）；规范的四个热管理状态做成模拟器里的状态机，阈值来自 MMIO 0x150，升温与降温阈值不同（迟滞）；Arrhenius 保持模型以 85°C/24 小时为锚点，输出保持期限、刷新流量与 MTBF，并把激活能作为扫描参数、报出结论随它变化的区间（理由见 A.2）。评估一章里给一组扫描实验，把这三样的数值报出来。

### B.2 Cylon（FAST '26，6 页）

题名 *Cylon: Fast and Accurate Full-System Emulation of CXL-SSDs*，作者 Dongha Yoon、Hansen Idden、Jinshu Liu、Berkay Inceisci、Sam H. Noh、Huaicheng Li（Virginia Tech），发表于第 24 届 USENIX Conference on File and Storage Technologies（FAST '26），2026 年 2 月 24 至 26 日，Santa Clara, CA，ISBN 978-1-939133-53-3，论文页 `https://www.usenix.org/conference/fast26/presentation/yoon`。PDF 已入库 `paper/ref_article/yoon2026-cylon-cxl-ssd-emulation.pdf`，SHA-256 `7f4ce2561fd1e858e9d83be440e4e2379cfeec3e62fabbde934d70dc1d44154f`。

**它是什么（材料里的事实）。** 建在 FEMU 之上的 CXL-SSD 全系统模拟器（FEMU 是基于 QEMU 的固态盘模拟平台），自称是第一个既提供真正的 CXL.mem load/store 语义与延迟不对称（缓存命中亚微秒、未命中几十微秒）、又提供可配置缓存策略的全系统平台。核心机制是混合访问路径：用动态 EPT 重映射（EPT 是虚拟化里把虚拟机物理地址翻译成宿主机物理地址的页表；动态重映射指运行中改这张表）让缓存命中的 load/store 直接由硬件完成、不触发虚拟机退出（虚拟机退出指虚拟机把控制权交回宿主机管理程序，代价是几微秒量级），未命中才陷入 FEMU 走固态盘时序模型。实现规模是给 FEMU（v8.0.0）加约 6,282 行、给 Linux 内核（v6.4.6）加 1,261 行，已上游合入 FEMU（`https://github.com/MoatLab/FEMU`）。验证方式是对着商用 CXL-SSD 原型 CMM-H（48GB DRAM 缓存、4KB 缓存行、1TB NVMe SSD 后端、Intel Agilex FPGA 控制器、PCIe Gen5）重现亚微秒命中与几十微秒未命中、匹配带宽与延迟分布，并在 Redis 与图分析上跟踪应用级性能趋势。

**学它三件事。** 一是它否定已有手段的写法，这是引言 P5 的模板：工业原型（三星 CMM-H）不透明、缓存管理由固件控制、没有策略旋钮；FPGA 框架 OpenCXD 抽掉了 NAND 行为因而无法评估延迟与带宽；事后回放的模拟器比真实时间慢几个数量级；逐周期精确模拟器对系统级研究过慢；QEMU 这类功能模拟器能跑未修改的操作系统与应用，但在速度、保真与可扩展性上不足。二是它把要求归成三条并逐条兑现——fidelity（保真）、speed（速度）、extensibility（可扩展），我们的一句话主张里那几项要求就是照这个方式组织的。三是它在 §2 末尾把这类研究的困难归成三条：原型不透明、要按内存语义建模而不是块设备、需要完整系统上下文。

**我们不采用的一点。** 它的章节结构是 1 Introduction → 2 Background and Motivation → 3 Related Work（用一张表按保真、速度、可及性给已有平台分类）→ 4 Cylon Design（4.1–4.7，Implementation 作为 4.8）→ 5 Evaluation → 6 Conclusion。把相关工作提到第 3 节这个做法我们不采用，相关工作仍放在评估之后。

**我们要补的、以及和它的关系。** 它做的是 CXL-SSD（把块存储挂到 CXL 上、按字节寻址当内存层用），我们做的是 HBF（NAND 与 GPU 同封装）；它在 CPU 侧用虚拟化做全系统模拟，我们在 GPU 侧用 PTX 改写让真实 kernel 照常执行；它不建模温度。它是同一个会议前一年的工作，既是最贴近的写法模板，也是必须引用的相关工作，差异化表述见附录 C.3。

题名 *FlashAccel: Leveraging High-Bandwidth Flash for High-Throughput LLM Inference*，作者 Xinyu Wang、Yalong Xue、Xiaotian Sun、Xiaoyu Zhang、Chunmeng Dou、Xueqi Li、Xiaoming Chen（通讯）。PDF 在 `paper/ref_article/wang2026-flashaccel-hbf-llm-inference.pdf`，SHA-256 `9a1021441048c570cb998bcef6b19c60ad1b8ae1a47867bd23df5ba864618fb3`，`refs.bib` 条目 `wang2026flashaccel`。它把 HBF 集成进带 HBM 的 GPU 做软硬件协同设计（掩盖访问延迟的体系结构支持、权重与 KV cache 的数据布局、能感知 HBF 的存储管理与编程模型），报出 6 个 HBF 堆叠让每 GPU 吞吐提升 2.54 倍、能效提升 1.93 倍（相对纯 HBM 的 GPU，100 ms 延迟约束下），读带宽 4.6 TB/s 对峰值写带宽 245.8 GB/s；评估用的是在 LLMCompass 之上搭的事件驱动模拟器加一个按 plane 粒度建模页访问延迟的 NAND 模拟器，不执行真实负载。

### B.10 HeatWatch（HPCA 2018，第 504 至 517 页，14 页）

题名 *HeatWatch: Improving 3D NAND Flash Memory Device Reliability by Exploiting Self-Recovery and Temperature Awareness*，作者 Yixin Luo、Saugata Ghose、Yu Cai（卡内基梅隆大学）、Erich F. Haratsch（希捷）、Onur Mutlu（苏黎世联邦理工与卡内基梅隆），发表于 2018 IEEE International Symposium on High Performance Computer Architecture，DOI `10.1109/HPCA.2018.00050`。PDF 已入库 `paper/ref_article/luo2018-heatwatch-nand-temperature.pdf`，SHA-256 `a1d2140c3c9c0ae2fedf7741f1e9d2af2fe777742509fc19875a5c559cc2f608`，`refs.bib` 条目 `luo2018heatwatch`。

**给我们的是"NAND 介质对温度敏感"这件事的一手依据**，五条可以直接用：

1. **温度到失效速度的换算公式。** 它的 Equation 1 是 `AF(T1, T2) = t1 / t2 = exp[ (Ea / kB) * (1/T1 - 1/T2) ]`，符号解释逐字为 "AF is the acceleration factor between t1 and t2, where t1 is the retention or dwell time under temperature T1, and t2 is the retention or dwell time under temperature T2. kB is the Boltzmann constant, which is 8.62 × 10^-5 eV/K. Ea is the activation energy, which is a manufacturing-process-dependent constant."
2. **激活能只有平面 NAND 的公开值。** "For a planar NAND flash memory device, Ea = 1.1 eV."，紧接一句 "To our knowledge, there is no public literature that reports the value of Ea for 3D NAND flash memory."。HBF 堆的是 3D NAND，所以这个常数对我们要模拟的 HBF 没有公开值。
3. **两个等效时间的概念。** 高温下的一段保持时间与室温下更长的一段保持时间造成同样的保持损失，他们把折算之后的量叫 effective retention time（等效保持时间）；同理，高温下的一小段空闲时间与室温下更长的空闲时间有同样的恢复效果，叫 effective dwell time（等效空闲时间）。dwell time 指两次编程或擦除操作之间的空闲时间，在这段时间里部分损伤会自行修复，这个现象叫 self-recovery（自恢复）。
4. **高温加速的量级与方向。** 脚注写 "Based on Arrhenius' Law, the same experiment would take more than 11 years to finish had we performed it at room temperature (20 °C)."；结论写 "We conclude that higher temperature increases retention errors but reduces program variation errors."——高温增加保持错误、减少编程变异错误，方向不单一，模型里要保留这一点。
5. **它自己的结果。** 相对固定读参考电压的基线（读参考电压指读一个存储单元时用来判断它存的是 0 还是 1 的比较电压，固定基线就是这个电压不随芯片状态调整），在 28 条真实存储负载轨迹上平均把闪存寿命提升 3.85 倍，与理想的读参考电压选择机制相差 0.9% 以内。

**我们要补的、以及要写清的差别（这一段是我的判断）**：一是把激活能做成敏感性扫描的参数而不是常数，理由见附录 A.2；二是 HeatWatch 测的是 3D NAND 芯片本身，不是装在 GPU 封装里的 HBF，两者的封装环境与工作温度窗口不同（规范给 HBF 的窗口是 0 到 105°C），把它的结论用到 HBF 上属于外推，正文里要写明。

## 附录 C：与已有工作的差异化表述

审稿人一定会拿这几篇来问：同组已有的 CXL 内存模拟器、最接近的 HBF 系统工作、同一个会议前一年的 CXL-SSD 全系统模拟器。三处差别都主动写进正文，不要等被问。

### C.1 与 CXLMemSim

下面三条是能说清的差别（这一节是我的判断，不是论文里的原话）：

1. **被模拟的对象不同**。一个是 CXL.mem 内存池，访问方式是普通的 load/store；一个是闪存支撑的近计算存储层，读按 64 字节寻址、写按 4 KiB 粒度、块内必须连续写、不支持片上垃圾回收。介质的物理限制完全不同，因此模型里必须有擦写寿命、数据保持和刷新这些在 DRAM 池里根本不存在的量。
2. **观测点不同**。一个用 CPU 性能计数器（Intel PEBS）加 eBPF 采样，一个改写 GPU 的 PTX 指令并在真实 kernel 执行中生效。前者是采样式的，论文自己承认必然丢信息并专门做了一个理想上界来对照；后者是每次访问都经过的路径，代价是开销更大（现在是 164.70x）。
3. **时序模型的来源不同**。一个是解析模型加 Gem5 对照，一个是真实硬件实测曲线加在线的介质模型。我们有一条别人没有的证据：解析模型在 512 页时比实测快 99.93%，也就是说在这一层，把参数表填进公式这条路会错到什么程度是有实测支撑的。

还有第四条，我认为是最能站住的一条：**温度在两篇里的地位不同**。CXL 内存池那篇里温度不是接口的一部分；HBF 规范把温度做成了主机能读、能设阈值、必须响应的寄存器与引脚，于是"模拟 HBF"必然包含"模拟它的热行为"。把这一条写在相关工作那一段的末尾，比列举功能差异更有说服力。

### C.2 与 FlashAccel

三条差别，写法上要注意这是对比加互补、不是贬低——它先在正文里证明这一层有人在做，我们再说明我们提供的是另一样东西。

1. **目的不同。** 它优化的是推理系统：怎么摆权重、怎么放 KV cache、怎么掩盖 HBF 的访问延迟，产出是一个更快的设计（2.54 倍吞吐、1.93 倍能效）。我们做的是评估工具：让别人能在硅片出来之前，把自己的设计放在真实负载下量一遍。两者是上下游关系，不是同一件事的两个做法。
2. **方法不同。** 它的评估是解析的事件驱动模拟——在 LLMCompass 之上建模、用 ScaleSim 估算延迟、再扩一个按 plane 粒度算页访问延迟的 NAND 模拟器，真实负载不被执行。我们是真实负载在真实 GPU 上照常执行、模拟器在执行过程中施加时序，时序来自真实硬件的实测标定。我们有一条支持这个选择的证据：解析模型在 512 页时比实测快 99.93%（实测 20,254,374 ns 对模型 14,096 ns）。
3. **覆盖不同。** 它全文没有出现 thermal 或 temperature，数据保持时间是一个固定的设定值（3 天）；我们把温度到降频、温度到数据保持、保持到刷新流量做成核心机制，因此能回答它回答不了的一类问题——同一套设计在真实热历史下还剩多少寿命余量、刷新要吃掉多少写入预算。这一条对应评估 Q8。

### C.3 与 Cylon

它是同一个会议前一年最贴近的方法学参照，差异要写得客气而具体（这一节同样是我的判断）：

1. **被模拟的对象不同。** 它模拟的是挂在 CXL 上、按内存语义访问的固态盘，后端是 1TB NVMe SSD、前面有 48GB DRAM 缓存；我们模拟的是与 GPU 同封装、用 UCIe 直连的 NAND 层，读按 64 字节寻址、写按 4 KiB 粒度，且有擦写寿命与数据保持这类限制。
2. **让真实负载执行的办法不同。** 它在 CPU 侧用虚拟化：动态 EPT 重映射让缓存命中的访问不触发虚拟机退出、未命中才陷入 FEMU 的时序模型；我们在 GPU 侧改写 PTX，让真实 kernel 照常执行、访问在执行过程中被计时。两条路线各有代价，它的代价是要改内核与虚拟机管理程序（给 FEMU 加约 6,282 行、给 Linux 加 1,261 行），我们的代价是覆盖不到已编译的 cubin。
3. **温度维度它没有。** 这一条不必展开，一句话带过即可，重点放在前两条上。

CXLMemSim 的引言结构（主 agent 用 pdftotext 从 `docs/ref_article/yang2023-cxlmemsim.pdf` 提取核实）：用加粗引导词分段。**Motivation.** 先讲内存搁浅（memory stranding，指服务器的 CPU 核被虚拟机占满、但相当一部分 DRAM 没人用而闲置）在云数据中心的经济代价，生产环境的访问记录显示最多 25% DRAM 容量被困住。**CXL.mem as a Solution.** 讲 CXL 是工业界已有的标准互连、CXL.mem 允许把内存池化、主要厂商都在做；接着一段说 CXL 内存比本地 DRAM 慢（小池额外 70–90 ns、机架级超 180 ns，早期原型延迟约本地 DDR 的 2–3 倍、带宽只有 50–80%），而且真实硬件拿不到。**The Need for CXLMemSim.** 逐条否掉已有评估手段：商品硬件不可得、解析估计与小规模原型不够、Gem5 这类全系统模拟器跑真实基准比原生慢上千倍、远程 NUMA 与 RDMA 替代法要么高估开销要么建不出 CXL 的 load/store 接口与交换拓扑。**Our Approach – CXLMemSim.** 才讲自己怎么做。最后是四条加粗贡献段。章节骨架是 Abstract → Introduction → CXL Background → System Design（"已有工作的局限"放在设计章内，作 3.6）→ Use Cases → Evaluation（准确率一节先行）→ Related Work → Conclusion。

新的主线五步：大模型推理受限于 HBM 容量、HBF 因此重要 → HBF 是工业界给出的答案（规范已发、容量 8 到 16 倍、Google 与 Tenstorrent 入盟）→ 已经有人在 HBF 上做推理系统设计，需求是真的，但 HBF 2027 年初才送样，他们只能用恒温的事件驱动模拟器评估 → 所以需要 HBFSim，这里列困难清单 → 我们的做法：真实负载照常执行、时序来自实测标定、温度接进可靠性闭环。

对比对象已经找到并核实：FlashAccel，arXiv:2607.10186v1 [cs.AR]，2026-07-11 提交，16 页，作者来自中科院计算所与国科大（通讯作者 Xiaoming Chen）。它做的正是把已有算法迁到 HBF 上：把 HBF 集成进带 HBM 的 GPU 的软硬件协同设计；最主要的结果数字是 6 个 HBF 堆叠让每 GPU 吞吐提升 2.54 倍、能效提升 1.93 倍（相对纯 HBM 的 GPU，在 100 ms 延迟约束下）。评估用的是在 LLMCompass 之上搭的事件驱动模拟器——事件驱动模拟指按解析出来的延迟模型推进一串时间点，不真的执行负载；LLMCompass 是一个搜索矩阵乘分块映射、并用 ScaleSim 估算延迟的 GPU 性能模型工具；他们再给它接一个按 plane（NAND 芯片内部能独立操作的子单元）粒度建模页访问延迟的 NAND 模拟器。缺口是硬事实：全文没有出现 thermal 或 temperature 这两个词。数据保持时间在文中只作为换取续航的杠杆出现——引用先前工作"把保持时间从 3 年降到 3 天可以把 P/E 周期延长最多 50 倍"，自己保守取 10 倍（P/E 从 100K 提到 1M），据此估计 SLC 闪存在 5 年寿命内每天约 55 个 P/E 周期、1 TB 的 HBF 每天可承受约 55 TB 写入。而数据保持时间恰恰是芯片内部温度的强函数（Arrhenius），这正是我们的热模型能直接检验的假设。

### E.3 第三版：把优势与发热写成同一个封装决定的两个结果

按用户要求，把"HBF 是第一份把可堆叠 NAND 定义为 xPU 同封装内存层的开放标准 → 同封装同时带来带宽约两个数量级、延迟约一个数量级的优势 → 同一个封装决定又把 NAND 放进 GPU 的高温环境"这条因果关系写进主线与相关章节，并加上"第一个"这个措辞的边界与各比值的出处要求。

**当时的对话回复段（存档）：**

这一版改的是一件事：把 HBF 的优势和它的发热困难当成同一个封装决定的两个结果，写进主线。原来的第二版主线只说 HBF 容量是 HBM 的 8 到 16 倍，把发热单独列在困难清单里，两者之间没有因果关系；现在改成一条链，温度就不再是我们额外挂上去的一个维度。

因果关系本身：HBF 是第一份把可堆叠 NAND 定义为 xPU 同封装内存层的开放标准，NAND 不再是插在 PCIe 插槽上的一台存储设备，而是和 GPU 装在同一个封装里、用 UCIe 直接相连的一层内存。UCIe 是芯片与小芯片之间的互连标准，规范讲解文的原话是通道"从一个芯片上的凸点到远端芯片的连接凸点测量，小于 2 毫米"。这段距离带来的直接后果是整个 PCIe、NVMe 协议与主机驱动栈都不存在了，于是有两方面的数量级优势：带宽方面，规范三档约 0.4 到 3.0 TB/s 每堆，而我们自己实测的企业级 PCIe 5.0 固态盘 Dell CD8P 顺序读只有 7.577 到 7.587 GB/s，比值约 50 到 400 倍；延迟方面，HBF 物理读约 10 µs 量级，而固态盘 4 KiB 随机读端到端通常几十到上百 µs，约一个数量级。这两个比值都是主 agent 用规范档位与我们实测数字算的推算值。访问语义也跟着变：从块设备协议变成 64 字节粒度的 load/store 式访问。相对 HBM 这一组不是优势而是互补：带宽同数量级，容量 8 到 16 倍，但延迟劣约两个数量级（约 10 µs 对约 100 ns）。

代价来自同一个决定：把 NAND 装进 GPU 的封装，等于让它一起承受 GPU 满载时的温度。我们实测同一块 GPU 在持续 BF16 负载下从 28°C 升到 73°C（另一次热机峰值 85°C），吞吐掉 8.10%，SM 时钟从约 2,062 MHz 降到 1,642 MHz；而 85°C 恰好是规范只保证数据保持 24 小时的那个温度点。规范自己也承认这件事有多重：工作时芯片内部温度窗 0 到 105°C、RTT/LTT/STT 四档迟滞降频、CATTRIP 过热引脚加停发 Credit 加 Status 0x9、按块读计数器提示刷新。一份规范为热写了这么多条文，本身就是"发热是这一类硬件的一等问题"的证据。

"第一个"这个话要怎么说才安全：官方口径是 SanDisk 2026-08-03 新闻稿的原句 "As one of the first technical standards of its kind in the memory and storage industry"，说的是"最早的一批此类标准之一"，是标准层面、不是芯片层面。所以论文里的写法定为"第一份把可堆叠 NAND 定义为 xPU 同封装内存层的开放标准"，锚定 OCP 规范。

哪些数字是推算、进论文前要补什么：两个"数量级"比值都是推算，进正文前每个比值都要配可核实引文，特别是固态盘 4 KiB 随机读延迟的出处、PCIe 5.0 x4 链路上限约 14 GB/s 的出处、HBM 约 100 ns 延迟的出处。我们自己 vmem 那条 4 KiB 冷读 P50 11,133 ns 不能拿来当固态盘本身延迟的证据。
