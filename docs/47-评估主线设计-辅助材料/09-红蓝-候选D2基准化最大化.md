## 1. commit 7241d6d「freeze randomized measured E5 matrix」:是协议冻结,不是实测结果

E5 是这个容量研究自己编号的第五道执行闸门。冻结矩阵(由新增的 `scripts/generate_pretrace_artifacts.py` 生成,写出 `08-experiment-matrix.json` 到结果目录)里的 `execution_gates` 一节逐条定义([一手]):

## 2. 真实 Qwen MoE 专家轨迹捕获(6f5cbc1)

**捕获字段**(`trace_schema.json` + `trace_collector.py`,[一手]):每 token × 每层一条事件——`phase`(prefill/decode)、`token_step`、`layer_id`、`topk_expert_ids`(校验唯一性与范围)、每个专家的张量记录(`source_shard`/offsets/`tensor_bytes`/shape/dtype/`page_begin`/`page_end`/`access_order_sequence`)、`request_id`/`sequence_id`/`prompt_id`、模型与环境指纹、git commit。**三个关键的「没有」**,采集代码自己写明:

## 3. 页粒度 HBF 回放时序引擎(d270003)

新增 `benchmarks/replay/hbf_trace_timing.cpp`(独立可执行文件)+ `trace_replay.py` 的外部时序模式([一手]全文读过)。**输入**:冻结 profile(JSON)+ 未命中事件 JSONL(每条:logical_address、bytes、page_bytes、read/write,序号必须连续);每个专家未命中被展开成该 profile 的 16 KiB 页请求。**输出**:三个分开的时间域——`modeled_device_service_ns`、`demand_exposed_stall_ns`、`emulator_dispatcher_wall_time_ns`,加 fast/reference 请求计数。**三档**:`--mode fast|hybrid|mqsim`;hybrid 用与运行时相同的 `HybridSampler`(warmup + 抽样进 reference);mqsim 全走 `MqsimOnlineEngine`。

**queue_depth 语义**:PR#3 修复(12ef138)在该分支祖先内(`git merge-base --is-ancestor` 验证通过,[一手]);分支顶端 `src/mqsim_adapter/mqsim_online.cpp` 第 271-367 行确实用 `profile.queue_depth` 限制在途请求([一手] grep)。**但要注意:回放引擎本身逐请求提交-等完成**(`run_reference` submit 后立刻 `run_next_completion`,下一页的 arrival_ns = 上一页完成时刻),**有效并发恒为 1,queue_depth 上限在这条路径上不会被触及**。这是引擎自我声明的语义(「ordered blocking demand misses」),不是缺陷,但意味着 EQ1-C 的排队/饱和保真不能靠这个引擎给出。另:零延迟档不存在——profile 校验拒绝 `read_latency_ns == 0`(`src/profile/profile.cpp:330`,[一手]),引擎对 service==0 直接抛错。
