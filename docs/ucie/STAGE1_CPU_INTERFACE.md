# Stage 1 CPU UCIe/AoU interface

This optional component connects one HBF AXI read interface to the existing patched MQSim CPU backend. Enable it with `HBFSIM_ENABLE_UCIE=ON` and `HBFSIM_ENABLE_MQSIM=ON`; the default daemon and GPU path do not load it. The production `ucie_mqsim_bench` always constructs a real `MqsimOnlineEngine`. Configure fails if UCIe is enabled without MQSim.

The source contract is [OCP HBF Architecture v0.7](https://www.opencompute.org/documents/ocp-hbf-architecture-specification-v0-7-0-final-pdf) §§4.2, 5.3, 6 and [AoU v0.8](https://openchipletatlas.org/specifications/aou/0.8) Appendix D, together with UCIe 3.0 §3.3.4 Streaming Format 6. AoU v0.8 marks its Appendix D HBF profile **under development**; this stage models that published draft profile and does not claim a finalized HBF wire standard. The first profile chooses one UCIe-A x64 Grade 2 (16 GT/s) module and one AXI port. Its ideal 256-byte flit serialization is 2 ns per direction. This is a wire calculation, not a measured link latency or useful-payload throughput.

Each Format 6 flit accounts for 2 UCIe header bytes, 4 CRC positions, a 10-byte AoU header, and 240 bytes (48 five-byte granules) of message area. An AoU HBF ReadReq occupies 3 granules (15 bytes); ReadData512 occupies 14 (70 bytes, including 64 data bytes). The link records MsgStart, message offsets, fragments spanning flits, empty granules and credit-only flits. It does not encode every bit of the AoU header or message fields, compute CRC, train the PHY, model retry, or establish protocol compliance. The OCP 36-bit module-local address is validated; the larger AoU address payload is not byte-serialized in this version.

AR and R have separate initialized, finite granule credits. The sample [profile](../../configs/profiles/ucie/hbf-grade2-single-module.json) labels its AR=12, R=56 and zero propagation as **SCENARIO_ASSUMPTION**. These are structural fixture choices, not specification defaults. A whole message's 3 or 14 granules are debited at MsgStart. An AR grant is scheduled after the request reaches and is submitted to MQSim; an R grant is scheduled only when the caller consumes the completion returned by `run_next_completion_until`. Grants travel on opposite-direction flits, including charged empty flits, with only legal AoU grant values 0, 1, 4, 8, 16, 32, 64, or 128. Counters and the bounded trace expose flit, wire, protocol, padding and credit-only costs separately. The profile's credit counts and propagation can be changed for scenario testing under the [schema](../../configs/schema/ucie-link.schema.json).

The public front end accepts one aligned 64-byte regular AXI read with a 14-bit AXI ID and a 36-bit module-local address. It rejects writes, partial beats, bursts, bad addresses, duplicate active request IDs, time travel, and a future arrival earlier than the most recently accepted arrival. It has a finite accepted-request bound that includes delivered completions awaiting caller consumption. Each accepted 64-byte read independently submits a cold 4 KiB page read through the existing MQSim `Host_Interface_HBF` path; this is 64 application bytes versus 4096 submitted media bytes and does not merge reads or model an HBF device page-buffer hit. MQSim's native read command and completion are observed separately. Its existing aggregate service cap remains a media-ready constraint before R-link transmission and is not labeled UCIe bandwidth.

Responses with one AXI ID enter the return link in request issue order, even if media completes in reverse order; ready messages can share a flit. Different IDs may return in another order. A backend error produces one non-ready software completion with zero interface data bytes; AoU ErrorMsg wire encoding is outside this version. The underlying MQSim simulator is process-global, so the production class guards against a second concurrent UCIe front end. Concurrent use with an independently created legacy MQSim engine is unsupported. There is no cancellation or public timeout API in this stage.

To rebuild and verify on a supported Linux CPU host with the pinned submodules initialized, run [the reproduction script](../../scripts/reproduce_ucie_stage1_cpu.sh):

```bash
./scripts/reproduce_ucie_stage1_cpu.sh build-ucie-stage1 full
```

The build directory must be an ignored `build*` directory inside this checkout because an existing service-client test requires its binary and artifacts there. The script configures CPU-only CMake, builds all default targets, runs the full CPU suite, and runs four real MQSim reads. `focused` reruns the UCIe tests, two MQSim regressions and benchmark against an already configured build. The [CPU checkpoint](../proofs/2026-09-29-ucie-stage1-cpu.md) records the actual clean run, raw counts, failed first build attempts, and interpretation limits. It is not a GPU or hardware performance claim.
