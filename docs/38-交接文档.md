## 一、项目是什么，现在到哪一步

### 被模拟的对象

HBF 的全称是 High-Bandwidth Flash（高带宽闪存）：把 NAND 闪存做成与 HBM（高带宽内存）相同的堆叠形态，放进 GPU 封装内部，用 UCIe（一种芯片与芯片之间的互连标准）与计算单元相连。SanDisk 与 SK hynix 通过 Open Compute Project 在 2026-08-03 发布了第一份技术规范。这类器件现在买不到，只能模拟。

### HBFSim 做的事

HBFSim 让真实的大模型推理负载照常在真实 GPU 上跑，同时在每一次碰到被登记为 HBF 的显存的读写上人为加上等待时间。实现办法是运行时改写 PTX 里的全局访存指令——PTX 是显卡代码的中间文本，人可以读、也可以改写；PTX 编译之后得到 cubin 这个二进制产物，里面装的是 SASS，也就是显卡真正执行的机器码。

USENIX FAST '27 秋季轮，截稿 2026-09-15 23:59 AoE，正文 12 页不含参考文献，强制双盲。投稿要求的全部细节以 `/root/hbfsim/FAST2027-CFP.md` 为准，日期与页数不许凭记忆写。

## 二、现在的三条挑战：这是唯一有效的版本

三条挑战各管一件事，互不覆盖：第一条管能不能把效果加到某一次访问上，第二条管这一次访问要花多久，第三条管整场运行的速率随时间下降。

### 第一条挑战

> **Challenge1: HBF 与 GPU 封装在一起，HBF 的每一次访问在封装内部被服务完毕，导致以前模拟器设置拦截点的方法论全部失效。**

「拦截点」指一个位于被测程序之外、每一次访问都必须经过、并且允许在那里加上等待时间的地方。关键在「之外」：被测程序的二进制一个字节都不改，慢下来这件事由机器上别的层次提供。

**这句概括的写法是用户多次点名定下来的，接手之后不许改回去。** 这一句逐字照用户的原话写，用户的原话是「HBF 与 GPU 封装在一起, HBF 的每一次访问在封装内部被服务完毕, 导致以前模拟器设置拦截点的方法论全部失效」；现在写在 `/root/hbfsim/HBFSim/paper/35-FAST27论文大纲与逻辑线.md` 的「论文主张」一节（该节起于第 25 行）里。三条硬性要求：

## 三、必须知道的已核实事实

按重要性排。这一节的每一条都是这一轮亲手打开原文读到的，不是转述。

### 关于 OCP 规范

**规范原文已经入库。** 文件在 `/root/hbfsim/HBFSim/docs/HBF_OCP/ocp2026-hbf-architecture-specification-v0-7-0.pdf`，v0.7.0 FINAL，130 页，日期 03 AUG 2026，作者 Chinnakrishnan Ballapuram（Sandisk）与 Dongsop Lee（SK hynix）。同目录下有 pdftotext 抽出的同名 `.txt`，216,144 字符。引规范时同时给 PDF 页码与 txt 行号。此前所有标着「等 OCP 规范」的待核实项全部结案。

**规范里的 `Host` 指 xPU，不是服务器 CPU。** 这不是推断，是规范自己写的：第 90 页 §8.5.1 `providing a direct test interface between the host(xPU) and the HBF`；第 15 页 `The High Bandwidth Flash (HBF) is tightly coupled to the xPU Host Compute die`；第 38 页 `The xPU to HBF communication interface uses AXI as protocol layer running on UCIe`。全文 130 页里 `CPU` 只出现一次，在引言的一句历史叙述里（第 13 页 `for decades from the CPU era`）。规范里所有 `host software`、`host read`、`host channel` 都是 xPU 这一侧。

**因此项目文档里不再使用「主机侧」这个词，已逐处改掉，共 15 处。** 指服务器 CPU 那一侧时写「服务器 CPU 那一侧」；强调这个位置在被测程序外面时写「被测程序之外」；指 HBF 规范意义上的访问发起方时写 xPU。

**HBF 的访问是带命令类型字段的 AXI 事务，不是普通读写指令。** 请求通道在封装内部，跑在 AXI over UCIe 上。此前写过的「HBF 没有这样一条离散的请求或命令通道」与规范原文相反，已删除。

### 关于读写粒度

- 页大小 4 KiB，txt 第 1008 行，第 15 页：`4KiB NAND page size`
- 读的粒度 64 字节、不跨 4 KiB 页边界，txt 第 993 至 994 行，第 15 页：`Burst Length of 64B to 4KiB in multiple of 64B for read access on 64B aligned address and does not cross 4KiB NAND page boundary`
- 一页要拆成 64 条读命令，txt 第 4095 至 4097 行，第 56 页：`All Read requests are 64-byte granularity; however, the host shall send 64 read commands to retrieve the complete 4KiB data with different AXI IDs.`
- 写的粒度是 4 KiB，txt 第 4182 行，第 58 页：`The write granularity to the Core die is 4KiB. The Base die controller first accumulates the complete 4KiB write commands and data is sent to the Core die.`
- 块内必须连续写、不许跳，违反返回写错误码 `0x6`；写到块内第 0 页触发整块自动擦除，txt 第 4186 至 4187 行，第 58 页：`HBF will internally auto-erase the NAND block from the host point of view, when receiving a page-0 (WL-0, STR-0, NAND block-X) write request of a NAND block.`
- 块内随机写不被支持，第 121 页 §11.5.2.2：`HBF doesn't support random write within the NAND block`；要改写一个块必须 `start writing from NAND block page 0, wordline 0, and string 0`。真机上返回写错误码 `0x2`（地址重叠）。

由此得到第二条挑战最干净的说法：一页 4 KiB 等于 64 次 64 字节的读访问，这 64 次里最多只有 1 次要付把整页从阵列感应出来的时间，另外 63 次直接从缓存缓冲取。

### 关于缓存缓冲

每个 bank 至少两个 4 KiB 缓存缓冲，命中立即返回（bank 指 NAND 芯片内部可以各自独立进行一次读取的一块存储区域）：

- txt 第 4118 至 4120 行，第 57 页：`HBF supports two cache buffers for each bank to hold up to at least two pages of data. It is recommended to read the full first 4KiB page before issuing a third 4KiB address that will evict the first 4KiB data.`
- txt 第 4121 至 4122 行：`The Base die shall immediately serve the cache hit read from the cache buffer if ordering is not violated.`
- txt 第 4113 至 4115 行，第 56 至 57 页：`a. Cache hit reads are served immediately if there are no ordering violations.` / `b. For cache miss reads, Core die sense is triggered when prior read for that specific bank is done.`
- 寄存器字段，txt 第 5806 至 5810 行，第 70 页：`Number of Cache Buffers per Bank (NCBB): Indicates the number of cache buffers per NAND Bank in the Base die. Each Cache Buffer Size is same as NAND Page Size(4KiB).` / `0x01: 2 Cache Buffers per Bank (default)`

`NCBB` 这个字段有 4 位宽，但只有取值 2 是合法的、其余全部标 Reserved，所以「每 bank 两个 4 KiB 缓存缓冲」不是厂商可以省掉的选项。**注意措辞：规范原文是每 bank 两个缓冲、每个 4 KiB（等于一页），不是每个缓冲装两页。**

### 关于延迟数值与带宽

**这份 130 页的规范，从头到尾没有给出一个读延迟的数值。** 全文检索结果：`latency` 出现 15 次，没有一次带数值；唯一沾时间单位的数字是上电电压斜率（100us、20us/V 到 20ms/V）和一个以 500 毫秒为单位的超时寄存器；全文只有两处交流时序表，一处是复位（Table 23、24），一处是 IEEE 1500 测试端口（Table 30）。规范给了带宽、粒度、页大小、缓冲数量、排序规则、错误路径，就是不给一次读要多久。凡是时间量一律推给产品：`NAND block size is defined in the product specification`（第 58 页）、`The reasons for restriction and duration of restriction are HBF product-specific`（第 119 页）、Table 33 的 `Endurance: Product Specific`、`Read Disturb: Product Specific`（第 106 页）。

**三档带宽是 0.384 / 1.536 / 3.072 TB/s**，Table 4，第 16 页。

要给读延迟区间时，可用的是 TileLens 扫的 1、2、5、10、20 µs（arXiv:2607.04031，原文 `page read latency across 1, 2, 5, 10, and 20 µs to cover the range`）与 NAND 芯片手册的 tR 25 到 90 µs。

### 关于主机侧没有逐次访问事件

规范全文检索的命中数：`page fault` 0 次；`doorbell` 0 次；`submission queue` 与 `completion queue` 各 0 次；`DMA` 0 次；`MSI` 0 次；`interrupt` 1 次而且无关（第 99 页一句警告）；`driver` 3 次，没有一次在数据通路上。另外，`TLB`、`MMU`、`page table`、`virtual address` 四个词的命中数都是 0——所以「地址由 GPU 自己的页表翻译」这半句的依据来自 GPU 侧的机制，不是规范，正文里要照这个分界写。

**这一条的诚实边界要自己先写出来：** 这是一份设备侧规范，它能确立的是「HBF 自己既不定义、也不要求任何封装外的参与」，它本身证不了某个 xPU 厂商不会在 HBF 的地址范围前面自己放一套缺页机制，因为 xPU 内部不在这份规范的范围里。
