Abstract

Modern serving systems offload reusable KV to a larger tier.
Reuse comes from repeated dialogue, common prefixes in shared
prompts and documents, and context revisited by agent workflows.
Mooncake and related systems therefore extend the KV pool into
CPU DRAM, remote memory, and SSDs [4, 16]. This offloading is
standard and essential: without it, a capacity-limited server must
reject requests or recompute evicted KV. It supplies the objects that
larger tiers store and restore.
High-Bandwidth Flash (HBF) aims to accelerate that tier. Roadmap
HBF stacks many NAND dies for internal parallelism and uses the
accelerator memory path instead of a PCIe/NVMe link [9]. Compared with an SSD, HBF has far lower read latency and far higher
bandwidth. It can help when read-mostly objects and system dataflow
are co-designed for HBF [6, 8]. A simple design keeps the Mooncake object path, replaces its SSD backing tier with HBF, and expects faster serving.
Whether that simple design works is untested. The HBF studies
above choose what to place in flash, so they do not say what happens when a running KV hierarchy hands the device whatever it
evicts. Device microbenchmarks do not settle it either, because the
swap changes more than access time. The package that gains flash
gives up near memory, and the traffic the tier receives is decided
by the runtime rather than by the medium, so the answer depends
on admission and queueing behavior that only a full serving stack
exposes.
This paper tests that design and finds it does not work. Under
the same runtime, we compare complete HBF-1 and HBF-2 organizations against SSD baselines using TokenSim, four complete twohour production traces, five dense and mixture-of-experts (MoE)
models, and H100/B200 profiles. HBF is slower on every request
metric: across H100 and B200, average end-to-end latency rises 2–
5.5×, and maximum service-level objective (SLO) goodput falls 1.1–
2.7×. Faster flash barely helps; changing HBF read/write latency by
3.75× moves average end-to-end latency by less than 1%.
The problem is the SSD-style hierarchy, not HBF itself. It sends
HBF its least friendly object, transient and write-heavy KV, whose
traffic collides with every physical limit of NAND. The boundary is
simple: faster media helps only when secondary-tier service is on
the request critical path (C1), later reads repay each flash write (C2),
and delivered bandwidth is sustainable (C3). § 5 formalizes these
as three necessary conditions, each with a falsifiable requirement

A faster storage device should make serving faster. We find the opposite. High-Bandwidth Flash (HBF) stacks NAND behind a wide,
package-local interface, promising flash-scale capacity with far lower
read latency and higher bandwidth than an SSD. The obvious move
is to keep an SSD-style Mooncake KV-offloading stack and swap
in HBF underneath. We built that system and measured it: an extended TokenSim, four complete two-hour Qwen-Bailian production traces, five dense and mixture-of-experts models, and H100/B200
profiles. The upgrade backfires. Average end-to-end latency rises
2–5.5× and maximum SLO goodput falls 1.1–2.7× across H100 and
B200, so the faster device yields a slower system. A cost-benefit
model explains the paradox: a faster far tier pays off only when
read I/O is the bottleneck, reads outweigh writes, and delivered
bandwidth is sustainable. Transient KV violates all three at once.
Buying flash through the package costs GPU near-tier capacity
and bandwidth, while HBF’s own read/write latency barely matters: scaling it 3.75× moves latency less than 1%. Worse, the twotier hierarchy keeps reuse in the near tier and hands HBF a relentless write-heavy stream. Writes outnumber reads on every trace,
so a 3D-ICE model shows the stack hits its thermal limit well below peak bandwidth, and a TLC tier wears out sooner than the
SSD pool it replaced. The device is fine; the drop-in deployment is
not. HBF sucks as an SSD replacement for transient KV, but earns
its place in LLM serving when used selectively with reuse-aware
placement, write budgeting, and thermal coordination.

Introduction

Large language model (LLM) inference stores a key and value vector for every retained token. The key–value (KV) cache grows with
context length, batch size, and active requests, limiting concurrency and retained context. Paged allocation, quantization, and selective retention reduce waste or bytes per token [7, 12, 15, 23] but
not the capacity limit. When the working set of prefixes and histories exceeds GPU memory, the system must place KV in a larger
tier.

Background

This section explains how inference creates, reuses, and offloads
KV state and why serving systems increasingly move it to a larger
tier. Section 3 introduces HBF separately to distinguish storage policy from device.

2.1

Paged and Pooled KV Storage

2.2.1 PagedAttention. vLLM introduces PagedAttention and blocklevel KV allocation [12]. A block table maps each request’s logical KV blocks to non-contiguous physical blocks in GPU memory. On-demand allocation reduces fragmentation, supports continuous growth, and enables common-prefix sharing and copy-onwrite without a large contiguous reservation.
Two requests share exact-prefix KV when their token prefixes
and model state match. The benefit grows with matched length but
vanishes after eviction. System prompts and multi-turn dialogue
create heavy reuse; independent API calls create little. The same
admission policy can therefore yield very different read/write behavior across traces.

KV Cache and Reuse in Agentic Serving

Agentic and conversational workloads dominate modern LLM deployments: multi-turn dialogue, tool-use loops, shared system prompts,
and retrieval-augmented generation (RAG). They revisit tokens,
reusing prompt prefixes and session histories across requests. Serving therefore depends less on raw compute than on memory capacity to retain useful prefixes and active histories and bandwidth to
restore or stream them without stalling the GPU.
LLM inference has prefill and decode phases. Prefill processes
prompt tokens in parallel and materializes KV state. A prefix-cache
hit avoids recomputing the matched prompt but still requires locating and delivering its saved blocks to the GPU. Decode generates tokens autoregressively and repeatedly reads the retained KV
history. Each transformer layer stores a key and value vector per

SSD offloading is now standard and provides KV objects for larger
tiers to store and restore.
2.3.2 Modern offload paths. In a naive SSD path, data moves through
host memory (GPU HBM → CPU I/O → NVMe → SSD). Submission overhead, extra copies, and fragmented small requests can
then dominate media service (Fig. 1(a)).
Modern paths remove much of this cost (Fig. 1(b)). Linux io_uring
uses shared queues to reduce system calls and context switches [13].
GPU Direct Storage (GDS) enables direct DMA between NVMe and
GPU memory. Tutti moves object identification and completion to
a GPU-side io_uring path, removing the CPU from each operation’s critical path [17].
SSD offloading is therefore a strong, actively optimized baseline. Drives remain replaceable outside the accelerator package,
and their controllers provide buffering, mapping, garbage collection, wear leveling, and bad-block management.
SSD remains off-package and bounded by the PCIe/NVMe link.
This motivates High-Bandwidth Flash (HBF), a higher-bandwidth,
package-local alternative introduced in Section 3. We evaluate HBF
by replacing or augmenting the SSD backing tier while preserving
the KV-object path above.

Reads sense pages or subarrays. Programs are slower than reads,
and erases use larger blocks. NAND lacks arbitrary in-place overwrites, so invalid pages require later reclamation. Aggregate bandwidth comes from concurrency across channels, dies, planes, and
subarrays, not DRAM-like latency for each access.
A representative stack integrates sixteen 128–256-layer NAND
dies, through-silicon-via (TSV) arrays, and a base die. The base die
concentrates mapping and management logic near the package, a
natural control-logic location that also concentrates area and heat
(Fig. 2) [9].
HBF connects through the GPU memory path rather than as an
NVMe block device. The GPU controller identifies HBF addresses,
and the base die translates requests into NAND operations. This
can avoid host software and PCIe/NVMe traversal but does not
guarantee DRAM-like latency or write behavior.
A read selects the HBF address, channel, die, plane, block, and
page. It then senses NAND and returns data through TSVs and the
package interface. The system places the object in HBM or a GPUvisible buffer before the request executes. A write allocates a physical page, programs NAND, updates logical-to-physical metadata,
invalidates any older page, and eventually reclaims invalid space.
Wear, bad-block, error-correction, and thermal metadata must remain consistent across this lifecycle.

3.2.1 HBF-1. (2028) is a single GPU whose silicon interposer is
filled entirely with HBF (Fig. 3a). The interposer can host only a
few stacks, so once HBF takes those slots no room is left for HBM,
and the fast near tier is pushed off the interposer to GDDR7 in
BGA packages on the card PCB. HBF-1 thus buys package-local
flash capacity by demoting its near tier from on-interposer HBM
to slower off-interposer GDDR.

HBF Organization and Stacking

HBF stacks 3D NAND dies behind wide vertical or package-level interconnects. It also includes a base die or distributed peripheral circuits, many independently accessible NAND regions, and a packagelevel link to the GPU. Together, these components provide much
more internal parallelism and interface bandwidth than a conventional SSD. The key distinction is simple: HBF changes how NAND
connects to the processor; it does not change NAND into DRAM.

Limitations of HBF

The wide interface does not change NAND, so HBF inherits three
device-level limits relative to HBM. First, latency: NAND reads and
writes take on the order of microseconds, roughly two orders of
magnitude longer than HBM accesses; programs are slower and
more energy-intensive than reads [8]. Die-, plane-, and channellevel parallelism raises aggregate bandwidth but does not close this
per-access gap.
Second, endurance: flash cells tolerate finite program/erase cycles, and elevated temperature accelerates wear [1]. A write-heavy
tier therefore degrades far faster than DRAM’s effectively unbounded
write endurance.
Third, power and thermals: per-stack HBF power is far higher
than HBM. H3 assumes roughly 160 W per HBF cube, so six stacks
can approach 960 W [6], potentially exceeding the GPU die’s peak
power. Package-local HBF therefore creates a new power and thermal problem rather than inheriting HBM’s modest envelope.

4.2

Metrics and Statistical Treatment

We report TTFT, TBT, end-to-end latency, delivered request and token throughput, queueing and connector delay, KV hits, blocks and
bytes read and written, the write/read ratio, prefix reuse, recomputation, and SLO goodput. For the architecture comparison we average each metric over the trace and model campaign at every system
and latency point, because the question is how the complete SSD,
HBF-1, and HBF-2 organizations behave, not how one favorable
point behaves. The write/read ratio and prefix hit rate in Finding 3
come from the per-tier byte counters over a full two-hour replay
of each trace, so they reflect fixed request contents and ordering
rather than a sampled window. Zero-read runs are excluded from
the ratio because it is undefined, and malformed result files are excluded. Throughout, we label every value as a measured simulator
output, a sourced device parameter, or a modeled projection.

Workloads, Models, and Platforms

Thermal Model

Two findings need device models the serving simulator does not
provide. The thermal model is described here, and the write-endurance
budget is given with Finding 6 (§8.2). For thermal behavior we
build a 16-Hi HBF stack similar to HBM4, with 128-layer 3D-NAND
TLC dies, and solve its steady-state heat flow with 3D-ICE [18]. We
drive the model with the read and write energy of a 16-token KV
block—the connector’s access granularity—and sweep sustained
single-stack bandwidth to obtain dynamic power and peak temperature. We set the safe junction temperature to 80◦ C, matching HBM3e, and model a throttling policy that closes the hottest,
highest-traffic planes and redirects writes to cooler planes once the
limit is reached. The thermal model is a projection for unreleased
hardware; we report it as such and use it to bound, not fix, the
thermal limits of an HBF tier.

rest of the serving pipeline. This is a system-level question; we
formalize it with a single cost–benefit relation. We express the net

Finding 3 leaves 𝜌 fixed by object class, so the remaining lever in
Eq. (8) is the write cost 𝐶. SSD KV serving already has the standard tool for lowering it. Mooncake-style batching coalesces many
small KV writes into large buckets, amortizing the drive’s slow peroperation I/O and turning scattered writes into near-sequential
transfers. Whether that win is a property of the optimization or
of the medium it was built for decides whether it carries onto HBF.
We run the identical bucketing mechanism on both media over
a shared traceA/traceB matrix, holding HBF’s random and sequential bandwidth equal so batching can help only by amortizing
fixed write-operation latency. We compare three arms, no-batch,
the Mooncake bucketed path, and a single-key control that pays
the bucketing cost without grouping anything.
Table 8 and Fig. 9(a) give the paired result. On SSD-12, request
p50 falls by 8.9–21.1% at every block size. The same mechanism
on HBF-2 recovers 2.69% overall, 5.2× smaller, and the benefit is
concentrated at the smallest block, +9.2% at 16 tokens, fading to
+0.72% at 128 and turning negative (−1.85%) at 512. The SSD gain
is flat across block size; the HBF gain decays to zero and then costs.
Composition of the write cost. The contrast follows from what
each medium’s write cost is made of. On SSD a write is dominated
by high fixed per-operation overhead and a random-access penalty,
and usable bandwidth is low relative to demand. Batching attacks
all three at once, so its win is large and survives coarse blocks.
HBF removes those levers by construction. Its access latency is low
and its random and sequential bandwidth are equal, so there is
no scattered-to-sequential conversion and no bandwidth cliff. The
only lever left is amortizing fixed operation latency, which pays off
only when a bucket is dense with tiny blocks, about 94 blocks per
bucket at 16 tokens but 4 at 512 (Fig. 9(b)). The single-key control
makes that residue explicit. With the batching path enabled but no
grouping it is worse than no-batch on every metric, because it pays
bucketing overhead for no amortization.
Batching helps SSD because it compensates for SSD’s specific
weaknesses. HBF does not have those weaknesses, so the optimization has almost nothing left to lower. The write cost 𝐶 cannot be
engineered down, so C2 still fails.

Finding 5: Write-Heavy Traffic Overheats
HBF and Throttles Bandwidth

Finding 3 established that the flash stream a KV hierarchy generates is write-heavy, and writes cost more power than reads. What
sustained bandwidth an HBF stack can hold under that traffic is
therefore open; the interface peak bounds it but does not answer
it.
Thermal model and throttling policy. A 3D-ICE [18] model of
a 16-Hi TLC stack, driven by the access energy of a 16-token KV
block, sweeps sustained single-stack bandwidth (§4). Safe junction
temperature is 80◦ C, matching HBM3e; the modeled throttling policy closes the hottest, highest-traffic planes and redirects writes to
cooler ones.
Dynamic power scales linearly with bandwidth, and the stack
hits the 80◦ C limit at only 202.27 GB/s and 53.72 W, far below interface peak, so it cannot run continuously above that point (Fig. 10(a)).

We measure the write volume the traces generate and compare
it against two endurance envelopes. The HBF write counter records
the media-write volume each trace sends to an eight-H100 HBF-2
tier over the two-hour replay, normalized to a daily rate. The SSD
reference is a capacity-matched pool of four KIOXIA CM7-V 3.2 TB
drives [10], whose vendor 3-DWPD rating gives 38.4 TB/day. For
HBF we adopt a labeled, deliberately favorable TLC assumption
with unit write amplification, which yields a 21.7 TB/day budget
for a five-year target; any real NAND management would only
lower it.
Every trace writes past both envelopes (48–140 TB/day), so under linear TBW exhaustion the nominal HBF tier lasts a constant
0.56× the SSD pool’s life across all four traces (Fig. 11). Coarsening
KV blocks from 16 to 128 to 512 tokens raises the apparent prefix
hit rate yet increases HBF write volume from 188 to 237 to 258 TB
(1.38×).
Why the shortfall is structural. HBF is attached like memory
but behaves like flash. An SSD hides the cost of writing NAND
behind a controller, and an HBF stack, presented to the GPU as
memory, has no equivalent place to put one. The services that controller provides for free (logical-to-physical mapping, write buffering, garbage collection, TRIM, wear leveling, bad-block handling,
and error correction) must be rebuilt in the base die, GPU memory controller, driver, or runtime [3]. That rebuilt control plane
is the movement and control term 𝐶 move of Eq. (6), work the SSD
tier never charged to the serving system. Managing the write side
needs device state (write budget, wear, hot regions), not a single
peak-bandwidth number. Block granularity does not route around
that state. Small blocks maximize the number of write operations,
while large blocks maximize bytes written and write amplification,
because partial-block reuse forces whole larger blocks to be rewritten. Both keep the device on the wrong side of Eq. (8).
HBF therefore wears out sooner than the SSD it replaces, which
is the endurance term 𝐶 life of Eq. (6), now measured. A design
writing short-lived KV into HBF pays twice, once for the slow
unbuffered program and again against a write budget it exhausts
faster.

9 Discussion and Related Work
9.1 Synthesis
The six findings falsify the three conditions of Section 5 in turn,
and together they mark where HBF does help. An object belongs in
HBF only when its restore delay is the serving bottleneck (C1), its
reads outweigh its writes (𝜌 > 𝜌 ★, C2), and the bandwidth it needs
is sustainable under the package’s power and endurance budget
(C3). Fig. 12 places representative object classes on the two axes
that decide this (exposed stall and reads-per-write), with sustainable bandwidth shifting the boundary. Transient decode KV sits
in the low-exposure, low-𝜌 corner where all three conditions fail;
weights and shared prefixes sit in the opposite corner, which is
where H3 and HAVEN place their HBF-resident state.
The three conditions use device-agnostic quantities: exposed
critical-path fraction, reads per write, and sustained bandwidth.
The same map therefore applies to other package-local far tiers
such as CXL-attached or near-data flash, not only to HBF. The
map gives the axes and the break-even rule of Eq. (8) rather than a
calibrated boundary across the latency×bandwidth plane. A working runtime requires flat GPU-managed access, reuse-aware admission, and thermal-aware write budgeting. This paper’s role is to
establish, with measurements, why that design is needed.

9.2

Related Work

KV-cache management. PagedAttention enables block allocation
and prefix sharing [12], quantization and compaction shrink KV
size [7, 15, 23], and Prompt Cache and CachedAttention reuse state
across prompts [4, 5]. Mooncake, LMCache, Strata, and Tutti offload KV across CPU, SSD, and network tiers with GPU-assisted
I/O [14, 16, 17, 22], and DeepSeek’s disk context cache evidences
persisted prefix reuse [2]. We ask how this SSD-offload stack behaves when its backing medium moves into the accelerator package.

9.3

Limitations

HBF is not a public product, so we label roadmap organization as
sourced and device values as modeled or swept, and report cost as
a qualitative gap rather than a calibrated ratio. Most importantly,
the architecture comparison changes GPU-local memory together
with the secondary tier, so it shows that the complete HBF organizations underperform under this SSD-style runtime; it does not
show that SSD is the better isolated medium. Simulator validation
reduces risk but does not replace measurements on future HBF silicon, whose package routing, controller behavior, and long-term
wear remain outside the present model.

10

Conclusion

Replacing an SSD KV tier with HBF does not improve LLM serving,
under the same Mooncake-style runtime it makes serving worse.
Our model explains why: a faster far tier helps only when read I/O
is the serving bottleneck (C1), reads outweigh writes (C2), and its
bandwidth is sustainable (C3), and all three fail for transient KV
behind an SSD-style connector. HBF is not the problem, using it as
a faster SSD for transient KV is.
