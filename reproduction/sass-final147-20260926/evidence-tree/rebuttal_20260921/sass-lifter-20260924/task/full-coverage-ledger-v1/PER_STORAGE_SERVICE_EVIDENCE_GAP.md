# Per-storage service evidence for expansion and final combined validation

Root source review, 2026-09-25. Status: DOC_DERIVED interface gap plus proposed host-only design for review. No implementation, no new GPU work, no change to active6706 or existing accepted representative evidence.

Current representatives select one registered storage each, so positive exact-module access/admission/completion closure together with live storage/Driver/output evidence attributes that selected service. After class expansion, many storages share a recovered module. One final positive module/global count does not identify which of those storages contributed. Future acceptance must not fill missing layer evidence using totals.

Exact frozen `task/qkv-real-model-agent-abi-v2/launch_gate.cpp:1168` access_snapshot synchronizes, reads existing module counters, disables accounting and caches final JSON. The joint snapshot is also terminal. `:3299` tracked_modules_snapshot refuses active accounting and exposes identities only. Calling these after every selected layer would change existing session lifecycle and cannot be treated as a passive checkpoint.

A minimal candidate is a new, default-off host-only quiescent checkpoint of the existing active counters. It would use the gate's existing accounting-transition exclusion and counter mutex, check current domain/session epoch/unloaded/late modules/poison state, synchronize at an intentionally quiescent validation point, read the already bound counter addresses and verified config, and return explicit CHECKPOINT data. It must not disable/re-enable/reset counters, mutate cached final JSON, create a new ownership lifecycle, or relabel a partial snapshot COMPLETE. Preserve existing ABI/legacy behavior; use an additive explicitly documented symbol if required. This is an interface proposal, not a device algorithm change or implemented capability.

A model adapter would place the before check after its unselected native reference and before the selected candidate, with an after check only following successful candidate return and synchronization on the actual execution thread. Each receipt must join actual registered base/extent, request/thread, exact original/patched/module identity and profile, and positive selected-module counter deltas with access/admission/completion closure and zero error deltas. Repeated layers sharing a module then cannot borrow earlier service totals. The end-of-request validator still checks total accounting, all expected call identities, output/token equality, registration union and final combined component identity.

Quiescent checks are validation instrumentation and may add synchronization cost; their wall time is not directly comparable performance evidence against a run lacking those checks. They must never be invoked by an external observer while a candidate is running. If the exact source shows a safe existing nonterminal API instead, prefer it and document that evidence. New PTX memory rewriting/device-helper algorithms remain outside this proposal. Root must review the concrete isolated design before implementation, and missing representative dependency still gates GPU expansion.

## Reassessment against the accepted contract

After inspecting the actual6603 `runs/qkv-model-combined-v3/result/dynamic-coverage-validation.json`, its accepted scope is per-storage modeled address rows joined to active COMPLETE exact modules with measured closure; it explicitly disclaims separate per-storage latency. Preserve that acceptance scope and old98 evidence. The concern above is specifically **totals alone**, not a finding that the existing per-storage-address plus actual-dispatch contract is invalid.

Before adding any checkpoint API, prefer the lowest sufficient final proof: for each new selected consumer join live registered base/extent, its independent output comparison, exact original/patched callback, profile/request/thread, address-matched coverage and complete exact-module counters; reject absent or native-fallback selected consumers individually. Enrich existing per-call host decision receipts if the current logs omit those join keys. This is materially different from filling missing consumers using positive totals. A new quiescent checkpoint is an optional design only if a concrete attribution ambiguity remains after those joins, and must not become an unrequested per-storage latency or exhaustive per-byte proof requirement. No checkpoint implementation is approved by this note.
