# 红队报告:保真度方法学视角

结论先行:三个候选都建立在同一条未经检验的传导链上——「在 CD8P 的端到端软件路径上验证过的东西,可以为用 MQSim 介质模型或解析参数算出来的 HBF 数字背书」。这条链的两端是两个不同的引擎,没有一个候选安排实验把它们接起来。分候选攻击在前,共同盲区在后。

## 一、对候选 C0(19 号规划)的攻击

### C0-1 §5 的硬件 A/B 与它的全部退路,在已冻结的实现上一条都跑不通

- **攻击对象:** C0 §5.2(hardware-backed A/B 三组对照)、§5.3(trace 回放退路)、§7.2 控制组 5(zero target delay)。
- **攻击内容:** §5.2 首选路线需要两件东西,一件未知、一件被实现明确拒绝:(a) capacity 页服务的后备介质可切换——现状未知,Gate 1 至今未执行,连「U787 = 6787p」这个机器身份本身都是推断(facts-for-design.md L67 标[推断]);(b) DRAMFS-zero 与 zero-target-delay 对照——profile 校验直接拒绝 `read_latency_ns == 0`(实验分支核查报告第 3 节,`src/profile/profile.cpp:330` [一手]),回放引擎对 service==0 抛错。而 §5.3 的退路要求 trace 携带 arrival timestamp 与 in-flight depth(C0 原文 §5.3 第 1 条),但冻结协议实际捕获的轨迹里 `gpu_event_timestamp_ns: None`、`previous_compute_gap_ns: None`,时间戳语义是「post-request JSONL materialization」即生成结束后落盘时刻,没有到达时间、没有并发信息(实验分支核查报告第 2 节 [一手])。也就是说:首选路线卡在两个未验证前提上,退路被自己冻结的采集格式堵死,zero-delay 对照被自己的校验器堵死。EQ1 占正文 45–55%,整条悬在这里。
- **证据:** 19-hardware-grounded-evaluation-plan.md §5.2/§5.3/§7.2;实验分支核查报告第 2、3 节;facts-for-design.md L67。
- **严重度:致命。** EQ1 是 C0 自封的「论文基石」,而它的三条实施路径与冻结实现互相矛盾,不改设计或不改代码(改代码又违反 Gate 0 冻结)就没有 EQ1。

### C0-2 「HBFSim 被验证了」这句话里,被验证的到底是哪个引擎,C0 从头到尾没说

- **攻击对象:** C0 §6(EQ1 全部)与 §15.1 推荐主张。
- **攻击内容:** HBFSim 有三个互不相同的时序引擎:CD8P 实测曲线档(fast 路径的实测曲线子模型)、参数化 fast 模型、MQSim 介质模型(reference)。CD8P held-out 验证只碰第一个;而 EQ3 相图与所有 HBF 投影数字出自后两个。C0 的措辞门槛表和 §15.1 的主张(「reproduces latency, saturation, and cache-capacity trends with quantified error bounds」)把误差数字整体授予「HBFSim」,不区分挣到这个误差的是哪条路径。审稿人只需问一句:「你的 held-out 误差是 vmem 曲线档的,你的相图是 MQSim 档的,前者的误差界凭什么覆盖后者?」C0 没有答案,也没有安排跨引擎一致性实验(facts-for-design.md L31:两条路径之间目前没有任何一致性检查代码 [转述])。
- **证据:** facts-for-design.md L23–26、L31;C0 §6.8、§15.1。
- **严重度:重大**(与共同盲区 1 同根,但 C0 的门槛表把它制度化了,单列)。

### C0-3 措辞门槛表的数值没有出处,而且按先例是自杀性的

- **攻击对象:** C0 §6.8(median ≤10%、P95 ≤20%、宏观 ≤15%、rank ≥0.90)。
- **攻击内容:** 三点。第一,数值无derivation:先例里 FEMU 宏观误差 0.5–38%(brief-2 §3)、MQSim 真实 trace 6–18%(brief-2 §4)、Accel-Sim 周期 MAE 15–30%(brief-2 §5)都过了顶会;把宏观门槛定在 ≤15% 意味着「做到 FEMU 的水平就必须降级为趋势主张」,这是替审稿人预设了一个比 FAST 已接受水平更严的标准,达不到时论文里躺着一张自己写的不及格判定。第二,rank ≥0.90 没有规定 n:Accel-Sim 的相关系数建立在 80 个负载、1,945 个 kernel 实例上(brief-2 §5 [一手核实于简报]),C0 的 held-out 集只有个位数配置,详见共同盲区之外的 D2-4。第三,「事前注册」的说服力依赖注册时点可查证,而 C0 自己的 E5 矩阵冻结声明都诚实写着「frozen after E4 trace validation...not represented as a pre-E4 preregistration」(实验分支核查报告第 1 节 [一手])——论文里的门槛表在数据全部到手后写成,审稿人无法区分「事前门槛」和「事后挑一个自己能过的门槛」,除非把冻结 artifact 的时间戳作为交付物,C0 未作此安排。
- **证据:** C0 §6.8;brief-2 §3(a)、§4(a)、§5(a);实验分支核查报告第 1 节。
- **严重度:重大。**

### C0-4 EQ1-B/C 的微基准不经过 GPU 注入路径,一行配置的近邻工具就能给出同样的证据

- **攻击对象:** C0 §6.3(request-size fidelity)、§6.4(QD/saturation fidelity)。
- **攻击内容:** §6.3/§6.4 定义的扫描(op × size × pattern × QD,报 CDF/parity/knee)全部是主机侧 I/O 测量对模型输出的比较,原文没有任何一处要求这些请求由 GPU 上被改写的 PTX 发出。这正是 NVMeVirt 已经对四台真实设备做过并做到 3.3–12.2% 上限误差的实验形态(brief-4 (a) [一手核实于简报]),也是 FEMU 0.8–11.6% 微基准的形态(brief-2 §3)。HBFSim 区别于这两者的唯一实质是真实 GPU 执行中的注入与 capacity 页服务,而 EQ1 的最大篇幅证据恰好不使用这个区别。审稿人的一行配置质问是现成的:「NVMeVirt 或 FEMU 填一个 tR=4 µs 的 profile,就能产出你 §6.3/§6.4 的全部图,你的新平台在这些图里体现在哪?」C0 对此无回答。
- **证据:** C0 §6.3/§6.4 原文(无 GPU 负载字样,对照 §6.2/§6.6 有);brief-4 (a);brief-2 §3(a)。
- **严重度:重大。**

### C0-5 统计设计漏了三件事:模拟侧无变异、器件无预处理协议、标定与验证隔两个月

- **攻击对象:** C0 §12(统计与可复现性规范)。
- **攻击内容:** (a) §12.1 要求微基准每点 ≥10 次,但模拟器给定 profile 与种子是确定性的——10 次重复在模拟侧产出同一个数,parity 图上是「硬件分布 对 模拟点值」,用哪个统计量对哪个统计量比、CI 怎么画,§12 没有定义;MQSim 侧合成负载的种子扫描也没有出现在任何扫描轴里。(b) 无 SSD 预处理协议:MQSim 自己的验证前置是写满 70% 逻辑空间、两个 4 小时阶段(brief-2 §4(a)),Amber 验证前顺序写满进稳态(brief-4 (b));C0 §3.3 引用了这条教训,§12 的 manifest 里却只有 temperature state,没有写入历史与预处理步骤。(c) 标定 CSV 采于 2026-07-30(facts-for-design.md L37 出处链),held-out 验证将在 2026-09 采——同一块盘隔六周、FTL 状态与磨损未记录,held-out 误差里混着器件漂移,C0 没有安排「重测一个标定点作漂移对照」这个一天就能做的控制。
- **证据:** C0 §12;brief-2 §4(a);brief-4 (b);facts-for-design.md L37。
- **严重度:重大**((b)(c) 各自足以让审稿人对误差数字打折)。

## 二、对候选 D1 的攻击

### D1-1 三介质迁移论证的 DRAM 那条腿是断的,而它是 D1 新增的主轴

- **攻击对象:** D1 E1 的三介质设计与 (b) 节链条第 2 环。
- **攻击内容:** 迁移论证要求「同一机制在三个延迟尺度上 held-out 误差都有界」。DRAM 点的目标延迟约 116.1 ns(且这个数是[推断],同机身份由一处顺带提及推出,Gate 1 未执行——D1 自己标注了)。但注入机制的自身开销远大于这个目标:纯插桩已慢 37–51%(facts-for-design.md L28 [一手]),每 warp 请求路径开销与建模延迟至今未分离(L29,拆分是待做工作)。在目标延迟 ~10⁴ ns(CD8P 单页)时开销或可忽略或可扣除,在目标 ~10² ns 时开销比信号大若干量级——DRAM 点的「held-out 误差」测出来的是请求路径开销,不是模型误差。除非 E2.1(时间拆分)先做完并能逐请求扣除开销,DRAM 腿给不出有界误差;而 D1 的链条把 E1 排为基石、E2 排在其后,依赖方向倒了。三介质坍缩成两介质(CXL SSD 形态还未知),「机制不携带介质私货」的论证就退化成 C0 已有的单代理运行,D1 相对 C0 的第一差异点(差异清单第 2 条)不复存在。
- **证据:** D1 E1 论证结构段;facts-for-design.md L28–29、L67;D1 差异点清单第 2 条。
- **严重度:致命**(对「三介质」这个主轴;E1 退化后 D1 需要重排)。

### D1-2 链条第 3 环整个押在 E1.3 上,而 E1.3 的前提未知、退路已被证明不可执行、失败后链条无定义

- **攻击对象:** D1 (b) 节第 3 环(「测,不算」)与 E1.3。
- **攻击内容:** D1 明文规定微观误差到宏观主张的传导只靠 E1.3 差分 A/B,不做解析传播。E1.3 采纳 C0 §5.2,其前提「后备介质可切换」D1 自己的表格写着「缺,需合作者当天回答」;其降级路径采纳 C0 §5.3 trace 回放——如 C0-1 所证,冻结轨迹没有到达时间与并发信息,按原 arrival gaps 回放在现有采集格式上不可执行。E1.3 若失败,D1 说「应用级主张全部降为条件式」,但链条第 4 环同时规定「E3 与 E4 只有在 E1/E2 通过后才有资格出现」——第 3 环空转时,按 D1 自己的规则 E3/E4 应被摘除,评估章只剩微基准,这个后果 D1 没有写,也没有为它准备章节形态。一条五环的链,断在第 3 环时全链的行为未定义。
- **证据:** D1 (b) 节第 3、4 环;D1 E1 新跑表「后备介质可切换与否未知」行;实验分支核查报告第 2 节。
- **严重度:重大。**

### D1-3 D1 自己引用的 Empirical Guide 教训要求验证排队与饱和,而 D1 的基础设施恰好验不了这一维

- **攻击对象:** D1 (b) 节第 0 环与图 2(QD 1–128 曲线)。
- **攻击内容:** D1 第 0 环原文:「机制侧的验证必须覆盖结构性行为(尺寸非线性、模式差异、队列、饱和)」,引 FAST '20 教训(brief-3 问题 2 [一手核实于简报])。但:回放引擎逐请求提交-等完成,有效并发恒为 1,queue_depth 上限在这条路径上不会被触及(实验分支核查报告第 3 节 [一手]);CD8P 标定走的 vmem 页错误路径没有 QD 旋钮;硬件-模拟器配对 QD 扫描 harness 不存在(核查报告 EQ1-C 行)。D1 的处置是把图 2 写成条件图(「仅在 E1.0 判定该介质可控 QD 时画」)——把自己链条宣布为必须覆盖的那一维,做成了可以静默消失的选做项。审稿人拿着 D1 自己引的 Empirical Guide 原话(失真根源在结构性行为)对照图目录,会发现四种结构性行为里排队/饱和一格是空的或条件的。
- **证据:** D1 (b) 第 0 环、图 2 说明;实验分支核查报告第 3 节、第 7 节 EQ1-C 行;brief-3 问题 2。
- **严重度:重大。**

### D1-4 E2.3 的 2×3 规模交叉表混着两个不同的适配器,回答不了 eq2

- **攻击对象:** D1 E2.3(TinyLlama × Qwen3-30B-A3B 的规模交叉 PoC)。
- **攻击内容:** 「小模型」格的 TinyLlama 用例只存在于 llama.cpp 适配器上,该 proof 明写不声称不透明 kernel 被改写,注入是 10 次固定 50 ms 延迟(项目 CLAUDE.md 第 4 节(7) [一手]);「大模型」格是 vLLM 适配器加实测曲线模型与覆盖门。两格之间变的不只是模型规模,还有框架、覆盖机制、注入形态——交叉表读出的「差异随规模拉开」无法归因给规模。eq2 的答案(「小模型跑最高精度、大模型跑快速」)要成立,必须在同一适配器内取两个规模(如 vLLM 上 Qwen3 家族两档),D1 没有这样设计。
- **证据:** D1 E2.3;项目 CLAUDE.md 第 4 节(7);facts-for-design.md L26–30。
- **严重度:重大。**

### D1-5 图 1(b) 承诺的延迟 CDF 叠画,模型侧给不出诚实的分布

- **攻击对象:** D1 图 1(b)(实测对模拟的延迟 CDF)。
- **攻击内容:** 实测曲线档存的是每尺寸的 P50(标定为最近秩 P50/P95,每目标 11 样本,facts-for-design.md L37 出处),注入是确定性延迟——模型侧的「分布」是每尺寸一个点质量,CDF 是台阶函数。与实测的连续 CDF(含尾部,如有界 fsync P50 408,305 ns 一类的长尾)叠画,图本身会暴露模型没有方差与尾部模型。先例里 CDF 对齐是分布层面的主张(MQSim 真实 trace CDF、Cylon 双峰形状,brief-2 综合一第 10 条);画了这张图等于主动邀请「你的尾延迟误差是多少」的问题,而三档引擎里只有 MQSim 档有分布输出,vmem 曲线档没有。要么不画、要么换成只对 MQSim 档画并写明,D1 现在的写法两头都不占。
- **证据:** D1 图 1 说明;facts-for-design.md L37;brief-2 综合一第 10 条。
- **严重度:重大**(承诺了一张会反噬的图)。

## 三、对候选 D2 的攻击

### D2-1 E3-c「排序不变性」是模式间内部一致性,被包装成可信度证据,先例引用是错位的

- **攻击对象:** D2 E3-c 与贯穿性主张链「E3 证明便宜模式给出与高保真模式相同的排序」。
- **攻击内容:** E3-c 比较的是同一套 profile 输入喂给 fast 档与 reference 档的排序一致性。两档共享同一份器件参数,且在 HBF 工作点(tR 1–20 µs、N 至 15,000、带宽至 3 TB/s)上没有任何一档被任何实测验证过——D2 自己采纳的限制条款写着「fast/hybrid 的误差只在 held-out 范围内成立」(C0 §15.2),而 held-out 范围是 CD8P 的 µs–ms 软件路径。两个未验证模型在验证范围之外互相吻合,证明的是实现共享代码,不是「拿它做比较不会做反」。D2 引 Accel-Sim 与 Sieve 作先例,但两者的排序验证都是模拟对硅片(Accel-Sim 逐计数器对 nvprof,Sieve 明写「not through simulation」,brief-2 §5、§10 [一手核实于简报])——先例支持「sim 对真值」的排序验证,不支持「sim 模式对 sim 模式」。这正是题面点名的「模型对模型互证冒充对真值验证」,而且被放在旗舰位置。
- **证据:** D2 E3-c、总骨架主张链;C0 §15.2(D2 采纳);brief-2 §5(a)、§10(a)。
- **严重度:致命。** 基准化卖点(「便宜档保序」)的证据形态在方法学上不成立,审稿人识破后连带质疑整章的验证意识。

### D2-2 把 reference 路径的可信度「接到 MQSim 的 FAST'18 验证上」——接不上,PR#3 就是反例

- **攻击对象:** D2 (b) 节链条第 3 步的那句话(「把 reference 路径的可信度接到 MQSim 的 FAST'18 验证上而不冒领」)。
- **攻击内容:** 三层断裂。第一,MQSim FAST'18 验证的量是请求响应时间,定义为从提交队列入队到完成队列收到响应(brief-2 §4(a)),包含主机接口层;我们的 reference 只取其闪存介质模型、绕过 NVMe/PCIe/SATA/驱动层(facts-for-design.md L23)——被验证的端到端量与我们使用的截段不是同一个量,验证背书不随截段转移。第二,验证介质止于 2016–2017 年 MLC/TLC(读 75 µs/编程 750 µs,brief-2 §4(a)),我们喂进去的 HBF profile 是 SLC、tR 1–20 µs,在其验证介质之外——brief-2 §4 专门为此写了警告段。第三,也是最硬的一条:PR#3 刚刚证明我们的集成可以让 MQSim 的一整层配置(queue_depth)被解析、校验、写入却从未生效,所有旧运行等效无限并发,修复后同一基准 p50 从 205,820 变成 659,840 ns、带宽从 166.9 掉到 50.9 GB/s(facts-for-design.md L45 [转述])——三倍量级的错误在「已验证组件」里静默存活了整个实验期。D2(以及 C0、D1)都没有安排那个便宜而决定性的实验:同一请求流分别喂 MQSim 原生全栈配置与我们的截段适配器,报两者的偏差。没有这个实验,「不冒领」只是一句话。
- **证据:** brief-2 §4(a) 与其 HBF 适用性警告段;facts-for-design.md L23、L45。
- **严重度:致命**(reference 是 E5 矩阵的参考时序、E2 Pareto 的准心、hybrid 抽样的去处;它的资格问题传染全部三个候选,D2 因把这句话写成链条正步而首当其冲)。

### D2-3 E1-c 的 Quartz 类比缺了 Quartz 的关键零件,降级路径退化成再拟合一条曲线

- **攻击对象:** D2 E1-c(6787p 已知延迟复现)及其降级路径。
- **攻击内容:** Quartz 的验证是:同一组程序在注入平台与真实高延迟机器(跨 NUMA)上各跑一遍,比应用级性能,0.2–9%(brief-3 1e [一手核实于简报])。复刻这个形态需要同一负载既能真实地跑在目标介质上、又能在 DRAM 上跑注入版——即需要后备介质可切换的页服务(或 GPU 能直接访问该介质)。D2 的 E1-c 依赖列表里只写了「6787p 访问权限」,没有列这个前提;若 Gate 1 查出 CXL SSD 只呈现块设备形态,GPU 页服务压根到不了它,E1-c 的「同一负载对比」无从谈起。降级路径(CD8P 上第二条独立软件路径,不同文件系统/io_uring)更糟:那是给同一台设备再标一条曲线、再验一次拟合,真值仍然是软件路径测量,不是 Quartz 那种「已知延迟的独立参照」——类比的说服力来源(真值独立于被验模型的产生过程)在降级后消失,而 D2 把降级写得像是等价替代。
- **证据:** D2 E1-c 与降级路径;brief-3 1e;实验分支核查报告第 7 节 EQ1-A/D 行(hardware-backed 后端无选择 harness)。
- **严重度:重大。**

### D2-4 四到六个档案上算 Spearman,统计上是空转

- **攻击对象:** D2 E3-c 的相关系数;连带 C0 §6.8 的 rank ≥0.90 门槛与 D1 E1.3 的排名相关。
- **攻击内容:** E3-b 的命名档案是四篇论文加 OCP 包络,n=4–6。样本这么小,任何一次反序就把相关系数拉到远低于 0.90,而即使完全一致,常规显著性检验也无从谈起——先例 Accel-Sim 的相关系数建立在 80 个负载、1,945 个 kernel 实例上,Sieve 也是整套 Cactus+MLPerf(brief-2 §5、§10)。三个候选都写了 rank 门槛或排名主张,没有一个写明 n、也没有一个的实验矩阵能提供两位数以上的可排序配置。把 rank ≥0.90 写进论文而 n=5,审稿人一行字就能打掉:「这个相关系数没有统计意义。」
- **证据:** D2 E3-b 档案清单;C0 §6.8;D1 E1.3;brief-2 §5(a)、§10(a)。
- **严重度:重大**(D2 首当其冲,因为排序保真是它的贯穿主张)。

### D2-5 E1-b 的 3/3 重切分:512 页那个「留出点」其实是外推点,弱点 2 换了个名字回到论文里

- **攻击对象:** D2 E1-b(取 1/16/256 页拟合、4/64/512 页留出)。
- **攻击内容:** 512 页在新标定集最大点(256 页)之外,对它的预测是按末段斜率外推——这正是项目已知弱点 2 明文标注的无实测支撑区(facts-for-design.md L40)。把它算进「held-out 误差」有两种结局:误差大,拉坏整个 held-out 汇总;误差小,则是拿外推点冒充内插验证,审稿人对照曲线在 64–512 页间的强非线性(标量模型在此区间从 −93.99% 恶化到 −99.93%)会追问模型形式是什么时候定的。这引出更根本的一点:6 个断点自 2026-08-11 起全文公开在 proof 文档里,任何「事前冻结的切分」都是在分析者看过全部数据之后做的——模型族选择已经泄漏了 held-out 信息。真正干净的 held-out 只有一种:模型冻结之后新采的离网格点(8/32/128/384 页与随机模式),D2 把它和重切分并列,11 天压力下最可能活下来的恰是不干净的那一半。
- **证据:** D2 E1-b;facts-for-design.md L37–41;proof 文档六断点表(项目 CLAUDE.md 第 4 节(1))。
- **严重度:重大。**

## 四、三个候选共同的盲区

**盲区 1:被验证的引擎不是产出 HBF 头条数字的引擎,传导链中间有一道没人接的缝。** CD8P held-out(三个候选的可信度基石)验证的是 fast 路径的实测曲线档,而且验证对象是含页错误、驱动、缓存插入的端到端软件路径(facts-for-design.md L40,弱点 5)。HBF 投影数字(C0 的相图、D1 的 E3、D2 的 N×tR 旗舰图)出自 MQSim 介质模型、解析组织计算或参数化 fast 模型——这些引擎从头到尾没被 CD8P 数据碰过。三个候选都用「机制已验 + 参数是投影」的 Quartz 句式,但 Quartz 的机制(epoch 末注入自旋延迟)在验证和投影里是同一个机制(brief-3 1e);我们的不是:验证的机制是曲线回放,投影的机制是排队模拟或解析公式。要堵这条缝,至少需要一个「同一请求流喂两个引擎、报偏差」的跨引擎一致性实验,现状是连一致性检查代码都不存在(facts-for-design.md L31),三个候选无一安排。

**盲区 2:MQSim 的裁判资格没人重新审。** 见 D2-2 的三层断裂,这里只补传染面:C0 把 MQSim 列为 reference hierarchy 里的「可解释参考」,D1 在 E3 降级路径里用重跑后的 MQSim 数字做「模拟侧锚线」,D2 的 E5 矩阵拿 MQSim 参考时序当四个必跑点的真值档。三者都在把一个对 2016–17 年 NAND 全栈验证过、刚被 PR#3 证明在我们的截段集成里可以整层失效而无人察觉的组件,当成不需要再检验的真值来源。便宜的补救实验(截段适配器对 MQSim 原生全栈,同流对比)在三个候选里都不存在。

**盲区 3:parity 图的比较量从未被定义,而未拆分的开销就坐在里面。** 每个候选都承诺 predicted-vs-measured parity 散点,没有一个写明纵轴取哪个时间域:`modeled_device_service_ns`(纯模型输出,但硬件侧的实测是含软件路径的端到端时间,两者不同质)还是墙上时间(含未拆分的每 warp 请求路径开销,facts-for-design.md L29,弱点 6)。取前者,比较两侧口径不齐;取后者,「模型误差」里混着模拟器开销。`hbfsim_stats_v2` 提供了七类分开的时间域(实验分支核查报告第 5 节),但没有候选把「先用 stats v2 定义 parity 的比较量、再谈误差」写成前置步骤。对保真度一章,这是审稿人最容易抓、最难当场补的一处含混。

**盲区 4:「一行配置近邻」检查,三个候选都没做。** 对外:FEMU(0.5–38% 已验证,延迟可配)、NVMeVirt(对四台真机 ≤12.2%,target 延迟/带宽是配置项,并用改配置扫参做过数据库案例)、Cylon(直接复用 FEMU 的已验证 NAND 时序)都能用一份 HBF 参数 profile 产出主机侧微基准保真图——三个候选的最大篇幅证据(微基准 held-out)没有一个强制经过 GPU 注入路径,于是没有一张主图是近邻工具改一行配置做不出来的。对内:15 号 item 1 被三个候选一致登记为「依赖不存在的代码」,但冻结分支的 profile 已有 channels/dies/planes/read_latency_ns 字段、`hbf_mqsim_bench` 已有 --bytes/--pattern/--arrival-gap-ns(实验分支核查报告第 7 节 EQ1-B/EQ3 行)——N×tR 扫描离「改配置就能跑」有多远,没人核过;这既可能意味着 E3 比排期便宜,也意味着「别人必须经过我们的平台」这句基准化论证要重新掂量,因为它可能只是一次配置扫描。

**盲区 5:器件状态与时间的混杂变量,统计协议全体失守。** 标定数据采于 2026-07-30,held-out 将采于 2026-09——同一块 CD8P 隔六周,无预处理协议(MQSim 先例:70% 逻辑空间、两个 4 小时阶段;Amber:顺序写满进稳态),无「重测一个标定点作漂移对照」的控制;本项目自己的实测证明这台机器的数字随热状态漂移 −8.10%(facts-for-design.md L51),而三个候选里只有 C0 的 E5 运行闸门(温度快照、GPU 独占)部分覆盖了模拟侧,硬件侧微基准的温度与写入历史控制在三个候选里都是空白。held-out 误差一旦偏大,没人能区分是模型错还是器件漂了——这会把整个 held-out 论证变成不可解释的数字。

**盲区 6:门槛不达标时的「降级」在写作上不可执行,没人排练过。** 三个候选都写了措辞降级路径(定量→趋势→部件级),但降级触发的时点是 Gate 3 之后、截稿前数天,而降级动的是摘要、引言、贡献列表——不是评估章内部的措辞。没有候选准备了「趋势版」的摘要与贡献列表草稿,也没有候选回答:如果 CD8P held-out 中位误差落在 FEMU 量级(百分之几十),论文的核心贡献句(实测标定)怎么改写。降级路径守不守得住,取决于降级版论文是否提前存在;现状是三份计划里它都只是一行字。
