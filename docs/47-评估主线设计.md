# 评估章主线设计:四个实验怎么论证模拟器可信

## 五句话总览

这五句是给所有读者的最短版本,不含数字与出处;逐条论证见下面各章。

HBF 说到底就是一大摞同时读写的 NAND 闪存,今天就买得到的 NVMe 闪存盘,是同一个家族里最弱的那一台。快的那一层根本不用模拟,程序本来就真跑在 GPU 自己的显存里,要模拟的只有慢的那一层。我们先让模拟器去算这台弱盘,拿模型定死之后才新测出来的真实数据考它,考过了,这套机制就是对的。机制一个字不改,只把并行度和介质延迟这些参数从弱盘的换成 HBF 规范给的,同一套办法就能算出那台还不存在的器件,推出去的部分明写是算的。换来的是不用等器件送样,今天就能回答把模型权重挪到这一层上、推理会慢多少。

## 零、结论与要点(只读这一节)

先定义三个后面一直用到的词。**live** 指应用照常在真实 GPU 上执行、模拟器在执行过程中施加时序与容量效应,不是先把访问序列记录下来事后回放。与 live 相对的是 **trace-driven replay**,也就是先记录一串页访问、事后把这串记录喂给时序引擎算出时间。**留出集(held-out)** 指模型冻结之后才采集、拟合过程物理上读不到的一组测量点,只有这类点上的误差才算验证。

### 三句话说清评估章怎么论证模拟器可信

1. 我们把「可能出错的东西」切成两半:注入机制可以拿今天买得到的真实器件验证,HBF 的介质参数只能是投影,两半分开报。
2. 每个引擎都被指定了一台真实硬件当它的参照物,谁参照谁写死在方法节里,达不到误差门槛就把措辞降一档,不删实验。
3. 被验证过的机制能做到查参数表做不到的事,所以别人以后研究 HBF 时,可以直接用我们的器件档案与参考结果来定位自己的假设。

三句话各自的展开在第一章(实验怎么做)、第三章(微基准怎么串成论证)与第五章(对用户三个关切的直接回答)。

### 近五年的做法,一句话

近五年八大系统会场的模拟器论文里,没有一篇是只靠注入延迟的构造分析、不锚任何真实硬件通过评审的;目标硬件买不到只是做模拟器的动机,不是免验证的理由,所以我们不但要找物理硬件,还要按「复现现有实验结果」来组织 E1(展开见第二章)。

## 一、四实验主线

**这一章的结论:四个实验按依赖顺序排,E1 是其余三个的前提,每一个都预先写好了失败时的降级写法。** 顺序是 E1 机制保真、E2 保真度的价格、E3 假设档案与 N×tR 投影、E4 路由翻转测验与 dense/MoE 适用范围。E3 与 E4 在正文里各有一句话写明它们依赖 E1 验证过的机制、误差界随 E1 走。执行细节、人天排期、删减顺序与决断点在附录 A。

下面每个实验按同一个顺序写五项:回答审稿人哪个问题、设计要点、核心图、已有数据、降级路径。

### E1 机制保真(mechanism fidelity)

**E1 不是「不找物理硬件、只根据注入延迟做分析」。** E1 用三台真实硬件,做三类「复现现有实验结果」。三台硬件分别是 Dell CD8P NVMe 固态盘、6787p 机器上的 CXL SSD、6787p 上的 DRAM;三类复现分别是复现 CD8P 实测延迟曲线在留出点上的值、复现真实器件的排队与饱和行为、复现真实后备存储带来的端到端减速。

三台硬件各自的角色写死如下。**CD8P** 是主参照,三类复现全部在它上面做。**6787p 上的 CXL SSD** 视第 0 天的能力盘点结果决定,盘点通过就作为第二台参照器件,盘点不通过就退出主线(先决检查写在本节末尾)。**6787p 上的 DRAM** 只用来量插桩开销的下限,不当保真度的验证器件——它的访问延迟太小,量到的绝大部分是插桩本身,理由在第五章 (b) 节按四件事写全。

**回答审稿人的哪个问题。** 用审稿人的口吻:「你的六个标定断点误差为零,是因为那六个点本来就是拟合输入。HBF 不存在,你拿什么证明注入机制对任何真实器件是准的?你的真值是什么?被验证的到底是哪个引擎——产 HBF 数字的那个,还是另一个?」

**正文呈现纪律。** E1 在正文里必须写成一个实验的内部分段,不得写成六个并列实验——否则违反用户「4 个大实验」的逐字上限。下面每一类复现后面括注它在执行清单里的子块编号(E1.2、E1.4、E1.3),附录 A 与附录 C 按这套编号排人天与去向。

#### 复现一:复现 CD8P 实测延迟曲线在留出点上的值(子块 E1.2)

在 CD8P 上采 12 个尺寸的顺序读:1、2、4、8、16、32、64、128、256、384、512、768 页。原来的 6 个断点(1、4、16、64、256、512)保留为标定集,在 parity 图上画空心点;**parity 图**指横轴放硬件实测值、纵轴放模型预测值的散点图,点越贴近对角线说明模型越准,图注写明这些点是拟合输入、不计入误差。模型冻结之后新采的 6 个离网格点(2、8、32、128、384、768)是**唯一用来判定误差门槛的留出集**,其中 768 页把「512 页之外全是外推」的那段区间变成实测,单独报告、不并入留出汇总。

留出集里包含一个由 GPU 发出的子集,走真实的 PTX 改写路径;hbf_vmem_sequential 用例链路已经存在,六断点对齐检查本身就是这个形态 [一手,项目 CLAUDE.md 第 4 节(2)]。这是 NVMeVirt 与 FEMU 无论填什么 profile 都产不出的证据形态。预处理协议照 MQSim 与 Amber 的先例做:顺序写满,把 SMART 写入历史写进 manifest [一手核实于 brief-2 §4 与 brief-4 (b)];另外重测一个 2026-07-30 的标定点作漂移对照。3/3 重切分降为稳健性附注,模型族见过全部数据这件事在方法节如实声明。

**为什么模式类测量不能进留出集。** 这是本轮红蓝对抗里最有价值的攻击之一,按四件事写清楚。

第一,说的是什么。留出集是模型冻结后才采、拟合过程读不到的点,只有它上面的误差算验证;模式类测量指 random、strided、反向、重复这几类访问模式下的测量,与顺序读相对。

第二,不这样做会看到什么具体错误结果。模式类模型没有任何自由参数——随机、反向、重复、跨操作的访问一律把突发长度重置为一,也就是全部按单页 11,133 ns 计,没有实测依据 [一手,事实清单标定现状]。它的误差在采数据之前就能算出来,量级是 −74.8%(常数页模型在 64 页处误差 −74.77% [一手,docs/proofs/2026-08-11-cd8p-vmem-tuning.md])。把一个误差已知在 −74.8% 量级的点放进留出集,只会有两种结局:要么按门槛表把全篇措辞降档,要么在采完之后把这些点从留出集里拿掉,而后者直接违反事前冻结。

第三,别人怎么处理。MQSim 用微基准反推真实 SSD 的内部参数,验证之前有两个 4 小时的预条件化阶段 [一手核实于 brief-2 §4];Accel-Sim 用 38 个微基准喂自动调参器之后另设验证集 [一手核实于 brief-2 §5];FEMU 主动报告误差随并发复杂度增长并给出归因,单线程单 plane 是 0.7%,16 线程 16 plane 是 38% [一手核实于 brief-2 §3]。共同做法是:参与拟合的维度与用于验证的维度分开,而完全没拟合过的维度照测照报为已知边界,不冒充验证。

第四,这个结论到哪里为止。模式类测量改入**特征化集**——一组照测照报、但不参与误差门槛判定的测量点,用来画出模型在哪些区间可信、哪些区间只能定性。门槛表只对顺序读的留出集生效。配一条负载侧论证:本文负载的未命中流由专家内部连续页主导,每 token 884,736 次页访问里只有 384 页(0.04%)真正不可预测 [转述,prefetch-accuracy-sweep artifact]。一旦以后补上随机模式的实测标定、让模式类模型有了自由参数,这些点就可以回到留出集。

#### 复现二:复现真实器件的排队与饱和行为(子块 E1.4)

在 CD8P 裸设备上用 fio 与 io_uring 扫队列深度 QD∈{1,2,4,8,16,32,64,128},同时用同一个到达过程喂 hbf_mqsim_bench 驱动的 MQSim 引擎,报带宽、P99 延迟与 saturation knee 三项的误差。**saturation knee** 指带宽随队列深度上升到不再明显增长的那个拐点。复现的对象是真实器件在并发压力下的行为形状,不只是某一个平均延迟值。

这是 MQSim 档唯一的硬件参照,也是唯一能防住 PR#3 那类问题的实验形态。那次问题的形状是:profile 里的 queue_depth 字段被解析、被校验、被写入,但 MQSim 只在 SATA/NVMe 接口下读这个字段,HBF 接口下从未读过,所有旧运行等效于无限并发,而且每一次运行都照常产出结果、不报任何错。修复后同一基准的 p50 从 205,820 ns 变成 659,840 ns、建模带宽从 166.9 GB/s 变成 50.9 GB/s [转述,拉取代理读 commit 12ef138 对照数字]。回放引擎恒定 QD=1 的限制不适用于这条合成到达路径 [一手,核查报告 §3 与 §7];删减顺序①触发之后,这一项是 MQSim 档仅剩的硬件参照,因此列为不可删项。

#### 复现三:复现真实后备存储带来的端到端减速(子块 E1.3)

先说这一类复现在做什么。容量模式下,GPU 侧缓存未命中要去一个**后备存储**取页,后备存储是调用方给的一个文件路径。同一个负载跑两遍:一遍把后备存储接到真的 CD8P 文件上,量真实器件给墙上时间带来的增量;一遍把后备存储留在 tmpfs 上、改用 CD8P 标定档来施加时序,量模拟给墙上时间带来的增量。**两个增量必须对上,这就是这一类复现要复现的东西。**

配置写死成三条臂,「臂」指同一组对照实验里的一个配置条件,三条臂之间只差一处配置。臂一是 tmpfs 后备存储加 epsilon 档,**epsilon 档**指把配置档里所有时序参数取成最小合法值(例如 read_latency_ns=1 ns)的一份配置,用作零延迟对照。臂二是 CD8P 文件后备存储加 epsilon 档,此时真实器件的延迟从页服务路径进入墙上时间。臂三是 tmpfs 后备存储加 CD8P 标定档。两个差分量取 C0 §5.2 的公式 [一手]:ΔT_HW 等于臂二减臂一,ΔT_SIM 等于臂三减臂一;报 normalized slowdown 的误差与配置排名的一致性。

**这条差分走的正是容量页服务路径,也就是别人采纳 HBFSim 时真正会用的那条交付路径。** 红队指出过一种常见毛病:验证的是一条路径,交付给用户的是另一条路径。三臂差分把验证路径与交付路径对齐,不存在这个缝隙。6787p 上的 CXL SSD 若第 0 天的能力盘点显示可用,作为第二设备臂加分,不作为主线前提。

#### 三类复现之前要过的四项先决检查(子块 E1.0,不进正文,只在方法节留一句话)

四项先决检查在第 0 天做完,任何一项没过就不采留出数据。第一,epsilon 档验证:实测它的残余建模时间,≤111 ns(单页实测 11,133 ns 的 1%)即接受为零延迟臂,配置校验拒绝的是 ==0 而不是小值(src/profile/profile.cpp:330)[一手,核查报告 §3]。第二,后备存储选择脚本(修复件编号 F2):容量模式的后备存储是调用方给的文件路径,机制上可以指任意设备,缺的只是一个选择脚本 [一手,核查报告 §7 EQ2 行]。第三,time_scale=1 复测 reference 基准点(修复件编号 F7):reference 验证默认 time_scale=100,是 164.70x 这个数字的来源之一 [转述,spec L420]。第四,hbf_mqsim_bench 的 channels/dies/planes 三个字段对「并行读出单元数 N」的语义映射探针;该工具已有 --bytes、--pattern、--arrival-gap-ns 三个开关 [一手,核查报告 §7 EQ1-B 行]。

与四项检查并行执行的是 Gate 1,也就是 19 号规划给「清点 6787p 机器上有哪些设备、各自是什么形态」这一步起的编号,命令清单(lspci、cxl list、daxctl、numactl 等)见 C0 §5.1 [一手]。Gate 1 不阻塞主线,它的结果只决定 CXL SSD 这台硬件进不进第二设备臂。另外定义一个后面会用到的词:**Snapshot B** 指把强制放行开关等全部运行时小改一次性合并成的一个冻结代码快照,第 2 天冻结,此后分析侧的离线脚本(留出切分、误差计算、绘图)不触碰运行时,因此不会引发实验重跑。

**E1.1 语义与覆盖。** 三项一致性照搬已有证据:vLLM 的 token ID 逐位一致、llama.cpp 的确定性文本一致、容量模式 checksum `14245581564465502923` 与基线一致 [均一手,docs/proofs/2026-08-11-hybrid-complete.md 与 2026-08-11-vllm-exact-live-delay.md]。覆盖统计(10,339 条覆盖决策、30 条被改写指令、0 条不支持指令 [一手,vllm-exact-live-delay])改按字节而不是按 launch 数报覆盖比例;按字节统计当前未实现 [一手,核查报告 §7 EQ1-A 行],划归论文侧的分析脚本。PR#4 的覆盖语义在冻结快照上验证 [一手,核查报告:PR#4 经 80fd29c 集成,936b8e5 补跨行 PTX 扫描];超显存 110 GiB 的一行证据放在这里,限定照抄原文,不声称 110 GiB 被物理读过 [一手]。

**E1.5 三档同流对照。** 把同一份容量未命中流(JSONL 文件)分别喂给 fast、hybrid、mqsim 三档,报逐流偏差;回放引擎已经支持 `--mode fast|hybrid|mqsim` 读同一份未命中文件,基础设施只差跑一次 [一手,核查报告 §3]。另有半件:把同一请求流喂给 MQSim 原生全栈配置,与我们的截段适配器对比并报偏差;这半件排在删减顺序①,触发时转为 artifact 里的复算项。

**E1.6 强制放行对照。** HBFSim 的覆盖门是 fail-closed 的,也就是遇到不支持的指令直接拒绝运行,而不是悄悄跳过。E1.6 加一个强制放行开关,跑出「这道门值多少」的数值;蓝队合并稿漏排了这次对照运行本身,裁决补为 0.5 天,item 7 是 blocking 项 [一手,事实清单工作单节],不进删减顺序。

### E2 保真度的价格

**回答审稿人的哪个问题。**「reference、fast、hybrid 三档如果成本差不多,谁都会用最高精度,三档设计就是过度工程;反过来 fast 若很快,误差是多少?我在什么规模下该选哪一档?」这正是用户对 eq2 的担心的正面回答。

**设计要点。** time_scale=1 复测(F7)之后才动笔。载体是同一个 vLLM 适配器、同一个模型(Qwen3-30B-A3B),覆盖 3 档(16 KiB、单专家、可行的最大档,依赖 item 14 的分批注册)乘以三种模式,画「建模请求数 × 墙上时间」。时间按四段拆开,用 hbfsim_stats_v2 的七类时间域,带 valid_fields 位掩码 [一手,核查报告 §5 c48feef]。

61 GB 全量注册不可行这件事 [一手,vllm-exact-live-delay] 一律标注为「当前集成的实现限制,不是保真度的机制成本」。纯插桩开销下限 37–51%(0.8898 s 对 1.4156 s 与 1.8269 s)[一手,vllm-timing-adapter] 报为任何一档都逃不掉的机制成本。Pareto 图逐点标出覆盖档;两根轴若来自不同配置,就拆成子图并在图注里写明每根轴的出处。hybrid 的旋钮扫描(热身 1,024 与抽样率 1% 各 3 档 [转述,spec §9.3])降为日程有余时才做的项。

**载体不是「小模型对大模型」。** TinyLlama 那一格走的是 llama.cpp 适配器,与 vLLM 那一格不可归因于模型规模,所以驱动变量改成同一适配器下的建模请求数。用户设想的「小模型跑最高精度、大模型跑快速」在证据上落地为「低建模请求数跑 reference、高建模请求数跑 fast 或 hybrid」,这一点要向用户说明。

**核心图。** 图 3 双联,按通栏排。左格是堆叠条形,四段分别是 native、插桩、服务路径、建模,覆盖 3 档乘三种模式。右格是误差与墙上时间的散点图,误差取 E1 的留出误差,reference、fast、hybrid 三档用固定的视觉编码,逐点标出覆盖档;这种误差对加速的平面画法取自 Sieve [一手核实于 brief-2 §10]。

**已有数据。** 基线 0.269996 s、fast 2.014352 s、reference 44.469084 s(164.70x;fast 对 reference 是 20.8x,两次 token ID 一致)[一手,hybrid-complete 与 vllm-exact-live-delay];插桩开销下限 37–51% [一手];61 GB 全量注册不可行 [一手]。**这几个数字全部要等 F7 核验口径之后才可以引用**,而且引用 164.70x 时必须同时写明 time_scale 口径,以及「建模介质延迟与每 warp 请求路径开销尚未分离」[一手,项目 CLAUDE.md 弱点 6]。

**为什么 164.70x 要先过 time_scale 复测。** 这是全案最大的一处**测量假象**风险——测量假象指量出来的差距其实来自实验设置本身,不是被测对象的性质。按四件事写清楚。

第一,说的是什么。time_scale 是 reference 路径上的一个时间缩放系数;reference 验证默认取 100,负载运行默认取 1 [转述,spec L420]。F7 指用 time_scale=1 重新测一遍 reference 基准点这件修复措施。

第二,不这样做会看到什么具体错误结果。20.8x 与 44.469084 s 两侧原始 manifest 的 time_scale 口径目前没有记录(缺,需合作者补,见附录 B 第 1 条)。如果 reference 那一侧带着 100 倍缩放,而正文把它写成「保真度的运行成本」,那么 E2 整节、以及用户 eq2 的整个取舍论题,都建立在一个可能被 100 倍放大的数字上;审稿人只要问一句「你的 reference 跑在什么时间缩放下」,这一节就没了。反过来,若复测显示差距坍缩,现在的三档设计论据就得换一套。

第三,别人怎么处理。Cylon 的做法是设一条把 NAND 延迟置零的控制臂,把仿真器自身开销与被建模的介质时间分开量 [一手核实于 brief-2 §1];Ganger 等人在 FAST '02 的做法是在目标器件尚不存在时,把模拟的服务时间与仿真器自身开销分开报告(**未核原文**,仅 C0 §17 登记;进 refs.bib 前必须按 verify-paper-sources 抓原文)。我们的 epsilon 档就是同一种控制臂。

第四,这个结论到哪里为止。F7 只解决口径记录这一件事,它不解决「建模介质延迟与每 warp 请求路径开销合并报告」这个已知弱点 [一手,项目 CLAUDE.md 弱点 6];那一条要靠 stats v2 的七类时间域拆分,拆不开就把限定句照写进正文。

**限定与措辞门槛。** 墙上时间刻画的是模拟器,不是对 HBF 硬件的投影,README 的自注原句照引:「These wall-clock ratios characterize the emulator, not projected HBF hardware.」[一手,经大纲 35 转录]。两条路径之间目前没有一致性检查代码 [转述,16-questions #4],所以只声称成本差异与旋钮效应;大纲里三处「可检验的一致性」的许诺改口径为「E1.5 的实测偏差加 token 一致」。

**降级路径。** F7 若显示差距坍缩,选档论据换轨到三个与 time_scale 无关的实测事实:37–51% 的插桩开销下限、profiling 阶段的同步请求导致 61 GB 注册不可行、reference 逐请求同步路径上覆盖与成本的线性放大(均 [一手]);两个分支的稿子都预先写好。覆盖档做不齐,就只留 16 KiB 一档加线性外推并明确标注——用户已明示接受「理论估算 or 最小 poc」[一手,事实清单用户裁定]。

### E3 假设档案与 N×tR 投影

**回答审稿人的哪个问题。**「HBF 的参数 OCP 规范上都印着,你的输出不就是把参数表抄一遍?社区为什么需要这个平台,而不是一张 Excel?」

**核心主张(来自 15 号文件)。** 规范 Table 2 的 3072 GB/s 是 UCIe 接口值;阵列一侧的可持续速率取决于规范没有给出数值的并行读出单元数 N。按 Table 3 的组织方式算出来是 262.1 GB/s(tR=4 µs)到 52.4 GB/s(tR=20 µs),比接口值低 11.7 到 58.6 倍 [一手,15 号文件经事实清单 L74]。带宽是模拟的输出、不是查表可得——这一句既是可信度论证,也是基准化论证。

**E3-a:N×tR 扫描。** N 取 {256, 1024, 3000, 15000},tR 取 {1, 2, 4, 5, 10, 20 µs},走配置扫描。第 2 天按先决检查的探针结果决断:channels×dies×planes 对 N 的语义映射若成立,就是配置加脚本,约 1 天;若不成立,退回解析计算 262.1–52.4 GB/s 加一条 MQSim 参照线,图改标 computed, not simulated。item 1 的主路代码不存在 [一手,事实清单 L73],但合成到达这第三条路是存在的 [一手,核查报告 §7 EQ1-B 与 EQ3 行]。

**E3-b:假设档案重演。** 把已发表论文的参数组合做成以论文命名的器件档案,四个档案分别是 flashaccel-like、micron-like、tilelens 区间、OCP 包络档。flashaccel-like 取 tR=4 µs、SLC、4 KB 页 [一手核实于 brief-1 §1(b)];micron-like 取 20 µs [一手核实于 brief-1 §4(b)],页大小该格写「缺,需合作者从原文补」——该文未给页大小值;tilelens 区间扫 1–20 µs,正文主用 5 µs [一手核实于 brief-1 §2(b)];OCP 包络档按 item 15 用规范公布数字重新取值,解掉弱点 8——现在的 aggressive 档是 1 TB/s、1 TiB,低于规范顶档约 3.0 TB/s、单堆 512 GB [一手,项目 CLAUDE.md 弱点 8]。**按 2 页的新页数账,四个档案的逐档说明整块进附录,正文只留一句主张加一张图。**

重演在真实的容量未命中轨迹上进行,用回放引擎的 mqsim 档逐档跑,整节标注 trace-driven replay,与 live 数字分开报。选这个载体的原因是缓存命中、逐出与排队的相互作用让结果无法查表复算;若换成 24 次确定性建模启动那个载体,审稿人可以用计算器复算出同一张表。每个档案的每一格都要带出处,没有出处的格写「缺,需合作者从原文补」。page_bytes 一律按原文的 4 KiB 重校验:回放引擎当前把未命中展开成 16 KiB 页请求 [一手,核查报告 §3],与先例和我们自己的手算差 4 倍,受影响的回放单元要重跑。

**E3-c:模式间一致性检查。** 档案排序在 fast 档与 mqsim 档下各算一遍,排序统计报样本量 n 与精确置换检验的 p 值(n=6 完全一致时单侧 p≈0.0014);门槛只对 n≥10 的容量矩阵单元(6 个容量比 × 3 种政策 × 负载 [一手,核查报告 §1])生效,小 n 只报数不设门槛;真值一侧的排序由 CD8P 留出配置上的小 n 报告补上。**这一项不再当作「验证」来卖。** Accel-Sim 与 Sieve 的排序验证都是对硅片做的,模拟器对模拟器的互证会被 PKA 的原话正面反驳:「Simulator versus simulator validation limits the workloads that can be validated...」[一手核实于 brief-2 §9(e)]。

**裁决新增的一条限定,正文必须写。** 在阻塞回放(QD=1)下,档案重演只能区分各档案的**延迟一侧**的假设;带宽与 N 一侧的区分只能来自合成到达扫描路径,做不上就标为解析结果。

**为什么 E3 不裁决他人已发表的结论。** 这一处的呈现形态被红队判为致命,改判之后才成立,按四件事写清楚。

第一,说的是什么。E3 把已发表论文的器件参数装进我们的框架重演,输出的句式一律是条件式:「若接受某档案的参数,则结论 X 在区间 Y 内成立或不成立」。输出不是「某篇论文的结论是错的」。

第二,不这样做会看到什么具体错误结果。E1 的误差界是在 CD8P 的端到端软件路径、顺序读、QD=1 条件下得到的,它不延伸到 N×tR 的外推区域。拿一个在那片区域没有验证过的组件去判定别人已发表的结论,审稿人会要求把整段删掉;红队 3 的 D2-1 就是按这个理由判的,裁决同意。

第三,别人怎么处理。Pond(ASPLOS '23)给出 182% 与 222% 两档以及 158 个负载的分布,不下单一裁决 [一手核实于 brief-3 问题 3];Mnemosyne(ASPLOS '11)用条件式结论加两点扫描 [一手核实于 brief-3 1c];PMEP(PMFS,EuroSys '14)与 NOVA(FAST '16)用两个命名档位(STT-RAM 与 PCM)把未知器件的取值范围框在中间 [一手核实于 brief-3 1a/1b]。E3 的命名档案就是同一个谱系。

第四,这个结论到哪里为止。E3 提供的是一套定位坐标系,全图标注 projection,并加敏感性带——对未验证的 MQSim 排队参数取一个合理区间扫出上下界,代替假的误差棒。一旦真实 HBF 器件到手,或者规范补上 N 的数值,同一张图就可以换成实测判定。

**核心图。** 图 4:横轴是 tR(对数轴),纵轴是稳态阵列带宽(或画 N×tR 等高线),已发表论文的工作点带引文标出,3072 GB/s 接口值画一条水平虚线,全图 projection 标注加敏感性带,外推区用浅色底纹标出。图 5:各命名档案下同一条容量轨迹的重演条形,标 trace-driven replay;图 4 与图 5 按通栏合并到同一个图版,删减顺序②触发时图 5 撤到附录或 artifact。

**已有数据。** 262.1–52.4 GB/s 的推算 [一手,15 号文件];各论文的参数,例如 FlashAccel 的 4,916 个 plane 匹配 4.8 TB/s [一手核实于 brief-1];超显存 110 GiB 的一行证据,限定照抄 [一手];MQSim 介质基准修复后 p50 659,840 ns、50.9 GB/s [转述,PR#3 对照数字]。

**限定与措辞门槛。** 全部是投影。N 的四个取值逐个写明来源:两个来自规范组织,两个是反推出来的需求量。重演的是「该论文的器件参数装进我们的框架」,不是复现该论文的完整系统。

**降级路径。** 探针失败,则改走解析计算加 MQSim 参照线,核心主张的措辞从「带宽是模拟的输出」改为「按规范组织推导、模拟侧以 MQSim 参照线佐证」——这句话怎么写列入用户过目项 #25。E3-b 若触发删减顺序②,撤到附录或 artifact。

### E4 路由翻转测验与 dense/MoE 适用范围

**回答审稿人的哪个问题。**「假设驱动的方法在哪里会得出错误结论?HBF 到底适合哪类模型、到什么程度?」

**翻转测验的设计。** 假设驱动的预测取 paper/37 那张独立均匀路由推算表(批 1 触及 6.2% 专家、72.3 tok/s,到批 128 触及 100%、4.5 tok/s;该文件自标「全部是推算」[一手,paper/37])。实测一侧用真实的逐序列路由,再做跨序列的独立组合:冻结的轨迹 schema 没有到达时间,契约锁定 max_num_seqs=1 [一手,核查报告 §2 与 §5],所以并发下的专家并集由约 32 条 prompt 的真实单序列轨迹独立组合而得,独立性假设明写在图注里。对照的零假设是 1−(1−k/E)^B。

**两个分支的稿子都预先写好。** 分支一,实测偏离推算表,偏离幅度足以改变「HBF 在该并发档到底可行不可行」的判断:那就是 Accel-Sim §VI 那种翻转案例 [一手核实于 brief-2 §5],并且可以用条件句回应 li2026 的「介质延迟改善 3.75 倍只让端到端变化不到 1%」(该文唯一的单变量对照组 [一手核实于 brief-1 §5(d)])——那个结论成立于介质延迟被掩盖的配置,我们给出它不被掩盖的区域,也就是低驻留、高 tR、低 N。分支二,实测与推算表吻合:产出变成「均匀路由假设的适用边界标定」,同样可以发表。

**dense 对照。** 同家族的 dense 模型做一次轨迹采集,报每 token 权重字节的对照。匹配方式取 C0 §8.4 的辨析 [一手]:激活计算量匹配优先,容量匹配写进 limitations。外部对照数字有三组:TileLens 的原句「All configurations remain memory-bound for Qwen due to MoE routing, whereas Llama transitions to compute-bound at a batch size of 256」[一手核实于 brief-1 §2(e)];Micron 的「weights-first 下 HBM+HBF 与 HBM-only 差 <0.4%,只有专家卸载才让 HBF 被用到」[一手核实于 brief-1 §4(e)];li2026 的逐模型数字(大 MoE 端到端变化 +280–285%,小 dense +184.1%),引用时带上「非单变量」与「容量账有缺口」两条限定 [一手核实于 brief-1 §5(e),按文档 44 的规矩]。dense 模型具体选哪一个,缺,需合作者定(建议同家族 dense 档)。

**预取纪律。** 一切数字标注 modeled 或 trace-level;运行时收益一律不写——冻结协议里 E9 = prohibited [一手,核查报告 §1],撤回门槛的原话照守 [转述,paper/36:76]。

**核心图。** 图 6 双联,按通栏排:(a) 实测的专家并集覆盖率对实测并发,叠画零假设虚线与 paper/37 推算表的点;(b) dense 与 MoE 的每 token 权重字节随并发变化。图注写明独立性假设,以及条件式的适用范围结论。

**限定与措辞门槛。** E4 的定位是 insight,不与保真度争地位,开头一句话写明「本节结论依赖 E1 验证过的机制,误差界随 E1」。只有一个模型家族;并发是组合估计,不是共同调度的实测;E4 的数字是字节数与并集的计数事实,不是时序预测。

## 二、近五年,模拟买不到的硬件怎么过验证关

**这一章的结论有三条。** 第一,「只做注入延迟分析、不锚真实硬件」在近五年八大系统会场零先例,这么做不合理,我们也没这么设计。第二,Quartz(Middleware '15)只用来说明论证的形状,真正支撑我们这套做法的先例是 2018 到 2026 这一批。第三,「尽可能复现现有实验结果」正是 E1 的组织原则,也就是第一章那三类复现。

这一章回答的是用户的原话:「你的意思是指我们不应该找其他物理硬件, 直接根据注入延迟分析吗? 这样合理吗, 15年论文能中一部分是他太早了没有那么严格, 查找最近5年论文看这么做合适吗, 请你给出分析. 我要求尽可能复现现有实验结果.」

本章的核实等级用两个标记:**[近五年调查一手]** 指调查代理亲手读到原文、主 agent 未亲核;**[近五年调查转述]** 指调查代理自己也标为二手的内容。调查报告 2026-09-04 产出,核对脚本 21/21 通过、退出码 0,证据落盘 `/root/hbfsim/tmp/simulator-validation-survey/`。

### 处境跟我们最像的那一篇:CXL-DMSim

CXL-DMSim(arXiv:2411.02282,当前版本 v7,页面原句「last revised 11 Jan 2026 (this version, v7)」;期刊版 IEEE Transactions on Computer-Aided Design of Integrated Circuits and Systems,TCAD 2025,DOI 10.1109/TCAD.2025.3607145)的处境与我们几乎一样:目标器件买不到。它自己在摘要里就这么写:「CXL is still in its infancy stage and lacks commodity products on the market, thus necessitating a reliable system-level simulation tool for research and development」;正文另有一句「there are currently no market-ready prototypes of CXL-based memory-disaggregated systems; CXL commodity products are also expensive to produce and purchase」[均 近五年调查一手]。

**关键在于它接下来做了什么。** 它没有因为「买不到」就免掉验证,而是找了两台真实器件当真值:一台是 CXL-FPGA,原文写「an Intel Agilex I-Series FPGA Development Kit with an integrated hard CXL IP」(16GB DDR4-3200,CXL 1.1,呈现为没有 CPU 的 NUMA 节点);另一台是自研 ASIC 器件(两个 CXL 内存控制器,128GB DDR5-4800)[近五年调查一手]。时序参数的标定原句是「have been meticulously calibrated and fine-tuned using end-to-end latency measurements on our hardware testbed」;带交换机那一档没有真件,改为对齐 XConn 公布的性能实测值 [近五年调查一手]。

误差报到逐负载:全负载平均模拟误差 3.4%(原句「The averaged simulation error is measured at 3.4% across all workloads in our experiments」),最小 1.9%(MERCI),最大在 Viper;STREAM 带宽建模误差平均约 4.3%;并引其他论文自报的数字作对照,Mess 6.0%、gem5Tune 6.2%、原生 gem5 15.0% [均 近五年调查一手]。它还把自己的失效区间写进正文:128MB 到 384MB 工作集区间的延迟持续高于真件实测,归因于 gem5 的 LLC 模型,并引文献称该 LLC 模型误差可达 56.4% [近五年调查一手]。这一条正是我们第三章第 3 步「误差地图」要照做的形态。

**它的评估章顺序也值得照抄。** 第 IV 章依次是实验设置、Usability and Fidelity(LMbench 延迟对齐、STREAM 带宽对齐、真实应用 Redis/Viper/MERCI 对齐)、收益探索、拥塞分析、可扩展性;第 V 章是讨论,依次是模拟开销、模拟误差(对测试台与对同类模拟器)、与其他模拟器的对比表 [近五年调查一手]。对比表的结论原句是「CXL-DMSim is the only one which has undergone extensive silicon validation」[近五年调查一手]。**对我们的含义是:「真值来自哪台真实器件、误差是多少」要放到与它第 IV-B 节同样显眼的位置。**

### 另外几篇近年工具论文,验证一律落在真实硬件上

四篇的形状一句话列全:Mess 在六家厂商的真机上实测带宽-延迟曲线族;uPIMulator 的模拟对象本身就是买得到的商用硬件;Virtuoso 对真实服务器 CPU 与真实 Linux 内核验证;再加上已经一手核实过的 NVMeVirt、Cylon、CXLMemSim、Pond、TPP,同一条规律。

- **Mess**(MICRO '24,arXiv:2405.10170)。基准在「Intel, AMD, IBM, Fujitsu, Amazon and NVIDIA servers with DDR4, DDR5, HBM2 and HBM2E memory」真机上实测出带宽-延迟曲线族,模拟器「closely matches the actual system performance」[近五年调查一手,摘要级]。
- **uPIMulator / Pathfinding**(HPCA '24,arXiv:2308.00846)。模拟对象是买得到的 UPMEM 商用 PIM 硬件,结果与真机对齐 [近五年调查一手,摘要级]。
- **Virtuoso**(ASPLOS '25,arXiv:2403.04635)。对真实服务器 CPU 与真实 Linux 内核验证,原句「models the IPC performance of a real high-end server-grade CPU with 21% higher accuracy than the baseline version of Sniper」[近五年调查一手,摘要级]。

### 反例检索:零命中,以及唯一一个不锚真件的同类模拟器去了哪里

调查用了六组检索词,方向覆盖「模拟器论文自称无法验证」「新兴硬件不存在」「注入延迟」「针对 Mess、uPIMulator、Virtuoso、QIsim 的定向核查」。**结论是:在 2021 到 2026 年 FAST、OSDI、SOSP、ASPLOS、ATC、ISCA、MICRO、HPCA 正式发表的模拟器与仿真器工具论文里,没有找到一篇只靠模型构造或注入分析、不锚任何真实硬件通过评审的** [近五年调查一手]。检索是抽样覆盖、不是穷举,这一点如实写明,但方向一致到值得当规律用。

最有说服力的对照是 DRackSim(arXiv:2305.09977),一个机架级内存分解模拟器,验证只做到「An incremental approach is followed to validate the core and cache subsystem of DRackSim with that of Gem5」——对另一个模拟器验证、不锚真件 [近五年调查一手]。它没有发在上面那八个会场,后续版本发表于 ACM SIGSIM-PADS 2024 [近五年调查转述,会场信息来自 ACM 页与 Penn State 记录,dblp 接口两次 503 未一手核对]。CXL-DMSim 的对比表也把 DRackSim 与 DisaggSim 列为未做硅验证的一类 [近五年调查一手]。**也就是说:不锚真件的同类模拟器是存在的,但它们出现在仿真方法学会场或 arXiv,不在这八个会场。**

一个边界情况如实报:QIsim(ISCA '23,量子控制处理器模拟,目标是确实不存在的万级量子比特低温控制硬件)。一手核实仅限它的 GitHub README:工具链锚在后布局综合(Design Compiler)与 SPICE 级仿真(JoSIM)上;检索结果转述它的验证方式为「已有工作加后布局分析加真实量子机实验」,论文验证节本身未一手读到 [近五年调查转述]。即便按转述,它也不是零真实锚点——锚在已流片的工艺库和真实量子机上,而且它属于架构设计论文,与存储、内存模拟器工具论文不同类。

### 旁证:器件一旦买得到,同类论文就不再接受模拟

- **HeMem**(SOSP '21,DOI 10.1145/3477132.3483550)。标题本身带「…and Real NVM」;作者自己写的 NVMW '22 扩展摘要原句是「We run our evaluation on a single socket of a dual-socket Intel Cascade Lake-SP system… Each socket has 192 GB of DDR4 DRAM and 768 GB of Intel Optane DC NVM.」[近五年调查一手,SOSP 正文在付费墙后未直接取到,引句出自作者本人的 NVMW 扩展摘要]。它还批评前人「evaluated with emulated NVM and does not capture the performance characteristics of commercially available NVM」——**用模拟的 NVM 做评估,在真件时代反过来成了被指出的缺陷。**
- **MEMTIS**(SOSP '23,作者公开 PDF)。测试台是「server equipped with Intel Xeon Gold 5218R @2.1 GHz processors (20 cores)」,每路 6×128GB Intel Optane DCPMM;两种配置,一种是真实 Optane,另一种是「2) DRAM + emulated CXL memory (crossNUMA DRAM with increased latency, load: 177ns)」[近五年调查一手]。**买得到的器件(Optane)必须用真件,买不到的器件(当时的 CXL)允许跨 NUMA 加延迟模拟,但只作为补充配置**,这与 Pond、TPP 是同一个模式。

### 三条结论,直接回答用户的问题

**第一,不锚真实硬件不合理,而我们也没这么设计。** 近五年顶会的模拟器与仿真器工具论文,验证关的通行做法是找一个真实的近亲当真值——买得到的真件、FPGA 原型、自研 ASIC、厂商实测数字,至少三者取一,然后报出逐负载的误差百分比 [近五年调查一手]。目标硬件完全买不到时,标准做法是用最接近的真实载体标定:CXL-DMSim 用 FPGA 原型加自研 ASIC,Cylon 复用已验证的 FEMU 时序加真实 CMM-H 原型趋势对齐,Pond 与 TPP 用跨 NUMA 加厂商确认。所以 E1 一定要有物理硬件,而且第一章已经写死了三台:CD8P、6787p 上的 CXL SSD(视盘点)、6787p 上的 DRAM(只量插桩开销下限)。

**第二,用户对 2015 年那批论文的判断我们接受,承接方式是把它降为形状参照。** Quartz(Middleware '15)在真实 NUMA 机器上把注入机制验到 0.2%–9% 误差、参数明说是投影 [一手核实于 brief-3 1e],我们引它只为说明「机制与参数分开验证」这个论证形状。真正支撑我们做法的先例全部落在 2018 到 2026:MQSim 与 FEMU(FAST '18)、Accel-Sim(ISCA '20)、NVMeVirt(FAST '23)、Pond(ASPLOS '23)、Mess(MICRO '24)、uPIMulator(HPCA '24)、Virtuoso(ASPLOS '25)、CXL-DMSim(TCAD 2025)、Cylon(FAST '26)。**误差门槛也按这一批取,不按 2015 年那一批取。**

**第三,「尽可能复现现有实验结果」这条要求,正是 E1 的组织原则。** 三类复现逐条对应:复现 CD8P 实测延迟曲线在留出点上的值,对应 CXL-DMSim 的 LMbench 延迟对齐;复现真实器件的排队与饱和行为,对应它的 STREAM 带宽对齐与拥塞分析;复现真实后备存储带来的端到端减速,对应它的真实应用对齐(Redis、Viper、MERCI)。差别只有一处,如实写明:它的三类对齐都在同一台真实器件上做,我们的三类复现分布在 CD8P 一台盘上、第二台器件视盘点结果,单盘限制写进 limitations 不加修饰。

## 三、微基准怎么论证模拟器可信

**这一章的结论:微基准本身不构成可信度论证,把它们排成一个前后传导的顺序才构成——前一步的结论是后一步的前提。** 这一章回答用户的原话「我们做了很多 micro benchmark,但是如何用这些 Micro benchmark 来论证我们的实验的模拟器是准确的?我还没想好」。传导方式写死,不许跳步;每一步都写清证据形态与先例出处。

六步先一句话列全:第 0 步(前提)机制与参数分离;第 1 步校准与验证分离;第 2 步跨器件与跨引擎参照;第 3 步误差地图;第 4 步应用级留出差分;第 5 步排名保真。

### 第 0 步(前提)机制与参数分离

把「可能错的东西」切成两类:注入机制可以对真实器件验证,介质参数对 HBF 只能是投影。Quartz(Middleware '15)就是这么写的——在真实 NUMA 机器上验证注入机制复现已知延迟的能力,误差 0.2%–9%,参数明说是投影 [一手核实于 brief-3 1e]。

反面教训来自 FAST '20 的 Empirical Guide:Optane 一代模拟失真的根源不在参数取值错,而在「这个器件就是慢一点的 DRAM」这个结构性假设错。该文的判决原句是「all of these emulation methodologies are inaccurate」;真器件的内部粒度是 256 B,RocksDB 的结论在真器件上直接反转 [一手核实于 brief-3 问题 2]。**所以机制一侧的验证必须覆盖结构性行为——尺寸非线性、模式差异、排队、饱和——不能只对一个平均延迟。**

### 第 1 步 校准与验证分离

对应复现一(E1.2)。证据形态是:事前冻结的标定集与留出集划分写进 artifact manifest,拟合脚本物理上读不到留出数据;正文只报留出误差的中位、P95 与最大值;parity 图上标定点空心、留出点实心;六断点零误差降格为一句「实现没把参数表读错」。

先例三条。MQSim 用微基准反推真实 SSD 的内部参数,验证之前有两个 4 小时的预条件化阶段 [一手核实于 brief-2 §4];Accel-Sim 用 38 个微基准喂自动调参器之后另设验证集 [一手核实于 brief-2 §5];brief-2 的综合判断第 1 步写的是「每个微基准让单一机制主导」[一手核实于 brief-2]。

### 第 2 步 跨器件与跨引擎参照

单器件的留出通过只证明了「这条曲线拟合得好」。所以要写死哪个引擎由哪个硬件参照:实测曲线档由 CD8P 留出集(含 GPU 发出的子集)参照;MQSim 档由复现二(E1.4)的队列深度配对、E1.5 的同流偏差、以及原生全栈对照参照;应用级由复现三(E1.3)的三臂差分参照,而三臂差分走的是交付路径。方法节里放一张显式的映射说明,写清哪个实验参照哪条路径。

DRAM 在这个顺序里只用来量插桩开销的下限,不作为保真度的验证器件,理由在第五章 (b) 节展开。范围论证是:HBF 的 tR 落在 1–20 µs 这个域 [一手核实于 brief-1],亚微秒级的验证不是 HBF 主张所需要的。先例四条:MQSim 对四块匿名真实 SSD 做队列深度与请求大小的验证 [一手核实于 brief-2 §4];NVMeVirt 对四类真实设备做到 ≤12.2%,而且先证明「仿真质量优于 FEMU」再谈保真 [一手核实于 brief-4 (a)];Ganger 等人在 FAST '02 提出目标设备不存在时把服务时间与仿真器开销分开(**未核原文**,仅 C0 §17 登记);Cylon 的 NAND 延迟置零控制臂 [一手核实于 brief-2 §1]。

### 第 3 步 误差地图

不假装全域有效。random 与 strided 按单页计的已知偏差(−74.8% 量级)照测照报,写成一张地图:哪些尺寸、模式、队列深度区间可信,哪些区间只能定性。真正参与误差判定的那一维是顺序读,负载论证是每 token 884,736 次页访问里只有 0.04% 不可预测 [转述,prefetch-accuracy-sweep artifact]。

先例两条。CXL-DMSim 把自己的失效区间写进正文——128MB 到 384MB 工作集区间的延迟持续高于真件实测,并归因于 gem5 的 LLC 模型(引文献称该 LLC 模型误差可达 56.4%)[近五年调查一手,arXiv:2411.02282 v7 全文;此条上一稿标为未核原文,本轮已由近五年验证调查读到原文]。FEMU 主动报告误差随并发复杂度增长并归因,单线程单 plane 0.7%,16 线程 16 plane 38% [一手核实于 brief-2 §3]。

### 第 4 步 应用级留出差分

微观误差到宏观主张,是测出来的,不是算出来的——访问之间的重叠让解析传播不可信。做法是 ΔT_SIM 对 ΔT_HW 的差分对比,加 Spearman 排名相关,不比原始墙上时间(C0 问题 D [一手])。措辞按门槛表分档,每个应用级数字旁边标注它走到了哪一档。

先例三条。Cylon 用 normalized slowdown 与定性趋势通过了 FAST,全文没有一个百分比误差数字 [一手核实于 brief-2 §1]——这是我们最差的落点。Quartz 的机制验证写法同第 0 步。FEMU 的宏观误差 0.5–38% 被接受,这是量级上的语境 [一手核实于 brief-2 §3]。

### 第 5 步 排名保真

对一个基准工具来说,「拿它做比较会不会做出相反的决定」才是别人引用时真正消费的性质。证据形态:排序相关一律报样本量 n 与精确置换检验的 p 值;≥0.90 的门槛只对 n≥10 生效;全体引擎对 tR 都单调时的一致是平凡的,这句告诫写进图注。

先例三条。Accel-Sim 的相关系数 >0.97,并在 §VI 给了两个「基线不准就得出相反设计结论」的案例 [一手核实于 brief-2 §5];Sieve 把相对精度单独立为一个评估维度 [一手核实于 brief-2 §10];SMARTS 的「可量化置信」表述可供 hybrid 抽样档谈误差界时引用 [一手核实于 brief-2 §6]。

### 这六步怎么收尾

E3 与 E4 只在 E1 与 E2 之后出场,正文一句话写明这个依赖;brief-2 的综合判断第 1 条统计到 10 篇先例里有 6 篇是以「先证准,再证准了才看得见的东西」收尾的 [一手核实于 brief-2]。

收尾还要有诚实的一面。10 篇先例里有 6 篇主动声明自己真值的缺陷 [一手核实于 brief-2 综合一第 7 条];我们对应地在正文自述三件事:六断点是构造出来的确定性检查、端到端 vmem 档不是介质档、随机模式没有实测依据。

## 五、对用户三个关切的直接回答

**这一章的结论:三个关切都有正面答案,其中一个(三模式成本差异)在复测之前不能写进论文。** 三个关切分别是三模式成本差异是否显著、6787p 物理介质怎么用进主线、dense/MoE 洞察实验放哪怎么写。

### (a) 三模式成本差异显著性

**已有数字已经显示差异巨大。** 同一个确定性 Qwen3-30B-A3B 用例:基线 0.269996 s、fast 2.014352 s、reference 44.469084 s,也就是 164.70x;fast 对 reference 是 20.8x [均一手,hybrid-complete 与 vllm-exact-live-delay]。而这还是只建模了 2,304 次启动中的 24 次、覆盖 16 KiB 的情况下的差距。

**但这些数字有一处必须先排除的测量假象:** reference 验证默认 time_scale=100 [转述,spec L420],而 20.8x 与 44.469084 s 两侧的口径没有记录(缺,需合作者补,附录 B 第 1 条)。所以 time_scale=1 复测(半天)是 E2 的先决检查,任何图表与措辞在它之前都不写;完整理由见第一章 E2 的四段说明。

**最小可行验证的设计:** 同一个 vLLM 适配器、同一个模型,覆盖 3 档(16 KiB、单专家、可行最大)乘三种模式,画建模请求数对墙上时间。曲线若分叉,选档的建议就有实测支撑;用户设想的「小模型跑最高精度、大模型跑快速」在证据上落地为「低建模请求数跑 reference、高建模请求数跑 fast 或 hybrid」。载体从模型规模改为覆盖档的原因是:换模型会同时换掉适配器,结果不可归因。

**坍缩分支也预先写好了,论题不会死。** 若 time_scale=1 下差距坍缩,选档论据换轨到三个与 time_scale 无关的实测事实:37–51% 的插桩开销下限 [一手];61 GB 全量注册在 profiling 阶段产生数量上不可行的同步请求 [一手];reference 逐请求同步路径上覆盖与成本的线性放大。

### (b) 6787p 物理介质怎么用进主线

用户的逐字要求是:「你要用6787p上的物理设施(如cxl ssd, or dram)等真实物理介质来模拟Hbf因为真的还没出来」。处置分三步。

第一步,第 0 天的 Gate 1 能力盘点,与主线并行、不阻塞。命令清单在 C0 §5.1 [一手]。机器身份目前是推断出来的(Xeon 6787P、256 GB DDR5-6400、实测延迟 116.1 ns、Smart CXL Module,由 docs/36 的一处顺带提及加上 CXLMemSim 的写法推出 [推断,事实清单]),须合作者确认,见附录 B 第 3 条。

第二步,按盘点结果分配角色。CXL SSD 若呈现 CXL.mem、DAX 或 NUMA 形态,就作为复现三(E1.3)三臂差分的第二设备臂,并提供第二条标定曲线,这是跨器件机制迁移论证的加分项。其上的 DRAM 作 epsilon 档与插桩开销下限臂。若只呈现块设备形态,就按阻塞语义回放对照,或者主线落在 CD8P 单设备上。

第三步,报告义务。Gate 1 的任何结果都要如实报告用户;用户这条约束在 Gate 1 失败时只能部分满足,这是一道显式的检查,不是把约束悄悄丢掉。

**为什么 DRAM 只能用来测插桩开销下限,不能用来验证模型保真度。** 这条被红队判为致命且蓝队全盘接受,按四件事写清楚。

第一,说的是什么。「保真度的验证器件」指拿它的实测延迟当真值,去判定模型预测的误差有多大;「插桩开销下限」指一次介质访问都不建模、只把注入机制挂上去就已经付出的那部分时间。

第二,不这样做会看到什么具体错误结果。6787p 上 DRAM 的实测延迟是 116.1 ns [推断,机器身份未盘点],而纯插桩开销把 0.8898 s 变成 1.4156 s 与 1.8269 s,也就是慢 37–51% [一手,vllm-timing-adapter]。在 116.1 ns 这个尺度上做逐请求注入,墙上时间里量到的绝大部分是插桩本身;报出来的所谓「模型误差」其实是插桩开销的表现,数字好看或难看都与模型准不准无关。

第三,别人怎么处理。Quartz 在真实 NUMA 机器上做机制验证拿到 0.2%–9%,因为它的注入粒度与 NUMA 的延迟量级匹配,而且它验证时用的机制与投影时用的机制是同一个 [一手核实于 brief-3 1e];我们不是——被验证的引擎与产 HBF 数字的引擎不是同一个,所以才需要复现二(E1.4)与 E1.5 把两个引擎接起来。Cylon 的做法是设一条零延迟控制臂,把仿真器自身开销单独量出来 [一手核实于 brief-2 §1],这正是 DRAM 在我们这里该扮演的角色。

第四,这个结论到哪里为止。它只说 DRAM 不能当保真度的验证器件,不说 6787p 没用。HBF 的 tR 落在 1–20 µs 域 [一手核实于 brief-1],CD8P 与 CXL SSD 都落在这个域里,所以它们可以承担验证角色。若哪天注入路径的开销降到百纳秒以下,这条结论要重算。

### (c) dense/MoE 洞察实验放哪、怎么写

**放哪:E4,倒数第一个实验,正文约 0.10 页**,与用户「倒数一个二个实验……helpful insight」的逐字定位一致。

怎么写才不与保真度争地位,五条。第一,开头一句话「本节结论依赖 E1 验证过的机制,误差界随 E1」,把它定位为整个论证收尾处的能力展示 [一手核实于 brief-2 综合判断第 6 条]。第二,证据形态是计数事实——哪些专家真被激活、权重何时读、读了多少字节——不是时序预测;这正是相邻三层工作共同缺的那一层(TileLens 的 trace 是真的但时序是模拟的,li2026 与 Micron 的专家行为全靠假设)[一手核实于 brief-1 综合判断]。第三,结论写成条件式的适用范围,例如「MoE 的流量优势存在于并发低于某阈值的区间,阈值由实测轨迹给出」,不写绝对判断。第四,外部对照数字全部带限定引用,li2026 按文档 44 的六条规矩;第五,预取的一切数字标注 modeled 或 trace-level,运行时收益不写。

翻转测验这个框架让 E4 同时反过来支持可信度故事——Accel-Sim §VI 的结论是不准的基线会导致错误的设计结论 [一手核实于 brief-2 §5]——而不占用保真度的证据位置。

## 附录 G 快的那一层为什么不需要替身:HBM、GDDR7 与 6787p

这一节回答用户的原话「6787p上有hbm吗? 如果没有hbm是否也要拿真实物理硬件代替?」,并把「用快速 NAND 介质模拟 HBF 很坏的一种状态」这个理解写精确。这里说的「替身」指拿一台今天买得到的真实器件,代替还没上市的 HBF 来当验证的真值。**结论先写:6787p 上没有 HBM,而且快的那一层本来就不需要任何替身。**

### G.1 快的那一层从来不被模拟

HBFSim 只对被登记为 HBF 的地址施加时序效应;同一次运行里没被登记为 HBF 的地址照常走显存原速,程序真跑在 GPU 自己的显存上 [一手,大纲 35「论文主张」C2 段]。所以快的那一层不是一个模型,它就是真机本身——它不存在「模拟得准不准」这个问题,也就不需要找一台真实硬件来当它的参照物。**要造替身的只有慢的那一层,也就是 HBF。** 第一章已经把这一层的替身写死:CD8P 是主参照,6787p 上的 CXL SSD 视 Gate 1 盘点结果作第二设备臂,6787p 上的 DRAM 只量插桩开销的下限、不当保真度的验证器件。

### G.2 6787p 上没有 HBM,跑实验的 GPU 上也没有

三条事实分开列,核实等级各自标出。

- 跑实验的 GPU 是 NVIDIA RTX PRO 6000 Blackwell(97,887 MiB 显存),显存介质是 GDDR7、不是 HBM [转述,合作者温度分支文档原句 "The available RTX PRO 6000 uses GDDR7" 与 "GDDR7 hardware must not be described as HBM"]。
- 6787p 即 Intel Xeon 6787P(Granite Rapids,86 核)。官方产品页给出的内存支持是 DDR5-6400 与 MRDIMM-8800、8 通道、上限 4 TB,没有 HBM [转述,Intel 官方产品页 https://www.intel.com/content/www/us/en/products/sku/241844/intel-xeon-6787p-processor-336m-cache-2-00-ghz/specifications.html]。
- 「共享机就是 CXLMemSim 论文里的 Server B」这层身份仍是 [推断],待第 0 天的能力盘点(Gate 1)确认。

因此对用户后半个问题的直接回答是:不需要。没有 HBM 这件事不构成缺口,因为快的那一层在我们这里从来不是被模拟的对象;真正需要真实物理器件的是慢的那一层,而 6787p 在主线里承担的正是这一层的角色(CXL SSD 作第二设备臂,DRAM 作插桩开销下限臂)。

### G.3 由此产生的两条披露义务,正文必须写

第一,我们的快层介质是 GDDR7。凡是依赖「快层与 HBF 速度之比」的结论,把快层带宽写成一个标明出来的参数,不写死成 HBM 的数。

第二,论文里容量模式现在叫「HBM 缓存」的那个部件要改名,改成「显存页缓存(device-memory page cache)」一类的说法,不把 GDDR7 称作 HBM。

### G.4 「用快速 NAND 介质模拟 HBF 很坏的一种状态」的精确版

**这个理解是对的,精确的说法是:CD8P 相当于 HBF 参数家族里并行度最低的那个角。** 它不是一块坏掉的 HBF,而是同一族参数取到最低并行度那一端的取值。

定量注脚如下。稳态读带宽恒等式是「带宽 = 并行读出单元数 × 页大小 ÷ 介质延迟 tR」。CD8P 实测顺序读 7.577–7.587 GB/s [一手,docs/proofs/2026-08-11-hybrid-complete.md],在 tR=4 µs、4096 字节页下折合约 7 个并行读出单元 [推断,由前两个一手输入算出];对照规范 Table 3 的组织方式推出来的是 256 个 [一手,15 号文件]。

这个角与三个实验的对应关系写死如下,三项各自标明身份。

- 机制在这个够得着的角上验准,靠的是 E1 的三类复现。
- 并行度与介质延迟向规范包络推,属于投影,在 E3 里做并明标。
- 排队这一维由 E1.4 的队列深度配对扫描锚定。

### G.5 两句界线

不声称 GDDR7 等于 HBM。不声称 CD8P 等于 HBF。
