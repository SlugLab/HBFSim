# Stage 2 CPU HBF device read coalescing

Stage 2 adds an optional, separate `UcieDeviceFrontend` around the Stage 1 AoU/UCIe `StreamingLink` and the real patched MQSim CPU backend. It is enabled only with `HBFSIM_ENABLE_UCIE=ON` and `HBFSIM_ENABLE_MQSIM=ON`. The daemon and GPU producers do not select this frontend. Its real constructor and `ucie_device_bench` fail when the native backend is unavailable. The older `UcieMqsimFrontend` remains a cold-read baseline; the two real frontends share a process-global single-engine guard.

The topology-facing fields come from [OCP HBF Architecture v0.7](https://www.opencompute.org/documents/ocp-hbf-architecture-specification-v0-7-0-final-pdf) Figure 4 and §§4.2, 5.3.1, 5.9.2.1: host channels, NCDU 1/2/4/8/16, reference 16 banks per die, 4 KiB pages, and two 4 KiB buffers per bank. A [512 GiB reference configuration](../../configs/profiles/ucie/hbf-stage2-reference.json) uses 16 host channels/modules and 32 GiB of 36-bit module-local AXI address space per module. At this stage, that reference is **validated mathematically and parsed**, while real 512 GiB high-address MQSim reads and four-stack execution belong to Stage 3. The two-bank 8 MiB ON/OFF profiles are explicitly `scenario_assumption` CPU fixtures; reduced bank count is not an OCP product grade.

Each HBF bank is mapped to a distinct MQSim native chip with one native die and plane. This is an internal service-resource mapping, **not** an assertion that an MQSim chip physically equals an HBF die or that Figure 4's entire internal bus is modeled. For module-local 4 KiB page `q`, `native_lpa=q*host_channels+module_id`, `bank=q%banks_per_die`, `core_die=(q/banks_per_die)%NCDU`, and `native_chip=q%(banks_per_die*NCDU)`. The real FTL read-only bank query checks mapped PPA when present and CWDP cold placement otherwise; strict `COMMAND_ISSUED` observations independently check native channel/chip/die/plane, logical page, and 4096 media bytes. `MEDIA_BEGIN` and `MEDIA_END` measure actual native sense intervals. These checks are per active group and remain effective when bounded diagnostic records drop.

The frontend accepts only aligned, registered, read-permitted 64-byte regular reads. It resolves the full span to a canonical backing identity, generation, stack/module/endpoint, and page before acceptance. Explicit aliases can converge on one canonical page; forged expected media pages or generations, unregistered spans, unsupported operations, time reversal, and duplicate active IDs are rejected. AR stays a distinct AoU request and each successful reader receives its own 64-byte R. Compatible requests merge only while one canonical page read is *in flight*; cache reuse after completion is a separate switch, default OFF. A cold media miss reserves one of exactly two per-bank 4 KiB slots **before** MQSim submission. A third same-bank miss waits in a finite FIFO until a slot is released; another bank can progress. With buffer cache ON, unpinned completed pages occupy those two real slots and can serve later reads. The current replacement choice prefers an empty slot, then the lower indexed unpinned slot; this policy is a research assumption, not a specified HBF replacement rule.

`advance_until(horizon)` moves the simulation clock without consuming caller results; `poll_completion()` actually consumes one result and releases its R credit and buffer reference. The convenience `run_next_completion_until()` combines those operations. Cancellation and deadlines are **software caller lifecycle controls**, not hardware cancellation or OCP readiness timeout packets: an already transmitted AR/R and any submitted native read continue to drain. An expired caller receives one terminal result at its deadline unless an earlier same-AXI-ID response imposes an ordering barrier. A completed R not yet polled can still time out; its buffer remains pinned until the frontend internally consumes the physical R. Non-Ready media returns one software error with no fabricated 64-byte R payload. The frontend preserves modeled media completion as the R-ready time, separate from native raw callback, AoU serialization, and caller consumption. The legacy aggregate media service cap is not treated as UCIe bandwidth.

The [strict device schema](../../configs/schema/ucie-device.schema.json) exposes the sourced HBF topology and the explicit coalescing/cache fixture choices. It references the existing NAND timing profile rather than adding unrelated NAND/HBM tuning fields. The legacy `hbm_cache_bytes` field is required by the older `Profile` parser but is `NOT_USED` by this MQSim HBF flow. AoU v0.8 Appendix D labels the HBF profile under development; Stage 2 continues the Stage 1 granule/flit abstraction, without bit-level packet codec, CRC calculation, PHY training/retry, writes, bursts, ECC, or physical page-buffer hardware equivalence.

Run the [Stage 2 reproduction script](../../scripts/reproduce_ucie_stage2_cpu.sh) from this checkout on a CPU host with the pinned dependencies:

```bash
./scripts/reproduce_ucie_stage2_cpu.sh build-ucie-stage2 full
```

The script builds all default CPU targets, runs full CTest, and executes real MQSim ON/OFF eight-read fixtures; `focused` runs the relevant UCIe/MQSim subset. In either mode it checks 8 separate AR/R transactions, 1 versus 8 native page reads, 512 application and AXI payload bytes, 4096 versus 32768 submitted media bytes, and nonzero wire bytes in both directions. Different legal completion times can change packet packing, so ON/OFF wire totals are reported rather than forced equal. The [Stage 2 CPU checkpoint](../proofs/2026-09-29-ucie-stage2-cpu.md) records exact commands and raw output after final validation. These CPU results are engineering behavior checks, not GPU integration, NAND timing accuracy, or a hardware speedup claim.
