## Reproduction and results

The independent clean build was configured inside the feature checkout with CUDA OFF, MQSim and UCIe ON, evaluation tools and CTest ON, and the optional PkgConfig probe OFF. The equivalent commands from the checkout are:

```bash
cmake -S . -B build-stage3-clean-final -G Ninja \
  -DHBFSIM_ENABLE_CUDA=OFF -DHBFSIM_ENABLE_MQSIM=ON \
  -DHBFSIM_ENABLE_UCIE=ON -DHBFSIM_ENABLE_EVAL_TOOLS=ON \
  -DBUILD_TESTING=ON -DCMAKE_DISABLE_FIND_PACKAGE_PkgConfig=TRUE \
  -DCMAKE_DISABLE_FIND_PACKAGE_CUDAToolkit=TRUE
cmake --build build-stage3-clean-final -j 4
ctest --test-dir build-stage3-clean-final --output-on-failure -j 4
```

The fresh build compiled 248 Ninja actions and CTest passed **70/70**, zero failures, in 85.75 s host wall time. The exact console outputs are retained in the Stage 3 review package as `stage3-clean-config.log`, `stage3-clean-build.log`, and `stage3-clean-ctest.log`. The [reproduction entry](../../scripts/reproduce_ucie_stage3_cpu.sh) was then executed with `HBFSIM_BUILD_JOBS=2 bash scripts/reproduce_ucie_stage3_cpu.sh build-stage3-clean-final focused`: its incremental build, default-profile resolve, **9/9 focused CTest PASS**, and four raw comparison checks completed with exit 0 in `stage3-repro-focused-final.log` (CTest wall time 144.01 s). The source `src/ucie/stack_worker.cpp` implementing the 24-hour idle guard had SHA256 `f310a9a46e8616c4da77ad8493043c5a0242e1f7210cf4325ca1d83f36288af3` and last-write time 14:31:48 UTC, before the clean worker binary at 15:04:43 UTC and 70/70 terminal at 15:08:35 UTC. The subsequent focused build produced worker binary SHA256 `17122b1040019842bf0c5e5b5d30ad0801a90dbca13e7d2ce2fb9c5ea34ea308`. Its `capacity-one` and `capacity-four` modes instantiate large MQSim geometries; the separately executed capacity fixtures below retain their original output.

The [default top profile](../../configs/profiles/ucie/hbf-stage3-4x512gib-top.json) resolves to 2 TiB total, four 512 GiB stacks, 16 modules/stack and 32 GiB/module. Each module remains within the 36-bit local AXI address. The 512,000,000,000 B/s aggregate media service cap is a **scenario assumption** split exactly into 128,000,000,000 B/s/stack; it is not the UCIe wire rate. The independently exercised service-cap input gave 40,966 ns for 100,000,000 B/s versus 10,316 ns for 1,000,000,000 B/s with fixed link and NAND parameters and one real native read per stack. The resolved JSON and raw result are in the review package.

The real four-worker balanced fixture completed one native read on **each** stack. Its final modeled horizon was 10,324 ns, with 256 original, unique, and delivered AXI bytes; 16,384 B were actually submitted to four media engines. The raw per-worker PID, RSS, LPA, native count and four-layer byte accounting are retained as `stage3-balanced-raw1.log`.

The fixed comparison sent the same four 64 B reads in independent and shared-upstream modes. With balanced placement, each stack issued one native read; modeled completion was 10,316 ns independent and 10,324 ns shared. With a hotspot on one stack, the native counts were 4,0,0,0 and modeled completion was 41,246 ns independent versus 41,252 ns shared. Shared mode consumed real upstream wire bytes: balanced AR/R 1,024/1,792 B; hotspot 3,840/3,328 B. The independent mode had zero upstream wire bytes. All cases preserved 256 original and unique bytes, 256 delivered AXI bytes, and 16,384 submitted media bytes. This measured difference is small for the cold-page fixture; it does not support a fourfold-bandwidth claim. The complete four raw lines are [retained here](artifacts/2026-09-29-ucie-stage3-compare.txt).

The 512 GiB one-worker run actually read first and last pages, including native LPA `134217727`, with two native commands and measured worker RSS 4,331,076 KiB. The four-worker 2 TiB run had last LPA `134217727`, six native commands distributed 4,1,0,1 and per-worker RSS 4,331,100–4,332,340 KiB. The third worker was instantiated but issued no command in that boundary fixture; the separate balanced fixture proves all four active. The high-capacity console output is [retained here](artifacts/2026-09-29-ucie-stage3-capacity.txt). Neither run allocated 2 TiB of payload. A 512 GiB worker consumed about 4.13 GiB RSS in this configuration; four workers need substantial RAM margin. `final_h` is simulated nanoseconds, RSS is process memory, and any `.time` result is host wall time.

The parent validates each complete original access before splitting it into 64 B AXI transactions, preserves canonical identity/generation and actual requested byte count, then dispatches bounded child work. One worker per stack owns a separate MQSim event engine; all workers share one integer-ns simulated coordinate through conservative horizons and same-time fixed-point feedback. Host reassembly and shared-link credits are finite. Worker IPC and host scheduling time are not device delay. Real native observer records check LPA, command count, bank identity and five command phases. The fixture coverage includes physical-drain ID reuse, cancel/deadline and crash exactly-once terminal results, aliases, short original spans, reassembly backpressure, and same-time ordering. This does not implement full HBF page-buffer circuitry or all Figure 4 internal buses. AoU v0.8 Appendix D marks its HBF profile under development; this model is not a complete bit-level codec.

## Compatibility and limits

The unchanged legacy HBF `MqsimOnlineEngine(Profile)` public-API mixed read/write, queue, timestamp and observer fixture produced byte-identical JSON on old main and the Stage 3 tree. Original MQSim SATA and NVMe CLI read/write traces also had equal semantic reports on old and new builds. These are legacy-API compatibility checks; the new UCIe frontend itself remains read-only, and a legacy GPU daemon run must not be labeled new UCIe GPU integration. Legacy model GPU compatibility is a separate experiment with its own raw receipt and result.

The four time domains are native sense `MEDIA_BEGIN/END`, MQSim raw callback and modeled completion, AoU wire serialization/propagation, and caller consumption. The 1 ns conservative synchronization is a correctness implementation, not a physical HBF clock or CDC delay. CTest's 85.75 s, worker startup, IPC and host CPU time are wall-clock cost, not modeled hardware latency. Hardware timing accuracy, PHY CRC/retry, ECC, writes and burst reads, production GPU routing, and large-trace throughput are outside this Stage 3 CPU result. The exact unique-byte interval statistic becomes inexact if its fixed diagnostic limit is reached; that condition is exposed, never counted as exact closure.
