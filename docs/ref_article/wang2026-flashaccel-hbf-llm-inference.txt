Abstract

1

Large language model (LLM) inference is increasingly limited by the capacity of High-Bandwidth Memory (HBM) in
GPUs, as model weights and KV cache grow rapidly. HighBandwidth Flash (HBF) provides higher capacity than HBM
while retaining comparable bandwidth, making it a promising substrate for capacity-constrained LLM inference. However, its inherently high access latency, low bandwidth utilization, and lack of support for heterogeneous resource management make it difficult to integrate HBF into GPUs for LLM
inference. We present FlashAccel, a co-designed system that
enables efficient LLM inference using HBF. FlashAccel integrates HBF into HBM-based GPUs, providing architectural
support to mitigate access latency. It improves bandwidth
utilization through specialized data layouts for both model
weights and KV cache, and introduces an HBF-aware storage
management layer together with a programming model to organize persistent data in HBF and coordinate heterogeneous
memory resources at the system level. Experimental results
demonstrate that integrating six HBF stacks into the GPU
enables FlashAccel to deliver an average improvement of
2.54× and 1.93× in throughput per GPU and energy efficiency
over the HBM-only GPU under 100ms latency constraint,
respectively.

The rapid advancement of large language models (LLMs)
is driving inference workloads toward multi-turn interactions [17, 66, 70], agents [43, 56, 64], and long-context processing [7, 8, 36]. Two key trends emerge in this evolution.
First, model sizes continue to grow following the scaling
law [29], at the cost of drastically increased parameter scale.
Second, new workloads increasingly rely on long context
lengths, leading to substantial growth in KV cache footprints
during inference [9]. These trends fundamentally increase
the memory capacity requirements of inference systems.
However, the capacity of High-Bandwidth Memory (HBM)
in GPUs has not kept pace with the rapid growth of model
size. Figure 1 shows that, although GPU memory capacity
has increased steadily over time, the memory footprint of
popular models has grown much faster. Today, models can
exceed terabytes in size, far surpassing the capacity of a
single GPU, which is at most a few hundred gigabytes. Meanwhile, as the context length has grown by 4× on average over
the past two years [5], the storage overhead of KV cache has
increased proportionally by 4×.
The limited HBM capacity introduces several critical challenges in LLM inference. First, during the memory-bound decode phase, insufficient memory capacity restricts the batch
size, leading to low compute utilization and throughput. Second, the memory pressure often forces early eviction of KV

Background & Motivation

2.1

LLM Workload

LLMs consist of multiple stacked transformer layers [55],
each requiring storage for static model weights (shared across
all requests) and dynamic KV cache (isolated per request) [55].
LLM inference consists of prefill and decode phases with distinct computational characteristics [33, 67]. Prefill processes
all input tokens together, making it predominantly computebound. In decode, each request provides one token per step,
leading to frequent access to the model weights and KV
cache, which makes it memory-bound.
As KV cache grows over inference steps, most frameworks [33, 71] adopt PagedAttention-style mechanisms [33]
that partition KV cache into fixed-size blocks for fine-grained
memory allocation, reducing fragmentation and improving
memory utilization. Frameworks also manage KV cache eviction. Upon request completion, the computed KV cache is
retained in memory for potential reuse by future requests.
When memory is exhausted, the framework evicts history
KV cache to serve new requests.
2.2

Memory Capacity Bottleneck

The rapid growth of model weights and KV cache has made
GPUs’ HBM capacity a fundamental bottleneck for LLM
inference. This bottleneck directly limits the batch size in the
decode phase. Consider running Qwen3-32B [63] on an H100
GPU [40] with 80GB HBM. After reserving approximately
64GB for model weights, only 16GB remains available for KV

Recent works such as AiF [35], Lincoln [52], and CambriconLLM [68] use Flash for LLM inference. They store model
weights in Flash and place compute units within Flash to
exploit plane-level parallelism. These designs enable edge
inference, but are not suitable for high-throughput inference.
These designs provide only hundreds of GB/s bandwidth and
few TFLOPS of computational capacity, far below modern
GPUs. These limitations in both bandwidth and compute
capacity directly restrict inference throughput. Moreover,
they store only model weights in Flash but ignore the large
KV cache footprint.
A more promising approach to accelerating LLM inference
with Flash is to integrate a Flash device of high bandwidth
with the GPU, alleviating its capacity bottleneck. The key
to achieving high bandwidth is exploiting plane-level parallelism. An HBF can be realized by increasing the number
of planes per die (e.g., partitioning a die into 16 planes [46]),
adopting HBM-like 3D stacking [28] to enable parallelism
across multiple Flash dies, and leveraging TSVs to provide
high-bandwidth interconnects between Flash and GPUs.
The main concern with storing KV cache in Flash is endurance. For example, single-level cell (SLC) Flash typically
provides about 100K P/E cycles [30, 39, 59]. Prior works [35,
52, 68] avoid storing frequently updated KV caches in Flash
to circumvent endurance limits. However, recent advances
in attention mechanisms make storing KV cache in Flash
feasible. According to the DeepSeek report [15], the prefill
cluster (approximately 764 GPUs) writes 266 billion new
tokens per day 1 . Building upon these inputs, the decode
cluster (approximately 1,051 GPUs) generates an additional
168 billion tokens. Based on these statistics, each GPU in the
prefill cluster writes 22.7TB of KV cache per day, while each
GPU in the decode cluster writes 26.9TB of KV cache per
day. SLC Flash can provide about 55 P/E cycles per day over
a 5-year lifetime. Thus, a 1TB HBF device can sustain about
55TB of data writes per day, which is sufficient for the inference workloads. In addition, relaxing retention guarantees

Challenges

3.1

High Access Latency

Compared with HBM, Flash exhibits significantly higher
access latency. Even with high read bandwidth comparable to
HBM, the high read latency of HBF severely degrades end-toend performance. Using HBF, the GPU receives the first batch
of data roughly 4 𝜇𝑠 (tR) after issuing an access request [32],
whereas HBM requires only about 100 𝑛𝑠 [27], which is a
40× gap. For example, a 4k × 4k FP8 GEMV operation can be
completed on H200 in approximately 4 𝜇𝑠. When using HBF
instead, it incurs an additional 4 𝜇𝑠 access latency, leading
to a 50% end-to-end latency increase.

Low Bandwidth Utilization

Due to the inherent high read latency, Flash exhibits low
per-plane bandwidth (e.g., a plane reads a 4KB page in 4
𝜇𝑠, 1 GB/s). Achieving high aggregate bandwidth requires
exploiting parallelism across thousands of planes. For example, matching the 4.8 TB/s bandwidth of H200 requires 4,916
planes to read concurrently.
We define a hyper page as a logical access unit that aggregates one page from every plane. Accessing multiple hyper
pages sequentially can maximize inter-plane parallelism and
approach the peak bandwidth. When accessing data in HBF,
we define plane load as the number of pages that need to
be read from a plane. Since a plane serves page reads serially, the overall read latency is determined by the maximum
plane load across all planes. If data is unevenly distributed
across planes, some planes become idle earlier while others continue reading, reducing plane-level parallelism and
bandwidth utilization. The resulting bandwidth loss directly
prolongs memory-bound decode.
This issue is particularly evident in weight access. For
an HBF of 4.8 TB/s bandwidth, its hyper page size is about
19MB. However, Figure 4(a) shows that a weight matrix in
Qwen3-235B is only 12MB. As a result, accessing a single
weight tensor activates only a subset of planes, leading to
insufficient parallelism and bandwidth utilization. Although
accessing multiple weight tensors consecutively increases
data size beyond a hyper page, its benefit still strongly depends on data layout. Existing inference frameworks usually
store weights in the order of variable initialization in the
source code, rather than the order they are actually accessed
during inference. In case ① of Figure 4(b), when weights A,
B, and C are accessed consecutively, the source-code declaration order places D between A and B, yielding a maximum
plane load of 3. In contrast, case ② of Figure 4(b) achieves a
maximum plane load of 2. Therefore, reorganizing weights
by execution order reduces the maximum plane load by 33%
and correspondingly lowers access latency.

The problem is even more complicated for KV cache because its data layout changes at runtime. At each inference
step, the system accesses a unified KV cache constructed
from the KV caches of all active requests. Since active requests change over steps, even if the unified KV cache is
evenly distributed across planes at one step, the balance does
not persist. As requests complete and new ones arrive, the
KV cache distribution becomes imbalanced in subsequent
steps. As shown in Figure 5, requests 1–4 are processed in
the first step, and their KV cache is evenly distributed across
planes2 . In a later step, if requests 1 and 3 complete, only requests 2 and 4 remain active. The unified KV cache becomes
imbalanced across planes, yielding a maximum plane load of
3 versus an average load of 2, resulting in a 33% bandwidth
loss. This imbalance becomes worse over time. Due to the
paging mechanism and eviction process, the KV cache of a
single request becomes fragmented across multiple planes.
Meanwhile, the active request set at each step evolves in
a near-random manner, resulting in an imbalanced distribution of unified KV cache across planes. Assuming each
partitioned KV block of the unified KV cache is uniformly assigned to planes, the load can be modeled as a balls-into-bins
problem [44, 51]. Under this model, distributing 100GB KV
cache of Qwen3-235B across 4,916 planes causes the maximum plane load to exceed the average load by 52%, leading to
52% bandwidth loss. Furthermore, existing attention kernels
parallelize across requests, resulting in simultaneous reads
of all requests’ KV cache. This strategy fails to align accesses
at hyper-page granularity. As shown in Figure 5, attention
kernels may simultaneously access two requests’ KV cache

3.3

System Resource Management

The third challenge is system-level support for HBF. Unlike
HBM, HBF is non-volatile, so the system must support persistent data organization inside HBF for objects such as model
weights and KV cache. It also has to coordinate HBF, HBM,
and SRAM during execution. Existing approaches do not fit
the management of HBF well. Using an HBM-style paging
mechanism for data stored in HBF provides direct and lowlatency access, but it does not support persistence, because
page table mappings are discarded when the program terminates. Conventional Flash stacks support persistence but
incur metadata and latency overhead from layered address
translation [1, 10]. Moreover, as HBF bandwidth approaches
that of HBM, treating Flash as a lower tier behind HBM becomes increasingly inefficient because it forces unnecessary
staging through HBM. Instead, HBF should be exposed as a
directly accessible resource for GPUs, while SRAM is used
to hide Flash access latency. This requires a storage management layer for persistent data in HBF and a programming
abstraction for accessing heterogeneous memory resources.

4

Hardware Design

FlashAccel combines HBF, HBM, and GPU cores into a heterogeneous accelerator for LLM inference. FlashAccel can
be realized using either co-located integration (CLI) [46] or
cascaded integration (CSI) [23], as illustrated in Figure 6(a).
CLI places HBF alongside the GPU, partially replacing HBM
to increase overall capacity and lower HBM cost. CSI connects HBF to the GPU in a daisy-chain manner through the
HBM base die, preserving more HBM stacks and thereby
maximizing HBM capacity and bandwidth. In this heterogeneous memory system, HBM and HBF serve complementary
roles. HBM handles small, frequently updated intermediate data for its low access latency, while HBF stores large,
read-dominated data such as model weights and KV cache.
Figure 6(b) shows the HBF stack architecture. Each stack
contains 8 Flash dies above a base die, interconnected by
TSVs. Each Flash die integrates an array die and a circuit die

through hybrid bonding. Following [52] and [46], FlashAccel
increases plane-level parallelism by scaling each Flash die
to 96 planes. Figure 6(c) shows that HBF integrates SRAM
buffers in different dies as caches for data prefetch to mitigate Flash latency. According to [52], the circuit die contains
substantial unused silicon area. FlashAccel places SRAM in
this unused area, providing each plane with an SRAM cache.
For the base die, in addition to the NAND controller and PHY,
we also integrate SRAM cache, increasing the overall SRAM
capacity. Each stack has a total SRAM capacity greater than
2 × 𝑃𝑒𝑎𝑘_𝐵𝑎𝑛𝑑𝑤𝑖𝑑𝑡ℎ × 𝑅𝑒𝑎𝑑_𝐿𝑎𝑡𝑒𝑛𝑐𝑦 to support the Flash
data prefetch mechanism described in Section 6.2.3, ensuring the basic double-buffered pipeline. We target SLC-based
HBF for its lower read latency and higher write endurance.
Although SLC Flash provides lower bit density than multilevel cell (MLC) and triple-level cell (TLC), HBF still retains
a substantial capacity advantage over HBM.

5

Data Layout Design

Data layout design is the core of FlashAccel co-design, because achieving high HBF bandwidth utilization depends
not only on hardware capability, but also on whether data
accesses can be arranged to match Flash parallelism. Efficient
data layout enables data accesses in HBF to approach peak
bandwidth.
5.1

Weights in HBF

To expose HBF parallelism, FlashAccel places static weights
across all planes in execution order, balancing load and approaching peak bandwidth. Figure 7 illustrates the weight
layout strategy. For a given model architecture, the computation graph of each inference step is fixed, which enables
offline determination of the execution order. FlashAccel partitions each operator’s static weights into page-sized units
(e.g., A0, A1, and A2) and maps them across all planes and
channels in round-robin order. After mapping the current
operator, the system continues with subsequent operators
according to the execution order, starting from the plane
immediately following the last assigned plane of the current operator. As a result, the entire weight set is approximately balanced across planes from a global perspective.

KV Cache in HBF

The layout of the KV cache is more complicated than that of
static weights because the active request set changes at every
inference step. FlashAccel organizes per-request KV blocks
as a unified KV cache. This abstraction enables write, offload,
and read policies that balance plane load and preserve HBF
bandwidth.
At the beginning of a decode step, the unified KV cache can
be divided into two types of KV blocks. Resident KV blocks
are already stored in HBF from previous steps and have not
been evicted. Nonresident KV blocks must be written into
HBF from a remote KV cache pool or from newly generated
prefill outputs produced on prefill GPUs. As shown in Figure 8 ❶, FlashAccel aggregates nonresident KV blocks into as
many full hyper pages as possible and writes them to HBF to
improve inter-plane balance. Residual blocks that do not fill a
hyper page are placed randomly to avoid hotspots. Balancing
incoming writes is insufficient because resident KV blocks
may already be skewed across planes. This imbalance reduces
bandwidth utilization in the memory-bound decode phase.
To address this issue, FlashAccel rebalances plane load after

the write phase through selective offloading. We first compute the average plane load of the unified KV cache and then
offload excess pages from overloaded planes to HBM until no
plane exceeds the average load (Figure 8 ❷). Benefiting from
HBM’s low read latency, the offloaded data can effectively
utilize HBM bandwidth. This selective offloading avoids extra HBF writes and thereby preserves Flash endurance. Since
the same unified KV cache is typically reused across multiple
subsequent decoding steps, the extra offloading overhead
can be amortized.
During attention computation, conventional kernels load
KV cache in parallel across requests. This may trigger concurrent reads to different requests whose KV blocks happen to
reside in the same plane, causing plane conflicts that reduce
parallelism. Figure 8 ❸ illustrates the proposed HBF-friendly
loading scheme. The GPU performs accesses to HBF at hyperpage granularity to maximize effective bandwidth, and then
processes all KV blocks within each hyper page in parallel. A
small fraction of KV blocks offloaded to HBM is fetched from
HBM in the same step. Using FlashAttention [14], we compute partial attention results per KV block and then reduce
them by request to obtain the final result.
Each decode step also produces new KV cache for every
request. We temporarily buffer them in HBM (Figure 8 ❹).
At the end of each step, once the filled blocks are sufficient
to form one or more full hyper pages, we flush them back
to HBF using the same hyper-page-based write policy (Figure 8 ❺). Since the KV cache generated at each decode step
is too small to form a hyper page, directly flushing it to
HBF would underutilize bandwidth. The proposed strategy
avoids inefficiency and improves bandwidth utilization for
KV cache writes and future reads.
Besides the above strategies, increasing the KV block size,
i.e., storing more tokens in every KV block, can further mitigate inter-plane load imbalance. Under random plane mapping, increasing the KV block size significantly reduces the
maximum plane load, as shown in Figure 9. A larger KV block
spans multiple NAND pages and is therefore distributed
across a group of adjacent planes rather than confined to a
single plane. This spreads load over multiple planes, weakens local hotspots and reduces the amount of rebalancing
required.
However, the KV block size cannot be arbitrarily large.
Since a KV block is typically written to HBF only after

Logical Address

it is filled, a larger block size leaves more partially filled
data buffered in HBM and increases HBM pressure. For the
Qwen3-235B model, a KV block size of 512KB with batch
size 256 requires at least 8GB of HBM, imposing high HBM
pressure on the CLI architecture. Larger block sizes also increase internal fragmentation. FlashAccel uses 256KB KV
blocks to balance plane-level skew and HBM pressure.

6.1

HBF-aware Storage Management

FlashAccel uses a lightweight HBF-aware storage layer for
persistent data placement. It treats model weights and perrequest KV cache as persistent objects, partitions them into
data units, and maintains per-object indexing metadata to
locate them. In conventional Flash storage stacks, locating
data typically requires two levels of indirection. The program
first uses file-system metadata to obtain a logical address,
which is then translated by the Flash translation layer (FTL)
in hardware (e.g., SSD controller) into a physical Flash address. Since Flash does not support in-place updates, the
two-level indirection is necessary. When data is modified,
the new data must be written to a different physical address,
and the FTL is responsible for tracking these remapped addresses. However, the FTL is costly for HBF, as it demands
a GB-scale logical-to-physical mapping table [22] stored in
low latency SRAM or DRAM, and incurs extra address translation overhead [1]. Our key observation is that both model
weights and KV cache follow append-only write patterns.
FlashAccel therefore eliminates the FTL and directly records
the physical address of each data unit in the object’s indexing metadata. As a result, locating data in HBF requires only
the indexing metadata, avoiding the overheads of FTL. By
storing the metadata in Flash, we ensure data persistence.
To match the block-level erase semantics of Flash, the storage layer adopts an isolated block allocation policy. Weight
objects and each request’s KV cache object are placed in
separate blocks. Because KV cache eviction occurs at request
granularity, erasing the KV cache of one request does not
affect weight objects or the KV cache objects of other requests, thereby avoiding write amplification and reducing
Flash wear [11].

6.2

Programming Model

FlashAccel exposes HBF through a programming model comprising an interface set and a runtime. After the program
invokes these interfaces, the runtime maintains page table
mappings from logical addresses to the physical addresses
of HBM, HBF, or SRAM. This design exposes heterogeneous
memory through a unified virtual address space. The programming model provides different interfaces for accessing
weights and KV cache stored in HBF, accounting for distinct
access characteristics. To address the HBF access latency
challenge, it also provides interfaces that leverage SRAM to
hide data access latency.
6.2.1 Weight Access Interface. Weights are the simplest
object in the model because they are static and read-only.
FlashAccel introduces a primitive NandMmap interface to expose weight objects stored in HBF to the virtual address
space. NandMmap maps a weight object in HBF into the virtual address space and returns a logical base address. The
program can subsequently access the mapped weights using
ordinary load operations on the returned logical address.
Upon a NandMmap call, the runtime first reserves a contiguous free range in the virtual address space, as shown in Figure 10(a). It then retrieves the metadata of the target object
from the storage management layer to obtain the physical
page addresses of the mapped data in HBF. Finally, it updates
the page table to associate the returned logical address range
with the corresponding physical addresses in HBF. Since
weights are static, these mappings can be established once
during model initialization and reused throughout inference.

, Xinyu Wang, Yalong Xue, Xiaotian Sun, Xiaoyu Zhang, Chunmeng Dou, Xueqi Li, and Xiaoming Chen

6.2.2 KV Cache Access Interface. Unlike model weights,
the KV cache is maintained separately for each request rather
than shared across requests. FlashAccel stores each request’s
KV cache as an independent persistent object in the HBF
storage management layer. However, during each inference
step, the system must jointly read and write the KV caches
of all active requests. To support this access pattern, we introduce a group object abstraction. GroupCreate logically
combines the KV-cache objects of active requests in the same
inference step into a single group object. Based on this abstraction, FlashAccel introduces three interfaces: GroupMmap,
GroupWrite, and GroupArrange, to support grouped reads,
append-only writes, and offloading, respectively.
GroupMmap maps a group object into a contiguous logical
address space and returns the base address and a read table.
The runtime first reserves a contiguous virtual address region, and then builds a plane-distribution table (Figure 11)
for all objects in the group and uses it to pack data from
different objects into hyper pages whenever possible. These
hyper pages are mapped contiguously into the virtual region
at hyper-page granularity. The runtime also returns the read
table to resolve each offset of the logical base address to
its corresponding object identifier. This design allows the
program to access the group object through one logical address range, while transparently serving HBF accesses at
hyper-page granularity for high bandwidth utilization.
GroupArrange performs the offloading mechanism described in Section 5.2. The runtime computes the load of
the group object across different planes and derives the average load. It then migrates data from overloaded planes in HBF
to HBM. Finally, it updates the page table so that the physical
addresses of the offloaded data point to their new addresses
in HBM (Figure 11). This interface alleviates load imbalance
across planes and improves overall read bandwidth.
GroupWrite handles append-only writes to the KV cache,
flushing data from HBM to Flash. GroupWrite takes a pointer
to data in HBM together with a write table that specifies
which object each portion of the data belongs to. Following the write policy described in Section 5.2, the runtime
splits data in HBM into hyper pages whenever possible and
distributes them across HBF in a plane-balanced manner.
For data smaller than a hyper page, the runtime randomly
selects planes for placement. The runtime updates the object
metadata in the storage management layer, the page table,
and the read table of GroupMmap according to the write table
and the plane addresses determined during placement, so
that the newly written data remains accessible.

logical address (e.g., the returned address of NandMmap and
GroupMmap for weights and KV cache, respectively) referring

Workloads: Table 1 summarizes the four representative

7.4

Write Issues

Flash suffers from write-side limitations in both bandwidth
and endurance. Table 2 shows that the write latency of program operation (𝑡𝑃𝑟𝑜𝑔 ) is significantly higher than the latency
of read (𝑡𝑅 ), which limits HBF write bandwidth. While the
read bandwidth reaches 4.6 TB/s for CSI, the peak write bandwidth is only 245.8 GB/s. The endurance is another concern.
Prior works [12, 37] demonstrate that reducing retention
time from 3 years to 3 days can extend P/E cycles by up to
50×. Conservatively, we assume that reducing the retention
time can extend the endurance by up to 10×, increasing the
P/E cycles from 100K to 1M. Even so, it still cannot match
the nearly unlimited write endurance of DRAM. However,
the wide adoption of new attention mechanisms, like GQA
and MLA, reduces write volume compared to multi-head
attention (MHA), making it possible to store KV cache in
Flash. Across all evaluated configurations, each HBF-based
GPU generates and writes at most 276MB of new KV cache
per second in the decode node (8×CSI running Qwen3-480B
under a 100ms SLO, 1138 tokens/s). In addition, based on
the input/output length ratio (i.e., ∼2.58:1) in agent workloads [58], each HBF-based GPU writes another 712MB of
KV cache per second from the prefill node. In total, each
HBF-based GPU writes 988MB of KV cache per second, taking only 3.9ms and incurring an additional overhead of 4%.
Over a 5-year deployment period, this amounts to 148,570TB
of total KV cache writes. With 1152GB capacity and 1M P/E
cycles, CSI provides 1,125,000 TBW, sufficient for KV cache
storage.
7.5

Prefill and KV Cache Reuse

During the prefill phase, each request usually contains enough
tokens to achieve high compute intensity, even without constructing a large batch size. In this case, both HBM-based
GPUs and HBF-based GPUs can process the prefill requests
efficiently. In multi-turn interactions, however, the GPU for
prefill needs to store the KV cache of previous turns for each
session for future turns in the same session to reuse it, avoiding the recomputation for these cached tokens. Larger capacity allows the system to reduces KV cache eviction. Figure 16
reports the KV cache hit rate measured using multi-turn
interaction traces [6] on different numbers of HBM-based

GPUs and HBF-based GPUs. Due to the large memory capacity, both 8×CLI and 8×CSI can store the KV cache for all
sessions and achieve the ideal hit rate. In comparison, even
when we scale the HBM-based GPU system to 16 GPUs, its
hit rate is still 50% lower than that of the HBF-based GPU
system. Figure 16 also shows that the higher hit rates of
8×CSI and 8×CLI reduce the number of tokens that require
computation by up to 89% compared with 8×H200, thereby
providing additional speedup.
7.6

Energy and Area Analysis

Flash memory suffers from high read energy consumption.
While hybrid bonding can reduce read power, measurements
from a real hybrid-bonded Flash prototype still show a read
energy of 8 pJ/bit [62], which is 2.7× higher than that of
HBM3e (2.99 pJ/bit [4]). After integrating HBF, the overall
TDP of CSI and CLI architectures increases 1.31× and 1.23×,
respectively. Nevertheless, thanks to the throughput advantages of HBF, we observe improvements in tokens per Joule.
Figure 17 illustrates the energy efficiency (tokens/J) of different accelerators under a 100ms SLO. On average, 8×CSI
and 8×CLI deliver 1.93× and 1.66× higher energy efficiency
than 8×H200, respectively.
Our evaluation shows that HBF occupies an area of 149mm2 ,
which is 1.23× larger than that of standard HBM3e (121mm2 ).
This overhead stems from our conservative assumptions
based on the design in [32], which uses only 96 wordline
layers. Recent technologies [13, 54, 61] have achieved over
300 wordline layers, significantly improving storage density
and reducing area overhead for a given capacity. Using array
dies with more wordline layers allows HBF to achieve area
parity with the HBM stack. Even with only 96 wordline layers, our HBF design still achieves 6.5× higher density than
HBM3e.

Related Works

Flash Offloading Strategy: Prior works [3, 21, 26, 50] offload model weights or KV cache to SSDs to mitigate the
DRAM capacity bottleneck, enabling LLM execution without
out-of-memory failures. However, these designs are fundamentally constrained by the low SSD bandwidth, leading to

, Xinyu Wang, Yalong Xue, Xiaotian Sun, Xiaoyu Zhang, Chunmeng Dou, Xueqi Li, and Xiaoming Chen

extremely high decode latency, which limits their practicality in datacenter deployment. FlashAccel addresses this issue
by increasing plane-level parallelism in Flash and employing
dedicated layout optimizations to achieve high bandwidth.
In-storage Processing Accelerators: These accelerators [35, 52, 68] place compute units inside Flash to exploit
its internal bandwidth for on-device inference. However, the
limited silicon area inside Flash restricts computational capacity, resulting in low throughput. Moreover, they do not
support storing KV cache in Flash, leaving capacity challenges unaddressed. FlashAccel instead integrates HBF with
GPUs to provide high computational capacity, and enables
KV cache storage via SLC Flash and system support for
append-only KV cache writes.
Processing-in-memory Accelerators: Some works [19,
24, 42, 47] accelerate attention execution using DRAM-based
processing-in-memory (PIM) which provides high internal
bandwidth but limited computational capacity. They mainly
target MHA that has low arithmetic intensity. Recent MLA
and GQA impose higher computational demands that are
difficult for PIM to sustain. In addition, PIM does not address
the inherent low density of DRAM which leads to high cost.
By contrast, FlashAccel improves density with Flash and,
through GPU integration, supports attention mechanisms
requiring more computation.

9

Conclusion

This work points out the key obstacles that prevent HBF
from translating its capacity advantages into LLM-serving
performance, and addresses them through co-design across
architecture, data layout, and system software. FlashAccel
introduces an SRAM cache at the architectural level and a
prefetch interface at the system level to mitigate the high
access latency of Flash. A specialized data layout fully leverages plane-level parallelism for weights and KV cache to
improve bandwidth utilization. An HBF management layer
and a programming model address the management and
usage of heterogeneous memory resources. Experimental results show that FlashAccel achieves 2.54× higher throughput
than HBM-based GPU.
