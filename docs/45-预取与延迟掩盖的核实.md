**结论:** HBFSim 里没有任何形式的预取,一处都没有。合作者说的"hit 了就是 HBM 速度"这一半在代码里成立:在容量档里,一次缓存命中的建模代价是精确的零,而且这个零是被强制的——一个没有介质动作却带了非零建模时间的请求会被当作故障,整轮运行失败(第 2 节)。

"预取能掩盖 HBF 延迟"这个想法在稠密模型上有真实的依据,不是一厢情愿:Transformer 解码逐层执行,一次访问的地址在数据真正被用到之前很久就已确定,提前量比一次 GPU 访问自己显存的延迟大两到四个数量级(第 6.2 小节)。但决定"会不会性能爆炸"的不是提前量够不够,是同时在途的访问数够不够。同时在途的访问数在 HBFSim 里今天被建模成 1(第 3.4 小节);而在混合专家模型上,下一层要用哪些专家要等上一层算完才知道,提前量本身也不成立(第 6.3 小节)。

**下面是核实过程与全部数字。**

## 0. 六个术语的说明

| 术语 | 一句话解释 |
|---|---|
| **按需调页（demand paging）** | 程序真正碰到那一页数据时才去读，读的这段时间程序停在那儿等——等待时间落在关键路径上。 |
| **预取（prefetch）** | 在还没用到之前就先把读发出去，等真正要用的时候数据已经到了——等待时间被挪出关键路径。**这两件事的区别不是快慢，是等待发生在哪里。** |
| **延迟掩盖（latency hiding）** | 让等待和别的工作同时进行。有两条路：一是预取（提前发），二是同时发很多个访问、互相重叠（并发）。 |
| **同时在途的访问数（memory-level parallelism, MLP）** | 任一时刻有多少个访问正在路上还没回来。这个数是 1，就是一个做完才做下一个；是 256，就是 256 个同时在做。 |
| **发射处 / 消费点** | 发射处是那条读指令本身所在的位置；消费点是后面第一条真正用到读回来那个值的指令。真机上线程是在消费点停，不是在发射处停。 |
| **利特尔法则（Little's Law）** | 一条排队论的等式：吞吐 × 延迟 = 同时在途的请求数。要达到某个吞吐、而单次访问要等这么久，就必须同时有这么多个访问在路上。 |

## 1. HBFSim 今天的机制，以及有没有预取

### 1.1 结论一句话

**HBFSim 里没有任何形式的预取。一处都没有。** 而且注入的方向是相反的：改写后的访问只会比原来更晚发出，不会更早。

### 1.2 负结论的证据（本轮重新跑过，不是转述）

```
grep -rn -E "cp\.async|memcpy_async|cuda::pipeline|__pipeline|mbarrier|bulk\.tensor|tensormap|prefetch|readahead|read_ahead" src/ include/ adapters/ benchmarks/ tests/
→ 退出码 1，零行输出
```
同样的模式在 `scripts/` `patches/` `third_party/` 下也是零行。大小写不敏感搜 `prefetch|read[-_ ]?ahead|lookahead|speculative|stride`，在 `src/ include/ adapters/` 下同样零命中。

全仓库（third_party 之外）只有 **三处** 命中，全部是微基准里的访问模式名字符串，不是机制：`benchmarks/cuda/hbf_microbench.cu:142`、`benchmarks/cuda/hbf_microbench.cu:166`、`scripts/run_microbench.py:137`。

公开 API 里也没有预取/预热/钉住的入口。`include/hbfsim/api.h:66-79` 是完整的八个函数：`hbfsim_abi_version`、`hbfsim_context_create`、`hbfsim_register_device`、`hbfsim_map_file`、`hbfsim_flush`、`hbfsim_get_stats`、`hbfsim_unregister`、`hbfsim_context_destroy`。唯一的缓存旋钮是 `include/hbfsim/api.h:33-35` 的枚举，只有一个值 `HBFSIM_CACHE_POLICY_NONE`，`src/cuda_runtime/context.cpp:1538` 拒绝任何其他值。

源码里唯一的异步 CUDA 调用是主机侧的页帧拷贝，且每一处后面紧跟同步，效果上是同步的，不是数据预取：`src/cuda_runtime/capacity_runtime.cpp:199-202`（`cuMemcpyHtoDAsync` + `cuStreamSynchronize`）与 `:216-218`（`cuMemcpyDtoHAsync` + `cuStreamSynchronize`）。

### 1.3 注入机制端到端（PTX 改写 → 内核里真停）

PTX 改写在每条 `(ld|st)(.volatile)?.global` 且地址形如 `[%rdN(+/-imm)]` 的指令**之前**插入 `call __hbfsim_resolve(addr, bytes, kind)`，然后把地址寄存器换成调用的返回值，最后才发出原来那条访存指令。发出顺序在 `src/ptxpass_hbf/transform.cpp:199-222`，最后一行 `:222` 是 `output << replace_address(*operation, address) << '\n';`。核实方法：核实代理**实际编译并运行了这个 pass**（`transform.cpp` + `ptx_memory_op.cpp`），对 `ld.global.u32 %r1, [%rd1+64];` 后跟 `add.s32 %r3, %r1, %r2;` 得到的真实输出，末尾是 `ld.global.u32 %r1, [%hbfsim_addr_1];`，再后面是**原样未插桩的** `add.s32 %r3, %r1, %r2;`。

延迟不是记账，是**内核里真的自旋等待墙上时间**：
- `src/cuda_runtime/device/hbf_device.cu:59-64` `gpu_time_ns()` 读 `%globaltimer`；
- `:66-70` `bounded_sleep` 调 `__nanosleep`，从 64 ns 起指数退避，上限 1,048,576 ns（约 1 ms）；
- 三处自旋循环：`:236-241`（参考路径）、`:364-374`（实测经验路径）、`:413-423`(解析快路径)，形式都是 `while (gpu_time_ns() < target) { ... bounded_sleep(...); }`；
- 统计计数器 `fast_requests` / `fast_modeled_ns` 在停完之后才加（`:375-377`），也就是说计数器是记账、不是停顿的替代品。

**这条停顿无法被躲开**：`replace_address`（`src/ptxpass_hbf/transform.cpp:63-70`）把调用返回值塞进访存指令的地址操作数，两者之间形成真实的数据依赖，ptxas 无法把访存指令提到调用之前。合作者仓库里我们自己写的问题清单已经这样记过：`docs/重要实现问题以及需补做实验/10-B-delay-injected-at-issue-not-at-use.md:21-25`「the two are joined by a real data dependence, and ptxas ... cannot move the memory instruction above the call. The wait therefore always completes before the access is issued.」

**Pass 里没有任何"哪条指令用到这个值"的分析**：`transform.cpp:143` 是 `while (std::getline(input, line)) {`，识别靠 `ptx_memory_op.cpp:79-80` 的正则。整个 pass 是一个按行读的正则改写器。

### 1.4 顺带一条覆盖漏洞（与预取直接相关）

`cp.async` 与 TMA（`cp.async.bulk.tensor...`）**被静默丢弃**：既不插桩，也不计入 `unsupported_instructions`。核实代理实跑该 pass，对含 `cp.async.ca.shared.global`、`cp.async.bulk.tensor.2d...`、`ld.global.nc.f32`、`ld.global.u32 [foo+8]`、`ld.shared.u32`、`atom.global.add.u32` 的内核，输出是 `rewritten=1 unsupported=2`，两条 unsupported 分别是 `ld.shared.u32` 与 `atom.global.add.u32`——三条会真正读全局内存的形式全部漏掉。原因：`transform.cpp:53-54` 的 unsupported 正则没有任何以 `cp.` 开头的分支。**更糟**：`src/ptxpass_hbf/plugin.cpp:283-288` 还会把 `ld|st.(param|local|shared|const)` 从 manifest 里滤掉，所以该内核的 manifest 只报 1 条 unsupported。文件化记录：`docs/重要实现问题以及需补做实验/07-B-cp-async-and-bulk-tensor-copy-unmatched.md:38-39, 53-60`，方向「Downward ... an access that reaches `HBF` costs nothing」。且 `tests/` `configs/` `adapters/` `benchmarks/` 下没有任何文件含 `cp.async` / `bulk.tensor` / `mbarrier`，测试集永远不会暴露这个洞。

## 2. 「hit 了就是 hbm 速度」在代码里成立的那一半

**成立，而且比他说的更强：在容量档（capacity mode，range mode 2）里，一次命中的建模代价是精确的零，并且这个零是被强制的，不是碰巧的。**

- 命中路径：`src/host_service/capacity_page_service.cpp:95-101`，`if (const auto resident = cache_.resolve(logical_page); resident) { ... return {.status = RequestStatus::Ready, .frame_address = *resident}; }`——`media` 字段留在默认值 `CapacityMediaNone`（`src/host_service/control_layout.hpp:57`），不产生任何介质动作。
- 强制：`src/host_service/request_dispatcher.cpp:381-382`，一个没有介质动作却带非零 `modeled_ns` 的请求被当作故障，`fail_all()` 整轮失败。也就是说"命中要收钱"在这套代码里是一个会让运行崩掉的状态。
- 命中之后返回的是页缓存里的真实帧地址，设备端加上页内偏移（`src/cuda_runtime/device/hbf_device.cuh:267-271`），内核随后对**真实 HBM** 发一次真正的 load。所以数据确实是以 HBM 速度被读到的。
- 还有第三条零建模代价的路径：`src/host_service/capacity_page_service.cpp:102-109`，`cache_.reclaim_eviction(logical_page)` 把一页从"正在被逐出"的状态救回来，同样返回 Ready 且不产生介质动作。

**所以"hit 不收 HBF 的钱"这半句，代码里是对的，且是硬性保证。回复里应当先承认这一半。**

缓存本身：全相联，按逻辑页号用 `unordered_map` 索引（`src/cuda_runtime/hbm_cache.hpp:55`），帧数 = `hbm_cache_bytes / page_bytes`（`src/cuda_runtime/capacity_runtime.cpp:26-27`），替换策略是 **CLOCK（二次机会）**，不是 LRU 也不是 FIFO：旋转指针 `clock_hand_`（`hbm_cache.hpp:58`），引用位买一次跳过（`hbm_cache.cpp:140-156`），扫描上限两轮。类里没有任何时间戳、最近使用链表或频率计数器。

## 3. 这句话覆盖不到的地方

### 3.1 第一处：「prefetch 就是这么干的」——不是。这套代码做的是按需调页，不是预取

**区别不在快慢，在等待落在哪里。** 预取是在用到之前把读发出去，等待被挪出关键路径；按需调页是碰到才读，等待留在关键路径上。HBFSim 实现的是后者，而且没有任何一行代码在做前者。

- `CapacityPageService::resolve` 每次调用只处理**一个**逻辑页，函数体 `src/host_service/capacity_page_service.cpp:88-187` 里**没有任何跨页的循环**，也没有第二次读。缺页读 N 永远不会顺带取 N+1。
- 填充是主机工作线程上的**同步阻塞 pread**，一次一页：`src/host_service/backing_store.cpp:208-215`，底层 `::pread` 在 `:27-29`。没有 io_uring、没有 aio、没有读线程池（我重跑了 `grep -rniE "io_uring|libaio|aio_read|thread_pool|std::async"`，`src/ include/ adapters/` 下无命中；全仓只有一个容量 worker jthread 和一个心跳 jthread）。
- 缺页时**发起的那个 lane 在内核里自旋阻塞**直到主机发布完成：`src/cuda_runtime/device/hbf_device.cu:206-218`。不是返回重试，不是让给别的 warp。而且**整组 lane 一起阻塞**，不只是发起的那一个：`:511-523` 选出 leader，其余 lane 卡在 `__shfl_sync` 上等 leader 的返回。
- **每次运行都是冷启动。** 帧构造时全空，`HbmCache::publish`（唯一让一页变成常驻的入口）在整个生产代码里只有一个调用者，就是缺页路径 `capacity_page_service.cpp:177`。没有注册时预热、没有启动时预热。更糟的是 `hbfsim_flush` 不是把脏页刷干净而是**把页逐出**（`capacity_page_service.cpp:253` 的 `begin_eviction_in_range(page, 1, true)` 后接 `:294-297` 的 `complete_eviction`，而 `hbm_cache.cpp:228-231` 清掉 `logical_page`），刷过的页下次再碰又是一次缺页。

> **写进回复的一句话建议**：命中免费这件事本身没有争议；但"prefetch 就是这么干的"这句里的 prefetch，指的是提前发出读、让等待落在关键路径之外。我们代码里没有这一步——是碰到才读、读的时候整组线程停在那里等。这两件事在模拟出来的时间上差的不是一点。

### 3.2 第二处：那个「hit」根本不在出实验数字的那条路径上

**容量档（mode 2）和时序档（mode 1）是两条互不相通的路，而论文里所有 HBF 时序结果走的是时序档。**

- 路由：`src/cuda_runtime/device/hbf_device.cu:515-519`，`resolution = range->mode == 1 && header->timing_model != 0 ? resolve_fast_or_hybrid(...) : resolve_leader(...);`。容量档（mode 2）**永远不走快路/混合路**，所以那条实测标定出来的 CD8P 曲线**从来不会作用在容量档的访问上**——容量档的缺页由 MQSim 计时。
- 反过来，**时序档没有任何常驻/命中过滤器**：`src/host_service/request_dispatcher.cpp:175-181`，非容量档的请求**无条件**产生恰好一个介质动作，每一次都产生，不查任何此前的常驻状态。
- 所以：容量档有命中但拿不到实测曲线；时序档有实测曲线但没有命中。**没有任何一种配置下，一次访问既被缓存命中、又按实测时序收费。** 一个容量档的访问，要么命中收零，要么缺页收 MQSim 的介质时间。

### 3.3 第三处：跨 warp、跨时间的重复访问被重复收费

- warp 内同页合并是做了的，而且做对了：`hbf_device.cu:503-523` 用 `__match_any_sync` 按 (range_id, page) 分组，每组只有 leader 发请求，结果用 `__shfl_sync` 广播。**一个 warp 里 32 条线程访问同一个 4 KiB 页，只产生一个建模请求。**
- **跨 warp 就没有了。** 我们自己的问题清单 `docs/重要实现问题以及需补做实验/09-B-no-page-residency-filter-across-warps.md:26-31`：「Once the same page is read by a second warp, or read again by the first warp a while later, the code charges another full media access. On hardware a large share of such accesses never reach the media at all: they are served by the L2 cache, or by the page cache...」方向：`:34-39`「Upward: the modeled time comes out above what the hardware would take. ... We have not measured either case, and give no factor here.」
- 同一份清单的 `05-A` 给了一个**推算的上界**：`docs/重要实现问题以及需补做实验/05-A-accounting-unit-is-the-kernel-launch.md:294-305`，重复收费带来的高估「by an upper bound we put at about 128 times, **which is our own inference and not a measurement**」。**【推算，非测量】**
- 而且 `include/hbfsim/api.h:58-64` 的 `hbfsim_stats` 只有五个字段（`requests_submitted`、`requests_completed`、`fast_requests`、`reference_requests`、`fast_modeled_ns`），共享控制头里也没有命中/未命中计数器。**一次运行的命中率在系统里读不出来。**（我重跑了 `grep -rniE "hit_count|miss_count|cache_hit|cache_miss|hit_rate"`，`src/ include/ adapters/ tests/ benchmarks/ scripts/` 下没有一处真实实现。）

### 3.4 第四处（最关键）：没有任何并发/重叠模型。全设备同时在途的访问数被建模成 1

**这是回复里最该讲清楚的一条。**

- 设备端累加建模时间的变量**只有一个 64 位字**：`src/cuda_runtime/device/hbf_device.cuh:64` 的 `alignas(8) std::uint64_t fast_channel_tail_ns;`，位于主机共享控制区（主机侧镜像 `src/host_service/control_layout.hpp:112`）。它是**全设备**的，不是每 warp、不是每线程、不是每通道、不是每 die。`grep -rn "fast_channel_tail_ns" src/ include/ tests/` 只有这两处声明加四处设备端引用（`hbf_device.cu:349, 355, 393, 400`）。`grep -rnE "smid|ctaid|tid\.|nctaid|blockIdx|threadIdx" src/ include/` **零命中**——不存在任何按 warp、按块、按 SM 的时序状态。
- **实测经验档（CD8P 标定档）下完全串行**：`hbf_device.cu:346-360`，整个服务时间（延迟加传输）都被压到那一个游标上，`start = max(tail, arrival); target = start + scaled_service;` 用系统作用域 CAS 推进。**全 GPU 上每一次 HBF 访问都排在其他所有访问后面。建模出来的同时在途访问数精确等于 1。**
- 解析快路径下略好一点但仍然：只有传输项排队，固定延迟可以重叠（`hbf_device.cu:393-409`，`target = max(arrival + base_scaled, transfer_target)`）。**延迟项的并行度无上界，带宽项的并行度精确等于 1。这不是带宽共享，是单通道严格先进先出。**
- 参考/MQSim 路径在主机侧重复同样的形状：`src/mqsim_adapter/mqsim_online.cpp:274-282` 的单标量 `bandwidth_cursor_ns`（成员声明在 `:305`）。
- **profile 里那个 `queue_depth` 旋钮什么都没接上——任何路径都没有。**（这一条是核实代理推翻第一轮调查结论后的更正，比原结论更强。）`src/profile/profile.cpp:259` 解析它，`:343` 要求非零，`src/mqsim_adapter/mqsim_online.cpp:118-119` 把它写进静态的 `Device_Parameter_Set::IO_Queue_Depth`——但**没有任何被实例化的组件读它**，因为 `mqsim_online.cpp:117` 设的是 `HostInterface_Type = HostInterface_Types::HBF;`，而上游 MQSim 里 `IO_Queue_Depth` 只在两处被消费：`src/exec/SSD_Device.cpp:355`（SATA）和 `:360`（NVMe）。本项目自己的补丁 `patches/mqsim/0001-online-hbf-api.patch` 加的 `case HostInterface_Types::HBF:` 分支构造 `Host_Interface_HBF` 时**根本没有传 IO_Queue_Depth 参数**，与它旁边的 NVMe 分支不同。
- 顺序段检测的状态**也是同一个全局字**：`hbf_device.cuh:71` 的 `empirical_burst_state`（偏移 256），位布局是 [上一页+1 | 上一次操作 | 连续长度]，打包在 `:425-426`。**整个被模拟的设备里任一时刻只能存在一条顺序链。** 我们自己的记录 `docs/41-三条挑战的完整写法与推导过程.md:379`：「`empirical_burst_state` 是共享控制区里的**一个** 64 位字…全设备所有线程束用比较并交换抢它…多个线程束交错访问时,连续段会被互相打断、`run_pages` 频繁归 1。」
- profile 声明的通道数根本没被读：`grep "channels|dies_per_channel|planes_per_die"` 在 `src/cuda_runtime/` 下零命中；而 `cd8p-vmem-p50.json` 声明 32 通道 × 8 die × 4 plane（`queue_depth` 写的是 1）。我们自己的问题清单 `11-B-one-scalar-for-all-channels.md:25-36` 已经记了：profile 说 16、32 或 64 个通道，时序表现得像 1 个；方向向上，最大偏差出现在接近饱和时。

### 3.5 第五处：延迟付在发射处，不是消费点

`docs/重要实现问题以及需补做实验/10-B-delay-injected-at-issue-not-at-use.md:26-31` 原文：

> On real hardware a global read is issued asynchronously: the instruction starts the access, the program keeps running, and the thread stops only when the destination register is read by a later instruction. **Putting the wait at the issue point turns an access that later instructions could have covered into a stall that nothing can cover.**

README 里的一句话总结（`docs/重要实现问题以及需补做实验/README.md:122`）用了 "overlapped" 这个词：「turns an access that could have been overlapped into a stall in place」。

方向：`10-B:33-37`「Upward: the modeled execution time comes out above what the same access pattern would cost on hardware. **We have not measured how far above, and give no factor here.**」

该文档自己留的反方意见（`:41-47`）：这可能是有意的取舍；容量档必须在发射处替换地址；而在纯时序档下，如果内核用到载入值的位置离载入很近，差别可能不大。

**但 `docs/36-三条挑战的一手核实证据.md:678` 提出了相反的读法**：必须留在发射处的是「换地址」这个动作，不是「付延迟」这个动作——地址替换是正确性动作、事后补救来不及，而建模出来的等待时间仍然可以挪到消费点付。**这一条与问题清单 doc 10 / doc 15 item 9 的写法冲突，需要合作者裁定。**

### 4.7 诚实的答案

1. **会炸，而且已经炸了一次——164.70x。**
2. **但这个数不能读成"HBF 会慢 164.70 倍"**，proof 文档自己就这么写的。
3. **炸的原因至少有三个，只有一个是真的器件延迟**：(a) 时间缩放系数 100，每次收费访问实际停 1 ms；(b) 全设备同时在途访问数被建模成 1；(c) 延迟付在发射处，把真机上会被 warp 调度掩盖的那部分全额计入。
4. **今天没有办法把它们分开**，因为计数器没导出、也没有零注入基线运行。这条已经立项为 `docs/重要实现问题以及需补做实验/15-experiments-we-must-add-before-submission.md` 的 **item 12**（"Split the 164.70x slowdown into modeled delay and emulator overhead"），给出的两个可行做法是：identity-injection 对照运行（注册范围、注入零延迟、看剩下多少），或者扫 `time_scale`。
5. **业界有两个直接对照的数**可以说明"不建并发就会高估"：CXLMemSim 报「Without ROB emulation, latency penalties were consistently overestimated by up to 30%」；Mess 报 ZSim 的固定延迟模型把峰值带宽报成 342 GB/s，而理论上限是 128 GB/s，**高出 2.7 倍**。**两个都在 CPU 侧、都在 DRAM/CXL 延迟量级，比闪存延迟低两到三个数量级——所以在闪存这一层，缺口只会更大，不会更小。**

## 5. 是不是每个 HBF 地址都要收 PTX 延迟

### 5.1 今天代码的答案（事实）

**今天是"每一个都收"，而且是无条件的。** `src/host_service/request_dispatcher.cpp:175-181`：只要 range 不是容量档，就无条件产生恰好一个介质动作，每一次都产生，不查任何常驻状态。设备端唯一的过滤是 warp 内同页合并（`hbf_device.cu:503-523`），也就是"每 (warp, range_id, 逻辑页) 一个请求"，跨 warp 和跨时间都不合并。

另外要注意：从 PTX 传进来的 `bytes`（比如 `ld.global.u32` 传的是 4）**只用来做校验**——`hbf_device.cuh:237-254` 的 `access_supported` 用它拒绝 `bytes == 0` 和跨页边界的访问——然后就被丢掉，换成 `range.page_bytes`（`hbf_device.cuh:286-288`），喂给时序模型的是整页的大小（`hbf_device.cu:383-384`）。**一次 4 字节的载入按整页收费。**

### 5.2 为什么"每个都收"是错的，分三层

**第一层：真机上大部分访问根本到不了介质。** 只有末级缓存未命中才到介质。今天没有任何一层过滤（`09-B` 全文）。这一层的高估上界推算约 128 倍**【推算】**。

**第二层：即使到了介质，它们不是一个接一个做的。** 今天是一个接一个（`fast_channel_tail_ns` 单游标）。规范声明的组织是 16 dies/cube × 16 banks/channel（`ocp2026-hbf-architecture-specification-v0-7-0.txt:1081-1109` Table 3）。

**第三层：即使真的停了，真机是在消费点停，不是在发射处停**（第 3.5 节）。

### 5.3 正确的模型长什么样——仓库自己已经写出了那个等式

`docs/重要实现问题以及需补做实验/15-experiments-we-must-add-before-submission.md:123-152`（item 1，标注 "Supports. The core claim. **Blocking.**"）给出的恒等式：

> The identity to implement is **`steady-state read bandwidth = parallel read-out units × page size ÷ tR`**. At 256 units and 4096-byte pages the identity gives **262.1 GB/s at tR = 4 microseconds and 52.4 GB/s at tR = 20 microseconds, which is 11.7 to 58.6 times below the 3072 GB/s of Table 2; reaching 3072 GB/s would take 3,000 to 15,000 parallel read-out units (inference).**

同一段定义："A **parallel read-out unit** is one place inside the device that can sense one page out of the storage array independently of the others." 并说明 256 这个数怎么来的：Table 3 的 `Banks per channel 16 units` × 16 channels = 256（inference，假设一个主机通道驱动一个 core die）。规范**不给 tR 的值**（primary）。

item 1 要扫的网格是 **24 个组合**：每 cube 并行读出单元数取 **256、1024、1536、4,883**，交叉介质延迟取 **1、2、4、5、10、20 微秒**；每格出两个数（稳态阵列读带宽、负载端到端吞吐），第三个数是**结论变号的那个位置**。

### 5.4 具体该怎么答用户的 [0,100]/[100,10000] 这一问

**不是"所有 HBF 地址都收"，也不是"所有 HBF 地址都不收"。正确的做法是把一次访问要不要收、收多少，拆成三个独立的判定，每个判定今天都缺一块：**

1. **这次访问会不会真的到介质？** 需要一个跨 warp、跨时间的页常驻记录，或者一个末级缓存命中率的输入。今天两样都没有（`09-B`；`15-…item 10` 明写方法 "**Not decided yet**"）。
2. **到了介质之后，它和多少个别的访问同时在做？** 需要把单游标换成按通道/按并行读出单元的多游标。今天没有（`15-…item 13` 就是这一条：「Producing the number requires a version of the fast path in which the counter is kept per channel」）。
3. **停在哪里？** 需要把等待从发射处挪到消费点。今天没有（`15-…item 9`）。

**只有这三件都做了，"每个 HBF 地址都收 PTX 延迟"才会自动变成"按 N 路并行 + 命中过滤 + 消费点停顿"的正确结果。** 在这之前，[100,10000] 这个范围里每个地址都收一次整页延迟、且全部串行，报出来的减速数不能读成器件的减速数。

### 5.5 一个必须避免的表述（大纲已经明令禁止）

`HBFSim/paper/35-FAST27论文大纲与逻辑线.md:613`：「**这条曲线现在按位置取值，没有建页寄存器命中、也没有建缓存缓冲命中——代码里没有这两样，正文不许写成建了。** 直接后果是重复读同一页现在比顺序读下一页还贵 10.0%（11,133 纳秒对 10,121 纳秒），与规范原文 `The Base die shall immediately serve the cache hit read from the cache buffer if ordering is not violated.`（第 57 页）相反」。

规范侧的原文（`docs/HBF_OCP/ocp2026-hbf-architecture-specification-v0-7-0.txt:4113-4122`）：每个 bank 两个 4 KiB 缓存缓冲；命中立即服务；未命中才触发 Core die sense。寄存器 `NCBB`（`:5806-5811`）把数量固定为 2，其余编码全部保留。

## 6. TPU 与华为 NPU 的静态图算不算几乎完美预取

### 6.1 先确认一件事：**我们自己的 vLLM 实验跑的就是 MoE 模型**

`docs/proofs/2026-08-11-vllm-exact-live-delay.md:8-11` 与注册的张量名 `model.layers.0.mlp.experts.w13_weight`（`:16-17`）：模型是 **Qwen3-30B-A3B**，Mixture-of-Experts。`05-A:134-137` 也明写「Qwen3-30B-A3B is a Mixture-of-Experts model with about 30.5 billion parameters in total and about 3.3 billion active per token」。

模型配置（HuggingFace 模型卡 + `config.json`，调查代理逐字核过）：`Number of Layers: 48`、`Number of Experts: 128`、`Number of Activated Experts: 8`、`hidden_size 2048`、`moe_intermediate_size 768`、`decoder_sparse_step 1`。**48 × 8 = 每词元 384 次独立的专家选择**【推算】。

### 6.2 支持"静态图 ≈ 完美预取"的最强证据（**稠密模型**）

稠密 Transformer 的解码逐层执行,算第 i 层的时候,第 i+1 层要读哪些权重的地址已经确定;这里说的提前量,指的是一次访问的地址被确定下来,到这次访问的数据真正被用到,中间隔了多久。在稠密模型上,提前量足够大,已经有系统据此实现了 prefetch 并公开了做法。

- **层序固定,下一层的权重地址在当前层还在算的时候就已经知道。** Mixtral-offloading(arXiv:2312.17238)L302-303 原文:「For regular (dense) models, this architecture allows for efficient offloading schedule that pre-loads the next transformer layer ahead of time, while the previous layer is still running.」
- **已经有系统这么实现了。** FlexGen(arXiv:2303.06865,ICML 2023)的 Algorithm 1 里有 `// Load the weight of the next layer` 与 `load weight(i, j + 1, k)`;L571-573 说明 FlexGen 把四件事重叠起来:下一层权重的加载、下一批的 cache 与激活的加载、上一批的写回、当前批的计算。
- **提前量的完整算式(本项目自己的推算,出处 `15-experiments-we-must-add-before-submission.md` item 2 的 232 到 243 行,该处标为 inference)。** Llama 3 8B 有 32 层、hidden 维度 4096、前馈维度 14336、8 个 key-value head;bf16 下每层权重 **436.2 MB**;在 H100 SXM5 的 3.35 TB/s 显存带宽下读一层要 **130.2 µs**。算第 i 层的这 130.2 µs 就是可以用来读第 i+1 层权重的时间,是 **20 µs** 介质延迟的 **6.5 倍**、是 **4 µs** 的 **32.6 倍**。再往后提前量更长:一个词元开始计算的那一刻,全部 32 层的地址就都定了,最后一层的权重在 **4.04 ms** 之前就已知,而整词元解码时间是 **4.17 ms**,也就是 20 µs 的 **202 倍**。作为对照,一次 GPU 访问自己显存的延迟在 H800 上实测是 **272.8 ns**(1755 MHz 下 478.8 个周期;Luo et al., `Benchmarking and Dissecting the Nvidia Hopper GPU Architecture`, arXiv:2402.13499, Table IV 与 Table III,一手)。

所以提前量比一次 GPU 访问自己显存的延迟大**两到四个数量级**,"静态图给出的地址知识足以提前把数据取回来"这个说法在稠密模型上有实测量级的支撑。提前量说明的是地址在时间上提前多久可知。提前量不保证那段时间里真的搬得完——搬得完不完由带宽和暂存容量决定,由 6.3 小节讨论。

### 6.3 反对的最强证据

#### (a) 即使地址完全已知，实测的掩盖效果也远不是"完美"

**这是整份材料里最有杀伤力的一个反证。** DeepSpeed ZeRO-Inference 官方博客（https://www.deepspeed.ai/2022/09/09/zero-inference.html，2022-09-09）逐字：

> **Layer prefetching allows ZeRO-Inference to hide portions of the transfer latency of the prefetched layers.**

实测 NVMe offload 下的预取加速比：**OPT-30B 1.13x、OPT-175B 1.14x、BLOOM-176B 1.21x**。同页还有一句：「We observe that prefetching did not improve CPU offload.」

**在稠密模型、地址完全静态可知的最有利条件下，预取只带来 13% 到 21% 的加速。完美的地址知识在实测上不足以做到完全掩盖。**

#### (b) MoE 的专家集合不是静态的

- Mixtral-offloading（arXiv:2312.17238）L303-308：「this schedule is no longer possible for Mixture-of-Experts models ... the system cannot pre-fetch the next layer until it learns which experts should be loaded. Modern open-access MoE language models choose active experts using the **final outputs of the previous layer**, which means they cannot be pre-fetched them in parallel with previous layer.」脚注 6（L326）：「not possible without changing the model architecture, which would require re-training」。
- Pre-gated MoE（ISCA 2024，arXiv:2308.12066）L136-147：「the two-stage process of (1) expert selection and (2) expert execution must be serialized back-to-back. Consequently, **the latency to migrate the activated expert parameters from CPU to GPU cannot be hidden** under MoE-offload」。它的解法是改架构 + 重训（L153-158），不是预测器。
- AdapMoE（arXiv:2408.10284）L138-148 补一句代价：「the structural modifications will complicate direct deployment. ... Adap-gating and Pre-gated MoE will even cause accuracy degradation if directly deployed without finetuning.」

#### (c) 已发表的专家预测命中率（**这一组是回复里最该带上的数**）

| 系统 | 报告的准确率 | 关键限定 |
|---|---|---|
| **Fate**（arXiv:2502.12224，中山大学） | **78.79%**（跨层门复用、不训练）；解码阶段区间 **76.94%–83.99%** | 原文 L667-673：「a prefetch accuracy of 78.79% without additional training or statistical costs. ... it still results in a **misprediction rate of over 20%**」 |

**套到我们的模型上**【以下全部为推算，输入值是核过的配置】：Qwen3-30B-A3B 每词元 384 次专家选择。逐次命中率 90% → 期望 **38.4 次未命中/词元**；97.15% → 仍有 **10.9 次/词元**；整个词元零未命中的概率：90% 时 **2.69e-18**，97.15% 时 **1.51e-05**。**一次未命中就足以把完整的闪存延迟暴露出来。**

#### (d) 提前量本身是一个独立的约束（不是知道地址就够）

- **ProMoE 把这件事写成公式**：`GoodPred = Accuracy × FetchRate`，其中 FetchRate 是"预测对了且**来得及取回**"的比例（L633-640）。L602-607：「improving accuracy often requires more prediction time, which can reduce the time available for prefetching」。多提前一步换时间要付 5% 的准确率（L883-886）。
- **Fate 实测了两难的两端**（L657-670）：准确率最高的那个预测点（`Attn_in_{i+1}`）后面的注意力层计算时间太短，来不及完成 I/O；提前到 `Attn_in_i` 有足够时间，但会造成相邻层之间的 I/O 冲突——第 i 层的传输还没完，第 i+1 层就开始它自己的了。
- **Fate 直接给出一般结论**（L210-213）：「Due to the physical limitation that **computation is faster than I/O, the GPU often waits for the expert transfer to complete**」。

#### (e) 暂存容量

Pre-gated MoE L498-509：要重叠，加速器内存必须**同时装下当前块的专家和下一块的整层专家**，可能压垮加速器内存；只取预测的子集来缩小缓冲区，就把误预测的惩罚请了回来。

#### (f) 带宽/算力上限：解码阶段根本没有算力可以藏东西

- **FlexGen 的 roofline 模型**（arXiv:2303.06865 L596-601）：`Tpre = max(ctog_p, gtoc_p, dtoc_p, ctod_p, comp_p)`。**在"完美重叠"的假设下，最慢的那一层仍然定下限。预取不能让一次传输变便宜，只能让它并发。**
- **已发表的 roofline 数据**（arXiv:2402.16363v6，Llama-2-7B，A6000，序列长 2048，batch 1，Table 1）：prefill 的算术强度 **1024–1215 OPs/byte**，全部 compute-bound；**decode 是 1 OPs/byte，每一个算子都是 memory-bound**。原文 L760-763：「during the prefill stage, the majority of computations are compute-bound ... Conversely, **in the decode stage, all computations are memory-bound**」。**算力与字节之比差约一千倍。**
- **TPU 上是一样的，而且是 Google 自己的论文说的**：Pope et al.（MLSys 2023, arXiv:2211.05102）L283-286：「The on-chip memory needs to load this KV cache from off-chip memory once for every token generated **during which the computational core of the chip is essentially idle**」。硬件参数 L1120-1123：TPU v4 每芯片 bfloat16 275 TFLOPS、HBM 32 GiB、带宽 1200 GB/s。
- **推算的 ridge point**：TPU v4 = 275e12 / 1.2e12 = **229 FLOP/byte**；TPU v6e = 920e12 / 1.64e12 = **561 FLOP/byte**（v6e 数值来自 https://docs.jax.dev/en/latest/pallas/tpu/hardware.html）。batch-1 解码在 1–2 FLOP/byte。**TPU 在解码阶段连自己的 HBM 都喂不满，比 HBM 慢几个数量级的一层根本没有东西可以藏在后面。**【推算，输入值是引用的原文数值】

#### (g) 编译器侧的直接反证：XLA 自己会因为提前量不够而**拒绝**预取

XLA 的 Memory Space Assignment（MSA）pass 是真正做这件事的编译器组件。https://raw.githubusercontent.com/openxla/xla/main/xla/service/memory_space_assignment/memory_space_assignment.h L156-170 逐字：

> - **Live range too short: The live range of a use segment is too short to prefetch a buffer to alternate memory**, according to some heuristic and not based on limited copy resource. * If the CostAnalysisPrefetchIntervalPicker is used, which is the default, live range too short is governed by the picker's **min_overlap_to_async_copy_ratio** argument.

它的默认调度器是一个**算力对拷贝的比值模型**（prefetch_interval_picker.h L190-197）：「It uses **min (independent computation duration) / (asynchronous copy duration) ratio** to guide whether the prefetch is within the lower bound.」并有硬上限（options.h L300-312 的 `max_outstanding_prefetches` / `max_outstanding_evictions`，L347-349 的 `int max_cross_program_prefetches = 1;`），以及明确的失败方式：「prefetching failed due to running out of asynchronous copies or asynchronous copy resource」。

JAX 官方的 TPU 流水线文档（https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html）也直白承认这个问题，并为此专门提供了 lookahead：「**there may not be enough compute work in the iteration immediately preceding the step when the block is needed to fully overlap with the memory transfer.**」并且「The default buffer count is **2** for all inputs and outputs.」（默认只有双缓冲；lookahead 默认关闭）。

#### (h) 华为昇腾侧：他们自己的旗舰论文说 MoE 让形状变成动态的，而且**解法不是预取**

华为云 CloudMatrix384 论文（arXiv:2506.12708v3）L1440-1443：「**Dynamic Shapes**: Data shapes for all-to-all communication are dynamic because the number of tokens assigned to each expert varies per decode iteration. This dynamism reduces execution efficiency due to the need for dynamic memory allocation and frequent CPU-NPU synchronization.」

他们的解法（L1452-1454、L1580-1582）是**静态预分配最坏情况的缓冲区**以支持静态图执行；再加上 **每个专家独占一个 NPU die 的大规模专家并行**（L1412-1413：「each expert placed on a dedicated NPU die. In the DeepSeek-R1 model, 256 router experts are deployed」）——也就是**把所有专家全部常驻，而不是从慢层预取**。

昇腾 CANN 的内存复用（https://www.hiascend.com/developer/techArticles/202407005-1）明确限定在"静态 shape 的神经网络在基于计算图模式执行时"，是设备内存内部的复用，**不跨存储层，也不含任何预取机制**；Memory Swap 是另一项单列的技术。

另有一份现场研究（arXiv:2607.08215v1，香港中文大学深圳，**预印本、单点现场研究，权重相应打折**）报告静态图这条路在实践中部分不可用：多模态模型用 `enforce-eager`（完全不做图捕获）跑，量化 MoE 模型的图路径会发出关于 OOM 和挂起的实验阶段警告（L643-657）。

#### (i) **一条重要的"查不到"**（必须原样带上这个限定）

调查代理**未能找到任何一手文档**描述 TPU 或昇腾 NPU 在编译器控制下从闪存/SSD 层预取**权重**。所有有文档的 offload 路径都终止在主机 DRAM：JAX 只暴露 `"device"` 和 `"pinned_host"` 两种 memory kind（https://docs.jax.dev/en/latest/201/memory-spaces.html）；CANN 的 Memory Swap 换到主机。Cloud TPU 系统架构文档只描述 HBM + 主机 infeed/outfeed 两层。TPU 片上暂存（VMEM）每 TensorCore 只有 **16–128 MiB**（v4 16 MiB、v5e 128 MiB、v5p 64 MiB、v6e 128 MiB、7X 64 MiB）。**结论标为【无法确认】，不是【不成立】**：这几份文档里没有，是有力旁证，不是定论。

### 6.4 答用户第二问的落点

**稠密模型：静态图给的是"地址完全已知"，这一半是真的；但"完美预取"是另一回事——实测只有 1.13x–1.21x 的收益，因为受限的是带宽和提前量，不是地址知识。**

**MoE：连地址都不是静态的。** 而我们自己跑的就是 MoE（Qwen3-30B-A3B）。最好的、不用改架构的预测器在解码阶段是 76.94%–83.99%（Fate）到 84.7%（ProMoE），而在与我们的模型最接近的 Qwen2-MoE 上跨层门式预测器塌到 66.9%。按每词元 384 次选择算，90% 的逐次命中率也留下 38.4 次未命中【推算】。

**顺带一条已经写进 bg.tex 的收窄**（`paper/bg.tex:143-156`，这是 .tex 里比大纲新的内容）：tR 取 50 µs 时单层窗口只覆盖 **2.60 倍**而不是 6.51 倍；一个矩阵乘 kernel 内部的预取窗口在 20 µs 下**已经慢 3 到 4 倍**（TileLens 的数）；MoE 的专家权重提前量是零。

## 7. 不预取、只靠海量线程并发，能不能掩盖闪存延迟

**这一条要单独讲，因为它是对"必须靠预取"这个前提本身的反驳，而且它给的正是我们缺的那个模型。**

### 7.1 BaM（ASPLOS '23，arXiv:2203.04910）

- **它明确写出利特尔法则**：「the parallelism required to tolerate access latency and achieve full throughput of the device is governed by Little's Law: **T × L = Qd**, where T is the target throughput, L is the average latency, and Qd is the minimal queue depth required at any point in time to sustain the target throughput.」
- **代入的数**：PCIe Gen4 x16 约 26 GB/s → 512B 粒度下 T = **51M 次/秒**，4KB 粒度下 **6.35M 次/秒**。Intel Optane L = **11 µs** → 需要队列深度 **561**（512B）/ **70**（4KB）。Samsung 980pro L = **324 µs** → **16,524**（512B）/ **2,057**（4KB）。
- **实测**：单块 Optane 只需 **16K–64K 个 GPU 线程**就接近峰值 IOPs；十块 Optane 达到 **45.8M 随机读 IOPs = 22.9 GB/s，是实测 PCIe Gen4 x16 峰值带宽的 90%**；随机写 10.6M IOPs = 5.3 GB/s。SSD 队列分配在 GPU 内存里，队列深度 1024。
- **"prefetch" 这个词在 BaM 全文出现 0 次。** 它的论证是按需细粒度访问 + GPU 线程并行，并且明确反对 CPU 编排的 proactive tiling（预取）：「BaM leverages GPU's **massive thread-level parallelism** and fast hardware scheduling to maintain the queue depths needed to hide storage access latency and to achieve peak storage throughput.」

### 7.2 GIDS（VLDB 2024，arXiv:2306.16384v2，同一个 UIUC/NVIDIA 组）

- 模型估计要达到 Optane 峰值 IOPs 的 95% 需要 **812 个并发访问**，实测在 **1024 个**并发访问下达到目标 IOPs。器件参数：4KB IO，Optane 峰值 1.5M IOPs、Samsung 980 Pro 700K IOPs，延迟 11 µs / 324 µs。
- 请求生成能力的差距：**GPU 每秒 7,700 万次特征请求，CPU 只有 410 万次**。
- 摘要原话：「fully tolerates the long storage latency by exploiting the massive data-level parallelism provided by GPUs」。**"prefetch" 在 GIDS 全文同样 0 次。**

### 7.3 反方也在同一条轴上：TileLens 与 FlashAccel 都说要靠"在途请求数"

这两篇都在我们仓库里，是**一手论文**，不是评论（这一条是核实代理推翻第一轮结论后的更正）：

- **TileLens**（`docs/ref_article/ju2026-tilelens-two-dimensional-memory-layout.txt`，"prefetch" 出现 **35 次**）：L1274 有一整节标题 "Adaptive Prefetching for HBF"；L1276-1278：「Even with a tile-major layout, HBF's read latency remains over 100× longer than HBM's. To hide this latency, **the memory controller must keep enough requests in flight to saturate the HBF bus.**」L1437-1438：「the prefetcher alone is sufficient to hide HBF latency.」L1697 也讨论 MLP：「of HBM can be easily hidden even with a smaller degree of memory-level parallelism (MLP). But as the NAND latency increases, and ...」
- **FlashAccel**（`docs/ref_article/wang2026-flashaccel-hbf-llm-inference.txt`，"prefetch" 出现 **27 次**）：L1149 一整节 "6.2.3 Data Prefetch"；L1151「SRAM resources to hide the high read latency of Flash」；L706 给了和 H3 一样的双缓冲定容规则：「Each stack has a total SRAM capacity greater than **2 × Peak_Bandwidth × Read_Latency**」。消融实验（L1420-1437）：**关掉预取掉 55% 吞吐**（对比权重布局 7%、KV cache 布局 15%）；纯 HBF 不做任何优化掉 65%，低于纯 HBM 的 GPU 基线。原文「**Prefetching plays a dominant role in mitigating access latency**」。它的评估载体是建在 LLMCompass 上的事件驱动模拟器加一个 NAND 模拟器（L1324-1332），**不是真实执行**。

### 7.4 这条反论对我们的直接含义

**BaM 和 TileLens 说的是同一件事的两种说法：闪存这一层的可行性取决于同时在途的请求数够不够，而不取决于用什么办法把它们撑到那个数（预取是一种，海量线程并发是另一种）。**

**而 HBFSim 今天把这个数建模成了 1——但两条路的程度不同，这一点原始核实里没有分开，本轮主 agent 亲自读代码后更正如下。**

- 走**实测曲线**那条路（`cd8p-vmem-p50`）时，整个服务时间都压在同一个游标上：`src/cuda_runtime/device/hbf_device.cu:345-359`，`start = tail > arrival ? tail : arrival`、`target = start + scaled_service`。**完全串行，同时在途的访问数恰好是 1。**也就是说，论文赖以立标定主张的那个 profile，正好是延迟并行度为零的那个。
- 走**解析模型**那条路（`nominal` 等）时，延迟部分是从各请求自己的 `arrival` 起算的，并发的访问之间会重叠；只有传输部分排在同一个游标上：`hbf_device.cu:381-406`，`latency_target = arrival + base_scaled`、`target = latency_target > transfer_target ? latency_target : transfer_target`。**这条路上延迟是并行的，带宽是串行的。**
 所以：
- 合作者说"prefetch 就是这么干的"——业界确实这么干，但业界的两种干法（提前发、或者同时发很多）**在我们的模型里都表达不出来**；
- 我们不需要在模拟器里实现预取才能回答这个问题；**我们需要的是能表达"同时有 N 个访问在途"的时序模型**。这一条已经是 `15-…item 1`（blocking）和 `item 13`。

### 7.5 已发表的、"不建并发就会错多少"的数

- **MDM**（MICRO 2020, DOI 10.1109/MICRO50266.2020.00085）：不建 MSHR（未命中状态保持寄存器，也就是一个缓存最多能同时挂多少个未完成的未命中）和排队延迟的 GPUMech，在访存发散型应用上**平均误差 298%**；MDM 相对详细模拟 **13.9% 对 GPUMech 162%**，相对真机 **40% 对 164%**。机制：「a cache with N MSHRs will process M requests in roughly **M/N batches** because it will block after the first N misses.」
- **Mess**（MICRO 2024，arXiv:2405.10170）：gem5 的固定延迟简单内存模型在 50% 读 / 50% 写流量下**模拟出 4 ns，而真机实测 261 ns**；应用级平均误差 **30%**（gem5 simple）、15%（内部 DDR5）、52%（Ramulator2），对比 Mess 的带宽-延迟曲线模型 **3%**。同一模拟器 ZSim 下三个模型的头对头：固定延迟模型报出的最大模拟带宽 **342 GB/s**，而理论上限 **128 GB/s**，**高出 2.7 倍**。
- **CXLMemSim**（arXiv:2303.06153v2，`docs/ref_article/yang2023-cxlmemsim.txt:1189-1210`）：「**Without ROB emulation, latency penalties were consistently overestimated by up to 30%**」，完整模型与硬件平均偏差小于 5%。**注意**：CLAUDE.md 里写的"HPDC '26"venue **未经一手核实**——arXiv 列表页没有任何 Comments 字段标注会场，引进 refs.bib 前要向合作者确认。
- **Cylon**（USENIX FAST '26，`docs/ref_article/yoon2026-cylon-cxl-ssd-emulation.txt:956-965`）明确拒绝固定缺页延迟：「**We do not use fixed miss delays**; latency depends on the current FTL and NAND state」。它转给 FEMU，FEMU 模拟通道、die、plane 并行、排队与 GC 干扰。
- **一处必须更正的流传数字**：常在检索摘要里出现的"Pond 报 CXL 远端 socket 模拟高 11%–22%"**不在 Pond 论文里**。真实的数来自 Mess 附录 B：远端 socket 内存延迟约高 **28 ns**，导致 perlbench **慢 5%**、lbm **快 11%**。
- **一处空白**：**没有找到**任何已发表工作在 GPU 上、针对闪存量级的延迟，做过"串行注入 vs 建了队列的注入"的头对头对照。上面两个直接测量都在 CPU 侧、DRAM/CXL 量级。**这既是我们的机会，也正是审稿人会问的那个实验。**【标为"从我检查过的来源看不存在"，不是"证明不存在"】

### 8.1 建议：**要图，但主图不是命中率曲线**

**推荐的主图（一张，两个坐标轴 + 一族曲线）：**

- **横轴**：介质延迟 tR，取 **1、2、4、5、10、20 微秒**（这是 `15-…item 1` 已经定死的六档，也和 TileLens 的扫描区间一致）。
- **纵轴**：**残余停顿占比**（residual stall fraction）——介质延迟里有多少最终变成了真实执行中的停顿，也就是**没被掩盖掉的那一部分**。这正是 `15-…item 2` 规定必须出的数：「the residual stall fraction: of the media latency, how much is covered by issuing the read one layer ahead of the layer that needs the data, and how much is left over as a stall in the real execution.」
- **一族曲线，每条对应一个"同时在途访问数"档位**：**256、1024、1536、4,883**（`15-…item 1` 已经定死的四档并行读出单元数），外加两条基线曲线——今天代码的 **1 路串行**，和一条**理想全掩盖 = 0**。
- **图上标出"结论变号的那条线"**：`15-…item 1` 明写第三个必须出的数是「the place in the grid where the conclusion changes sign, meaning the boundary on one side of which the workload runs faster with the weights in `HBF` and on the other side of which the workload does not.」

**为什么这张图比单独一条命中率曲线强，四条理由：**

1. **命中率单独没有意义，因为掩盖不掉的那部分才是代价。** ProMoE 已经把这件事写成公式：`GoodPred = Accuracy × FetchRate`——预测对了但来不及取回，等于没预测对。一条只画准确率的曲线，把 FetchRate 那一维完全丢掉了。
2. **今天的代码里读不出命中率。** `hbfsim_stats`（`include/hbfsim/api.h:58-64`）只有五个字段，共享控制头里也没有命中/未命中计数器，`HbmCache` 里唯一的计数器是 `dirty_pages_`（`hbm_cache.hpp:59`）。要画命中率必须先加计数器，而残余停顿占比可以由端到端时间差直接测出来。
3. **残余停顿占比同时回答两个审稿人一定会问的问题**：一是"HBF 的延迟劣势要不要紧"（这是大纲 line 322 明写的立论支点），二是"你们的模拟器把不该收的钱收了多少"（这是我们自己的 doc 10 / doc 36:606 承认的结构性过收）。**同一张图既是器件结论，又是模型保真度的自证。**
4. **它把 MLP 这一维摆到台面上**，而这正是 BaM 的利特尔法则、TileLens 的 "keep enough requests in flight"、和我们 `fast_channel_tail_ns` 单游标三者交汇的地方。审稿人翻开源码看到一个全局标量，而论文只画了一条命中率曲线，会很难看。

**配图（第二张，可选，用于 MoE 那一段）**：横轴是专家预测命中率（把已发表的 66.9% / 78.79% / 84.11% / 84.7% / 90% / 96% / 97.15% 标成竖线），纵轴是同一个残余停顿占比。这张图的作用是把"别人的预测器落在哪一档"和"那一档还剩多少停顿"接起来，并且顺便说明**过取（over-fetch）不是免费的**——Fate 的 97.15% 是用约 3.75 倍权重流量换来的【推算】。
