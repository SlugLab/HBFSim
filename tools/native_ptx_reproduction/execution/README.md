# Supported-weight reproduction

This directory provides one-shot CPU preparation and GPU execution entry points. The caller supplies real source-built binaries, model files, collected PTX, the existing GPU reservation, and a finite watchdog lease through explicit, hash-bound configuration. No command creates a second GPU queue or changes the external reservation. Keep each output directory new; failed attempts remain intact.

The exact-entry CPU pipeline is:

1. `stage_exact_v3.py --input STAGE_INPUTS.json --output NEW_STAGE_RUN` transforms seven full raw PTX modules and eight explicitly selected kernels. Embedding uses an entry-scoped static `__assertfail` proof; BF16 Fill has an entry-scoped no-call proof. These proofs avoid treating unrelated entries in the large Torch modules as supported. Two norm entries share one raw module; four MoE raws each contribute one entry. The input identifies the new base pass, the independently built aggregate-metadata pass, exact native bindings, four MoE raws and their SHA-256 values. Broad kernel regex selection is not accepted as evidence for these Torch entries.
2. `compile_stage_v1.py --stage-receipt NEW_STAGE_RUN/STAGE_RECEIPT.json --compiler NEW_COMPILER --compiler-sha256 SHA --o0-raw EXACT_NORM_RAW_SHA --output NEW_COMPILE_RUN` compiles each staged module with the actual agent compiler API and records the rewritten PTX, exact options, logs and cubin. Norm uses O0; other modules use O3; max registers remain 64. This is CPU-only validation.
3. `join_native_v1.py --stage-run NEW_STAGE_RUN --bindings OLD_EXACT_BINDINGS.json --auto-prepare AUTO_PREPARE.py --join-tool ../scoped_join/join_scoped_staging_provenance.py --output NEW_JOIN` uses the collected native PTX membership proof to create fresh Torch and norm sidecars, then updates exactly four native bindings to the new staged bytes. The old binding manifest is an explicit input, not a hidden fallback.
4. `compose_bundle_v1.py --inputs BUNDLE_INPUTS.json --output NEW_BUNDLE` checks every component SHA before creating a new symlink view. Sources remain external and mutable; preflight hashes the resolved bytes again at execution time. The file map includes the core, daemon, gate, agent, compiler, attach loader, server, probe, pass, and their source-build receipts. A composed bundle is not GPU validation.

`reproduce.py preflight --config CONFIG.json --workspace-root WORKSPACE --scope layer0 --overall-seconds 1800 --check-resources` validates the exact paths, hashes, all eight checkpoint/tokenizer files, selected full storages, stage/module identities, bundle and binding sidecars, GPU identity, reservation start ticks, free RAM/VRAM and lease margin. `native` and `staged` use the same 2-input/2-output workload and GPU memory utilization. Launch commands use argv arrays and new result directories. `staged` also requires a successful matching native baseline, a fresh positive epoch, and `--baseline-result`.

The verifier requires the native output tokens, complete selected storage bytes, addressed modeled rows for every selected storage, active module identities, count/byte conservation, and zero recorded errors. Registration alone does not prove dynamic coverage. Unsupported weights remain native and are outside the claimed supported subset. The supplied `example.giga.json` is the archived successful cohort; its external paths must be replaced for a new build. `MODEL_FILE_IDENTITY.json` is the exact eight-file checkpoint inventory used by preflight. `config.schema.json` documents the run configuration.

The new source-built cohort's CPU stage is `new-cohort-layer0-cpu-v1/stage-run-v4` (7 raws/8 rows), compile is `compile-run-v1` (7/7 rc0), and native join is `native-join-v1` (four scoped bindings). The matching 0.75 native baseline finished `PASS_NATIVE` in `results/new-cohort-layer0-native-075-v1` with output `[[70,13]]`. Its staged run finished `PASS_8_OF_8_ADDRESSED_ACTIVE` in `results/new-cohort-layer0-staged-075-v1` with the same output, 14,962,944 addressed accesses / 239,149,056 bytes and zero recorded errors. The exact inputs and original command receipts remain in those independent directories. Earlier broad-selector CPU failures in `stage-run-v1/v2` are preserved.

`fixtures/native-bindings-template.giga.json` and `fixtures/expected-layer0.giga.json` / `fixtures/expected-all98.giga.json` record the exact four native entries and eight / 98 full-storage selections used by this cohort. `fixtures/collector-references.giga.json` identifies the external Torch and vLLM collector manifests. The binding template names the archived Torch e3bdd and vLLM 4cb19 containers, and `join_native_v1.py` currently selects these two groups by those SHA prefixes. This is a fail-closed, cohort-specific adapter; it does not auto-discover arbitrary replacement container versions. Build new collector manifests and review an adapter change for another DSO. The raw PTX, model checkpoint, overlays, compiler and runtime binaries remain external, explicit inputs; the examples are not a self-contained artifact bundle.

The CPU checker `cpu_checks.py` accepts explicit config and archived result paths. The archived runner test receipt is `supported-weight-reproduction-runner-cpu-v1/CPU_TEST_RESULT_V6.json`; it replayed 8/98 successes, a new native start receipt, lexical overlays, and negative coverage/storage/stage/output cases without launching a GPU. The source-built staged run's terminal and dynamic-coverage evidence is in its own `finish.json`, `cell/result.json`, `cell/registration.json`, and `coverage.jsonl`.
