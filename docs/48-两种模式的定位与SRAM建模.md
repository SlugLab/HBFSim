# 两种模式的定位与 SRAM 建模

## 一、结论与三条措辞建议

先把三条建议一句话列全,后面逐条展开。

- 论文正文里一个字都不要提 1:55 这个比例,也不要提 2 GiB 显存缓存配 110 GiB 逻辑范围这组配置。
- 把「HBM 缓存」这个叫法从正文里去掉,改成「显存帧缓存」(bounded device-memory frame cache)。
- 报容量模式的数字时,一律写清这个数字替代的是哪一层硬件。

### 建议一:1:55 这个比例不进正文

2 GiB 配 110 GiB 是 2026-08-11 那次功能冒烟测试的配置,而那份证据文档自己就写明了它证的是什么。原句是 `This proves a logical span above VRAM and correct page routing; it does not claim that 110 GiB was physically read during the 128-access run`(`docs/proofs/2026-08-11-hybrid-complete.md:46-48`)[一手]。**也就是说,这组配置证的是「逻辑跨度超过显存」与「页路由正确」两件事,它从来不是性能结果,更不是 HBM 与 HBF 之间的容量比。**

一旦这个数出现在正文里,读者会自动把它读成我们主张的层次比例,也就是「快的那一层配多少、慢的那一层配多少」。**已发表的设计给出的比例是 1:8(Micron)到 1:16(H³)[转述],1:55 在已发表工作里没有先例。** 审稿人看到一个比所有先例大三到七倍的比例,第一反应是我们在主张一种没有依据的层次配置,而不是我们在做一次功能测试。

真正该报的容量比在实验分支的扫描里已经是对的,不必另行设计。`adapters/vllm_capacity/trace_replay.py:21-29` 定义 `RATIOS = ((1,0),(1,1),(1,2),(1,4),(1,8),(1,16))`[一手],覆盖了已发表设计的整个区间。切分粒度也已经写死成完整的专家对象,`placement_policy.py` 开头的原句是 `All policies operate on equal-sized, complete expert objects (w13 + w2)`[一手]。

### 建议二:「HBM 缓存」这个叫法要从正文里去掉

`paper/design.tex` 的 D6 一节现在的原文是 `Capacity ranges instead use a bounded HBM frame cache backed by a sparse host file`[一手,`paper/design.tex:212-215`]。**这一句正是让审稿人误读的源头**,原因有两条,各自独立成立。

第一条是事实层面的:我们跑实验的那块 GPU,显存介质是 GDDR7,不是 HBM。合作者温度分支的文档里有两句原话,`The available RTX PRO 6000 uses GDDR7` 与 `GDDR7 hardware must not be described as HBM`[转述]。把 GDDR7 写成 HBM,审稿人只要查一下 RTX PRO 6000 的规格就能发现。

第二条是主张层面的:「HBM 缓存」这个叫法暗示我们主张一种「用 HBM 去缓存 HBF」的架构,而 OCP 规范 §11.1.2 的原文是 `Due to the large difference in memory capacity for HBF and HBM, memory management shall be performed separately if used together`[一手]。规范明确要求两层分开管理,我们的措辞却读起来像在提出相反的组织方式。建议把这一处改成 `bounded device-memory frame cache`,中文写作「显存帧缓存」——**这个词只描述我们的模拟手段用了一块显存,不对被模拟器件的层次关系做任何主张。**

### 建议三:每个比例都写清它替代的是哪一层硬件

论文里会出现两个容量比,量的是完全不同的两件事,混在一起读者必然读错。**第一个是显存驻留区对 HBF 的比,按已发表设计取 1:8 到 1:16 [转述],它回答的问题是「多少权重驻留得下」。** 第二个是基底裸片上的 SRAM 缓冲对 HBF 的比。基底裸片(base die)指堆叠封装最下面那一层逻辑芯片,HBF 的控制逻辑与缓冲都做在这一层上。

第二个比例是 40 MB 对 3 TB,约 1:75,000 [推断,由 H³ 的 40 MB 与 3 TB 两个转述输入算出]。这个比例不是按「装得下多少权重」定的,而是按 `2 × 带宽 × 延迟` 定的,回答的问题是「介质延迟掩不掩得住」。两个比例相差三个数量级还都成立,恰恰因为它们量的不是同一件事;正文里每次报其中一个,都要在同一句话里写出它替代的是哪一层硬件。

## 二、两种模式:我们是不是已经写了、只是没写好

**答案是:已经写了,只是写在一句话里,而且用错了一个词。** 先把两个名字定下来,全文只用这两个名字。时序模式指范围里的数据留在真实显存原处、地址不变,模拟器只在内核访问这段地址时插入等待;容量模式指数据放在主机上的后备文件里,显存只留一块有界的页缓存,内核访问到不在缓存里的页时把它取进来。

### 现状:正文里已有的三句

`paper/design.tex` 的 D6 第一段原文是 `D6 answers C1. Timing ranges preserve their original address. Capacity ranges instead use a bounded HBM frame cache backed by a sparse host file. A miss hands a page to the host service, which reads or programs the media model and copies the frame; dirty eviction writes the exact bytes back.`[一手]。两种模式的区别其实已经在这几句里说清楚了:地址保不保留、数据搬不搬。**缺的不是区别本身,是「这两种模式各自代表什么、为什么需要两种」这一层。**

### 代码层面的区别(本轮代码核查,全部一手)

- **时序模式的编号是 `HBFSIM_RANGE_MODE_TIMING = 1`。** 设备端把访问地址原样返回(`src/cuda_runtime/device/hbf_device.cuh:260-262`),数据留在真实显存里不动;注册入口 `hbfsim_register_device` 要求传进来的指针是一块真实的、非托管的显存(`src/cuda_runtime/context.cpp:1073-1120`)。
- **容量模式的编号是 `HBFSIM_RANGE_MODE_CAPACITY = 2`。** 注册入口 `hbfsim_map_file` 用 CUDA 虚拟内存只预留地址、不映射物理页(`src/cuda_runtime/vmm.cpp:178-201`),设备端返回的是页缓存里那一帧的地址(`hbf_device.cuh:267-271`)。
- **两个注册入口互相拒绝。** 已经按时序模式注册的范围不能再按容量模式注册,反之亦然(`context.cpp:1462-1466` 与 `context.cpp:1531-1535`)。
- **设备端的分流只有一行,而且条件写死。** `hbf_device.cu:515-519` 的判断条件是 `range->mode == 1`,所以容量模式无论上下文选 fast 还是 hybrid,时间都由 MQSim 介质模型算出;那条 CD8P 实测曲线从来不作用在容量模式上。

最后一条是本轮核查里最要紧的一条,它直接决定论文里哪个数字能引哪条曲线。**容量模式报出来的任何时间都不能说成「由 CD8P 实测曲线标定」,因为设备端根本没有走那条路径。**

### 判断:两种模式都要写,但要换一种说法

**判断是:两种模式都要写进论文,但要写成「一套注入机制的两种地址翻译策略」,不要写成「两个模式」。** 三条理由如下。

- **不写时序模式,审稿人无法知道我们有一个不搬运数据的形态。** 数据留在原处、内核照常按原地址读、只在读的时候被拖慢,这正是 OCP 规范与已发表设计描述的形态;不写它,等于把我们唯一对得上主流架构的那一半藏起来。
- **不写容量模式,超显存那条证据就没有出处。** 110 GiB 逻辑跨度那次运行是「工作集大于显存也能跑」的唯一实验支撑,而这一条又是「HBF 存在的理由是容量」这条论证的落脚点。
- **写成「两个模式」会招来一个不必要的问题:「你们是不是做了两个系统?」** 写成「同一套机制的两种地址翻译」则一句话能说清,而且有依据——时序模式与容量模式共用同一个 PTX 改写入口、同一个 `__hbfsim_resolve` 解析函数、同一张范围表、同一个覆盖门、同一种延迟施加办法(在 GPU 上自旋等 `%globaltimer`),差别只在地址怎么翻译、数据放在哪里[均一手,本轮代码核查]。

### 两种模式各自承担多少贡献,如实写

时序模式承担全部关于器件时序的主张,包括 CD8P 实测曲线的标定与留出验证。容量模式承担的是一条能力主张:工作集大于显存时程序仍然能跑完,并且结果正确。**容量模式不承担任何关于 HBF 架构组织方式的主张——这句话要明写进论文正文,它就是防误读的那道闸。**

## 三、基底裸片上的 SRAM 缓冲怎么模拟(零行代码)

H³ 给 SRAM 缓冲定容量的公式是 `容量 = 2 × 带宽 × 介质延迟`,把 1 TB/s 与 20 µs 代进去得到 40 MB [转述]。这里的 SRAM 缓冲指做在 HBF 基底裸片上的一小块静态随机存储器,作用是在介质读出的同时把下一批数据先取进来,把介质延迟掩住。**要在 HBFSim 里模拟这块缓冲,不需要写一行 C++ 代码,只需要新增一个档文件。** 档文件(profile)指 `configs/profiles/` 下那种 JSON 配置,里面写死一套器件参数,运行时整个读进来。

### 为什么不用改代码,五条依据(本轮代码核查,全部一手)

- **缓存大小本来就是档文件里的一个字段。** 字段名是 `hbm_cache_bytes`(`include/hbfsim/profile.hpp:94`),解析在 `src/profile/profile.cpp:263-264`。
- **这个字段除了「不得大于 capacity_bytes」没有任何下限。** 校验代码在 `profile.cpp:352-355`;运行时另外只要求它非零、并且能被 `page_bytes` 整除(`src/cuda_runtime/capacity_runtime.cpp:20-25`)。40 MiB 等于 41,943,040 字节,对 4096 与 16384 两种页大小都能整除。
- **缓存是一次 `cuMemCreate` 整块分配出来的**(`src/cuda_runtime/vmm.cpp:247-282`),所以把缓存配小不会引入按帧分配的额外开销。
- **小缓存已经被现有测试跑过。** `tests/gpu/capacity_runtime_live_test.cu:58` 用的是 2 页,`tests/integration/public_cuda_lifecycle_test.cpp:138` 用的是 32,768 字节。
- **双缓冲式的顺序推进不必新写策略。** 档文件字段 `readahead_pages`(`profile.hpp:95-98`,生效点 `capacity_runtime.cpp:150`)会在一次按需缺页之后把接下来 N 页排队;缺页指内核访问到一个不在页缓存里的页,必须先从后备存储取进来。

最后一条值得多说两句,因为它决定了 40 MiB 这个小缓存跑起来是什么形状。排进队列的预读页由工作线程取,而工作线程只在没有待处理请求时才去取(`capacity_worker.cpp:134-147`);取的时候允许挤掉一个干净的受害页(`capacity_page_service.cpp:269-292`),逐出指把页缓存里的某一页腾出来给新页用,干净指这一页没有被写过、腾出来不必写回。**在只读权重上顺序推进时受害页恒为干净,所以行为形状就是「取下一页、腾出上一页」,与双缓冲一致。**

### 所以要做的只有一件事:新增一个档文件

新增一个约 20 行的 JSON 档文件,例如 `configs/profiles/hbf-sram-buffer-40mb.json`,与现有的 `cd8p-vmem-p50.json` 同形。三个字段这样填:`hbm_cache_bytes` 写 41943040、`page_bytes` 写 4096、`readahead_pages` 写 1 或 2。跑基准连脚本都不用改,`scripts/run_microbench.py` 已经有 `--cache-bytes` 参数;不需要 GPU 的那一侧用 `benchmarks/prefetch/hbf_capacity_readahead_bench.cpp`,它已有 `--frames` 与 `--readahead` 两个参数,并且分开报告按需缺页与预读各自打到介质的次数[均一手]。

### 一处要先量、不要先写进论文的推断

页缓存的逐出策略是 CLOCK(`src/cuda_runtime/hbm_cache.cpp:132-176`)[一手]:每页带一个「最近用过」的标记,要逐出时绕圈扫描,遇到带标记的页就把标记清掉、放它一马,遇到不带标记的就逐出。**在纯顺序访问流上,CLOCK 可能退化成近似 FIFO,因为每页只被访问一次、只拿到一次被放过的机会。** 这是主 agent 的推断,没有跑过实验 [推断];写进论文之前要用上面那个基准跑一次证实或证伪。

### 现有测试与旧证据会不会受影响

只要不动默认值,一个测试都不会失效——`readahead_pages` 的缺省值仍然是 0 [一手]。`tests/integration/test_over_vram.py:26` 断言的是 2 GiB,但同一个文件在 `:20` 自己就传了 `--cache-bytes 2G`[一手],所以保留原用例、另加一个 40 MiB 用例即可,不必改断言。

旧的 110 GiB 容量证据本身仍然成立,因为它证的是逻辑跨度与页路由,与缓存配多大无关。**但论文如果要按 40 MB 缓冲报告结果,就需要在新档文件下重跑同一个 128 次访问的用例**:`checksum` 应当不变,`wall_ns` 会变大。

## 四、design 一节与架构图的修改意见

**本节只给意见,不动任何文件。** 原因是 `paper/design.tex` 正在被另一个会话修改,本轮如果直接改,两边会互相覆盖。下面三组意见,交给动 `paper/design.tex` 的那一方执行。

### D6 一节的两处措辞

第一处是把 `bounded HBM frame cache` 改成 `bounded device-memory frame cache`,理由见第一节建议二。第二处是在 D6 开头补一句,说明容量模式的定位;英文怎么写交给写正文的人定,中文意思是:容量模式是一种模拟手段,今天没有 HBF 器件,为了让工作集大于显存的负载能跑起来,把数据放在后备文件里、显存留一块有界的帧缓存;**这不是我们对 HBF 系统组织方式的主张,规范 §11.1.2 要求 HBM 与 HBF 分开管理。**

### 两种模式写在哪里

建议不新开小节,而是在 D6 第一段把「同一套注入机制、两种地址翻译」这句话补上,并把时序模式那一半指回 D1 与 D3——那两节已经讲了注入点与两条时序路径。**理由是版面:评估章正文已经压到 2 页,设计章再开一个新小节会挤掉别的内容。**

### 架构图上的四条修改意见

- **快的那一层不要只写 HBM。** 图上标成 `GPU device memory (GDDR7 on our testbed; HBM on datacenter parts)`,把测试平台的实际介质和数据中心部件的介质分开写。
- **HBF 与快的那一层画成并列两层,中间是访问路径,不是包含关系。** 不要把 HBF 画在 HBM 下面,那种画法读起来就是「HBM 缓存 HBF」。
- **图上若要画 SRAM 缓冲,画在 HBF 基底裸片那一侧**,并标 `latency-hiding buffer, sized 2 x BW x tR`;不要画成显存里的一块,那会和显存帧缓存混成一个东西。
- **容量模式那条数据通路用不同线型。** 后备文件到显存帧缓存这条线用虚线一类的区分画法,并在图注里注明它是模拟手段、不是被建模器件的结构。

## 五、代码怎么写:交合作者的执行清单

五项按「改动尽可能少」排序,每项写清做什么、动哪个文件、多少行、验收标准是什么。

### 第一项:新增 SRAM 缓冲档文件

做什么:按第三节给的三个字段值新建 `configs/profiles/hbf-sram-buffer-40mb.json`。动哪个文件:只动这一个新文件,约 20 行 JSON,零行 C++。**验收标准是 `hbf_capacity_readahead_bench` 能在这个档文件下跑完,并分开报出按需缺页与预读各自打到介质的次数。**

### 第二项:量一次 CLOCK 在顺序流上的行为

做什么:用第一项建好的档文件,跑 `benchmarks/prefetch/hbf_capacity_readahead_bench.cpp`,证实或证伪第三节末尾那条「CLOCK 在纯顺序流上退化成近似 FIFO」的推断。动哪个文件:一个都不动,只跑基准。**验收标准是给出两个数——逐出次数与命中率。**

### 第三项:要同时报两列对比时,怎么让两列可比

做什么:如果论文要并列报「时序模式直接读」与「容量模式经页缓存」两列,最省的做法是同一个档文件跑两次,只换注册入口——一次用 `hbfsim_register_device`,一次用 `hbfsim_map_file`。**但必须让两列同源:把上下文模型设成 `HBFSIM_MODEL_REFERENCE`(`include/hbfsim/api.h:38`)[一手],让时序模式那一列也走 `resolve_leader` 与 MQSim。** 否则一列用 CD8P 实测曲线、另一列用 MQSim,两列的绝对时间不可相减。

代价是慢:reference 档对 fast 档是 44.469 s 对 2.014352 s [一手]。动哪个文件:一个都不动,零行代码改动,只改跑基准时传的参数。验收标准是两列都打印出所用的上下文模型名,并且名字相同。

### 第四项:把时序模式今天的两条硬限制写进论文的限制一节

第一条:时序模式要求传进来的指针是一块真实显存,所以时序模式跑不了大于显存的工作集[一手,`context.cpp:1073-1120`];这是形态本身决定的,不是加一个开关能解决的。第二条:时序模式一侧没有任何预取——在全仓库检索 `cp.async`、`memcpy_async`、`prefetch`、`readahead` 四个词,时序模式一侧零命中[一手,本轮代码核查]。**因此时序模式量到的减速,是「完全不做延迟掩盖」那一端的上界,论文里报这个数字时要带上这句限定。**

### 第五项:一项缺料,需要合作者补测

容量模式即使命中页缓存,也要跨两个进程往返一次:设备端压环、守护进程弹出、再交回应用进程里的容量工作线程。这一趟的真实耗时不计入任何建模时间,但照样占墙上时间,而仓库里没有单独测过这一趟要多久。**缺的就是这一项——需要合作者补一次容量模式命中路径的往返耗时测量**,验收标准是给出一个带分布的耗时数(至少 P50 与 P99),并写明测量时的负载条件。
